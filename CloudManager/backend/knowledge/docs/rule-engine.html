一、设计目标

优化建议不是写死的，而是由 可配置规则引擎 驱动：运维按需定义"检测什么、什么条件、省多少"。

二、7 种规则类型

类型检测逻辑
闲置资源近 30 天 CPU < 5%
规格降配CPU 峰值 < 40% 且内存 < 50%
未使用资源7 天无访问流量
预算告警本月花费 > 预算 80%
趋势上涨连续 3 月涨幅 > 15%
预留实例持续运行 > 6 个月
存储优化快照保留 > 90 天

三、MatcherRegistry 注册表

class MatcherRegistry:
    _registry = {}
    @classmethod
    def register(cls, rule_type): ...
    @classmethod
    def get(cls, rule_type): ...

新增规则类型 = 实现一个匹配器并注册，即插即用（类 ActionRegistry 模式）。

四、执行与报告

  • 执行：execute_rule 按检测范围（云 / 账号 / 区域 / 类型）过滤资源，跑匹配器生成建议。
  • 报告单号：RPT-YYYYMMDD-NNN，当天序号递增，便于追踪。
  • 报告下钻：云 → 账号 → 区域 → 资源类型 左树右表联动，支持 CSV 导出。

五、设计价值

平台提供"规则引擎能力"，规则内容由运维配置，避免面试时被追问"规则怎么定的"深坑，同时体现可扩展架构。
