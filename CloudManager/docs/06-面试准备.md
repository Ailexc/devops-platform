# 06 · 面试准备

> 本文档为面试叙事线与高频深度问题的应答要点，配合 Demo 演示使用。

## 一、项目叙事线（建议讲述顺序）

1. **业务背景**：企业内部多云管理需求
   - 为什么需要：多朵云统一入口、流程合规（操作先审批）、成本管控、审计留痕
2. **架构设计**：四层架构
   - 前端（仿 AWS 控制台）→ 后端 → 工单系统 → CMDB
   - 重点讲清：**为什么操作要绕工单系统**（解耦/合规/留痕）
3. **核心难点**（深度题，逐个准备）：
   - 云适配层如何抽象、如何新增一朵云
   - 异步云操作的最终一致性、失败重试、幂等
   - CMDB 多态资源建模与取舍
   - 权限与数据隔离（RBAC + 部门数据权限）
   - CMDB 与云上数据的一致性（同步/回写/漂移检测）
4. **成果与价值**：业务闭环 + 成本优化 + 审计合规
5. **主动说局限**（反而加分）：单云起步、成本数据为模拟、监控未深入 —— 展示技术判断力

## 三、高频深度问题与应答要点

### Q1：为什么操作不直接调云 API，而要绕工单系统？
- 解耦：前端/业务层不依赖云厂商 API，云厂商变更只影响执行器
- 合规：所有变更先审批后执行，满足企业审计要求
- 留痕：完整工单 + 审批 + 执行日志，可追溯
- 补充：这也让"多云切换"成本更低

### Q2：云适配层怎么设计的？新增一朵云要改什么？
- 统一 `CloudProvider` 接口（纳管/查询/操作/账单）
- SPI/策略模式插件化，新增云 = 新增 Provider 模块 + 注册，上层零改动
- 统一资源模型 + metadata JSON 承载差异化字段
- 强调：这是"多云管理系统"名副其实的关键

### Q3：云操作是异步的，怎么保证最终一致？
- 状态机：待审批→审批中→待执行→执行中→成功/失败
- 执行器领取任务后调用云 SDK，轮询/事件回调推进状态
- 失败：有限重试（上限 3 次）+ 人工介入
- 幂等：唯一 request_id 去重，防止重试重复创建资源
- 执行成功回写 CMDB + 通知前端刷新

### Q4：CMDB 资源模型怎么建表？多态资源怎么处理？
- 公共字段主表 + metadata JSON 存差异化字段
- 对比：单表多字段（冗余）、每类一表（查询难统一）
- 权衡：查询统一性 vs 扩展灵活性
- 补充：资源关系表支撑拓扑；变更历史表支撑审计与漂移检测

### Q5：CMDB 和云上真实数据怎么保持一致？
- 定时同步（全量/增量）
- 操作后主动回写（工单执行成功触发）
- 漂移检测（对比云上真实状态与 CMDB 记录，告警差异）

### Q6：权限怎么设计的？
- 功能权限：标准 RBAC（角色-权限点）
- 数据权限：资源按 department_id 隔离，查询统一拼装过滤
- 操作审计：Spring AOP + 注解零侵入记录

### Q7：成本管理怎么做的？（若有）
- 账单采集（Demo 用模拟账单生成器，如实说明）
- 成本趋势、按部门分摊、预算告警
- 资源闲置检测（规则引擎：低利用率 → 建议停机/降配）
- 强调价值：帮企业降本 20-30%（行业共识）

### Q8：这个项目有哪些不足/后续规划？
- 如实说：单云起步（AWS）→ 已扩展阿里云；监控模块未深入；成本数据为模拟
- 后续规划：接入更多云、监控告警、智能化优化建议
- 要点：主动暴露可控短板，体现自我认知与技术判断力

## 四、演示脚本要点（Demo 演示时）

1. 首页：多云总览（账号/资源数/成本/告警）
2. 计算模块：主机列表（来自 CMDB）→ 演示"申请主机"完整流程：
   - 提交申请 → 工单生成 → 审批 → 执行（Mock 异步）→ 资源出现在列表
3. 工单中心：展示流程状态机与审批记录
4. 成本中心：趋势图 + 部门分摊 + 优化建议
5. 审计中心：操作留痕查询
6. 结尾：一句话总结架构价值

## 五、避坑提醒

- 所有 Mock/模拟能力，面试时**主动说明**，不隐瞒
- 技术深度优先于功能数量：把"工单状态机""云适配层""幂等"讲透，胜过罗列 20 个功能
- 不夸大 QPS/规模：如实定位为"企业内部管理系统"
