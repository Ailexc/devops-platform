🔐 ABAC 标准架构详解

Attribute-Based Access Control — 从理论到业界实践，理解为什么你的"ABAC-lite"是正确方向

1. 什么是 ABAC

ABAC（Attribute-Based Access Control，基于属性的访问控制）是一种授权模型，它根据 用户（主体）、资源（客体）和 环境 的 属性，通过策略引擎动态判定是否允许某个操作。

👤 主体属性 + 📦 资源属性 + 🌐 环境属性 + ⚡ 操作 → ✅ 允许 / ❌ 拒绝

核心公式

允许 = 策略评估(
    主体属性: { 角色, 部门, 安全等级, 地理位置... },
    资源属性: { 类型, 所有者, 分类, 敏感度... },
    环境属性: { 时间, IP, 设备状态, 威胁等级... },
    操作:     { 读取, 写入, 删除, 部署... }
  )

与 RBAC 的本质区别

维度RBAC（基于角色）ABAC（基于属性）
授权依据静态角色 → 权限点映射动态属性组合评估
粒度粗（角色级）细（属性级，理论上无限）
变更成本高（改角色=改所有人）低（改策略即可，不影响用户）
上下文感知❌ 不能✅ 可以（时间、地点、设备等）
数据量小大（需要属性存储和策略引擎）
典型场景企业内部管理系统云平台（AWS IAM）、SaaS、零信任

2. 标准 ABAC 四组件架构（NIST 标准）

NIST SP 800-162 定义了 ABAC 的标准参考架构，包含四个核心组件：

📝 PAP Policy Administration Point
策略管理点
⬇ 定义策略
🧠 PDP Policy Decision Point
策略决策点
↕
🚪 PEP Policy Enforcement Point
策略执行点
🔍 PIP Policy Information Point
策略信息点
⬇
🎯 目标资源 API / 数据 / 页面 / 按钮

组件详解

组件职责类比
PAP 策略的定义、存储、版本管理 立法机构——制定法律条文
PDP 接收鉴权请求，加载策略+属性，做出 allow/deny 决策 法官——依据法律+事实做出判决
PEP 拦截请求，转发给 PDP，根据结果执行或拒绝 门卫——拦住你，问法官能不能放行
PIP 从数据源获取主体/资源/环境的属性值 调查员——去查户口本、房产证

一次完整鉴权流程

┌──────┐   ① 请求       ┌──────┐   ② 鉴权请求    ┌──────┐
│ 用户 │ ─────────────→ │ PEP  │ ─────────────→ │ PDP  │
└──────┘                └──────┘                └──┬───┘
                                                    │ ③ 获取属性
                                                    ▼
                                                 ┌──────┐
                                                 │ PIP  │ ← 用户表/资源表/LDAP/...
  ┌──────┐   ⑥ 响应       ┌──────┐   ⑤ 决策      └──────┘
  │ 用户 │ ←───────────── │ PEP  │ ←───────────── │ PDP  │
  └──────┘   ✅/❌        └──────┘   allow/deny   └──────┘
                                                    │ ④ 查询策略
                                                    ▼
                                                 ┌──────┐
                                                 │ PAP  │ ← 策略存储
                                                 └──────┘
💡 关键理解：在你们的系统中，check_user_can() 就是 PDP，@require_resource_permission 装饰器就是 PEP，User/Group/BusinessLine 模型就是 PIP 的数据源，而策略函数本身（_policy_group_manage）就是 PAP 定义的策略。

3. 策略语言：如何描述"谁能在什么条件下做什么"

标准 ABAC 使用专用的策略语言来描述规则。业界有两大流派：

XACML（eXtensible Access Control Markup Language）是 OASIS 标准，基于 XML，2003 年提出。它是 ABAC 的"学院派"实现。

<Policy RuleId="group-manage" Effect="Permit">
  <Target>
    <Subjects>
      <Subject>
        <SubjectMatch MatchId="string-equal">
          <AttributeValue>audit_admin</AttributeValue>
          <SubjectAttributeDesignator AttributeId="is_audit_admin"/>
        </SubjectMatch>
      </Subject>
    </Subjects>
  </Target>
  <Condition>
    <Apply FunctionId="not">  <!-- 审计管理员拒绝 -->
      <Apply FunctionId="boolean-equal">
        <SubjectAttributeDesignator AttributeId="is_audit_admin"/>
        <AttributeValue>true</AttributeValue>
      </Apply>
    </Apply>
  </Condition>
</Policy>
优缺点：功能完整但极其冗长。一个简单的"组负责人可管理本组"需要用上百行 XML 描述。这导致 XACML 在实践中几乎被抛弃。

OPA（Open Policy Agent）是 CNCF 毕业项目，使用 Rego 声明式语言描述策略。它是当前业界最流行的 ABAC 引擎。

# 策略: 组管理权限
package org.access

# 默认拒绝
default allow = false

# 审计管理员不可管理
allow {
    not input.user.is_audit_admin
    input.resource.type == "group"
    input.action == "manage"
    is_group_leader(input.user.id, input.resource.id)
}

# 辅助函数: 判断是否为组负责人
is_group_leader(user_id, group_id) {
    group := data.groups[group_id]
    group.leader_id == user_id
}

OPA 的优势：

  • 策略独立部署（sidecar 或独立服务）
  • 热加载，无需重启应用
  • 输入输出 JSON，和语言无关
  • 内置策略测试框架
你们现在的 Python 策略函数其实就是 Rego 策略的"硬编码版"——逻辑一样，只是没有用独立策略语言。对于不经常变的策略，硬编码更简单直接。

AWS IAM 使用 JSON 策略文档，是业界最大规模的 ABAC 实践。

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["ec2:StartInstances", "ec2:StopInstances"],
    "Resource": "arn:aws:ec2:*:*:instance/*",
    "Condition": {
      "StringEquals": {
        "aws:ResourceTag/Environment": "dev"
      }
    }
  }]
}

而 Google 的 Zanzibar（全球权限系统）采用关系图谱（ReBAC）：

# Zanzibar 风格的元组
("group:payment-arch", "member", "user:zhaoliu")
("user:lisi", "owner", "group:payment-arch")

# 查询: 赵六能否查看支付架构组?
Check("user:zhaoliu", "view", "group:payment-arch")
→ 遍历关系图: member → group → owner? 没有直接关系 → deny
Zanzibar 的关键洞察：绝大多数权限都可以表示为资源之间的关系。Google 用它支撑了 Gmail、Drive、YouTube 等所有产品的权限系统，日处理超过 200 亿次鉴权请求。你们的 Group.leader、SubjectMembership 本质上就是 Zanzibar 关系元组的简化版。

4. 你们的 ABAC-lite 与标准 ABAC 的对比

你们当前的实现确实是 ABAC 的简化版，但不是"缩水版"——而是有意识的范围裁剪。以下是逐项对比：

为什么 ABAC-lite 对你们是正确选择

你们的已知约束：
• 用户规模不大（数百～数千）
• 属性维度有限（核心是组织关系树）
• 策略变更频率低（组织架构变动不频繁）
• 没有多租户需求

→ 在这些约束下，标准 ABAC 的灵活性是过度设计。你们用更简单的方案覆盖了 99% 的场景。

5. 业界实践案例

公司方案核心思路
AWS IAM + ABAC 基于资源标签（Tag）的 ABAC。策略用 JSON 描述。
特点：用户不需要权限→资源需要标签匹配。
你们的数据权限模型与此异曲同工——资源（应用）有 owner_group，用户通过组织关系匹配。
Google Zanzibar (ReBAC) 关系图谱：(object, relation, subject) 三元组授权。
你们代码中 (user, 'primary', group) 的 SubjectMembership 就是 Zanzibar 关系元组。
Google 使用 Spanner 存储，日处理 200 亿+ 鉴权。
GitHub ReBAC (借鉴 Zanzibar) 资源通过层级关系继承权限：Team → Repo → Branch。
你们的 Group → BusinessLine 层级继承与此一致。
字节跳动 自研 ABAC 引擎 内部权限中台，支持可视化策略配置。本质上也是用组织关系 + 资源标签做策略评估。
Kubernetes RBAC + ABAC 可选 RBAC 作为默认。从你们 v1→v2→v3 的演进路径，K8s 也走过：
1.x 只有 RBAC → 后来引入 ABAC 模式 → 最终推荐 RBAC + 准入控制器的组合。
你们（Demo） ABAC-lite 在 RBAC 的教训基础上，去掉权限点，保留组织关系作为核心属性，用策略函数评估。

6. 面试话术：如何讲清楚这套架构

如果面试时被问到"你们系统的权限是怎么设计的"，可以按这个思路回答：

// ── 第一句：定位问题 ──
"我们经历过传统 RBAC 的阶段：角色→权限点映射。
结果就是权限点爆炸，几百个 API 需要手动勾选，漏配就报错。
用户侧也抱怨我们功能藏着不给用。
所以我们决定不再用'用户拥有哪些权限点'这种做加法的模型。"

// ── 第二句：方案选择 ──
"我们调研了业界方案，包括 OPA/Rego、AWS IAM 和 Google Zanzibar。
考虑到我们的场景——组织关系树是核心属性维度，策略变动不频繁，团队规模不大——
我们选择了 ABAC-lite 方案。"

// ── 第三句：实现要点 ──
"核心技术是：不同'用户有没有权限点'，而是问'用户在某个资源上能不能做某个操作'。
判定依据是组织关系链——你是不是业务线负责人？是不是组负责人？是不是成员？
每次请求实时计算，不缓存权限结果。
后端用装饰器做 PEP 守卫，前端用树节点的 manageable 标记做 UX 适配。"

// ── 第四句：与标准 ABAC 的差异 ──
"标准 ABAC 有四个组件：PAP/PDP/PEP/PIP。
我们的 PDP 就是 check_user_can() 函数，PEP 就是 @require_resource_permission 装饰器，
PIP 就是 Django ORM，PAP 就是 Python 策略函数本身。
我们没有引入独立策略语言（如 Rego/XACML），
因为我们属性维度固定、策略变化少，硬编码更简洁，零学习成本。"

// ── 第五句：安全设计 ──
"我们特意不设超级管理员。只有审计管理员，能看到全部数据但任何操作都被拒绝。
is_audit_admin 字段只能通过手动 SQL 设置，没有页面也没有 API。
这是为了减小攻击面——管理员账号即使被攻破，也只能看不能改。"

// ── 第六句：与行业趋势的关联 ──
"有趣的是，我们的 SubjectMembership（用户-组关系）
和 Google Zanzibar 的 (object, relation, subject) 三元组本质上是一个模式。
只是 Zanzibar 在全局规模用 Spanner 存储，我们在本地用 SQLite。
我们的方向和业界趋势一致——从静态角色定义走向动态关系评估。"
总结一句话："我们用简化的 ABAC 模型，以组织关系为核心属性，通过实时策略函数评估替代了传统 RBAC 的静态权限点映射。在灵活性和复杂度之间找到了适合我们场景的平衡点。"

7. 未来演进路径：从 ABAC-lite 走向更完整的 ABAC

你们当前的实现是一个很好的起点。如果未来系统规模增长，可以按以下路径逐步演进：

阶段改造触发条件
现在 🟢 Python 函数策略 + Django ORM 属性源 —
阶段 1 策略注册表可配置化（将策略条件存入数据库，允许页面配置） 非技术人员需要自定义授权规则
阶段 2 引入 OPA sidecar 替代硬编码策略函数 策略变更频繁，需要热加载；或需要统一策略引擎给多个服务使用
阶段 3 PEP 下沉到 API 网关，对业务代码完全透明 微服务化，需要统一鉴权入口
阶段 4 引入 Zanzibar 风格的关系图谱存储（如 SpiceDB） 用户量百万级，需要水平扩展和低延迟
但建议：不要提前复杂化。你们的 ABAC-lite 可以支撑到数百人甚至上千人的团队。等到真的遇到痛点再演进，而不是为了"用上 OPA"而用 OPA。
