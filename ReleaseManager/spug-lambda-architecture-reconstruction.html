1 系统全景：两层安全架构

Spug 发布系统的核心设计理念是安全隔离：内网服务不能直接持有云平台密钥，所有对 AWS 的操作必须经过 API Gateway + Lambda 作为安全代理。

关键要点：Spug-backend 不持有任何 AWS 密钥，所有的 AWS 操作（EC2 SSM、EKS kubectl、ECR 推送）都由 Lambda 执行。这意味着即使内网被攻破，攻击者也无法直接操作 AWS 资源。

2 应用生命周期：从工单到 Spug 同步

一个应用从申请到可以在 Spug 上发布，需要经过两个完全解耦的阶段。

第一阶段：工单流程（与 Spug 无关）

# 业务方提交"新增服务"或"存量服务新增环境"工单 ↓ 工单系统自动化节点调用运维 API ↓ 运维 API 根据提交信息生成初始 K8s YAML ↓ YAML 存入运维 Git 仓库并首次 apply 到集群 ↓ 应用信息录进 CMDB（应用名、语言、业务线、负责人等）

此阶段 Spug 完全不参与。YAML 中的 image 通常写入约定的初始值（如占位镜像），目的是让 Deployment 对象先在集群中存在。后续每次发布都由 Spug-lambda 通过 kubectl set image 来修改。

第二阶段：Spug 从 CMDB 同步

Spug 定时/事件驱动从 CMDB 同步应用数据 ↓ 根据 language 字段匹配 Spug 内部镜像配置表 ↓ 绑定到 Application 表：builder_image + base_image ↓ Java → maven:3.9-temurin-21 + temurin:21-jre-alpine Go → golang:1.23-alpine + alpine:3.20 Node → node:20-alpine + node:20-alpine Python→ python:3.11-slim + python:3.11-slim
关键设计：开发者不需要在工单中填写镜像信息。Spug 同步时根据 language 字段匹配预设规则，自动完成镜像绑定。应用基础镜像和环境基础镜像均在 AWS ECR 中预置。

3 CI 构建：异步执行链路

CI 构建采用全异步模式。Spug-lambda A 只做"创建 Job"这一个轻量操作（1-2 秒），真正的编译在 EKS Job 中异步跑。通过 SQS 做异步回调，后端收到状态后通过 WebSocket 推送给前端实时展示。

设计要点：通过两个 SQS 队列解耦 —— build-log-queue 承载实时日志（允许丢失），build-status-queue 承载构建终态（精确一次投递）。这绕过了 Lambda 15 分钟的超时限制——Java 项目编译 20 分钟也不会出问题。

4 构建脚本：为什么每个应用维护一份

你的困惑：每个应用/环境都要维护一份构建脚本，Lambda 仓库变成配置库。为什么不能统一模板？

现实中的差异来源

表面上看都是 mvn build 或 go build，但每个应用脚本里暗藏了大量隐式差异：

# app-a/prod.build.sh（Java 应用，Maven 多模块 + 特殊 profile） mvn clean package -DskipTests -P prod \ -Dsonar.host.url=... \ -Dmaven.repo.local=/cache/m2 docker build -t $ECR_REPO/$APP:$TAG . docker push $ECR_REPO/$APP:$TAG # app-b/prod.build.sh（Node 应用，前端 + 后端 + CDN 部署） npm ci --production=false npm run build:server npm run build:client aws s3 cp dist/ s3://app-b-static/ --recursive docker build -t $ECR_REPO/$APP:$TAG . docker push $ECR_REPO/$APP:$TAG # app-c/prod.build.sh（Go 应用，编译产物走 EC2 路径） go build -o app -ldflags "-X main.version=$TAG" aws s3 cp app s3://app-c-binaries/$TAG/ aws ssm send-command --instance-ids i-xxx \ --document-name AWS-RunShellScript \ --parameters commands="aws s3 cp s3://app-c-binaries/$TAG/app /opt/app && systemctl restart app"

演进路线

阶段方案覆盖度
第 1 层按语言提供默认模板 + override 机制80% 通用 + 20% 特殊
第 2 层模板变量注入（Profile、缓存路径作为参数）95% 通用
第 3 层构建脚本归业务方，存项目仓库（spug.build.sh）100% 去中心化
核心矛盾：这本质上不是技术问题，而是组织问题——业务团队想要自主权，Lambda 维护者想要通用性。

5 CD 部署：kubectl set image 模式

CI 构建完成后，CD Lambda 直接通过 kubectl set image 修改集群中正在运行的 Deployment。不经过 Git 仓库，不重新 apply 整个 YAML。

回滚能力：K8s 的 Deployment 天然支持 kubectl rollout undo。在 Spug 层面，回滚操作通过调用 CD Lambda 来执行，Lambda 内部决定是执行 rollout undo 还是用旧的 image tag 再执行一次 set image。

6 质量门禁：环境逐级收严

同一个发布单从 dev 走到 prod，每进一级环境多一层检查：

门禁DEV / TESTSTAGINGPROD
Git 分支限制不限release/*main
代码 Review不检查至少 1 人 Approve至少 2 人 Approve
安全扫描不检查SAST 扫描SAST + 依赖扫描
审批无需审批应用负责人审批技术经理 / 架构师
镜像要求任意构建任意构建必须从 staging 晋升
灰度 / 全量直接部署直接部署灰度 10% 观察 全量

在代码层面，这体现为发布状态机中每个阶段的前置检查条件：

8 关键设计决策与演进方向

决策选择权衡
安全隔离API Gateway + Lambda 代理层增加链路复杂度，满足安全合规
CI 执行Lambda 创建 EKS Job + SQS 异步回调绕过 15 分钟超时；需额外队列监控
实时日志CI Job SQS Backend WebSocket 前端全链路异步，延迟约 1-3 秒
CD 方式kubectl set image 直接修改集群简单直接，不回写 Git；Git 中 YAML 可能过期
YAML 生成工单自动化 运维 API 运维 Git 仓库与 Spug 解耦，各司其职
镜像绑定Spug 从 CMDB 同步后按语言匹配开发者无感，规则需维护
构建脚本每个应用/环境独立维护灵活但冗余，存在软件腐烂趋势
1. 构建脚本模板化
按语言提供默认模板覆盖 80% 场景，特殊应用通过 override 或变量注入处理。
2. 引入 GitOps
将 CD 从 set image 演进为 ArgoCD 模式，每次构建后自动修改 Git 仓库 YAML 由 ArgoCD sync 到集群。
3. 构建脚本归业务方
将脚本迁移到业务代码仓库（spug.build.sh），Lambda 构建时从 Git 拉取，脚本版本与代码版本天然一致。
