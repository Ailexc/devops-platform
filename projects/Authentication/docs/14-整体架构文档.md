## 二、四种接入方式

### 2.1 方式一：网关会话（CloudManager / WorkFlowCenter / PermissionCenter / MockApp / PilotApp）

**适用场景**：内部系统，流量经统一网关。

**认证链路**：
```
用户点击应用卡片 → /api/auth/sso-url → 返回 home_url（干净 URL，无 token）
    ↓ 浏览器跳转（自动带 _gw_session Cookie）
    ↓ 网关 forwardAuth → /api/auth/verify
    ↓ 读 _gw_session Cookie → 验证会话 → 注入 X-Auth-* 头
    ↓ 业务后端读 X-Auth-* 头 → 正常工作
```

**安全特性**：
- Token 不进浏览器 URL
- 浏览器只持有 HttpOnly Cookie（JavaScript 不可读）
- 网关有状态会话（不是每请求验 JWT）

### 2.2 方式二：一次性授权码（TaskManager / EventManager）

**适用场景**：跨网络应用，网关覆盖不到。

**认证链路**：
```
用户点击应用卡片 → /api/auth/sso-url → 返回 home_url?code=<一次性授权码>
    ↓ 浏览器跳转（code 非 JWT，泄露无害，60s 有效期，用完即毁）
    ↓ 业务前端用 code 调认证中心 /api/auth/redeem-code 换 JWT
    ↓ JWT 不进浏览器 URL，业务后端本地持有
    ↓ 业务后端从 JWKS 拉公钥验签
```

**安全特性**：
- URL 上是一次性授权码（非 JWT），泄露无害
- JWT 由业务后端向认证中心兑换，不经过浏览器 URL
- 授权码 60s 过期 + 用完即毁

### 2.3 方式三：OIDC 客户端（ReleaseManager）

**适用场景**：外部/异构系统，标准协议接入。

**认证链路**：
```
用户点击应用卡片 → /api/auth/sso-url → 返回 home_url/oauth/login
    ↓ 跳转认证中心 /oauth/authorize（标准 OIDC 授权码 + PKCE）
    ↓ 用户已登录（IdP 会话）→ 自动 302 回 callback?code=xxx
    ↓ 业务后端用 code + client_secret + PKCE verifier 换 JWT
    ↓ JWT 不进浏览器，业务后端本地持有
```

**安全特性**：
- 标准 OAuth 2.1 / OIDC 协议
- PKCE 防授权码注入
- client_secret 只在后端
- Token 不进浏览器 URL

### 2.4 方式四：直连验签（DirectApp）

**适用场景**：演示应用，不经网关，本地验签。

**认证链路**：
```
用户点击应用卡片 → /api/auth/sso-url → 返回 home_url?code=<一次性授权码>
    ↓ 业务后端用 code 换 JWT → 从 JWKS 拉公钥本地验签
```

## 三、会话体系

### 3.1 三种会话 + 一次性授权码

| 会话 | Cookie 名 | 作用域 | 有效期 | 用途 |
|------|-----------|--------|--------|------|
| **IdP 会话** | `auth_idp_session` | 认证中心 | 8h | OIDC authorize 时检查，免重复登录 |
| **门户 BFF 会话** | `portal_session` | 门户 | 8h | 门户 SPA 从 BFF 会话恢复用户信息 |
| **网关会话** | `_gw_session` | 网关 IP（所有端口共享） | 8h | 网关 forwardAuth 校验，替代 URL 传 token |
| **一次性授权码** | 无（URL 参数） | 认证中心 | 60s | 方式二安全跳转，用完即毁 |

### 3.2 会话签发时机

```
用户登录门户
    ↓ OIDC 授权码 + PKCE → 认证中心
    ↓ 认证中心回调 → 门户 BFF
    ↓ 同时签发：
        ├─ portal_session（门户 BFF 会话）
        ├─ auth_idp_session（IdP 登录会话）
        └─ _gw_session（网关会话，所有业务系统共享）
```

### 3.3 会话清除时机

```
用户登出门户
    ↓ /portal/api/logout
    ↓ 同时清除：
        ├─ portal_session
        └─ _gw_session
    ↓ 跳转 /oauth/logout（清除 IdP 会话）
```

## 四、Cookie 共享机制

### 4.1 为什么同 IP 不同端口能共享 Cookie

根据 **RFC 6265**，Cookie 的域（domain）不包含端口。因此：

```
Set-Cookie: _gw_session=xxx; Domain=192.168.3.155; Path=/
```

这个 Cookie 会被浏览器发送到 `192.168.3.155` 的所有端口：
- `http://192.168.3.155:8088`（门户）
- `http://192.168.3.155:8090`（云管）
- `http://192.168.3.155:8091`（工单）
- 等等...

### 4.2 Cookie 安全属性

| 属性 | 值 | 说明 |
|------|-----|------|
| `HttpOnly` | ✅ | JavaScript 不可读，防 XSS 窃取 |
| `SameSite` | `Lax` | 允许顶层导航（点击链接跳转）自动带 Cookie |
| `Secure` | ❌（Demo） | 生产环境需启用（HTTPS） |
| `Path` | `/` | 全路径有效 |
| `Max-Age` | `28800`（8h） | 与会话 TTL 一致 |

## 五、网关 forwardAuth 机制

### 5.1 请求流程

```
浏览器 → Traefik → forwardAuth → /api/auth/verify
                                      │
                                      ├─ 读 Cookie _gw_session
                                      │   └─ 有效 → 返回 200 + X-Auth-* 头
                                      │
                                      ├─ 读 Authorization: Bearer <JWT>
                                      │   └─ 有效 → 返回 200 + X-Auth-* 头
                                      │       └─ 自动创建网关 Session（后续走 Cookie）
                                      │
                                      └─ 都没有 → 返回 401
                                           │
                                           ▼
                                      Traefik 拦截请求，返回 401 给浏览器
```

### 5.2 Traefik 配置

```yaml
auth-forward:
  forwardAuth:
    address: "http://auth-backend:8000/api/auth/verify"
    trustForwardHeader: true
    authResponseHeaders:
      - "X-Auth-User"
      - "X-Auth-Username"
      - "X-Auth-Name"
      - "X-Auth-Source"
    # 关键：从认证服务器透传 Set-Cookie 到浏览器
    addAuthCookiesToResponse:
      - "_gw_session"
```

### 5.3 `addAuthCookiesToResponse` 的作用

当 `/api/auth/verify` 返回 `Set-Cookie: _gw_session=xxx` 时，Traefik 会将这个 Cookie 透传给浏览器。这使得：

1. 门户登录时签发的网关 Session Cookie 能被浏览器保存
2. 后续请求自动携带这个 Cookie
3. 网关验证 Cookie 后注入身份头

## 八、安全设计

### 8.1 Token 安全

| 风险 | 当前方案 | 说明 |
|------|----------|------|
| URL 泄露 | ✅ 已解决 | Token 不进浏览器 URL |
| XSS 窃取 | ✅ 已解决 | HttpOnly Cookie，JavaScript 不可读 |
| CSRF | ✅ 已解决 | SameSite=Lax，跨站请求不带 Cookie |
| 授权码注入 | ✅ 已解决 | 一次性授权码，60s 过期，用完即毁 |
| Referer 泄露 | ✅ 已解决 | URL 上无敏感信息 |

### 8.2 会话安全

| 措施 | 说明 |
|------|------|
| 会话 ID | `secrets.token_urlsafe(32)`，密码学安全随机 |
| 会话 TTL | 8 小时，与 IdP 会话一致 |
| 会话清除 | 登出时清除所有相关会话 |
| 并发安全 | `threading.Lock` 保护会话存储 |

## 十、面试叙事

### 10.1 核心亮点

1. **三种企业级接入方式在一个项目里全部落地**：
   - 网关会话（内部系统，零鉴权代码）
   - 一次性授权码（跨网络，Token 不进 URL）
   - OIDC 客户端（外部系统，标准协议）

2. **Token 永远不进浏览器 URL**：
   - 网关会话：HttpOnly Cookie
   - 一次性授权码：非 JWT，60s 过期，用完即毁
   - OIDC：授权码 + PKCE，Token 只在后端

3. **网关有状态会话**：
   - 不是每请求验 JWT（无状态）
   - 维护用户会话（有状态）
   - Session Cookie 自动续期

4. **RFC 依据清晰**：
   - RFC 9700 §4.1：Access tokens should not be passed in the URL
   - draft-ietf-oauth-browser-based-apps §6.1：BFF 模式
   - RFC 6265：Cookie 域不含端口，同 IP 所有端口共享

### 10.2 面试问答

**Q：为什么不用 JWT 做无状态认证？**

A：JWT 无状态认证的问题是 Token 必须在客户端持有。放在 localStorage 有 XSS 风险，放在 URL 有泄露风险。业界规范（IETF 草案）推荐 BFF 模式：Token 只在服务端，浏览器只持有 HttpOnly Cookie。

**Q：网关会话和 JWT 有什么区别？**

A：网关会话是有状态的——服务端存储会话信息，浏览器只持有会话 ID（Cookie）。JWT 是无状态的——Token 本身包含用户信息，服务端不需要存储。对于浏览器应用，有状态会话更安全（Token 不进浏览器）。

**Q：一次性授权码和 OIDC 授权码有什么区别？**

A：本质上相同——都是一次性、短时效、用完即毁。区别是 OIDC 授权码是标准协议（RFC 6749），有完整的安全机制（PKCE、state、nonce、redirect_uri 白名单）。一次性授权码是简化版，用于内部系统跳转。

**Q：同 IP 不同端口怎么共享 Cookie？**

A：RFC 6265 规定 Cookie 的域（domain）不包含端口。所以 `Set-Cookie: _gw_session=xxx; Domain=192.168.3.155` 会被浏览器发送到 192.168.3.155 的所有端口。
