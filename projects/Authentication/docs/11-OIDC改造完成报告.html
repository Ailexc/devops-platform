01一句话结论

改造前是「自研 token 透传 + 一个形似 OIDC 的骨架」两套互不认账的体系；改造后认证中心对外就是一个规范的 OIDC Provider（OAuth 2.1 Authorization Code + PKCE），门户以标准 OIDC 客户端身份接入（BFF 模式），oidc-demo 作为第二个标准客户端演示第三方接入，内部遗留应用仍走网关模拟链路但已在文档中明确标注边界。

02改造前后对比

改造前（自研私有协议）

  • 门户登录：自研 POST /api/auth/login，token 存 localStorage
  • SSO 主链路：sso-url 生成 ?token=统一JWT，URL 传 token
  • OIDC 形似骨架：id_token ≡ access_token、无 PKCE/nonce、redirect_uri 用前缀匹配、refresh 无轮换、授权码存内存、state 不强制
  • 两套体系不互认：OIDC token 的 aud=client_id 过不了网关 aud=devops-portal 校验
  • 网关 forwardAuth 与 OIDC 各走各的，面试难以自圆其说

改造后（规范 OIDC）

  • 门户登录：门户 BFF 走 OAuth 2.1 授权码 + PKCE，token 只在后端，浏览器仅 HttpOnly Cookie
  • 认证中心 = 标准 IdP：authorize / token / userinfo / end_session / openid-configuration / JWKS
  • id_token 与 access_token 职责分离；nonce 防重放；refresh 轮换 + 复用检测；授权码/refresh 哈希入库
  • OIDC 链路统一（门户 + oidc-demo 都是标准客户端），aud=client_id 全程一致
  • 内部应用（mock/pilot）保留网关模拟接入，明确标注为「内部兼容链路，非 OIDC 标准」

06面试叙事要点（怎么讲）

  1. 为什么用 OIDC 而不是自研 token？——“统一入口 + 多系统”正是 OIDC 的典型场景：认证中心是 IdP，各系统是 RP。自研 token 透传无法回答‘token 怎么签发/校验/轮换/撤销’，OIDC 有完整规范，面试官可以对着标准问，我也能对着标准答。”
  2. 授权码 + PKCE 讲法：“OAuth 2.1（RFC 9700）把 PKCE 设为授权码流必选项，防止授权码被中间人截获。我的实现里 code_challenge 在 authorize 时绑定，token 时用 code_verifier 校验，且授权码只存哈希、一次性、5 分钟过期。”
  3. id_token vs access_token 分离：“id_token 是身份断言（谁），含 nonce 防重放、iss/aud 校验；access_token 是授权凭证（能访问什么），aud=client_id。改造前两者是同一个 JWT，这是最大的不规范点。”
  4. refresh token 轮换 + 复用检测：“RFC 9700 建议轮换：每次刷新发新 token 作废旧 token；如果被轮换过的旧 token 再次出现，判定泄露并撤销整个 family——这是自研系统最难做对的一块。”
  5. BFF 模式：“门户作为 OIDC 客户端，token 只在后端，浏览器只有 HttpOnly Cookie。这样 XSS 拿不到 token，符合现在 SPA + OIDC 的最佳实践（BFF pattern）。”
  6. 单点登出：“门户走 end_session 端点（RP-initiated logout）同时清 IdP 会话，一次登出全局登出。”
  7. 内部系统边界（诚实话术）：“内部遗留应用（mock/pilot）Demo 里走网关 forwardAuth 模拟链路，接口上作为‘内部兼容接入’保留；对外标准接入统一走 OIDC（oidc-demo 演示）。真实生产里内部系统也应逐步迁到 OIDC。”——这句话让面试官知道你不是没意识到边界，而是有意为之。
