1一次 SSO 访问的全景

先看完整的一次访问，再拆解凭证，避免"只见树木不见森林"

👤 用户/浏览器 🏠 统一门户 🔑 认证中心 📦 业务前端 🛡️ 网关 📦 业务后端
输入用户名密码登录门户
认证中心校验 → 签发统一 JWT → 交给浏览器
★ 凭证诞生：JWT 此刻来到前端（浏览器）手里
点击应用 → SSO 跳转（带 token 或 code）
业务前端拿到统一 JWT 并存好
调业务 API：带 Authorization: Bearer JWT
★ 凭证使用：前端带着 JWT 请求后端
网关 forwardAuth 校验 JWT → 注入 X-Auth-* 头
业务后端读 X-Auth-* 头，返回数据
→ 全程只登一次，凭证始终是那一张统一 JWT

一个最容易混淆的点：换 token 在后端，用 token 在前端

换 token（OIDC 授权码）

"去认证中心领 token"这一步只能由业务后端做，因为要带 client_secret（机密只存在后端）。
→ 这就是"token 给后端"的含义：换票的动作在后端。

用 token（请求 API）

真正发请求时，是浏览器（前端）带着 Authorization: Bearer JWT 请求业务后端。
→ 这就是"前端拿 token 请求后端"：用票的是前端。

✅ 不矛盾："换 token"在后端（安全），"用 token"在前端（使用）。后端领到 token 后转交前端，或前端用 PKCE 直接领——最终前端持票请求后端。

3两种 SSO 机制：token 跳转 vs OIDC 授权码

核心差异 = 凭证交换的"阶段数"：一阶段 vs 两阶段

token 跳转 一阶段 · Demo 现状

🔑认证中心签发 JWT
↓ 直接带 ?token= 跳转
📦业务系统网关/后端验签即放行

一次性给票，简单直接；JWT 在 URL 里（有泄露风险）。

OIDC 授权码 两阶段 · 企业标准

🔑认证中心先给"兑换券" code
↓ 阶段①：浏览器拿 code
📦业务后端阶段②：code + client_secret 换真 token
↓ token 转交前端使用
👤前端带 Authorization 头请求后端

先换券再换票；token 不进浏览器 URL，更安全。

为什么"两阶段"更安全？（OIDC 的核心设计动机）

设计作用
token 不经过浏览器 URL减少泄露面——token 只发给应用后端，不进浏览器地址栏/历史/日志
code 一次性 + 短时效即使 code 被截获，也很快失效、无法复用
换 token 要 client_secret只有"真正的应用后端"能换到 token，防止恶意冒充应用
⚠️ 如果 OIDC 也是"一阶段直接给 token"，它就和 token 跳转没区别了——两阶段正是它安全性的来源。面试问"为什么用授权码模式"，答案就是这三点。

4凭证的两种传递载体：URL vs 请求头

"JWT 放 URL 还是放 Authorization 头？"——其实是两个不同阶段的载体，不矛盾

阶段① SSO 跳转（页面导航）

从门户跳去业务系统的页面，此时页面还没加载、前端无法设请求头，token 只能"带过去"：

home_url?token=eyJhbGciOi...

Demo 用 URL（简单，有风险）；更安全用 HttpOnly Cookie / 先跳 /sso 端点种 cookie。

阶段② API 请求（标准方式）

进入系统后，前端调业务 API 时把 JWT 放请求头（RFC 6750 标准）：

Authorization: Bearer eyJhbGciOi...

这是 JWT 长期、高频的传递方式；URL 方式只是跳转那一瞬间的过渡。

⚠️ 记住：URL 传 token 是不推荐的生产做法（token 会进浏览器历史、服务器日志、Referer）。Demo 用它只是简化演示；生产请用 Cookie 或 OIDC。

5两层身份凭证：别把"用户"和"应用"搞混

一套 SSO 里其实有"两种身份"，凭证各不相同

👤用户凭证 = JWT证明"是哪个用户在访问"
登录后签发，前端持有
≠
📦应用凭证 = client_id/secret证明"是哪个应用在调用"
注册后发放，后端持有
维度用户凭证（JWT）应用凭证（client_id / client_secret）
证明的是哪个人（张三）哪个应用（NoteManager）
怎么获得用户登录认证中心后签发应用注册时系统发放
谁持有浏览器/前端应用后端（secret 机密）
干什么用访问业务 API 时验身份OIDC 换 token 时验应用身份
保密级别需防护（防泄露/盗用）client_id 公开；client_secret 绝密
✅ 一个用户可访问多个应用；一个应用可为多个用户服务——两层身份独立，这是理解 SSO 的关键。

6client_id / client_secret 到底干嘛的？

它俩是"应用的身份凭证"，用途取决于 SSO 类型

SSO 类型需要 client_secret 吗原因
token 跳转
Demo 现状		 ❌ 凭证就是 JWT 本身，业务系统验 JWT 签名即可，用不到应用凭证
OIDC 授权码
企业主流		 ✅ 前端发起授权用 client_id（公开标识）；后端换 token 用 client_secret（机密，只存应用后端）
client_idclient_secret
角色应用身份证号（公开）应用后端密钥（机密）
能公开吗✅ 可以（会出现在授权 URL）❌ 绝不能，只存应用后端
类比用户名 / 门牌号密码 / 保险箱钥匙
💡 一句话：client_id 公开标身份，client_secret 机密证明身份。两者是应用的凭证（不是用户的），只由应用自己使用、绝不分发他人。Demo 自动生成它们是为接 OIDC 预留。

7高频混淆点问答（FAQ）

把最容易绕晕的几个点集中澄清

Q1：JWT 到底是放 URL 还是放 Authorization 头？
两个场景：SSO 跳转那一刻（页面导航，前端还拿不到 token）用 URL/Cookie 带过去；进入系统后的 API 请求用 Authorization: Bearer 头（标准）。URL 只是过渡且不推荐生产用。
Q2：token 是给业务前端还是业务后端？
最终给前端持有、由前端带着请求后端（你没理解错）。"给后端"指的是 OIDC 里换 token 的动作在后端（要 client_secret），领到后仍转交前端使用。
Q3：token 跳转和 OIDC 本质一样吗？
体验上都是"登一次"，但机制阶段数不同：token 跳转=一阶段直接给票；OIDC=两阶段先换券（code）再换票（token），两阶段正是它更安全的原因。
Q4：client_secret 为什么不给前端？
它是机密凭证，放在前端会被任何人看到。只有应用后端能安全保管，所以"换 token"只能由后端发起。纯前端应用（无后端 secret）则用 PKCE 代替。
Q5：为什么业务后端能信这个 JWT？
JWT 用 RS256 非对称签名：认证中心私钥签发，公钥经 /.well-known/jwks.json 发布。任何系统用公钥验签即可，篡改即失效——所以可以"谁都能验、又没人能伪造"。

9用一个「景区通票」故事，把整套机制串起来

前面的章节偏术语，这一节换个讲法：把 SSO 想象成一座景区

景区里的东西对应的 SSO 概念
景区大门（买一张通票）统一门户 + 认证中心（登录一次，发一张统一 JWT）
这张"通票"统一 JWT（一张票，所有景点通用）
进景点前的检票闸机统一网关 forwardAuth（进每个应用先验一次票）
闸机旁的验票窗口verify 端点（帮闸机确认票真不真）
闸机验完在票上盖的章X-Auth-* 头（把"你是谁"写清楚，交给景点）
一个个景点业务系统（收到盖了章的票，直接放你进）
不经过闸机的侧门直连自验签（应用自己在门口核对票，用公钥验 JWT）
✅ 一句话故事：你在景区大门买一张通票（登录拿 JWT）→ 每进一个景点，门口的自动闸机（网关）替你验一次票（verify）→ 验过就盖个章（X-Auth-*）放你进（业务系统），全程不用再买票。

10验票窗口 verify：怎么请求？带什么？

就像去窗口验票：你把票递过去，验票员点头（200）或摆手（401）

① 把票放在哪？两种递法（二选一）

方式① 把票放"口袋"里（标准）

用请求头带票，不显眼、干净：

Authorization: Bearer 一张JWT

（放 header 里，像把票放口袋，不举着）

方式② 把票举在手上（Demo 兼容）

直接挂在 URL 上：

GET /api/auth/verify?token=一张JWT

（放 query 里，像把票举在手上，容易被人看到——不推荐生产）

② 请求长这样（方法：GET）

GET /api/auth/verify + 请求头 Authorization: Bearer <JWT>
→ 验票员（认证中心）拿你的票去核对签名、看有没有过期

③ 验票员怎么回？

🎫拿票来验Bearer JWT
→
🪪验票窗口 verify查签名/有效期/用户
→
✅票真 → 200放行，并给身份章
X-Auth-User 等
🎫票假/没票无头或无效
→
🚫拒绝 → 401拦截，不放行
返回码含义验票员动作Body / 头
200票有效点头放行{"code":200,"user":{...}} + 响应头 X-Auth-*
401票无效/缺失摆手拒绝{"code":401,"user":null}

11接入网关 = 给景点入口装一台「自动验票闸机」

这样景点自己不用查票，闸机（网关）统一帮你查

装闸机前 vs 装闸机后

❌ 不装闸机（应用自己验）
🎫游客（请求）带 Bearer JWT
↓
🏛️每个景点门口自己查票每个应用都要写验签代码（麻烦、重复）
✅ 装闸机（经网关）
🎫游客（请求）带 Bearer JWT
↓
🛡️统一闸机（网关）先拦下，转发给验票窗口 verify
↓ 验过 → 盖章 X-Auth-*
🏛️景点（业务系统）只收盖章的票，零验签代码

给一个应用"装闸机"，只需要配三段

①定义闸机middlewares.auth-forward
指向 verify 验票窗口
→
②把闸机装到入口routers 配规则
挂上 auth-forward
→
③闸机通向景点services 指向
应用容器地址

配置示意（gateway/dynamic.yml，我们 mock-app 就是这样的）： 

middlewares:
  auth-forward:                 # ① 闸机：去哪个窗口验票
    forwardAuth:
      address: "http://auth-backend:8000/api/auth/verify"
      authResponseHeaders: ["X-Auth-User","X-Auth-Username","X-Auth-Name","X-Auth-Source"]
routers:
  my-app-api:                   # ② 闸机装到景点入口
    rule: "Host(`myapp.xxx`) && PathPrefix(`/api/`)"
    service: my-app-service
    middlewares: [auth-forward]
services:
  my-app-service:               # ③ 闸机放行后通向哪个景点
    loadBalancer:
      servers: [{ url: "http://my-app:8080" }]
✅ 装完之后，景点（业务后端）收到的每个请求都已经"验过票、盖过章"了——它只要读 X-Auth-* 头就知道是谁，一行鉴权代码都不用写。

接入网关要改多少？

两种模式：各自要做什么 / 不做什么

经网关接入（forwardAuth）不接网关（直连 JWKS 自验签）
谁验票网关（转发 verify 或网关本地验）应用自己（本地验 JWT）
网关做什么配 forwardAuth（middlewares/routers/services），请求自动 验票→放行+盖 X-Auth-* 章 / 拦截不参与
应用拉公钥❌ 不用✅ 从 /.well-known/jwks.json 拉取缓存
应用调 verify❌ 不用（网关代调）❌ 不用（本地验签，可选外包）
应用后端改造读 X-Auth-* 头（≈0 行鉴权）加一个验签中间件（20-30 行）
认证中心挂了新请求被拦（verify 不可用）已发 token 仍可验（本地验签）
适用场景网关能覆盖的应用外部 / 内部服务互调
🎯 记忆口诀：网关模式 = 「闸机统一验票，应用收盖章的票」；直连模式 = 「应用自己对着门口的防伪图核票，不回去问大门」。两种模式应用都不用去请求 verify——verify 是给"不会自己验票的网关"准备的。
