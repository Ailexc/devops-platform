为什么是授权码 + PKCE

授权码（Authorization Code）+ PKCE（Proof Key for Code Exchange）是 OAuth 2.1 / OIDC 推荐的标准登录流程。它把登录过程分成两个阶段，让 token 永远不经过浏览器，从而把最敏感的凭证锁在服务端。

流程逐步拆解

以门户为例（门户 SPA → 门户 BFF → 认证中心），完整六步：

  1. 发起：门户 BFF 生成 PKCE 验证值 code_verifier，算出挑战值 code_challenge = SHA256(verifier) 的 base64url；同时生成 state（防 CSRF）与 nonce（防重放）；
  2. 跳转授权端点：302 到 /oauth/authorize，携带 client_id、redirect_uri、scope=openid、state、nonce、code_challenge、code_challenge_method=S256；
  3. 用户登录：认证中心要求用户登录并确认；
  4. 回一次性授权码：302 回 redirect_uri，携带 code（5 分钟有效、一次性）与 state；
  5. 换 token：BFF 用 code + code_verifier + client_secret 调 /oauth/token，换取 id_token / access_token / refresh_token；
  6. 校验并建会话：校验 id_token 的 nonce 与签名，建立 HttpOnly 会话。
# PKCE 生成（示意）
verifier   = secrets.token_urlsafe(48)                       # 随机验证值
challenge  = base64url( sha256( verifier ) )                 # 挑战值
# 发起时只把 challenge 交给认证中心；换 token 时才用 verifier

PKCE 到底防什么

授权码模式有一个经典风险：授权码在回跳过程中可能被截获（如恶意应用注册了类似回调、或中间人）。截获者拿到 code 后，若没有额外保护，就能直接去换 token。

PKCE 的解法是把"授权码 → token"绑定到发起方：

  • 发起方自己生成 code_verifier（只有它知道）；
  • 授权端点只登记它的 code_challenge（哈希值，即使泄露也无法反推 verifier）；
  • 换 token 时必须同时给出 code_verifier，认证中心用同一哈希算法比对 challenge。

因此，截获到授权码的攻击者没有 verifier，换不到 token。这就是 OAuth 2.1 把 PKCE 从"可选"变为"强制"的原因——它让即使没有 client_secret 的纯前端 SPA 也能安全使用授权码流程。

本项目落地：认证中心对授权码做 PKCE 强制校验（缺失 code_verifier 直接拒绝）、授权码 5 分钟有效、一次性、以哈希入库；门户 BFF 与 oidc-demo 均完整实现 PKCE。

为什么分两阶段

对比"隐式流程（直接把 token 发到前端）"，授权码流程的核心收益：

对比授权码 + PKCE隐式流程（已废弃）
token 落点只在应用后端直接出现在浏览器 URL / 前端
泄露风险低（token 不进浏览器）高（URL 历史、日志、XSS 均可窃取）
标准地位OAuth 2.1 唯一推荐已从 2.1 删除

小结

  • 授权码 + PKCE = 两阶段换票，token 永不进浏览器。
  • PKCE 把授权码绑定到发起方，防截获冒用，是 OAuth 2.1 强制项。
