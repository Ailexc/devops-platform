三个概念的关系

一句话概括：OIDC 是在 OAuth 2.0 之上加了"身份层"；OAuth 2.1 是 OAuth 2.0 的安全强化收敛版。本项目遵循的是 OAuth 2.1 授权码 + PKCE + OIDC 这一套现代组合。

OAuth 2.0（2012）→安全强化→OAuth 2.1（收敛版）
OAuth 2.x（授权框架）+OpenID Connect（身份层）=OIDC（认证 + 授权）

OAuth 2.0：授权框架

OAuth 2.0 解决的是授权问题：让用户授权第三方应用访问自己在某个服务上的资源，而不用交出密码。核心角色：

  • 资源所有者：用户；
  • 资源服务器：持有用户数据（本项目 = 业务系统）；
  • 授权服务器：签发令牌（本项目 = 认证中心）；
  • 客户端：申请访问的应用。

但它只管"你能不能访问"，不管"你是谁"。access_token 对客户端是不透明的（opaque），客户端无法从令牌本身得知用户身份。

OIDC：在 OAuth 上加身份层

OpenID Connect（OIDC）在 OAuth 2.0 授权码流程之上增加了标准化的身份层：

  • 新增 scope=openid 与 id_token（JWT 身份断言，含 sub、name、nonce 等）；
  • 新增 /.well-known/openid-configuration 发现文档，客户端可自动发现端点；
  • 新增 /userinfo 端点，用 access_token 获取用户标准属性；
  • 定义了 nonce（防重放）、end_session（登出）等。

所以 OIDC = OAuth 2.0 授权 + 标准化身份信息，既管"你是谁"，又管"你能访问什么"。

OAuth 2.1：2.0 的安全收敛版

OAuth 2.0 有多个可选 flow 和宽松配置，实践中最容易踩坑。OAuth 2.1 把这些收敛为更安全的最小集合：

2.0 中的宽松做法2.1 的收敛要求
授权码流程可不用 PKCE授权码 + PKCE 强制
Implicit（隐式）流程允许发 token删除 Implicit 流程
redirect_uri 可前缀匹配精确匹配
资源所有者密码凭证流程（password）删除
refresh_token 可无限复用建议轮换 + 复用检测

对本项目而言，门户 SPA + BFF 正是 2.1 推荐的标准形态：SPA 不能有 secret → 用 PKCE；需要后端 → 用 BFF 持有 secret。

本系统的遵循情况

OAuth 2.1 / OIDC 要求本项目实现
授权码 + PKCE 强制✅ 全部客户端强制校验 code_verifier
redirect_uri 精确匹配✅ 精确白名单，前缀匹配已废弃
state 防 CSRF✅ 回调严格比对 state
nonce 防重放✅ id_token 内嵌 nonce 并校验

小结

  • OAuth 管授权（能不能访问），OIDC 在其上加身份层（你是谁），OAuth 2.1 是安全强化版。
  • 本项目 = OAuth 2.1 授权码 + PKCE + OIDC，标准协议实现。
  • 标准的意义：可对接任意成熟 IdP、面试可讲清、安全默认内置。
