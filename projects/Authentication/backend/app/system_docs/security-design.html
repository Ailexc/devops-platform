安全设计原则

本项目的安全设计遵循一个核心思想：安全不是自己发明，而是用标准协议内置的防护，并对高风险点做纵深加固。没有凭感觉"搞一套"，每一层都有明确的对抗目标和实现。

协议层四重防护

防护对抗的攻击实现
stateCSRF（伪造授权回调）发起时生成随机 state，回调时严格比对，不一致即拒绝
nonceid_token 重放id_token 内嵌 nonce，客户端校验与发起时一致
PKCE授权码被截获后冒用code_verifier 只有申请方持有，换 token 时校验
授权码一次性 + 短时效授权码被重用5 分钟有效、用过即废、以哈希入库

凭证安全

  • Token 不落浏览器：门户 BFF 模式下，id/access/refresh 三种 token 只存在于服务端；浏览器只有 HttpOnly 会话 Cookie（JS 读不到，防 XSS 窃取）；
  • client_secret 只在后端：应用注册时一次性展示，后续不可查看，支持重置；
  • 密码 bcrypt 哈希：本地用户库密码不以明文存储；
  • 授权码 / refresh_token 哈希入库：数据库泄露无法直接换取 token；
  • RS256 非对称：私钥只在认证中心，公钥可公开分发，谁都能验、没人能伪造。

凭证传递规范

传递方式安全等级本项目用法
OIDC 授权码 + PKCE最安全门户 / oidc-demo 登录主流程（方式三）
HttpOnly Cookie推荐门户 BFF 会话（portal_session）+ 网关会话（_gw_session）
一次性授权码推荐方式二安全跳转（非 JWT，60s 过期，用完即毁）
URL 参数 ?token=Demo 简化已废弃 → 网关会话 Cookie / 一次性授权码替代
Authorization: Bearer推荐业务 API / userinfo 调用（方式二/三后端持有 JWT）
安全改造：URL 参数 ?token= 已废弃。方式一改用网关会话 Cookie（HttpOnly，RFC 6265 同 IP 共享），方式二改用一次性授权码（非 JWT，泄露无害）。Token 永远不进浏览器 URL。参考 RFC 9700 §4.1、draft-ietf-oauth-browser-based-apps §6.1。

认证失败不降级

身份源支持降级链（Local → LDAP → Okta），但降级有严格的边界：

  • 只降"不可用"：身份源连接超时 / 服务宕机时才降级到下一个，保证登录不中断（高可用）；
  • 绝不降"认证失败"：用户不存在 / 密码错误是明确失败，直接 401——防止攻击者穿透到弱身份源。
安全边界："认证失败不降级"是必须坚守的底线。如果密码错误也能降级，攻击者就能用弱口令逐一探测所有身份源。

审计

每次登录都写入认证日志（auth_logs 表）：来源（local/ldap/okta）、结果（成功/失败）、IP、时间戳。管理员可在「系统 → 认证日志」查看，安全事件可追溯。

小结

  • 协议层：state / nonce / PKCE / 一次性授权码四重防护。
  • 凭证层：token 不进浏览器、secret 只在后端、哈希入库、RS256。
  • 身份层：认证失败绝不降级 + 全量审计。
