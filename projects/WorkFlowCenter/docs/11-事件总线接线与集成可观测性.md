# 事件总线接线与集成可观测性（11-开发计划）

> 目标：让「事件日志」板块从"空"变"活"，补齐集成健康度看板与开放 API 治理。
> 设计原则：**事件日志瘦身**——本系统只留「集成可观测」最小事件集，审计/合规全量留痕走外部审计平台（已推给审计中心）。

---

## 一、背景

- 现状：`EventBus`（写 EventLog + 异步 Webhook 投递 + HMAC 签名 + 重试）已完整实现，但**业务代码从未调用 `publish`**，导致事件日志/投递记录全空。
- 用户判断（已确认）：
  - 事件日志不做"全量审计仓库"（那类归外部审计平台），只做**关键节点事件 + 投递记录**，量小且能反映整体工单工作流
  - 操作人维度不重复记录（审批历史/流程追踪已覆盖）
  - 集成健康度看板、开放 API 治理有价值，需补齐

## 二、设计原则

| 原则 | 说明 |
|---|---|
| 事件瘦身 | 每张工单生命周期只发 **5~10 条关键事件**（启动/任务创建/任务完成/驳回/完成/终止） |
| 审计外推 | 全量操作留痕（谁改了哪个字段、前后值）不落本系统，交给外部审计平台 |
| 集成可观测 | 本系统只留"事件已发生 + 是否投递成功"两类最小记录 |
| 不重复 | 操作人在流程追踪/审批历史看，事件日志只关联对象（instance/task/ticket） |

## 三、阶段一：事件总线接线（流程引擎关键节点 publish）

### 事件类型清单

| 事件类型 | 触发点 | 说明 |
|---|---|---|
| `process.started` | `engine.start()` 末尾 | 流程启动 |
| `task.created` | `engine._create_tasks_for_node()` 末尾 | 审批/办理节点创建待办 |
| `task.completed` | `engine.complete()` 末尾 | 节点审批/办理完成（result=approve 等） |
| `task.rejected` | `engine.reject()` 末尾 | 节点驳回 |
| `process.completed` | `engine._advance()` end 分支 | 流程正常结束 |
| `process.terminated` | `engine.terminate()` 末尾 + reject 内 | 流程终止/驳回终止 |

### 接线方式
- `engine.py` 加私有辅助 `_publish_event()`（方法内 `import EventBus`，避免循环依赖）
- 各接线点调用并带 payload（instance_no / node_key / node_name / result / 来源）

### 数据量预期
- 一张工单：start(1) + 每审批节点 created/completed(各1) + completed/terminated(1) ≈ 5~10 条
- 投递记录：每个活跃订阅 × 匹配事件 各 1 条（当前订阅 1 条，事件数可控）

## 四、阶段二：集成健康度看板（投递可观测）

### 后端
- 新增统计端点 `GET /api/v1/webhook-stats/`（或并入 events）：返回
  - 投递汇总：总 / 成功 / 失败 / 重试中
  - 每个订阅：名称、最近投递时间、最近成功/失败、失败数、最后响应
  - 最近失败列表（10 条）
- 失败重放：`POST /api/v1/webhook-deliveries/:id/retry/` 或批量重放失败投递

### 前端（事件日志页改造）
- 页顶加「投递健康」卡片：总/成功/失败计数 + 每个订阅状态 + 最近失败
- 事件日志表格保留（列表 + 详情 + payload）
- 失败投递行加「重放」按钮

### 说明
- 投递失败在 Demo 中为**模拟**（`_deliver_pending_webhooks` 实际发 HTTP 到 example.com 会失败）——可构造几条失败/成功投递记录用于演示，或投递逻辑对 `.example.com` 目标标记"模拟成功"

## 五、阶段三：开放 API 治理（调用统计）

### 后端
- 新增 `ApiCallLog` 模型：app（InitiatorApp 外键）/ code / method / path / status_code / duration_ms / created_at
- 程序发起接口（`process-instances/start` 带 `X-App-Code/X-App-Key` 分支）记录调用
- 统计接口：按 app 汇总调用次数 / 错误数 / 最近调用 / 平均耗时

### 前端（开放 API 页）
- 「业务方接入 · 接入方登记」表格加列或页顶统计卡：各接入方调用量 / 错误 / 最近调用
- 体现"API 治理"（配额/限流可说明，不强制实现）

## 六、实施步骤

1. **阶段一**：engine.py 接 6 个事件点 → 运行 seed 数据或实操触发，确认 EventLog 有数据、投递记录生成
2. **阶段二**：events 统计端点 + 前端投递健康卡 + 失败重放
3. **阶段三**：ApiCallLog 模型 + 调用统计展示
4. 快照更新（demo_full.json）+ 前端重建 + 浏览器验证

## 七、验收标准

- [x] 事件日志页有真实数据（能按类型筛选，展示工单工作流事件链）
- [x] 事件发布后自动产生 Webhook 投递记录
- [x] 投递健康卡显示成功/失败/重试，可对失败重放
- [x] 开放 API 页展示各接入方调用统计
- [x] reset_demo 后上述数据完整

## 八、不做的事（控制范围）

- 不做全量审计仓库（操作人/前后值）——流程追踪已覆盖，审计外推
- 不做真实外部 HTTP 出站调用（任务中心/发布平台仍为说明/模拟）
- 不做速率限制/配额强制执行（仅说明 + 调用统计）
- 不做事件溯源（Event Sourcing）
