# Demo 工单系统设计方案

> 目标：实现一个符合行业实践、可用于面试演示的工单系统 demo。
> 技术栈：Django 5 + DRF + django-fsm + JSON Schema + Celery/Redis + drf-spectacular + PostgreSQL

---

### 领域分层（对应旧版"两大块"的现代化拆分）

| **工单业务** | 工单类型、动态表单 schema、业务数据（form_data）、优先级 | 表单+工单配置 |

| **权限** | RBAC + 对象级权限 | —（新增） |

## 二、核心数据模型

### 1. 流程引擎

```
ProcessDefinition（流程定义 = 工单模版）
├─ key         唯一标识（如 "server_request"）
├─ name        名称
├─ version     版本号（key+version 唯一，发布后不可变）
├─ status      draft / published / disabled（草稿/已发布/停用）
├─ definition_json  流程定义 JSON（节点模型，见下）
├─ form_schema      动态表单 JSON Schema（2020-12）
└─ created_by / timestamps

ProcessInstance（流程实例 = 流动工单）
├─ definition       FK → ProcessDefinition
├─ instance_no      工单号（如 "WO20260803001"）
├─ status           FSM：running / suspended / completed / terminated
├─ current_node_key 当前节点
├─ variables        JSONField（流程全局变量，节点间传递 + 表单数据）
├─ business_key     业务键（程序提单关联外部业务）
├─ started_by / started_at / ended_at
├─ title            工单标题（由表单字段或发起时指定）
└─ priority / queue （可选 ITSM 字段）

NodeTask（任务 = 待办）
├─ instance         FK → ProcessInstance
├─ node_key / node_name / node_type
│                    approve(审批) / handle(办理) / cc(抄送) / service(自动) / manual
├─ assignee         FK → User（处理人）
├─ candidate_users  JSON（候选办理人，或签/会签场景）
├─ status           pending / claimed / completed / cancelled / skipped
├─ result           approve / reject / submit（办理结果）
├─ opinion          审批/办理意见
├─ due_at / claimed_at / completed_at / completed_by
└─ countersign      会签信息 JSON：{mode, total, completed, passed, threshold}

TaskInstance（会签/或签子任务）
├─ task             FK → NodeTask
├─ assignee         FK → User
├─ status           pending / completed / cancelled
└─ result / opinion / completed_at

ApprovalRecord（审批/办理记录，只增不改）
├─ instance / task
├─ user / action（approve/reject/submit/auto）/ opinion
└─ created_at

EventLog（领域事件日志）
├─ instance / task（可空）
├─ type（ticket.created / task.completed / instance.completed ...）
└─ payload(JSON) / created_at
```

### 2. 能力注册中心

```
Capability（原子能力注册）
├─ code         唯一标识（如 "cmdb.create_host"）
├─ name / description
├─ endpoint     执行地址（作业平台 API 或本地 Python 调用）
├─ input_schema / output_schema   JSON Schema（入参/出参契约）
├─ execute_mode  sync / async
└─ is_active

TaskJob（任务执行记录）
├─ instance / task（关联的流程节点）
├─ capability      FK
├─ job_id          外部作业平台任务 ID
├─ status          queued / running / succeeded / failed / cancelled
├─ input_data      JSON（入参快照）
├─ output_data     JSON（出参快照）
├─ sync            bool（同步 or 异步）
├─ error_message
└─ timestamps（queued/started/finished）
```

### 3. 工单业务

```
TicketType（工单类型，可选增强）
├─ code / name
├─ priority_matrix  JSON（影响×紧急度→优先级）
├─ sla_policy       JSON（可选）
└─ is_active

Ticket（业务工单视图，与 ProcessInstance 通过 business_key 关联）
├─ ticket_type  FK
├─ instance     OneToOne → ProcessInstance（或经 business_key 关联）
├─ form_data    JSONField（表单提交数据，与 variables 同步）
└─ 状态         FSM（新建→分派→处理中→已解决→已关闭，ITSM 生命周期）
```

> **设计取舍**：demo 主链路用 `ProcessInstance` 承载工单（模版→流动工单→任务），`Ticket` 作为可选 ITSM 增强层展示"状态机驱动工单生命周期"。二者通过 `business_key` 关联，体现"流程引擎与业务解耦"。

### 4. 权限与组织

```
User（继承 Django User）
Department（部门，含 parent 支持上级链）
Role（复用 Django Group 或自建，含 code）

权限模型：
- 全局权限：Group + Permission（发起工单/管理模版/管理能力/查看全部）
- 对象级权限：django-guardian（谁能查看/办理这张单、这个任务）
- 数据范围：待办=assignee 或 candidate 包含当前用户；已办=completed_by=当前用户
```

## 三、流程定义 JSON 模型（对标钉钉/飞书 + BPMN 语义）

```json
{
  "name": "服务器申请流程",
  "version": 1,
  "nodes": [
    {
      "key": "start",
      "type": "start",
      "name": "发起",
      "next": "approve_dept"
    },
    {
      "key": "approve_dept",
      "type": "approve",
      "name": "部门审批",
      "approvers": {"type": "manager_level", "level": 1},
      "mode": "countersign",
      "next": "condition_amount"
    },
    {
      "key": "condition_amount",
      "type": "condition",
      "name": "金额条件分支",
      "branches": [
        {"condition": "{amount} > 10000", "next": "approve_cfo"}
      ],
      "else_next": "service_create"
    },
    {
      "key": "approve_cfo",
      "type": "approve",
      "name": "CFO 审批",
      "approvers": {"type": "specified", "users": ["cfo"]},
      "mode": "single",
      "next": "service_create"
    },
    {
      "key": "service_create",
      "type": "service",
      "name": "自动开通服务器",
      "capability": "cmdb.create_host",
      "params": {"hostname": "{hostname}", "cpu": "{cpu}"},
      "execute_mode": "async",
      "next": "cc_admin"
    },
    {
      "key": "cc_admin",
      "type": "cc",
      "name": "抄送管理员",
      "cc_users": {"type": "role", "role": "it_admin"},
      "next": "end"
    },
    {
      "key": "end",
      "type": "end",
      "name": "结束"
    }
  ]
}
```

### 节点类型

| type | 说明 | 对应 BPMN/行业 |
|---|---|---|
| start / end | 开始/结束 | Start/End Event |
| **approve** | 审批节点（支持会签/或签/依次） | 用户任务 + 多实例 |
| **handle** | 办理节点（可绑定能力/表单填写） | 用户任务（办理类） |
| **service** | 自动节点（调用注册能力，同步/异步） | 服务任务 |
| **cc** | 抄送节点（不阻塞，生成只读通知任务） | 非阻塞用户任务 |
| **condition** | 条件分支（基于变量求值） | 排他网关 XOR |
| **parallel** | 并行分支（可选扩展） | 并行网关 AND |

### 审批人配置（动态审批人，国内特色）

```json
{"type": "specified", "users": ["u1"]}          // 指定人
{"type": "role", "role": "cfo"}                  // 角色
{"type": "manager_level", "level": 1}            // 发起人第 N 级主管
{"type": "department_manager"}                   // 指定部门主管
{"type": "initiator_choice", "candidates": ["u1","u2"]}  // 发起人自选
{"type": "field", "field": "approver"}           // 表单字段指定
```

### 会签/或签模式（节点级属性）

| mode | 语义 | 完成条件 |
|---|---|---|
| single | 单人审批 | 1 个任务完成 |
| countersign | 会签（全部通过） | completed == total 且全部通过 |
| or_sign | 或签（任一通过） | completed >= 1 且任一通过 |
| sequential | 依次审批 | 顺序生成子任务，逐个完成 |
| percent | 百分比通过（扩展） | completed >= total * percent% |

## 四、流程引擎执行器（核心）

### 引擎 API（对外动词，对标行业标准）

```
POST   /api/v1/processes/{key}/start       启动流程（前端提单/程序提单）
POST   /api/v1/tasks/{id}/claim            认领任务
POST   /api/v1/tasks/{id}/complete         完成任务（审批/办理）
POST   /api/v1/tasks/{id}/delegate         委派
POST   /api/v1/tasks/{id}/reject           驳回（到指定节点）
POST   /api/v1/instances/{id}/suspend      挂起
POST   /api/v1/instances/{id}/resume       恢复
POST   /api/v1/instances/{id}/terminate    终止
GET    /api/v1/tasks?scope=todo|done|cc|created  待办/已办/抄送/我发起
GET    /api/v1/instances/{id}/timeline     流程追踪（时间线）
```

### complete_task 执行流程（单个数据库事务内完成）

```
1. 事务开始 + select_for_update 锁任务（防并发重复办理）
2. 校验：任务状态为 pending/claimed、当前用户有办理权限、结果字段满足校验器
3. 写入 ApprovalRecord（审批记录/意见）
4. 若是多实例任务：更新会签计数，未满足完成条件 → 提交事务返回（等待其他子任务）
5. 满足完成条件 → 任务置 completed，节点结果写入 variables（流程变量）
6. 推演下一节点：
   - condition → 按顺序求值 branches 条件（基于 variables）→ 选中分支
   - approve/handle → 解析审批人 → 生成 NodeTask（含子任务）
   - service → 创建 TaskJob（同步执行 or 异步提交）→ 生成/等待
   - cc → 生成只读 cc 任务
   - end → 实例置 completed
7. 发布领域事件（EventLog）
8. 提交事务
```

### 幂等设计

- 所有写操作支持 `Idempotency-Key` 请求头（中间件，命中缓存返回原响应）
- 任务完成以"任务 ID + 状态校验 + 行锁"防重复
- Worker 幂等：以 DB 状态为准，队列只投递
- 程序提单：`business_key` 唯一约束，重复发起返回已存在实例（`get_or_create` 语义）

## 五、同步/异步任务与作业平台

### 同步任务（service 节点，execute_mode=sync）

```
complete 或引擎推演到 service 节点 →
  创建 TaskJob(status=queued)
  直接调用能力（本地执行器 或 作业平台 HTTP 同步 API）
  成功 → TaskJob=succeeded + 输出写入 variables → 推演下一节点
  失败 → TaskJob=failed + 节点任务标记失败/可重试 → 实例挂起等待人工处理
```

### 异步任务（execute_mode=async）

```
引擎推演到 service 节点 →
  创建 TaskJob(status=queued)
  提交到作业平台（返回 job_id）→ TaskJob=running
  节点任务（或"等待服务完成"的中间状态）→ 实例/任务进入"办理中/等待"
  前端轮询 GET /api/v1/task-jobs/{id} 或订阅 WebSocket/SSE
  作业平台将状态写入 Redis Streams（demo mock 平台）→
    队列监听 Worker 消费 →
      更新 TaskJob 状态（succeeded/failed）+ 输出写入 variables →
      引擎收到事件 → 推演下一节点
```

### 作业平台抽象（旧版"作业平台"的现代化）

```
JobPlatformClient（接口）
├─ submit(capability, input) → job_id       注册/提交任务
├─ get_status(job_id) → status              查询状态
└─ （可选）register(capability)             注册原子能力

实现：
├─ MockJobPlatform（demo 内置：本地线程/异步模拟执行，状态写 Redis Streams）
└─ HttpJobPlatformClient（真实 HTTP 客户端，通过 URL 配置）
```

### 能力注册中心

- 能力 = `Capability` 记录（code/输入输出 schema/执行模式）
- demo 内置若干原子能力：`cmdb.create_host`、`dns.add_record`、`mail.send`、`external.approve` 等（Python 本地实现 + mock 异步执行）
- 服务节点绑定能力 = 能力中心返回的可注册能力之一（与旧版"可绑定任务由后端返回"一致，但通过注册中心 + schema 化更规范）

## 六、自动办理（策略驱动）

### 设计

```
自动办理 = 节点策略配置 + 规则求值 + 系统代理执行 + 审计留痕

Node 策略字段：
{
  "auto_handle": true,
  "auto_policy": "auto_approve" | "random_proxy" | "condition_auto",
  "auto_condition": "{amount} <= 1000",      // 满足条件才自动
  "auto_result": "approve"
}
```

### 执行

1. 任务创建时（或到达办理节点时）检查节点 `auto_handle` 配置
2. 求值 `auto_condition`（基于 variables）；不满足 → 正常流转人工办理
3. 满足 → 系统代理执行：
   - `auto_approve`：直接 approve，审批人记录为 `system`，ApprovalRecord 注明 `"Auto-approved by policy"` + 策略详情
   - `random_proxy`：从候选办理人中随机选一人作为"被代理者"，仍走正常办理动作，审计记录 `"proxy by policy"`（保留旧版能力）
   - service 节点：直接创建 TaskJob 执行（本就自动化）
4. 全部写入审计日志，可追溯

> 相比旧版"随机抽人"：demo 强调**策略化 + 可审计**，随机代理只是策略之一。

## 七、动态表单（JSON Schema）

```
TicketType/ProcessDefinition.form_schema 示例：
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "hostname": {"type": "string", "title": "主机名", "minLength": 3},
    "cpu": {"type": "integer", "title": "CPU 核数", "minimum": 1, "default": 4},
    "amount": {"type": "number", "title": "金额（元）"},
    "approver": {"type": "string", "title": "审批人", "enum": ["a","b"]}
  },
  "required": ["hostname", "cpu"],
  "uiSchema": {
    "hostname": {"ui:widget": "input"},
    "cpu": {"ui:widget": "number"}
  }
}
```

- 前端：**form-create / form-create-designer**（Vue3 + Element Plus 生态）可视化配置并渲染表单
- 转换层：form-create 规则 ↔ 标准 JSON Schema（存储与后端校验用 JSON Schema）
- 后端：DRF 自定义 `JSONSchemaField`，提交时用 `jsonschema` 校验（Draft 2020-12）
- 条件表达式基于表单字段（`{amount} > 10000`），由引擎求值
- 表单 schema 版本化：随流程定义版本走

## 九、权限模型

```
角色（Group）：
- admin      管理员（全部权限 + 模版/能力管理）
- agent      代理/处理人（办理、认领、分派）
- user       普通用户（发起、查看自己的、确认关闭）

数据范围：
- 待办：assignee == user 或 user ∈ candidate_users
- 已办：completed_by == user
- 我发起的：started_by == user
- 抄送我的：node_type=cc 且 user ∈ cc_users
- 管理员：全部

对象级权限（django-guardian）：
- 查看权限：发起人 / 当前/历史任务处理人 / 抄送人 / 管理员
- 办理权限：任务的 assignee / 候选办理人 / 管理员
```

## 十一、Demo 演示剧本（面试用）

1. **登录**（三种角色：admin / agent / user）
2. **管理端**：创建"服务器申请"工单模版（表单 JSON Schema + 流程配置：部门审批→金额条件→CFO审批→自动开通→抄送）
3. **发起**：user 填表提交 → 生成流动工单 + 待办
4. **审批**：agent 在待办看到任务 → 认领 → 审批（会签/或签演示）
5. **条件分支**：金额 > 1 万走 CFO 审批，否则直通
6. **自动办理**：service 节点自动调用能力（同步/异步），异步演示 TaskJob 状态回传（mock 作业平台 + 队列监听）
7. **抄送**：管理员收到抄送
8. **流程追踪**：查看实例时间线（EventLog）
9. **程序提单**：通过 API 以 business_key 发起（幂等演示）
10. **权限**：非处理人看不到/不能办别人的任务

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M1 骨架** | Django 项目 + settings + Docker Compose(OrbStack) + 认证 | 后端可启动，JWT 登录 |

| **M6 前端** | Vue 3 + Element Plus + form-create + LogicFlow：模版配置/表单渲染/待办已办/流程追踪 | 浏览器完整演示 |
| **M7 演示脚本** | seed 数据 + 一键演示脚本 + README | 面试演示流畅 |

## 十三、已确认决策（2026-08-03 讨论）

| 决策项 | 结论 |
|---|---|
| 前端 | **完整 Vue 3 + Element Plus 前端**（form-create 表单 + LogicFlow 建模 + 待办已办/流程追踪） |
| 部署 | **Docker Compose + OrbStack**（postgres/redis/api/celery/worker/frontend），遵循项目 OrbStack 规范 |
| 作业平台 | **真实 HTTP 客户端**（接口抽象 JobPlatformClient + HTTP 实现，mock 平台作为备用实现） |
| ITSM 增强 | **基础版**：优先级 + 评论（内/外部）+ 站内通知；SLA 暂缓 |
| 工单建模 | **独立 Ticket 业务层**：Ticket 表经 business_key 关联 ProcessInstance，展示流程与业务解耦 |
| 演示数据 | 预置完整 seed（用户/角色/能力/演示模版）一键跑通 |
