🔄 2. 模型对比：Per-Pipeline vs Per-Environment

❌ 当前模型（Per-Pipeline）

  • 一个发布单跨所有环境（dev→test→staging→prod）
  • 11 个步骤：构建→部署→验证×4环境→审批→灰度→全量
  • 每个步骤手动点"执行"
  • 和真实 Spug 不一致

✅ 目标模型（Per-Environment）

  • 一个发布单 = 单个环境
  • CI + CD 两阶段，全自动串行
  • 点「发布」后自动跑，只看日志
  • 还原真实 Spug 架构

核心变化

维度旧（Per-Pipeline）新（Per-Environment）
发布单粒度跨所有环境单个环境
Pipeline 步骤11 步2 步（CI + CD）
用户操作每步手动执行点发布后自动跑
日志展示散落在各步骤双面板（CI + CD）
部署策略创建时选择保持，但默认滚动
环境选择Pipeline 隐含创建时明确选择

🗄️ 3. 数据模型改造

Release 模型 微调

当前 Release 已有 environment 和 env_config 字段，数据模型基本不变。主要变化：

字段当前改造后说明
statuspending/approved/running/...简化 pending/running/ci_success/cd_success/failed/rolled_backCI/CD 两阶段状态
current_stage11 种 stage 值简化 ci / cd / done只有两个阶段
deploy_strategyrolling/canary/blue_green保持面试加分项
deploy_modek8s/ec2保持

ReleaseTask 模型 大改

从 11 步简化为固定 2 步：

阶段含义执行方式Executor 参与
ciCI 构建executor op=build（模拟 Pod 构建）✅
cdCD 部署executor op=deploy（apply/set image）✅

自动串行：CI 完成后 backend 自动触发 CD，无需用户手动操作。

新增/调整的字段

模型字段类型说明
Releaseis_first_deployBooleanField首次部署标志：true→apply YAML，false→set image
Releaseselected_podsJSONFieldStatefulSet 可选 Pod 发布时的 Pod 列表
Releaseworkload_typeCharFielddeployment / statefulset（从 GitLab YAML 解析）

废弃/移除

  • ReleaseTask.STAGES 从 11 种简化为 ['ci', 'cd']
  • 前端 Pipeline 组件不再使用 Steps 组件，改为 CI/CD 双面板
  • backend/utils/k8s_client.py 可删除（能力已迁移到 executor）

创建发布单流程

POST /api/v1/releases/ { "application": 1, // 应用 ID "environment": 2, // 环境 ID（单个） "version": "1.2.1", "branch": "main", "commit_id": "abc1234", "deploy_strategy": "rolling" // 默认滚动 } → 后端自动： 1. 创建 Release (status=pending) 2. 创建 ReleaseTask(ci) + ReleaseTask(cd) 3. 触发 CI：提交 executor op=build 4. CI 完成 → 自动触发 CD：提交 executor op=deploy 5. 返回 { release_id, ci_status, cd_status }

⚙️ 5. Executor 改造

新增 op=build（模拟 Pod 构建）

executor 收到 op=build 请求 │ ├─ [模拟] 创建构建 Pod: builder-{language}:latest │ namespace=build, 临时 Pod │ ├─ [模拟] git clone → checkout {branch} │ commit: {commit_id} │ ├─ [模拟] 编译/打包 │ Python: pip install → python -m build │ Go: go build -o /app │ Node: npm install → npm run build │ ├─ [模拟] COPY 产物 → 应用基础镜像 │ 构建镜像: {app_code}:{version} │ ├─ [模拟] docker push → ECR │ registry: 123456789.dkr.ecr.us-east-1.amazonaws.com │ └─ [模拟] 清理构建 Pod

变更 op=deploy

场景判断依据执行动作
首次部署is_first_deploy=truekubectl apply -f deployment.yaml（从 GitLab 拉取）
后续部署is_first_deploy=falsekubectl set image deployment/{name} {name}={image}
StatefulSetworkload_type=statefulset根据 selected_pods 选择性更新

新增 op=pods

查询指定应用在目标环境的 Pod 列表，返回给前端供用户选择发布目标。区分 Deployment（全部 Pod）和 StatefulSet（可选 Pod）。

🎤 10. 面试叙述建议

核心故事线（Per-Environment 模型）

💡 开场叙述

"我们的发布系统是按 应用+环境 粒度管理的。每次发布对应一个目标环境，流程分为 CI 构建 和 CD 部署 两个阶段，全自动串行。用户点「发布」后，系统自动拉起构建 Pod 编译打包，构建完成后自动触发集群部署。整个过程通过两个实时日志面板展示——上方 CI 日志，下方 CD 日志。"

🔧 CI 阶段叙述

"CI 阶段由 Lambda 拉起一个临时 Pod，使用环境基础镜像（含编译器/运行时）作为构建环境。Pod 内执行 git clone → 编译 → 打包，然后把产物 COPY 进应用基础镜像构建最终镜像，推送到 ECR。构建完成后 Pod 自动销毁。这样每个环境都有独立的构建产物。"

🚀 CD 阶段叙述

"CD 阶段分两种情况：首次部署时，系统从 GitLab 拉取预先申请好的 YAML 配置（由工单系统调用运维原子任务生成），执行 kubectl apply 创建全新 Deployment。后续发布时，Deployment 已经在集群里了，只需要 kubectl set image 修改镜像字段，K8s 自动执行滚动更新。对于 StatefulSet，还支持选择特定 Pod 进行发布。"

🏗️ 两层架构叙述

"由于安全要求，后端不能直接操作 AWS 资源。所有集群操作通过 API Gateway → Lambda 这个安全代理层执行。后端负责用户鉴权和权限校验，Lambda 只需要验证请求确实来自后端（通过公私钥签名）。这确保了即使后端被攻破，攻击者也无法直接操作集群。"

🎯 部署策略叙述（诚实 + 扩展）

"我们线上系统只做了滚动更新，因为是内部系统，发布频率不高，滚动更新完全够用。灰度和蓝绿我们调研过但当时评估 ROI 不高——灰度需要 Service Mesh 或 Ingress 做流量拆分，蓝绿需要双倍资源。不过我在 demo 系统里把这几种策略都实现了，主要是想展示我对 K8s 部署策略的理解。"

🔑 面试加分点总结

1. Per-Environment 模型：理解发布粒度的设计取舍
2. CI/CD 两阶段：知道构建和部署的职责边界
3. 两层安全架构：公私钥签名 + 请求内容绑定
4. 首次 vs 后续部署：kubectl apply vs set image 的区别
5. Deployment vs StatefulSet：有状态服务的发布差异
6. 双镜像策略：编译镜像 vs 运行镜像的分离
7. 工程判断力：知道什么场景用什么方案，不做过度设计
