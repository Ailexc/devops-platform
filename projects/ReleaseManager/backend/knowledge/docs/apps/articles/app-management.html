📦 应用管理知识文档

1. 应用管理核心概念

什么是应用（Application）？

在发布系统中，Application 是服务部署和运维管理的基本单元。一个「应用」对应一个可独立部署、独立运行的服务实例，它关联了代码仓库、构建配置、部署配置、环境配置等所有与发布运维相关的元信息。

应用是发布系统数据模型的核心枢纽，串联起「代码 → 构建 → 制品 → 部署 → 运维」整个 CI/CD 流程。

应用管理 vs 发布管理：两个模块的职责划分
对比维度应用管理发布管理
关注点应用的「配置」：谁来管、怎么部署、部署到哪里应用的「变更」：改了什么、何时上线、如何上线
核心对象应用、环境、部署配置发布单、流水线、发布策略
操作频率低频（新建/修改应用配置时）高频（每次功能上线都需要）
典型角色应用负责人、架构师开发工程师、SRE、审批人
权限特征编辑权限（配置变更）操作权限（执行发布）

💡 设计要点

将「配置管理」和「变更操作」分离，是发布系统设计的核心原则之一。应用管理关注「是什么」，发布管理关注「怎么变」，两者职责清晰、边界明确。

应用的生命周期

创建 → 配置 → 发布 → 运维 → 下线

  • 创建：注册应用基本信息（名称、编码、开发语言、Git 仓库、负责人等）。
  • 配置：为各环境配置部署参数（集群、命名空间、副本数、部署策略等）。
  • 发布：通过发布单将应用的新版本部署到目标环境。
  • 运维：日常的监控、扩缩容、重启、回滚等运维操作。
  • 下线：应用不再需要时，从环境中移除并归档。

每个阶段都有对应的操作入口和权限控制，确保应用从创建到下线的全流程可管理、可追溯。

2. 应用与环境的绑定关系

一个应用对应多个环境

在发布系统中，一个应用通常需要部署到多个环境：

dev test1 test2 test3 test4 pre prod

每个环境独立部署运行：开发环境（dev）用于开发自测，测试环境（test1-4）用于 QA 测试，预发环境（pre）用于上线前最终验证，生产环境（prod）面向真实用户。

每个环境的配置独立
配置项说明
集群不同环境可能部署在不同的 K8s 集群或 EC2 集群中
命名空间K8s 环境下，每个环境对应独立的 Namespace，实现资源隔离
副本数测试环境通常 1-2 个副本，生产环境需要更多副本保障高可用
部署策略测试环境可用滚动更新快速迭代，生产环境可能需要灰度发布逐步放量
资源配置测试环境资源配额较低，生产环境资源充足（CPU / 内存限制）
环境配置的继承与覆盖机制

为减少重复配置，系统支持环境配置的继承关系。例如 test1-test4 可以继承 test 基础配置，仅覆盖差异部分（如数据库连接串、域名等）。生产环境配置通常独立维护，不与测试环境共享任何敏感信息。

为什么需要环境隔离？
  • 安全隔离：测试环境的 Bug 或异常不会影响生产环境真实用户。
  • 资源隔离：测试负载不会抢占生产环境的 CPU、内存、网络等资源。
  • 数据隔离：测试环境使用测试数据库，不会污染生产数据。
  • 权限隔离：不同环境有不同的访问和操作权限，生产环境操作需要更严格的审批。
  • 并行验证：多个测试环境（test1-4）可以同时验证不同版本或不同功能特性。

3. 应用元信息设计

基础属性
字段说明
name 名称应用的可读名称，如「用户中心」
code 编码应用的唯一标识符，如「user-center」
language 开发语言Python / Go / Node.js / Java 等
repo_url / repo_branchGit 仓库地址与默认分支，用于关联 CI 构建
owner_ids 负责人应用的第一责任人列表，负责应用配置和发布审批
priority / sla / security_level优先级（p0-p3）、可用性 SLA（99.9% 等）、安全等级
is_core / tech_stack是否核心应用、技术栈列表
构建配置（双镜像设计）
配置项说明
builder_image 环境基础镜像包含编译工具链的镜像（JDK+Maven、Node.js+npm），用于 CI 阶段的代码编译和构建
base_image 应用基础镜像预装应用运行所需环境的镜像（JRE、Python 运行时），不含编译工具，作为最终运行镜像的基础层

这与「双镜像设计」理念一致：构建镜像负责编译，应用基础镜像负责运行，两者解耦使最终镜像体积更小、安全性更高。系统通过 ImageRegistry（镜像注册表）按开发语言管理默认的双镜像配置。

部署配置（AppEnvConfig，按环境独立）
配置项说明
environment 环境dev / test / pre / prod 等，一个应用可配置多套
cluster / namespace目标 K8s 集群 / EC2 集群，以及 K8s Namespace
deploy_strategy 部署策略滚动更新 / 蓝绿部署 / 灰度发布（灰度有 canary_percent 比例）
replicas 副本数Pod 或实例数量
image_repo / container_port镜像仓库地址、容器端口（默认 8080）
health_check_path 健康检查健康检查路径（默认 /health）与超时时间
cpu_limit / memory_limitCPU / 内存资源配额限制
auto_rollback 自动回滚发布失败时是否自动回滚

每个环境一份独立配置，通过 unique_together (application, environment) 保证应用在单环境只有一份配置。

权限关联
  • 所属业务线：应用归属的业务线决定了权限继承的基础范围，同一业务线的成员默认拥有该业务线下应用的查看权限。
  • 负责人：应用的第一责任人，拥有该应用的编辑权限，同时也是发布审批的默认审批人。

4. 应用管理功能全景（本 Demo）

应用列表页
  • 以卡片/表格形式展示应用列表，支持按业务线、应用编码筛选。
  • 展示应用的核心信息：名称、编码、语言、负责人、状态、所属业务线。
  • 入口：从列表点击进入应用详情，或直接「新建发布」进入发布流程。
应用详情页
  • 基本信息：应用名称、编码、开发语言、双镜像（环境基础镜像 / 应用基础镜像）、仓库地址、描述、创建时间等。
  • 环境配置 Tab：按环境（dev/test/pre/prod）分组展示部署配置，包括集群、命名空间、部署策略、副本数、镜像仓库、容器端口、健康检查、资源配额、自动回滚等。
  • 编辑 Drawer：修改描述、状态、负责人、双镜像配置；配置变更若命中审批策略则走审批流（requires_approval 时显示审批流预览）。
与发布、运维的联动
联动能力说明
新建发布从应用详情直接进入「新建发布」，自动带入应用与环境配置
部署策略环境配置决定该环境默认的部署策略（滚动/蓝绿/灰度），发布单可覆盖
运维操作扩缩容（scale）、重启（restart）、停机/启动（stop/start）、流量摘挂（traffic）
发布历史应用维度查看该应用的发布记录、CI/CD 日志、自动验证结果

💡 Demo 中的约定

蓝绿部署新建 {app}-blue 环境（Pod 标签 track=blue），旧环境 track=stable 保留回滚；灰度新建 {app}-canary 独立 Service 入口。详见《部署策略详解》。

5. 真实 Spug 的演进

V1 版本：以发布记录为中心
  • 应用信息散落在各发布记录中，没有统一的应用管理入口。
  • 查看应用配置时需要先找到该应用的发布记录，再从发布记录中查看。
  • 修改应用配置需要重新创建发布单，操作路径长、效率低。
  • 应用的「配置」和「发布」强耦合，难以独立管理。
V2 版本：以应用为中心
  • 新增独立的「应用管理」模块，以应用为中心组织信息。
  • 应用详情页统一展示所有环境配置和发布历史，一目了然。
  • 操作面板将发布、回滚、重启等操作集中在应用详情页，一键触达。
  • 配置变更与发布操作解耦，修改配置不需要创建发布单。
权限分离
模块权限特征说明
发布管理只读 + 操作查看发布历史，执行发布、回滚、重启等操作
应用管理编辑配置修改应用的基本信息、环境部署配置、构建配置等

💡 设计要点

将「配置管理」和「变更操作」分离，是发布系统设计的核心原则之一。应用管理关注「是什么」，发布管理关注「怎么变」，两者职责清晰、边界明确。

6. 面试重点

Q1 应用管理模块的核心职责是什么？

应用管理模块负责应用的全生命周期管理，包括：注册应用基本信息（名称、编码、语言、仓库）、管理应用的部署配置（集群、命名空间、副本数、部署策略）、维护应用与环境的绑定关系、控制应用的权限归属（业务线 + 负责人）。它是发布系统的「配置中心」，为发布管理提供基础的元数据支撑。

Q2 一个应用如何管理多个环境的配置？环境之间如何隔离？

一个应用通过「环境配置」表关联多个环境（dev/test1-4/pre/prod），每个环境有独立的集群、命名空间、副本数、部署策略等配置。环境之间通过以下方式隔离：① 部署在不同的 K8s 集群或 Namespace 中实现资源隔离；② 使用不同的数据库实例实现数据隔离；③ 通过 RBAC 权限控制实现操作隔离；④ 支持配置继承机制，子环境继承父环境配置并覆盖差异项，减少重复配置。

Q3 应用管理和发布管理的权限如何划分？

应用管理授予「编辑配置」权限，允许修改应用的基本信息、环境部署配置、构建配置等；发布管理授予「只读 + 操作」权限，允许查看发布历史和配置，执行发布、回滚、重启等操作。这种设计将「配置管理」和「变更操作」分离，各角色职责清晰。应用负责人通常拥有应用管理的编辑权限，而开发工程师和 SRE 拥有发布管理的操作权限。

Q4 应用的生命周期管理包含哪些阶段？

应用的生命周期分为五个阶段：创建（注册应用基本信息）→ 配置（为各环境配置部署参数）→ 发布（通过发布单将新版本部署到目标环境）→ 运维（日常监控、扩缩容、重启、回滚等）→ 下线（从环境中移除并归档）。每个阶段都有对应的操作入口和权限控制，确保应用从创建到下线的全流程可管理、可追溯。

Q5 新建一个应用时，需要配置哪些信息？

新建应用需要配置三类信息：① 基础属性（名称、编码、描述、开发语言、Git 仓库地址、业务线、负责人）；② 构建配置（环境基础镜像、应用基础镜像）；③ 部署配置（部署模式 EC2/K8s、部署策略滚动/蓝绿/灰度、目标集群、命名空间、副本数、资源配额等）。此外还需要为各环境（dev/test/pre/prod）分别配置差异化参数，如环境变量、配置文件、健康检查策略等。
