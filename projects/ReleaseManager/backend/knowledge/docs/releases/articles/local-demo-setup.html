1. 架构总览

💡 核心思路：本系统将 AWS Spug 的两层安全架构（backend + Lambda）映射为本地三服务架构（backend + executor + K8s），通过模拟模式在无真实集群时也能完整跑通发布流程。

# demo-apps/config/python-app/dev/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: python-app
  namespace: release-demo
  labels:
    app: python-app
    language: python
spec:
  replicas: 2
  selector:
    matchLabels:
      app: python-app
  template:
    metadata:
      labels:
        app: python-app
    spec:
      containers:
      - name: python-app
        image: python-app:latest
        imagePullPolicy: IfNotPresent   # ← 本地镜像，不从仓库拉取
        ports:
        - containerPort: 8080
        env:
        - name: APP_VERSION
          value: "1.0.0"
        - name: ENV
          value: "dev"
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
---

kind: Service
metadata:
  name: python-app
  namespace: release-demo
spec:

    app: python-app

    targetPort: 8080
  type: ClusterIP

环境审批模式审批人来源步骤说明
dev无需审批—0直接发布，跳过审批
test1单人审批应用负责人1应用 owner 审批即可
pre多级审批app_owner → group_leader2先应用负责人，再组负责人
prod多级审批app_owner → bl_leader2先应用负责人，再业务线负责人

审批人动态解析

系统不绑定固定审批人，而是根据策略中的 `approver_source` 动态查找：

_resolve_approver(release, source)
  ├── app_owner    → release.application.owner  （如：李四）
  ├── group_leader → release.application.owner_group.leader
  └── bl_leader    → release.application.business_line.leader

发布单状态流转

创建(draft) → 发起审批(submitting) → 审批通过(passed) → 点击发布 → CI→CD → 完成(completed)
                │                        ↓ 驳回
                └── rejected → 可重新发起

9. 常见问题与排障

Q: executor 显示 simulate=true 怎么办？

executor 的 k8s_client.py 通过 `config.load_kubeconfig()` 连接 K8s。如果失败会进入模拟模式。排查步骤：

# 1. 检查 kubeconfig 是否指向 OrbStack
kubectl config current-context
# 应输出: orbstack

# 2. 检查 executor 的 kubernetes 库能否加载 kubeconfig
cd executor && source ../.venv/bin/activate
python -c "from kubernetes import config; config.load_kubeconfig(); print('OK')"

# 3. 如果失败，检查 kubernetes 库版本
pip show kubernetes

Q: executor 报错 "命名空间不存在" 怎么办？

首次部署时，executor 的 deployment.yaml 中 `namespace` 字段需要对应的命名空间存在。

# 方法一：手动创建
kubectl create namespace release-demo

# 方法二：修改 deployment.yaml 中的 namespace 字段
# 把 namespace: release-demo 改为 namespace: default

Q: 首次部署和后续部署有什么区别？

首次部署后续部署
判断依据`is_first_deploy=true``is_first_deploy=false`
判断逻辑DeployHistory 中无成功记录已有成功部署记录
kubectl 命令`kubectl apply -f deployment.yaml``kubectl set image deployment/{name} ...`
日志表现「创建 Deployment」「创建 Service」「检测到现有 Deployment」「滚动更新中...」

Q: CI 阶段是真实构建吗？

是的。CI 阶段（op=build）由 executor 执行真实的 `docker build`：

  • 读取 `demo-apps/{app}/Dockerfile`，执行 `docker build -t {app}:{version} .`
  • 利用 Docker 层缓存加速（基础镜像和依赖安装层只下载一次）
  • 构建完成后自动打 `latest` 标签

CD 阶段（op=deploy）同样执行真实 `kubectl apply` / `kubectl set image` + `kubectl rollout status`。

Q: deployment.yaml 中的 image 应该写什么？

本地开发环境下，镜像直接使用 `docker build` 产出的本地镜像名：

# 本地构建的镜像（docker build -t python-app:1.0.0 .）
image: python-app:latest
imagePullPolicy: IfNotPresent  # 关键：不从远程仓库拉取，使用本地镜像

CI 构建流程会自动产出 `{app}:{version}` 标签的镜像，同时打 `latest` 标签供 deployment.yaml 引用。

Q: 为什么 dev 环境不需要审批而 test 需要？

这是由审批策略表 `ReleaseApprovalStrategy` 控制的。dev 环境配置为 `mode=none`（无需审批），test1 配置为 `mode=single + app_owner`（应用负责人审批）。创建发布单时系统自动根据环境匹配策略判断 `need_approval`。

10. Dockerfile 编写指南

💡 设计原则：CI 系统不修改用户的 Dockerfile。应用代码仓库自带 Dockerfile，executor 直接执行 docker build。builder_image / base_image 字段仅作为元数据记录，供展示和合规校验使用。

Python 应用 Dockerfile

# demo-apps/python-app/Dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY main.py .
EXPOSE 8080
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]

Go 应用 Dockerfile（多阶段构建）

# demo-apps/go-app/Dockerfile
# 阶段 1：编译
FROM golang:1.23-alpine AS builder
WORKDIR /app
COPY go.mod main.go ./
RUN CGO_ENABLED=0 GOOS=linux go build -o /app/server .

# 阶段 2：运行（极简镜像）
FROM alpine:3.20
WORKDIR /app
COPY --from=builder /app/server .
EXPOSE 8080
CMD ["./server"]

Node.js 应用 Dockerfile

# demo-apps/node-app/Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json .
RUN npm install --production
COPY server.js .
EXPOSE 8080
CMD ["node", "server.js"]

Dockerfile 关键注意事项

要点说明
EXPOSE 端口必须与 deployment.yaml 中的 containerPort 一致（本系统统一为 8080）
健康检查端点建议提供 /health 端点，K8s readinessProbe 会调用它
镜像拉取策略本地环境使用 imagePullPolicy: IfNotPresent，避免从远程仓库拉取
Docker 缓存优化先 COPY 依赖文件（如 requirements.txt），再 COPY 源码，最大化利用层缓存
多阶段构建Go 等编译型语言推荐多阶段构建，最终镜像不含编译工具链，体积更小

11. deployment.yaml 编写指南

完整模板（Deployment + Service）

# 文件路径: demo-apps/config/{app}/dev/deployment.yaml
# 首次部署: kubectl apply -f deployment.yaml（同时创建 Deployment + Service）
# 后续部署: kubectl set image deployment/{app} {app}={app}:{version}

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {app-name}
  namespace: release-demo
  labels:
    app: {app-name}
spec:
  replicas: 2
  selector:
    matchLabels:
      app: {app-name}
  template:
    metadata:
      labels:
        app: {app-name}
    spec:
      containers:
      - name: {app-name}
        image: {app-name}:latest          # CI 构建产出的本地镜像
        imagePullPolicy: IfNotPresent     # 本地环境必须设置
        ports:
        - containerPort: 8080
        env:
        - name: APP_VERSION
          value: "1.0.0"
        - name: ENV
          value: "dev"
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        readinessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
        livenessProbe:
          httpGet:
            path: /health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: {app-name}
  namespace: release-demo
spec:
  selector:
    app: {app-name}
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP

deployment.yaml 关键字段说明

字段说明必须
metadata.namespace目标命名空间，需预先存在（如 release-demo、dev、test1 等）✅
spec.replicasPod 副本数，根据环境调整（dev=2, prod=3+）✅
imageCI 构建产出的镜像名，格式为 {app}:{version}，同时有 {app}:latest 标签✅
imagePullPolicy本地环境设为 IfNotPresent，避免拉取远程镜像✅ 本地
readinessProbe就绪探针，K8s 据此判断 Pod 是否可接收流量推荐
livenessProbe存活探针，失败时 K8s 会重启 Pod推荐
Service (同文件)ClusterIP 类型，暴露 80→8080 端口映射，供其他 Pod 或 port-forward 访问✅
⚠️ 注意事项：
  • 不要使用 serviceAccountName，除非已创建对应的 ServiceAccount
  • 每个环境（dev/test/prod）应有独立的 deployment.yaml，副本数和资源限制可以不同
  • kubectl apply -f deployment.yaml 会同时创建 Deployment 和 Service
  • 如果部署失败，检查 kubectl describe pod -n {namespace} 查看 Pod 事件
