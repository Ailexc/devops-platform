🔍 本地环境配置 — 问题总结与排障报告

1. 问题全景：从模拟模式到真实部署

本地环境配置经历了从模拟模式（只输出日志，不操作集群）到真实模式（kubectl apply/set image 真实执行）的演进。核心路径如下：

初始状态 executor → simulate: true → 只输出日志，不操作 K8s │ ├─ 问题1: kubernetes v35 API 变更 → kubeconfig 加载失败 ├─ 问题2: YAML 引用 serviceAccountName → Pod 创建被拒 ├─ 问题3: 镜像指向 ECR → 拉取不到 ├─ 问题4: 命名空间 release-demo 不存在 → apply 失败 └─ 问题5: 本地无镜像 → Pod 无法启动 修复后 executor → simulate: false → kubectl apply + set image 真实执行 │ └─ Pod 真实运行，服务 200 OK

2. 问题 1：Kubernetes Python 库 API 变更

问题 kubernetes v35 移除了 load_kubeconfig()

现象：executor 启动时 config.load_kubeconfig() 抛出 AttributeError: module 'kubernetes.config' has no attribute 'load_kubeconfig'

原因：安装了 kubernetes v35.0.0（最新版），该版本将 load_kubeconfig() 重命名为 load_kube_config()（下划线分隔）。

影响：executor 无法连接 K8s 集群，始终进入模拟模式。

修复 兼容新旧版本 API
# executor/app/k8s.py — _init_client()
if hasattr(config, 'load_kube_config'):
    config.load_kube_config()   # v35+ 新 API
else:
    config.load_kubeconfig()    # v34- 旧 API

验证结果："simulate": false → "message": "真实模式（已连接 K8s 集群）"

💡 经验教训：Python 生态库的大版本升级经常会改 API 命名。对于关键依赖（如 kubernetes 库），应该在 requirements.txt 中锁定版本范围，如 kubernetes>=28,<35。

3. 问题 2：YAML 引用不存在的 ServiceAccount

问题 Pod 创建被拒：serviceaccount "python-app" not found

现象：kubectl apply 成功，Deployment 和 Service 创建成功，但 Pod 一直 Pending，kubectl describe rs 显示 FailedCreate。

根因：YAML 中的 spec.serviceAccountName: python-app 引用了一个不存在的 ServiceAccount。

原始 YAML 片段：

spec:
  template:
    spec:
      serviceAccountName: python-app  # ← 这个 SA 不存在！
      containers:
      - name: python-app
修复 移除 serviceAccountName

在真实 Spug 项目中，SA/Role 绑定由工单系统自动生成。但 demo 系统没有这个流程，所以直接移除该字段。K8s 会自动使用 default ServiceAccount。

for f in $(find demo-apps/config -name "deployment.yaml"); do
  sed -i '' '/serviceAccountName/d' "$f"
done
💡 与真实项目的区别：在真实 Spug 中，工单系统调用运维原子任务生成 YAML 时，会同时创建 ServiceAccount、Role 和 RoleBinding。这是 demo 与真实系统的一个结构性差异。

4. 问题 3：镜像地址指向不存在的 ECR

问题 镜像 123456789.dkr.ecr... 拉不到

现象：executor 的 deployment.yaml 中镜像地址为 123456789.dkr.ecr.us-east-1.amazonaws.com/go-app:latest，但本地没有这个 ECR 仓库。

根因：这是 mock 的 ECR 地址，需要替换为本地可用的镜像来源。

修复 本地镜像 + dev.sh 自动构建

采用 方案 A+B（本地镜像 + 启动时自动构建）：

  1. 所有 deployment.yaml 中的镜像名改为本地名：go-app:latest、node-app:latest、python-app:latest
  2. 添加 imagePullPolicy: IfNotPresent（使用本地镜像，不拉远程）
  3. dev.sh 启动时自动执行 docker build 构建三个 demo 应用镜像
  4. executor 的 build 阶段输出本地镜像名（而非 ECR 地址）

5. 问题 4：K8s 命名空间缺失

问题 deployment.yaml 引用 release-demo 命名空间不存在

现象：executor 日志显示 apply 成功，但 kubectl get pods 为空。

根因：YAML 中 namespace: release-demo，但 OrbStack 集群只有 default/kube-system/kube-public/kube-node-lease 四个系统命名空间。

修复 创建所有需要的命名空间
kubectl create namespace dev
kubectl create namespace test1
kubectl create namespace pre
kubectl create namespace prod
kubectl create namespace release-demo

6. 问题 5：镜像拉取失败与本地构建策略

问题 go-app 镜像构建失败（网络超时）

现象：node-app 和 python-app 构建成功，但 go-app 因 Docker 拉取基础镜像超时而失败。

日志：DeadlineExceeded: failed to fetch anonymous token: dial tcp ... i/o timeout

原因：OrbStack 的 Docker 环境拉取 Docker Hub 镜像时网络不稳定（可能需要代理或镜像源）。

修复策略 dev.sh 中容错 + 后续可重试
# dev.sh 中的构建逻辑已包含容错
if docker build -t "$APP_NAME:latest" . 2>/dev/null; then
    ok "$APP_NAME:latest 构建成功"
else
    warn "$APP_NAME:latest 构建失败（不影响模拟模式）"
    BUILD_OK=false
fi

当前状态：python-app ✅、node-app ✅、go-app ⚠️（后续可手动重试 docker build -t go-app:latest demo-apps/go-app/）。

10. CI 真实构建改造记录

改造背景

最初 CI 阶段（op=build）只是输出模拟日志（固定时间间隔的 clone → compile → push），镜像由 dev.sh 启动时提前构建。这导致：

  • CI 和 CD 之间的因果关系断裂——CI 说"构建成功"但实际什么都没 build
  • dev.sh 承担了不应有的构建职责（启动脚本应该只负责启动服务）
  • CI 日志是固定模板文本，不是真实的构建输出

改造方案

采用方案 A：executor 真实执行 docker build：

  • CI 阶段在宿主机执行 docker build，产出镜像到本地 Docker daemon
  • OrbStack 的 K8s 与宿主机 Docker 共享同一个 daemon，Pod 可直接拉取本地镜像
  • CD 阶段通过 imagePullPolicy: IfNotPresent 使用 CI 产出的镜像

改造内容

文件改动
executor/app/runner.py_do_build() 从模拟日志改为 subprocess.run(["docker", "build", ...])
dev.sh移除启动时的 docker build 代码

CI 构建流程（真实）

# executor 收到 op=build 后的真实执行流程：
  1. 模拟 builder pod 准备 + git clone 日志
  2. subprocess.run(["docker", "build", "-t", "python-app:3.0.0", "demo-apps/python-app/"])
  3. 读取 docker build 输出 → 写入 TaskLog
  4. docker image inspect → 获取镜像大小
  5. 返回镜像名 → CD 阶段使用该镜像

# CI 产出的镜像直接用于 CD：
  docker build -t python-app:3.0.0 → 本地 Docker daemon
  kubectl set image deployment/python-app python-app=python-app:3.0.0
  Pod 从本地 daemon 拉取（imagePullPolicy: IfNotPresent）
