1. 真实架构：内部 Spug 发布系统

📌 概述

这是基于开源 Spug 进行深度二次开发的企业级 CI/CD 发布系统，运行在 AWS 云上。由于安全要求，Spug 不能直接操作 AWS 资源，因此设计了独特的「两层安全架构」——内网 Spug-backend + AWS Spug-lambda（API Gateway + Lambda）安全代理层。

项目背景

内部 Spug 是一个自建的 CI/CD 发布系统，运行在 AWS 云上。由于安全要求，Spug 不能直接操作 AWS 资源，因此设计为 「两层架构」：

🏢 Spug-backend（内网）

开发者操作界面，负责触发构建、管理发布流程。不能直接操作 AWS API。

☁️ Spug-lambda（AWS）

由 API Gateway + AWS Lambda 构成，作为安全代理层，执行所有实际的 AWS 操作。

CI 构建过程 — 双镜像设计

💡 关键设计

Spug 在项目配置中绑定两个镜像——环境基础镜像（用于编译）和应用基础镜像（用于组装产物）。镜像名称按规则自动生成，开发者只需关心「选择什么应用基础镜像去拷贝产物」。

架构设计亮点

🔒 安全隔离设计

Spug-backend 在内网，不能直接操作 AWS。通过 API Gateway + Lambda 作安全代理层，所有 AWS 操作由 Lambda 执行，天然符合最小权限原则。

🎯 双镜像设计

环境基础镜像负责编译，应用基础镜像负责运行环境。开发者只需绑定应用基础镜像，Spug 自动完成组装、命名、推送，降低使用成本。

🔄 双路径统一平台

同一套平台同时支持 EC2（产物部署）和 EKS（镜像部署）两条路径，根据项目类型自动分流，适合混合部署场景。

📦 镜像自动命名

最终镜像名由 Spug 按规则生成（项目名:构建ID），开发者无需关心命名规则，降低认知负担。

2.2 完整发布链路

  1. 用户在前端创建发布单（选择应用、环境、版本）
  2. 后端创建 Release + ReleaseTask（CI/CD 两个阶段任务）
  3. 后端提交 CI 任务到 executor（op=build，传递 Dockerfile 路径和构建参数）
  4. executor 执行真实 docker build，实时 SSE 日志回传到后端
  5. CI 成功后自动触发 CD（op=deploy，传递镜像名和部署目标）
  6. executor 执行 kubectl apply / set image + kubectl rollout status 等待就绪
  7. CD 成功后更新 Release 状态为 completed，前端实时展示最终结果

2.3 CI 构建流程

  • 读取 demo-apps/{app}/Dockerfile（用户自带的构建文件）
  • 真实执行 docker build -t {app}:{version} .（利用层缓存加速重复构建）
  • 自动打 latest 标签（docker tag {app}:{version} {app}:latest）
  • 构建日志逐行回传到前端（SSE → TaskLog → WebSocket 推送）

2.4 CD 部署流程

  • 首次部署：kubectl apply -f deployment.yaml（创建 Deployment + Service）
  • 后续部署：kubectl set image deployment/{app} {app}={image}:{version} → kubectl rollout status
  • 自动回退：如果 set image 失败（Deployment 不存在），自动回退到 apply
  • Pod 状态追踪：通过 kubectl rollout status 实时监听滚动更新进度

2.5 审批系统

  • 基于 ReleaseApprovalStrategy 的动态审批人解析
  • 支持无审批 / 单人审批 / 多级审批三种模式
  • 审批通过后自动触发发布执行（CI 任务提交到 executor）

4. 关键设计差异

🔒 安全架构差异
  • Spug：两层隔离（内网 + AWS Lambda），Spug 不能直接操作云资源
  • Demo：EdDSA 签名认证，backend ↔ executor 单向信任
🎯 镜像策略差异
  • Spug：双镜像设计（环境镜像编译 + 应用基础镜像组装），镜像名自动生成
  • Demo：用户自带 Dockerfile，CI 直接 docker build，builder_image/base_image 仅作元数据
☁️ 执行环境差异
  • Spug：Lambda 无服务器 + EKS Pod，按需弹性扩缩
  • Demo：本地 FastAPI 进程 + OrbStack K8s，固定单机部署
🚀 部署路径差异
  • Spug：EC2（SSM 远程命令）+ EKS（kubectl），双路径统一平台
  • Demo：仅 K8s 路径（kubectl apply/set image），单路径简化

5. Demo 系统重点说明

5.1 关键模型

Model说明关键字段
Release发布单（状态机 draft→running→completed/failed）app, env_type, version, status, ci_task, cd_task
ReleaseTask阶段任务（ci/cd，各有独立状态）release, op(ci/cd), status, executor_job_id
TaskLog执行日志（level=info/step/ok/warn/error）task, level, message, seq, ts
ReleaseApprovalStrategy审批策略（env_type → mode → approver_source）env_type, mode, approver_source
Application + AppEnvConfig应用和环境配置name, language, env, image, namespace
ImageRegistry镜像注册表（语言→builder/base image）language, builder_image, base_image

5.2 状态流转

Release 状态机:

  ┌───────┐     触发执行      ┌─────────┐     CI+CD 全部成功    ┌───────────┐
  │ draft │ ───────────────▶  │ running │ ──────────────────▶  │ completed │
  └───────┘                   └────┬────┘                      └───────────┘
                                   │
                                   │ CI 或 CD 失败
                                   ▼
                            ┌─────────┐
                            │ failed  │
                            └─────────┘

failed 状态需区分:
  - CI 失败: ReleaseTask(ci).status == 'failed'
  - CD 失败: ReleaseTask(cd).status == 'failed'

5.3 日志系统

  • executor 内存存储，SSE 流式推送（/api/executor/jobs/{id}/logs）
  • 后端 _watch_execution 线程消费 SSE，写入 TaskLog 数据库
  • 前端 CI/CD 双面板实时展示（useReleaseLogs hook 定时轮询）

5.4 已知限制

  • executor 内存存储，重启丢失
  • 单 executor 实例，不支持并发构建
  • 审批为模拟模式（Demo 自动通过）
  • 无真实 Git 集成（源码在本地 demo-apps/）
