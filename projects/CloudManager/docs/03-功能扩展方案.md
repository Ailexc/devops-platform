# 03 · 功能扩展方案

> 核心原则：**守住"真实内部系统"人设，用业务复杂度取胜，不靠技术炫技**。
> 扩展必须能自圆其说 —— "企业里真的会有人这么干"。

## 一、总体评估结论

原有系统的架构骨架（**前端 → 后端 → 工单系统 → CMDB**）是真实企业多云管理系统的标准形态，本身具有说服力。短板在于**只有 AWS 一朵云、功能单薄**。

**可以扩展，但把握两个边界：**
1. **向上守住**：所有扩展必须能自圆其说，符合企业现实
2. **向下守住**：不做本身独立成产品的重功能（完整监控平台、完整 CI/CD、生产级 FinOps），避免面试追问漏馅

**推荐优先级：多云适配 > 服务目录/自服务 > 成本管理 > 权限与审计 > CMDB 深化 > 智能资源建议**

## 三、分层落地方案

### L0 层：真实还原（项目骨架，必做）
还原原有四层架构（详见 [02-系统架构设计.md](02-系统架构设计.md)）：
- 前端仿 AWS 控制台，按资源模块分区
- 后端转发操作请求到工单系统，不直接执行
- 工单系统：流程编排 + 审批流转 + 自动化执行
- CMDB：唯一数据源，前端全部展示数据从 CMDB 拉取

**这一层要还原的关键设计（面试深度点）：**
- 为什么操作要绕工单系统（解耦/合规/留痕）
- CMDB 与云上数据的一致性策略（定时同步 + 变更回调 + 漂移检测）
- 异步云操作的最终一致性、失败重试、幂等

### L1 层：合理扩展（原系统的自然延伸）

**① 多云适配层（核心扩展）**
- 抽象 `CloudProvider` 统一接口：纳管 / 查询 / 操作 / 账单
- 实现 AWS + 阿里云两个 Provider，其余留扩展位
- 统一资源模型：EC2/ECS、VPC/VPC、安全组 → 统一对象
- 面试点：适配器/策略模式、SPI 插件化、如何新增一朵云

**② 服务目录与自服务**
- 用户自助申请主机（选规格/网络/安全组）→ 自动生成工单 → 审批 → 自动交付
- 配额管理（部门维度）、申请模板
- 面试点：把"申请 → 审批 → 交付"串成完整业务闭环

**③ 成本管理（FinOps 轻量版）**
- 账单数据采集（真实项目可用模拟数据，Demo 内置账单生成器）
- 成本趋势、按部门/项目分摊、预算与超支告警
- 资源闲置检测（低利用率主机 Top N）
- 面试点：行业热点，一句"帮企业降本 20-30%"胜过技术炫技

**④ 权限与审计**
- RBAC（超级管理员/云管理员/运维/只读）
- 数据权限（按部门/项目隔离资源可见性）
- 操作审计（谁在何时对哪个资源做了什么，全程留痕）
- 面试点：多租户 + 数据权限是必考题

**⑤ CMDB 深化**
- 资源关系建模（应用→主机→安全组→子网→VPC）
- 资源变更历史、配置项漂移检测
- 资源拓扑可视化
- 面试点：多态资源建模深度（表结构设计）

### L2 层：亮点扩展（可选，差异化加分）

**⑥ 智能资源优化建议（规则引擎版）**
- 基于规则的闲置/低效资源检测（如 CPU<5% 连续 7 天 → 建议停机/降配）
- 输出"优化建议清单 + 预估节省金额"
- **注意**：做规则引擎，别硬蹭"AI 大模型"人设；若原项目没用过 LLM，面试追问会露馅

## 四、防穿帮清单（明确不做）

1. ❌ 不做生产级监控平台（Prometheus/Grafana 全家桶）—— 独立产品，超出系统边界
2. ❌ 不做完整 CI/CD —— 那是 DevOps 平台
3. ❌ 不做多云 K8s 统一调度（Karmada 等）—— 偏离内部管理系统定位
4. ❌ 不夸大架构 —— 如实说"企业内部管理系统，QPS 不高，核心价值在业务闭环与流程治理"，主动讲短板反而加分
5. ❌ 不声称"完美多云" —— 如实说"适配器模式支持 AWS/阿里云，其余云按需扩展"

## 五、各扩展点的面试价值与风险提示

| 扩展点 | 面试价值 | 风险提示 |
|---|---|---|
| ① 多云适配 | 架构抽象能力（设计模式） | 需能画出接口设计并讲清新云接入流程 |
| ② 服务目录 | 业务闭环能力 | 需讲清配额与审批联动逻辑 |
| ③ 成本管理 | 行业视野（FinOps） | 需说明 Demo 数据为模拟生成，不夸大 |
| ④ 权限审计 | 企业级基本功 | 需讲清 RBAC 与数据权限的实现细节 |
| ⑤ CMDB 深化 | 领域建模深度 | 需能讲清多态资源建表方案及取舍 |
| ⑥ 智能建议 | 差异化亮点 | 明确是规则引擎，不虚构 AI 能力 |
