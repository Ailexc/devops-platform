## 一、背景与目标

### 1.1 为什么做

成本优化模块当前只有两个基础页面（成本趋势、优化建议），优化建议是**写死的规则函数**（`views.py` 里的 `generate`），面试时无法解释"规则怎么定、怎么维护"。

V5 Demo 验证了**可配置规则引擎**的价值 —— 规则由运维在页面上配置（检测范围 + 检测逻辑），平台提供引擎能力，报告按云 → 账号 → 区域 → 类型下钻。这既解决了功能真实性问题，也避开了"具体规则怎么定"的面试深坑。

### 1.2 V5 Demo 能力目标（验收基准）

| 视图 | 核心能力 |
|---|---|
| **① 成本优化总览** | 大屏式结论展示：统计卡（待处理/预估节省/覆盖云/已处理/环比）+ 4 图表（按云节省、资源类型分布、区域成本、趋势）+ 建议明细列表（点行看详情） |
| **② 规则配置** | 规则按云分组列表；新建/编辑规则（检测范围：云/账号/区域/资源类型 + 检测逻辑：类型/优先级/JSON条件/标题模板/节省估算）；全量检测 + 单规则检测 |
| **③ 分析报告** | 报告列表（摘要卡 + 查看详情 + 导出 Excel）；详情页左侧维度树（云→账号→区域→类型）+ 右侧明细表格联动 + 汇总条 + 类型筛选 |

| 模块 | 现状 | 复用价值 |

### 2.2 与 V5 的差距（需新建）

| 差距 | 说明 |
|---|---|
| ❌ 无可配置规则模型 | 只有 `OptimizationSuggestion`，规则逻辑写死在 `views.py` |
| ❌ 无规则引擎服务层 | 无独立的条件解析/匹配/估算/报告生成逻辑 |
| ❌ 无分析报告模型 | 无历史执行记录、无层级树快照 |
| ❌ 无规则/报告 API | 只有 bills/suggestions 基础接口 |
| ❌ 无大屏总览 | 前端没有统计卡 + 多维图表页 |
| ❌ 建议无维度冗余 | `OptimizationSuggestion` 只有 `resource` FK，无法按云/账号/区域/类型快速聚合 |
| ❌ 成本数据单云 | Mock 只有 1 个账号，v5 需要多云（AWS/阿里云/腾讯云）演示 |

## 四、后端改造点与工作量

### 4.1 数据模型层（backend/cost/models.py）

**新增模型：**

```python
class OptimizationRule(models.Model):
    """可配置优化规则 —— 由运维在页面配置"""
    name = CharField('规则名称', max_length=128)
    rule_type = CharField('规则类型', max_length=16,
        choices=[('idle','闲置资源'),('downsize','建议降配'),('unused','未使用'),
                 ('budget','预算告警'),('trend','趋势异常'),
                 ('reserved','付费模式优化'),('storage','存储优化')])
    severity = CharField('优先级', max_length=8, choices=SEVERITY_CHOICES, default='medium')
    description = TextField('规则说明', blank=True)
    # ★ 检测范围：云/账号/区域/资源类型（JSON，关联 CloudAccount/Resource 的维度）
    scope = JSONField('检测范围', default=dict)
    #   {"cloud": "阿里云", "account": "", "region": "cn-hangzhou", "resource_type": "instance"}
    # ★ 检测条件：声明式 JSON（引擎解析）
    conditions = JSONField('检测条件', default=dict)
    #   {"resource_type":"instance","status":"stopped","min_days":7}
    title_template = CharField('标题模板', max_length=128, default='{resource_name} 建议处理')
    description_template = TextField('描述模板', blank=True)
    saving_config = JSONField('节省估算配置', default=dict)
    #   {"type":"spec_ratio","percent":40}  /  {"type":"fixed","amount":50}  /  {"type":"none"}
    is_enabled = BooleanField('启用', default=True)
    priority = IntegerField('执行优先级', default=0)
    created_at / updated_at

class RuleExecutionLog(models.Model):
    """规则执行日志（每次执行留痕）"""
    rule = FK(OptimizationRule, related_name='executions')
    scope_snapshot = JSONField('执行时范围快照', default=dict)   # 留档，规则改了也能追溯
    matched_count / created_count / execution_time_ms
    executed_at

class OptimizationReport(models.Model):
    """分析报告 —— 一次检测的完整结果快照"""
    title = CharField('报告标题')
    operator = CharField('执行人', default='system')
    trigger = CharField('触发方式', max_length=16,
        choices=[('manual','手动全量'),('single','单规则'),('schedule','定时')])
    summary = JSONField('汇总统计', default=dict)     # {total_rules,total_matched,total_saving,cloud_count}
    tree_snapshot = JSONField('层级树快照', default=dict)  # 云→账号→区域→类型 聚合
    items_snapshot = JSONField('明细快照', default=list)   # 每条建议完整数据（冗余，导出用）
    executed_at
```

**改造模型：**

```python
class OptimizationSuggestion(models.Model):
    """优化建议 —— 归属某次报告 + 冗余维度字段（按维度快速聚合）"""
    report = FK(OptimizationReport, related_name='suggestions', null=True)
    resource = FK(Resource, on_delete=CASCADE)        # 保留，关联具体资源
    # ★ 冗余维度（避免每次 join）：
    account = FK(CloudAccount, null=True)
    provider_type / region / resource_type
    rule = FK(OptimizationRule, null=True)            # 命中哪条规则
    suggestion_type / severity / title / description / estimated_saving / is_resolved
```

**工作量**：模型定义 + 迁移文件 0.5~1 人日

### 4.2 规则引擎服务层（新增 backend/cost/engine.py）

```
RuleEngine
├── execute_rule(rule)          # 执行单条规则
│   ├── 解析 scope → 过滤 CloudAccount + Resource 基础查询集
│   ├── 解析 conditions → 匹配器分发（idle/downsize/unused/budget/trend）
│   ├── 计算 estimated_saving（saving_config：fixed/spec_ratio/none）
│   └── 写入 OptimizationSuggestion + 写 RuleExecutionLog
├── run_all(rules=None)         # 全量检测（并行/串行 + 汇总）
├── build_tree(items)           # 构建 云→账号→区域→类型 层级聚合（V5 报告树）
└── match_* (条件匹配器)         # 每种规则类型的匹配逻辑（可扩展注册式）
```

**设计要点（面试亮点）：**
- **条件匹配器注册表**（类似 `provider/actions.py` 的 `ActionRegistry`），新增规则类型 = 注册一个匹配器，不用改引擎
- 条件为**声明式 JSON**，引擎负责解析执行，不写死在代码
- 匹配的数据源是 **CMDB 的规范化 Resource**（天然支持多云），引擎本身与云无关
- 空闲/降配检测依赖 CPU 利用率指标 —— 生产对接监控系统，Demo 用 `metadata` 模拟（如实说明）

**工作量**：1~1.5 人日

### 4.5 监控数据采集链路（采集器 → CMDB → 成本引擎）

> **2026-08-12 确认**：真实工作场景中已有**采集平台**负责从各云/监控系统采集数据并沉淀到 CMDB（`task-management` Demo 即为此复现）。监控数据采集（如 Prometheus 利用率）可作为采集器的一类新采集任务，链路自洽。

```
数据源层（分云）                采集器层 task-management（统一拉平）      CMDB（cloud_manager）        成本引擎
CloudWatch(AWS)    ─┐
云监控(阿里云)       ─┼─→ 新增 resource_modules/metrics/ 采集   ──→  Resource.metadata  ──→  downsize 匹配器
Prometheus(自建)    ─┘    PromQL/API → 统一摘要字段               (avg_cpu_7d 等)         (消费 metadata)
```

**① 采集端（分云）**：不同云使用各自监控源 —— AWS 走 CloudWatch、阿里云走云监控、自建走 Prometheus。Prometheus 通过 **HTTP REST API**（`/api/v1/query`、`/api/v1/query_range` + PromQL）获取，返回 JSON。

**② 采集器侧（统一拉平）**：复用 `task-management` 的 ResourceDef 注册制，新增 `resource_modules/metrics/`：
- `ResourceDef: name="MetricsSummary"`，数据源类型（prometheus / cloudwatch / cloudmonitor）在配置层 `AccountRegion.endpoint` 指定
- 采集指标 → 统一转换为标准字段 `{cloud, account, region, resource_id, avg_cpu_7d, avg_mem_7d}` → 计算摘要 → 按 `cloud_resource_id` 关联写入 CMDB `Resource.metadata`
- 复用现有调度层（cron 每日）与执行层（SyncPipeline），**与资源同步完全一致**

**③ 消费端（不分云）**：成本优化引擎只读 CMDB，`downsize` 匹配器消费 `metadata.avg_cpu_7d`，对下游完全透明。

**边界结论（能做/不能做）**：

| 能力 | 数据来源 | 能做 | 备注 |
|---|---|---|---|
| 闲置/未使用/预算/趋势 | 配置态 + 成本 | ✅ | 纯成本域 |
| **降配（真实利用率）** | 采集器拉监控 → CMDB metadata | ✅ | 链路已打通 |
| 付费模式 / 存储优化 | 成本账单 + 定价 | ✅ | 纯成本域 |
| 实时监控大盘 | — | ❌ | 那是监控平台的事 |
| 调度/网络/容器专项 | 专项数据 | ⚠️ 扩展位 | 规则类型注册制，成本低 |

## 十一、面试话术（沉淀）

> "成本优化这块我们做了**可配置规则引擎**：规则不是写死在代码里，而是运维通过页面配置检测范围（云/账号/区域/资源类型）和检测逻辑（声明式 JSON 条件），平台提供引擎能力。规则类型通过匹配器注册表扩展，新增类型不用改引擎。每次检测生成**报告快照**，可按云→账号→区域→资源类型下钻查看明细，并可导出源数据。
>
> 成本数据由外部定时任务同步到 CMDB，我们只做展示与分析；利用率类检测的数据来自**统一的采集平台**（对接 CloudWatch/云监控/Prometheus），采集后统一拉平写入 CMDB 的 metadata，我们的引擎只消费 CMDB，不直接对接监控，边界清晰。整体思路类似 Prometheus AlertManager —— 规则可配置，引擎负责评估。
>
> 规则类型覆盖了业内的**核心成本优化场景**（闲置/降配/未使用/预算/异常/付费模式/存储 7 类），且类型通过匹配器注册表可扩展；付费模式、存储优化是纯成本域（账单+定价），无需监控数据。
