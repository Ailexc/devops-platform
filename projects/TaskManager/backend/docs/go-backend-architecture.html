1️⃣ 项目概述与设计目标

1.1 项目背景

CMDB 任务管理平台是一个多账号 × 多区域的云资源同步任务编排系统，负责 AWS 资源（EC2、VPC、RDS 等）的自动发现、同步和关系计算。

核心场景：运维团队需要定期从多个 AWS 账号的多个区域采集云资源数据，建立资源间的关联关系（如 EC2 → VPC、RDS → VPC），并提供可视化的任务管理和执行历史追踪。

项目经历了三个阶段的演进：

  1. V1 (django-q)：初期原型，功能验证
  2. V2 (Celery)：生产版本，完整的两波次编排
  3. V3 (Go + asynq)：架构升级版本，性能优化 + 部署简化

  • 不追求一次性全量迁移（按里程碑渐进落地）

2️⃣ 设计理念与原则

2.1 核心设计原则

🎯
契约驱动开发
以 openapi.json 为唯一事实来源，Go 后端严格对齐 Python 版的请求/响应格式，确保前端零改动
🔧
执行与编排解耦
资源同步（执行层）与两波次调度（编排层）完全分离，编排层可独立升级而不影响执行逻辑
📦
单二进制多角色
一个二进制文件通过 --role 参数切换 API/Worker/Scheduler，简化部署和运维
🛡️
幂等与容错
任务执行天然幂等，支持断点续跑、自动重试、断路器保护

2.2 关键权衡决策

决策 1：asynq 而非 machinery
原因：machinery 虽有 group/chord 原语但社区活跃度弱；asynq 无原语反而促使我们自研状态机——这正是"执行与编排解耦"的架构升级点。
决策 2：GORM 而非 ent
原因：需要逐字段对齐现有 PostgreSQL 表结构（含 JSON 字段），GORM 的灵活性更贴合；ent 适合 schema 从零设计。
决策 3：自研调度器
原因：django-celery-beat 的"预建占位 + 哨兵 cron"语义简单明确，一张表 + 一个 cron 轮询即可复刻，不值得引入重型调度框架。

3️⃣ 技术选型与理由

3.1 Web 框架选型

框架 优势 劣势 选择
Gin 生态最大、中间件丰富、性能优异 泛型支持较晚 ✅ 采用
Fiber 性能极佳（基于 fasthttp） 生态较小、不兼容 net/http ❌
Echo API 设计优雅 社区活跃度低于 Gin ❌

3.2 任务队列选型

Celery (Python)
  • 原生支持 chord/group/chain
  • 社区成熟，文档完善
  • 进程模型：prefork 多进程
  • 配置复杂（broker/backend/serializer）
asynq (Go)
  • 基于 Redis，轻量级
  • 支持优先级/延迟/周期任务
  • 内置 Web UI 监控
  • 无 chord/group 原语（需自研）

3.3 ORM 选型

选择 GORM 的核心理由：需要逐字段对齐现有 PostgreSQL 表结构（含 JSONB 字段），GORM 的 datatypes.JSON 和原生 SQL 支持更贴合迁移需求。

组件 选型 版本 理由
Web 框架 Gin v1.9+ 生态最大、中间件丰富
ORM GORM v1.25+ JSONB 支持好，迁移友好
任务队列 asynq v0.24+ 基于 Redis，轻量级
Redis go-redis v9 事实标准
配置 viper v1 环境变量/文件统一
日志 slog 标准库 零依赖、结构化日志
断路器 gobreaker v2 轻量、成熟

4.2 进程模型

Go 后端采用单二进制多角色架构，通过 --role 参数切换运行模式：

# API 服务模式
./cmdb-server --role=api --port=8080

# Worker 模式（消费任务队列）
./cmdb-server --role=worker

# Scheduler 模式（定时调度）
./cmdb-server --role=scheduler

# 全功能模式（开发/Demo）
./cmdb-server --role=all --seed
优势：部署从 3 个不同运行时镜像收敛为 1 个镜像；交叉编译；内存占用低一个量级。

5️⃣ 核心模块设计

5.1 两波次编排状态机

这是整个系统的核心亮点，将 Celery 的 chord 语义升级为自研状态机，实现"执行与编排解耦"。

两波次编排状态机
PENDING
→
WAVE1_RUNNING
→
WAVE2_RUNNING
→
FINALIZED

Wave1（资源同步）

  • 所有资源类型（EC2、VPC、RDS 等）并行执行
  • 单资源失败不阻塞组（返回失败结果而非抛异常）
  • Redis Hash 记录计数（total/succeeded/failed/done）

Wave2（关系计算）

  • Wave1 全部完成后触发
  • 计算资源间绑定关系（如 EC2 → VPC）
  • 完成后进入 Finalize 阶段

5.4 调度器设计

复刻 django-celery-beat 的"预建占位"语义：

阶段 enabled crontab 行为
初始化预建 false 哨兵（2/31） 不加载
前端设置 cron true 真实 cron 正常调度
前端取消 false 哨兵 不再调度
