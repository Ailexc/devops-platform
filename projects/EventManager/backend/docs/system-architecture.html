⚡

大量并发 · 快速执行

事件到达具有突发性（实例批量启停、故障演练、扩缩容等场景瞬间涌入大量事件）， 系统必须能快速接收、快速入队、异步处理，绝不能阻塞上游 Lambda / EventBridge， 也不能让事件积压导致 CMDB 数据滞后。

🛡️

稳定性 · 可靠性

CMDB 是下游系统的数据底座，事件丢失或重复会直接污染数据。系统必须做到至少一次投递、 幂等处理、失败自动重试、重试耗尽进死信（可人工回放），保证「事件不漏、数据不错」。

🔍

可回溯 · 可观测

每个事件都有完整生命周期：接收 → 入队 → 路由 → 处理 → 完成/失败， 全链路 append-only 日志 + trace_id 追踪；配套统计面板、队列深度、Worker 状态、失败告警， 出现问题时能快速定位、复盘与回放。

🧩

可扩展 · 易维护

事件类型按 Handler 注册表 模式组织，新增事件类型只需新增 Handler 类并注册， 无需改动核心链路；Worker 支持水平扩展，队列解耦，可按流量弹性伸缩。

🕰️ 真实系统演进史 Evolution

从 v1 到 v3，三段演进对应三种不同的架构思路与工程取舍。

V1 · django-q 时代（非本人实现）

简单粗暴，但性能有限

初版使用 django-q 作为任务 Worker。django-q 基于数据库轮询分发任务， 实现简单、上手快，但存在明显天花板：

  • 数据库轮询模型，任务吞吐受限，高并发下成为瓶颈；
  • 对长时间任务、突发流量缺乏弹性，容易积压；
  • 监控、重试、死信等能力薄弱，问题难以回溯。

这一版本并非本人实现，但为其后的重构提供了「为什么要改」的完整背景。

V2 · 线程 + 执行历史（本人接手，工期紧张）

简单改造，后发现线程不可靠

接手后工期紧张，采用了轻量改造：将任务改为线程执行， 同时补充了执行历史记录与日志记录，让系统「看得见」。

  • ✅ 执行历史 + 日志：每个任务的处理过程、结果可查，具备初步可回溯能力；
  • ⚠️ 线程模型不可靠：进程重启线程即丢失、无法跨进程调度、无分布式语义；
  • ⚠️ 无法水平扩展：单机线程池受限于进程资源，峰值流量依然扛不住；
  • ⚠️ 缺少消息确认与重投递，事件可能丢失，可靠性无法保障。

这一阶段的收获：「记录 + 日志」的思路是对的，它让后续重构有了可验证的基线； 但线程调度方案是错的，它无法支撑可靠性目标。

V3 · Celery + 可观测（本人主导重构）

真正的可靠性保障，支撑下游 6+ 系统

开始主导重构，引入 Celery 作为核心 Worker， 并系统性补齐监控与可观测能力，从架构上真正保障数据可靠性：

  • 🚀 Celery 分布式任务：消息队列（RabbitMQ）解耦，Worker 可水平扩展，具备消息确认与重投递；
  • 🔄 可靠投递：至少一次投递 + 幂等处理 + 指数退避重试 + 死信队列（人工回放）；
  • 📈 监控可观测：队列深度、Worker 状态、处理耗时、成功率、失败告警，问题可第一时间发现；
  • 🔍 全链路可回溯：事件时间线、trace_id、执行历史、日志，支撑问题复盘与审计；
  • ⏰ 定时数据同步：配合定时同步系统做数据补偿兜底，事件驱动 + 定时对账双保险；
  • 🧩 支撑下游：凭借稳定可靠的数据底座，支撑下游 6+ 系统应用。
✅ 演进主线：「能跑」（django-q）→「看得见」（线程+历史+日志）→「靠得住」（Celery+可观测+同步兜底）。 每一阶段的问题都真实存在，也因此有了明确的演进方向。

📥

接收与入队

API 接收事件 → 校验 Schema → 生成 trace_id → 投递 RabbitMQ 后立即返回 202，上游零阻塞。落库事件 + 记录「接收」日志。

🔀

路由分发

Worker 消费消息，根据 event_type 匹配 Handler 注册表（支持通配符 aws.ec2.*），路由到对应处理器。

⚡

异步处理

Handler 统一 async 编程模型，处理结果写回事件 + append-only 时间线；耗时、Worker、队列均记录。

🔁

重试与死信

失败自动重试（指数退避）；重试耗尽进死信队列，支持 手动重试 / 批量回放，事件绝不静默丢失。

🛡️

幂等保障

基于事件 ID + 数据库行锁（select_for_update）做去重，重复投递只处理一次，保证 CMDB 数据不错。

📊

统计与监控

仪表盘：总数/各状态分布/成功率/平均耗时；队列深度；Worker 在线状态；近期失败 Top，可观测性强。
