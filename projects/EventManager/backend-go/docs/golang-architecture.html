3.2 关键决策理由

💡 为什么用 asynq 而不是 machinery/river？

asynq 基于 Redis，内置指数退避重试、死信队列、任务调度与监控面板，是 Celery 功能最接近的 Go 方案。同时省掉 RabbitMQ 依赖，部署面更小。Go 栈只需 PostgreSQL + Redis，Python 栈需要 PostgreSQL + Redis + RabbitMQ。

💡 为什么用 GORM 而不是 sqlc？

本项目查询复杂度中等（筛选/聚合/JSONB 查询），GORM 开发效率高，且 clause.Locking 原生支持 SELECT FOR UPDATE，与 Django select_for_update 语义对齐。sqlc 更适合纯 SQL 场景。

💡 为什么用 SELECT FOR UPDATE NOWAIT 而不是 Redis 分布式锁？

数据库锁与业务状态在同一事务内，原子性更强。NOWAIT 避免了长事务阻塞，拿不到锁直接报错让 worker 快速失败。省去了 Redis 锁的续期（watchdog）复杂度。

7. 核心机制

7.1 幂等保障

Worker 消费任务时，在同一个数据库事务内完成锁获取、状态检查、状态更新三步操作：

// 事务开始
tx := db.Begin()

// ① 获取行锁（NOWAIT: 拿不到立即失败）
tx.Clauses(clause.Locking{
    Strength: "UPDATE", Options: "NOWAIT",
}).Where("id = ?", eventID).First(&event)

// ② 幂等检查
switch event.Status {
case model.StatusProcessing, model.StatusCompleted:
    tx.Rollback(); return nil  // 跳过
}

// ③ 标记处理中
event.Status = model.StatusProcessing
event.WorkerID = workerID
tx.Save(&event)

// ④ 提交事务（释放锁）
tx.Commit()

// ⑤ 在事务外执行 Handler（可能很慢）
handler.Handle(ctx, &event)
为什么锁持有时间极短？ 步骤 ①~④ 在毫秒级完成，Handler 执行（步骤 ⑤）在事务外进行，不会阻塞其他事件的处理。

7.2 重试与 DLQ

指数退避公式

$$delay = \min(base \times 2^{retry\_count},\ max\_delay) \times jitter$$

其中 $base = 4s$，$max = 300s$，$jitter \in [0.5, 1.0)$

重试次数计算实际延迟
14 × 2¹ × [0.5~1.0]4~8 秒
24 × 2² × [0.5~1.0]8~16 秒
34 × 2³ × [0.5~1.0]16~32 秒
44 × 2⁴ × [0.5~1.0]32~64 秒
5min(128, 300) × [0.5~1.0]64~128 秒
Jitter 的作用： 随机抖动避免多个失败事件在同一时刻重试，防止"惊群效应"对下游服务造成冲击。

  • Gin + GORM（轻量高性能）
  • asynq（原生 goroutine 并发）
  • Redis 直连（免 RabbitMQ）
  • PostgreSQL + Redis（共享）
  • 单进程 10 goroutine
  • 镜像 <50MB（静态编译）
  • 启动 <1s（单二进制）
