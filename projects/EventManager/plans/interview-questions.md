# 维度一：基础（Broad 覆盖）

> 重点主线：**并发、及时性、可靠性**。覆盖面要广，答错任何一题都可能致命。

## 1.1 语言基础（Python）

**Q1. 线程、进程、协程的区别？各自适用什么场景？**
- 考察点：并发模型的基本认知
- 要点：
  - 进程：独立内存空间，CPU 密集 + 多核利用；开销大、通信贵（IPC）
  - 线程：共享内存，I/O 密集；受 GIL 限制；切换开销小于进程
  - 协程：单线程内用户态调度，I/O 等待时让出；开销最小、可高并发；无法利用多核
  - 本系统：Celery 用 eventlet（协程池）承接大量 I/O 密集型事件处理

**Q2. GIL 是什么？对并发有什么影响？如何绕过？**
- 考察点：Python 并发本质
- 要点：同一时刻仅一个线程执行字节码；CPU 密集多线程无加速；I/O 密集无影响（等待时释放）；绕过方式：多进程、C 扩展、asyncio/协程、JIT（PyPy）

**Q3. async/await 的原理？asyncio 事件循环怎么工作？**
- 考察点：异步编程理解深度
- 要点：事件循环调度协程；遇到 await 挂起让出控制权；I/O 就绪后回调恢复；单线程高并发；阻塞调用会卡死整个循环

**Q4. `select_for_update` 是干什么的？有什么坑？**
- 考察点：数据库锁 + 并发安全
- 要点：行级排他锁，事务内生效；用于防并发重复处理；坑：必须配合事务、超时（nowait/skip_locked）、死锁风险、长事务持锁影响吞吐
- 本系统：幂等标记用 `select_for_update(nowait=True)` 抢锁

## 1.2 并发与异步

**Q5. 什么是高并发？怎么衡量？QPS/TPS/RT 是什么？**
- 考察点：性能指标概念
- 要点：QPS=每秒请求数、TPS=每秒事务数、RT=响应时间；吞吐 = 并发 × (1/RT)；峰值 vs 平均值

**Q6. 为什么事件系统需要"快速接收、异步处理"？**
- 考察点：及时性/解耦思维
- 要点：事件具有突发性；同步处理会拖垮上游（Lambda/EventBridge 超时）；快速返回 202 + 入队异步处理，实现削峰填谷；上游零阻塞

**Q7. 消息队列解决了什么问题？没有它行不行？**
- 考察点：MQ 的价值认知
- 要点：解耦（生产者不关心消费者）、削峰填谷（缓冲突发）、异步、可重试、多消费者扩展；没有 MQ 则下游处理慢会反向阻塞上游，事件丢失无法恢复

## 1.3 消息队列（RabbitMQ）

**Q8. RabbitMQ 的核心概念？Exchange / Queue / Binding 的关系？**
- 要点：生产者→Exchange（路由规则）→Binding→Queue→消费者；Exchange 类型：direct/topic/fanout/headers

**Q9. 什么是消息确认（ack）？RabbitMQ 的消息确认机制？**
- 要点：消费者处理成功后 ack，broker 才删除；auto-ack vs manual-ack；未 ack 会重投；nack/reject 可进死信
- 本系统：Celery acks_late 语义

**Q10. 消息丢失发生在哪几个环节？如何避免？**
- 要点：三环节——生产者发丢失（publisher confirm）、Broker 存储丢失（持久化/镜像）、消费者处理丢失（手动 ack）；本系统至少一次投递 + 幂等兜底

**Q11. 什么是死信队列（DLQ）？怎么配置？**
- 要点：消息被拒绝/过期/超阈值后转入的队列；DLX（dead letter exchange）；价值：问题消息不丢、可人工干预；本系统：重试耗尽自动进 DLQ，支持手动回放

## 1.4 可靠性 / 一致性

**Q12. at-least-once / at-most-once / exactly-once 分别是什么？**
- 要点：三种投递语义；exactly-once 极难（分布式下需幂等 + 去重）；常用方案 = at-least-once + 幂等（近似 exactly-once）

**Q13. 什么是幂等？如何实现？**
- 要点：重复执行结果一致；实现：唯一键去重、状态机检查、数据库锁；本系统：事件 ID + `select_for_update` 抢锁 + 状态检查

**Q14. 重试策略有哪些？什么是指数退避？为什么加抖动？**
- 要点：立即重试/固定间隔/指数退避/退避+抖动；指数退避避免重试风暴；抖动避免惊群效应；本系统 `countdown = min(2^retry * 4, 300)`

**Q15. 什么是 append-only 日志？事件溯源（Event Sourcing）是什么？**
- 要点：只追加不修改；完整历史、可回溯、可审计、可重放；事件溯源 = 用事件序列重建状态；本系统 event_logs 时间线

## 1.5 数据库

**Q16. 关系型数据库事务的 ACID？隔离级别？**
- 要点：原子性/一致性/隔离性/持久性；读未提交/读已提交/可重复读/串行化；脏读/不可重复读/幻读

**Q17. JSONB 字段和普通字段的区别？查询有什么注意点？**
- 要点：无固定 Schema 存 JSON；支持内部字段查询（`raw_payload->>'batch_id'`）；注意：嵌套查询无法走普通 B-tree 索引，大数据量需 GIN 索引；本系统用 JSONB 存原始事件

**Q18. 什么是索引？JSONB 字段怎么建索引？**
- 要点：B-tree 默认；JSONB 用 GIN 加速 `@>` / `?` / `->>` 查询；索引不是越多越好（写放大）

## 1.6 框架与组件（Django / Celery / Redis）

**Q19. Django 的 ORM 是什么？QuerySet 是惰性的吗？**
- 要点：对象关系映射；惰性求值（真正执行时才查库）；链式调用；避免 N+1（select_related/prefetch_related）

**Q20. Celery 是什么？核心组件有哪些？**
- 要点：分布式任务队列；Broker（RabbitMQ/Redis）、Worker（执行者）、Result Backend（存结果）、Beat（定时）；支持任务重试、超时、进度

**Q21. Redis 的常见数据结构与典型用途？**
- 要点：String/List/Hash/Set/ZSet；用途：缓存、队列、计数器、分布式锁、发布订阅；本系统：Celery 结果后端、进度上报

**Q22. 什么是 HTTP 202 Accepted？为什么异步接口用它？**
- 要点：请求已接受但处理未完成；配合 Location/异步查询轮询；避免同步阻塞

**Q23. 什么是水平扩展 vs 垂直扩展？**
- 要点：加机器 vs 加配置；MQ+Worker 天然支持水平扩展；无状态设计是扩展前提

# 维度二：进阶（深度深挖）

> 围绕本系统核心技术点深挖，展示"为什么这么设计、坑在哪、怎么权衡"。

## 2.1 Celery 深度

**Q1. Celery 任务状态机？PENDING→RECEIVED→STARTED→SUCCESS/FAILURE 各代表什么？**
- 考察点：Celery 内部机制
- 要点：PENDING（未开始/结果丢失）、RECEIVED（已入队）、STARTED（开始执行，需 task_track_started=True）、SUCCESS/FAILURE/RETRY；本系统轮询状态接口按状态机推进

**Q2. `acks_late` 是什么？设了和没设有什么区别？**
- 要点：默认任务开始前 ack（任务丢失不重试）；acks_late 任务完成后才 ack（worker 崩溃可重投）；配合 `reject_on_worker_lost`；代价：可能重复执行，必须幂等兜底；本系统 `acks_late=True` + 幂等

**Q3. `prefetch_multiplier` 和并发数的关系？为什么会"饥饿"？**
- 要点：worker 一次性预取多少消息；预取太多会独占队列消息，其他 worker 饿死；事件量大时要调低；配合多 worker 均衡

**Q4. eventlet / gevent / threads / prefork 四种 pool 的区别？为什么事件系统选 eventlet？**
- 要点：prefork=多进程（CPU 密集）、threads=线程（受 GIL）、eventlet/gevent=协程（I/O 密集高并发）；事件处理是典型 I/O 密集（调 AWS/HTTP），eventlet 单进程高并发、内存占用小；坑：协程内不能有阻塞调用（会卡住整个 pool），必须 patch 或用异步客户端

**Q5. Celery 的 soft_time_limit 和 time_limit 区别？超时后会发生什么？**
- 要点：soft 超时抛 SoftTimeLimitExceeded（可捕获优雅退出）、hard 超时直接 kill 进程；本系统 fast 任务 30s/60s，slow 300s/600s

**Q6. Celery 任务结果存哪？django-db 和 Redis 后端怎么选？**
- 要点：结果后端存 task 返回值；django-db 持久化可审计但写库有开销、Redis 快但内存、需过期策略；本系统用 django-db（可靠）+ 进度 meta 存 Redis

**Q7. 为什么 worker 无状态才能水平扩展？扩 worker 时队列怎么重新分配？**
- 要点：任务间不共享内存状态；消息在 broker 中，新 worker 加入即可消费；配合 prefetch 调整负载均衡

## 2.2 RabbitMQ / 消息可靠投递

**Q8. 从生产者到消费者，一条消息可靠投递的全链路保障？**
- 要点：publisher confirm（生产确认）→ 队列持久化 + 镜像队列 → 消费者 manual-ack → DLX 死信；三层保障 + 业务幂等 = 端到端可靠；本系统「至少一次 + 幂等 + 重试 + 死信」

**Q9. 如何用 RabbitMQ 实现延迟队列 / 重试队列？**
- 要点：TTL（消息过期）+ DLX（死信路由）实现延迟；消息过期后进死信队列再路由回主队列，实现延迟重试；本系统 Celery 的 countdown 由 broker 层面实现

**Q10. 队列积压了怎么办？如何快速恢复？**
- 要点：先确认不丢（队列消息在）→ 快速扩容 worker 消费 → 必要时临时清掉低优先级 → 分析根因（消费慢/Handler 卡死/死循环）→ 预防：监控队列深度 + 告警

## 2.3 幂等 / 一致性设计

**Q11. 幂等标记为什么用 `select_for_update(nowait=True)`？换成 Redis 分布式锁行不行？**
- 要点：数据库行锁和状态更新在**同一事务**，原子性最好；Redis SETNX 更快但锁过期/误删/主从切换有风险；两个 worker 同时处理同一事件：DB 锁保证只有一个拿到，另一个 nowait 立即失败跳过
- 追问：锁粒度、持有时间、死锁怎么避免？

**Q12. 至少一次投递 + 幂等，如何近似达到"精确一次"的效果？**
- 要点：投递侧（生产者确认+重投）保证不丢；消费侧（幂等+去重）保证不重；两者组合 = 业务上恰好一次；这是业界标准方案，exactly-once 靠分布式事务/两阶段提交成本极高

**Q13. 重试会破坏幂等吗？重试和幂等如何共存？**
- 要点：重试是"同一事件再次执行"，幂等保证"再次执行结果一致"；所以**重试次数再多也不产生副作用**；设计上重试计数器与业务数据分离

## 2.4 数据模型 / 可回溯

**Q14. 为什么要 append-only 事件日志（event_logs 时间线）？**
- 要点：完整生命周期可回溯、可审计、可复盘；与 events 状态表分离，历史不可篡改；能回答"这个事件到底经历了什么、卡在哪一步"

**Q15. trace_id 的作用？如何实现跨组件追踪？**
- 要点：一次事件处理链路唯一 ID，贯穿 API→MQ→Worker→DB；问题定位时按 trace_id 聚合所有日志；本系统事件生成 trace_id 并贯穿日志

**Q16. JSONB 查询 `raw_payload__batch_id` 的性能问题？怎么优化？**
- 要点：JSONB 内字段查询默认走不了普通 B-tree 索引；量大时需要 GIN 索引或抽列冗余；本系统事件量级下直接查询可接受，真实系统量大时会冗余出独立 batch_id 列并建索引

## 2.5 可观测性 / 前端

**Q17. 事件系统的监控指标该怎么设计？**
- 要点：三个维度——**吞吐**（QPS/成功率）、**延迟**（平均/P99）、**队列**（深度/积压趋势）；加 Worker 状态、失败原因分布；告警阈值要基于基线，避免告警疲劳

**Q18. 前端轮询刷新 vs WebSocket？为什么轮询够用？**
- 要点：轮询简单可靠、无状态、易水平扩展；WebSocket 实时推送但增加连接管理复杂度；事件处理延迟秒级，5s 轮询足够；注意轮询退避和并发控制（TanStack Query 自动去重）

**Q19. 前端如何避免轮询把后端打挂？**
- 要点：统一请求去重（query key）、失败退避、页面不可见时暂停、批量聚合接口；本系统 TanStack Query 的 refetchInterval + 状态驱动

## 2.6 框架选型

**Q20. Django Ninja vs DRF vs FastAPI？为什么选 Ninja？**
- 要点：三者都基于 Pydantic；Ninja 更轻、声明式路由、自动 OpenAPI、与 Django ORM 同生态、支持 async 视图；FastAPI 异步更强但和 Django 集成弱；团队 Django 背景选 Ninja 学习成本最低

**Q21. Pydantic v2 的 Schema 校验解决了什么问题？**
- 要点：请求/响应数据声明式校验、自动序列化、类型安全；减少手写校验代码；错误信息标准化

## 3.3 峰值与阻塞事故（最有价值的故事）

**Q5. 讲讲你经历过的一次"大量阻塞"？**
- 追问链：
  1. "什么时间？什么原因触发的？"
  2. "当时队列积压了多少条？持续多久？"
  3. "你怎么定位到根因的？排查过程？"
  4. "先恢复还是先定位？具体操作了什么？"
  5. "有没有丢数据？下游感知如何？"
  6. "事后做了什么改进防止再发生？"
- 答题要点：用 **STAR 结构**（情境-任务-行动-结果）；要有真实细节（时间、数字、命令、面板）；重点讲"事后改进"体现成长性

**Q7. 你说支撑下游 6+ 系统，你对接过哪些？**

# 维度四：场景（全局思维）

> 面试官模拟真实场景，考察**全局思维**：目标 → 方案 → 权衡 → 风险 → 价值。
> 答题框架（五段式）：**① 明确目标与约束 → ② 给出方案与架构 → ③ 权衡取舍 → ④ 识别风险与兜底 → ⑤ 说明价值**

## 4.1 场景：突发峰值风暴

**题目**：某账号某区域在上午 10 点进行大规模故障演练，事件量是平时的 50 倍瞬间涌入。你是负责人，怎么应对？

- 考察点：应急处理全局观（先保什么、再做什么）
- 回答框架：
  1. **目标**：事件不丢（底线）、尽快消化、CMDB 数据不过期
  2. **方案**：快速接收（API 层不动，入队返回 202）→ 扩容 Worker 加速消费 → 必要时降低非核心任务优先级
  3. **权衡**：扩容 vs 过载（DB 连接、下游压力）→ 保护下游（限流/背压）而非压垮它
  4. **风险**：队列无限增长（监控积压 + 磁盘）、DB 写入压力、下游被打挂
  5. **价值**：削峰填谷能力被验证，积累扩容 SOP
- 加分点：提到**先观察队列深度再扩容**、**与下游沟通限流**、**事后复盘输出预案**

## 4.2 场景：Broker 故障

**题目**：RabbitMQ 突然挂了，如何保证事件不丢？

- 回答框架：
  1. 事前：消息持久化、镜像队列（高可用）、生产者 confirm
  2. 事中：broker 不可用时**降级策略**（如本地暂存/同步处理兜底，本系统 test-lab 就有 broker 降级为同步执行的例子）
  3. 事后：broker 恢复后积压自动消费；配合**定时数据同步兜底**（事件驱动 + 定时对账双保险）
  4. 关键：CMDB 数据一致性靠"事件 + 定时对账"，单一链路故障不影响最终一致
- 加分点：讲出"降级 + 对账"的双保险思路，而非单一依赖 MQ

## 4.3 场景：新增服务类型

**题目**：现在要新增一个 AWS 服务（比如 EKS）的事件接入，从事件接收到 CMDB 更新，全流程怎么设计？

- 回答框架：
  1. Handler 注册表加一个 `aws.eks.*` 的 Handler，零侵入核心链路
  2. 定义 Schema（事件字段）→ Transform（转 CMDB 格式）→ 幂等（按资源 ID）→ 可回溯（时间线）
  3. 上线流程：灰度（先小流量）→ 观察成功率/延迟 → 全量
  4. 考虑失败场景：重试、死信、与定时同步的对账
- 加分点：提到"Schema 声明 + 转换器"的分层设计（对应真实系统 schema/transform/model）

## 4.4 场景：保证数据"永不滞后"

**题目**：如何设计一个系统，让 CMDB 数据"尽可能及时且可靠"？延迟目标怎么定？

- 回答框架：
  1. **事件驱动为主**：实时承接 AWS 事件，秒级更新
  2. **定时同步兜底**：周期性全量/增量对账，发现事件丢失或遗漏自动补偿
  3. **监控**：同步延迟、成功率、对账不一致数量
  4. **自动化修复**：对账发现差异自动触发同步任务
  5. **延迟目标**：P95 < 某秒、对账窗口 < 某分钟——目标要可量化、可考核
- 加分点：强调"事件驱动 + 定时对账"是**双保险**，单一机制都无法保证最终可靠

## 4.5 场景：下游拖垮

**题目**：下游某个系统处理能力跟不上，你的事件会积压，怎么保护自己和上游？

- 回答框架：
  1. 解耦：下游慢不影响接收（队列缓冲）
  2. 保护下游：限流/背压，避免把下游打挂
  3. 隔离：慢下游单独队列，不拖累其他事件
  4. 降级：非关键事件可延迟处理，关键事件优先
  5. 沟通：与下游排障、扩容、容量规划
- 加分点：提到**队列隔离 + 优先级**的设计

## 4.6 场景：从零设计

**题目**：如果让你从零设计一个"高并发、可靠、可回溯"的事件处理系统，你怎么设计？

- 回答框架（大综合）：
  1. **需求与指标**：明确 QPS、延迟、可靠性目标、可回溯要求
  2. **架构**：API 快速接收 → MQ 解耦 → Worker 水平扩展 → 存储（事件表 + append-only 日志 + 结果产物）→ 可观测
  3. **可靠性**：至少一次 + 幂等 + 重试 + 死信 + 定时对账
  4. **可回溯**：trace_id + 生命周期时间线 + 产物落盘
  5. **技术选型权衡**：MQ 选型、Worker 选型、存储选型，每个都说清为什么
  6. **演进规划**：先 MVP（单机+简单队列）→ 再分布式 → 再可观测，控制复杂度
- 加分点：体现**分阶段演进**而非一步到位；每个决策都有"权衡"意识
