📦 能力包与接口契约

业务设计复盘总结

本文复盘系统的核心业务抽象——能力包（Capability）：如何把「接口权限」声明式地打包成可申请、可审批、可授权的单元，并借 OpenAPI 解析出接口契约。

1. 能力包模型

能力包是权限的声明式载体，把散落的接口权限组织成可复用的业务单元：

概念说明示例
能力 Capability对某一业务域的权限集合主机监控
数据模型 DataModel能力操作的对象host（主机）
预设 Preset能力的一组固定权限组合（接口子集 + 数据范围）只读监控 / 完整监控
权限点 Action最小接口权限单元host:list / host:read / host:create

2. 授权闭环：从声明到生效

应用 Owner
   │ ① 声明能力（绑定接口 + 数据模型）
   │ ② 配置预设（接口组合 + 可申请主体 + 数据范围）
   │ ③ 上架市场（走审批）
   ▼
能力市场（用户视角）
   │ ④ 浏览 → 选预设 → 选主体（人/程序） → 选数据范围
   │ ⑤ 提交申请（走审批：申请人≠审批人，SoD）
   ▼
审批通过（系统自动）
   │ ⑥ 生成 Casbin 策略（动作级）
   │ ⑦ 写入 OpenFGA 关系元组（数据级，可选）
   │ ⑧ 策略分发 → 网关实时生效

3. 数据范围控制

预设可配置数据级控制（数据范围维度），申请者只能访问匹配范围内的数据实例：

// 数据范围维度示例：环境 × 地域 × 实例
env    ∈ { prod, staging, dev }
region ∈ { cn-east-1, cn-north-1 }
instance ∈ { host-01, host-02, ... }

// 申请：prod + cn-east-1 → 运行时按 grantee 解析为 CEL 条件
条件: env == "prod" && region == "cn-east-1"

4. 接口契约（OpenAPI 解析）

系统的接口权限点（Action）由 OpenAPI 规格自动解析而来，并携带接口契约（调用示例），让权限申请方「所见即所得」：

// Action 携带的接口契约字段
{
  "code": "host:read",
  "name": "读取主机详情",
  "method": "GET",
  "path": "/api/v1/hosts/{id}",
  "req_example": "GET /api/v1/hosts/1",
  "resp_example": "{ \"id\": 1, \"name\": \"web-01\", \"env\": \"prod\" }"
}
解析链路：应用注册时提供 OpenAPI → 解析器提取每个 operation 的 parameters / requestBody / responses → 用 schema 示例生成器产出请求/响应示例 → 落库到 Action。
消费端：能力市场预设卡片展示 method + path + 可展开的请求/响应示例；应用详情「我接入了谁」展示上游接口契约。让授权决策有据可依。

5. 安全边界：应用管理 vs 应用市场

应用管理（/apps）是 Owner 私有的管理工作台；应用市场（/app-market）是公开申请门户。两者语义不同，边界必须清晰：

面可见性内容
应用管理仅 Owner / admin完整详情、权限点、凭证、网络信息
应用市场全部登录用户公开目录（id/code/name/类型/简介）+ 申请接入所需网络/鉴权信息
修复教训：早期管理面接口对任意登录用户放行，非 Owner 能看到所有应用及凭证信息。修复为按 Owner 过滤 + 收紧 mgScope + 拆出公开目录接口。

6. 踩坑复盘

  • 授权主体映射：程序申请（ReqSubjectApp）落库策略时需映射为服务主体（SubjectService），否则主体类型错乱、策略失效。
  • Action ID 回填：UpsertAction 对已存在记录不返回 ID，权限点引用会变成 [0,0]；需重新 ByCode 查询。
  • 接口契约聚合：「我接入了谁」的上游接口需跨所有策略按应用聚合 action_ids，才能得到完整契约视图。

7. 小结

能力包把「接口权限」声明式地组织成可申请、可审批、可授权的业务单元；接口契约让授权决策透明化；清晰的公私边界保障安全。这是系统业务层的核心。
