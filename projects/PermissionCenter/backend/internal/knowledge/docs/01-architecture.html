🏗️ 系统架构总览

架构设计复盘总结

本文是 Permission Center（去中心化 IAM 演示系统）的架构复盘。系统承担「还原工作场景 + 扩展学习 + 演示能力」三重价值，因此在设计上刻意将权限领域的核心概念（PEP / PDP / PAP / PIP）显性化为可观测的组件。

1. 设计理念：去中心化 IAM

传统 IAM 以「中心」为视角（管理全量用户与应用）。本系统采用去中心化 / 以「我」为中心的视角：每个用户看到的是自己拥有的权限，每个应用 Owner 管理自己的应用与能力。权限不再是集中下发的「黑盒」，而是可声明、可申请、可审批、可追溯的闭环。

六大设计理念：① 组即角色（删除独立 Role 表）；② 授权即审批（SoD 职责分离）；③ 双引擎鉴权（Casbin + OpenFGA）；④ 能力包（声明式权限）；⑤ 策略分发（Agent + Bundle）；⑥ 全链路可观测（TraceID）。

2. 四平面架构（PEP / PDP / PAP / PIP）

平面职责本系统实现
PEP 策略执行点拦截请求、解析主体、转发鉴权Traefik 网关 forwardAuth → /v1/gateway/check
PDP 策略决策点计算最终授权决策iam-server：Casbin（动作级）+ OpenFGA（数据级）双引擎
PAP 策略管理点策略的创建、更新、发布管理面 API：审批即策略，授权全闭环
PIP 策略信息点提供主体/资源等上下文信息身份解析（用户/组/组织链路）+ 资源模型

4. 全链路数据流

4.1 运行时鉴权（数据面）

请求(GET /api/v1/hosts, X-User: bob)
   │  Traefik 拦截 → forwardAuth 回调
   ▼
PEP 解析：请求 → action 映射（host:list）→ 注入 X-PEP-Token
   ▼
PDP：1) 决策缓存命中？ → 直接返回
     2) Casbin 动作级：bob ∈ 研发一部 → host:list ✓
     3) OpenFGA 数据级：bob can_read host-01 → 过滤数据范围
   ▼
决策：200 OK（返回有权限的数据） / 403 Forbidden

4.2 授权闭环（管理面）

声明能力 → 配置预设（接口+数据范围） → 上架市场
   → 用户申请（选主体+数据范围） → 多级审批（SoD）
   → 审批通过瞬间：Casbin 策略 + OpenFGA 关系元组 自动生成
   → 策略分发到 Agent → 网关实时生效

5. 关键设计取舍

为什么用双引擎？Casbin 擅长规则驱动的 RBAC 动作级判断；OpenFGA 擅长大规模关系化的数据级授权（谁能访问哪个实例）。两者各司其职，动作级短路、数据级兜底。
为什么用 Redis 决策缓存？鉴权是高频热路径。决策缓存（TTL 内命中直接放行）大幅降低 PDP 计算与 DB 压力；策略发布时按 app 全量失效，保证一致性与时效。
为什么审批即策略？策略不手动创建，而是由上架预设 / 用户申请自动触发。审批通过瞬间生成策略，从源头保证「策略 = 授权的物化」，杜绝旁路授权。

6. 复盘小结

  • 四平面划分让鉴权职责清晰，也便于讲解与扩展。
  • 去中心化视角让每个角色（Owner / 申请人 / 审批人 / 管理员）都有明确的工作台。
  • 双引擎 + 缓存 + Agent 分发构成「性能 / 一致性 / 可用性」三角的平衡。
