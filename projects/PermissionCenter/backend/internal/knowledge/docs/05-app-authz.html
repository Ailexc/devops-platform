🔐 应用间鉴权

架构设计复盘总结

本文复盘系统「应用之间如何安全调用」的方案：认证（你是谁）与鉴权（你能不能）分离、网关 PEP 接入、凭证与授权分离。

1. 核心模型：认证 vs 鉴权

认证 AuthN：调用方用凭证（client_id / secret）向 IAM 换取短期访问令牌（JWT）。回答「你是谁」。
鉴权 AuthZ：网关 / 应用内 SDK 验令牌（你是谁）后，再问 PDP「这个身份对这个动作/这条数据能不能」。回答「你能不能」。
一句话：凭证负责身份（一次签发），授权负责范围（多次追加）；认证在前、鉴权在后。

2. 市面常见做法

方式身份载体签发方校验适用
静态 Token / API Key固定字符串平台查签发记录轻量 / 内网
OAuth2 Client Credentials短 TTL JWT授权服务器验签 + aud/scope/expM2M 标准
mTLS / SPIFFE客户端证书CA / 网格TLS 握手验书高安全 / 网格

本系统采用 OAuth2 Client Credentials（M2M 事实标准）+ 网关 PEP 执行。

3. 系统方案：网关 PEP

调用方 consumer
   │ ① client_id + secret → /v1/oauth/token 换 access_token
   ▼
请求（Authorization: Bearer token）
   ▼
Traefik 网关（PEP）
   │ ② forwardAuth 回调 → /v1/gateway/check（注入 X-PEP-Token）
   ▼
iam-server（PDP）
   │ ③ 校验 PEP 共享密钥（防绕过网关直连）
   │ ④ 解析身份 → Casbin 动作级 + OpenFGA 数据级
   ▼
决策：200 转发 / 403 拦截（deny-by-default）

4. 防绕过设计

共享密钥信任链：PEP 组（/v1/authz、/v1/gateway）要求 X-PEP-Token 等于配置的共享密钥。只有网关（PEP）持有该密钥，外部无法绕过网关直接调用 PDP。
凭证与授权分离：应用申请（接入单）签发的凭证（Client Credentials）只解决「能不能连」；「能用哪些能力」由能力包授权（接口 + 数据范围）决定。先打通访问，再申请细粒度权限。

5. 端到端工作流

1. 应用 Owner 注册应用 → 登记鉴权方式（Client Credentials）+ 网络信息
2. 声明能力 → 配置预设 → 上架市场（审批）
3. 调用方（程序身份）申请接入 → 审批通过 → 签发 client_id/secret
4. 调用方申请能力包（选主体+数据范围）→ 审批通过 → 策略自动创建
5. 网关放行：token 有效 + 动作级通过 + 数据级匹配 → 200

6. 面试叙事要点

  • 为什么用 OAuth2 CC 而不是 API Key：令牌无状态（验签即可）、短 TTL 可吊销、支持 scope 最小权限。
  • 认证与鉴权分离的价值：一次认证，多次鉴权；凭证只管身份，授权管范围。
  • 网关 PEP vs SDK 接入：网关零侵入（对目标应用透明）；SDK 更灵活但每应用集成成本高。
  • deny-by-default：默认拒绝，显式放行；任何引擎不可用时 fail-closed。

7. 小结

应用间鉴权的本质是「出示身份凭据 + 让对方按策略决策」。本系统以 OAuth2 CC 换令牌、以网关 PEP 做执行点、以 PDP 双引擎做决策，并用共享密钥防止绕过，构成了完整且可讲解的安全链路。
