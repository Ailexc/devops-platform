🔍 系统观测设计

工程实践复盘总结

本系统的定位是「还原工作场景 + 扩展学习 + 演示能力」。可观测性不是为了监控生产，而是把黑盒化的鉴权链路显性化，供演示与学习。本文复盘 5 项观测能力的接口契约、数据来源与踩坑。

1. 观测原则

  • 数据不新增表：全部从现有决策日志 / Redis 缓存 / OpenFGA / bundle 记录聚合。
  • 只读优先：唯一写操作是「清空决策缓存」（排障用）。
  • 挂在管理面（JWT + mgScope），统一入口。

2. 五项观测能力

2.1 决策缓存工作台

接口说明
GET /api/v1/debug/cachedec/pset 键数 + 累计决策 + 命中率 + 键明细
POST /api/v1/debug/cache/clear清空 authz:dec:*（策略变更不生效时一键失效）

命中率 = 决策日志中 pep->>'from'='cache' 条数 / 总决策。缓存键值格式：1|pid1,pid2（allow）/ 0|（deny）。

2.2 鉴权指标面板

GET /api/v1/debug/metrics
{
  "summary": { "total": 461, "allow": 334, "deny": 127,
               "source_dist": {"cache": 12, "remote": 449},
               "p50": 1, "p90": 10, "p95": 17 },
  "trend": [ { "hour": "2026-08-12 07", "total": 28, "allow": 18, "deny": 10 } ],
  "top_actions": [ { "action": "cmdb:host:read", "count": 243 } ]
}

延迟百分位用「ORDER BY + LIMIT 偏移」近似；趋势按小时分组。

2.3 OpenFGA 数据面图谱

GET /api/v1/debug/ofga
{ "model_id": "...", "type_defs": [...], "types": [...], "total_tuples": 0, "by_type": [...] }

读取最近授权模型的 type 定义，并按资源类型分组读取全部关系元组（ReadTypeTuples）。

2.4 bundle 内容展开

策略分发记录（GET /api/v1/apps/:id/bundles）新增 policy_preview（前 20 条策略概要）与 force_remote（强制回源动作），前端「📦 内容」展开查看。

2.5 Owner 巡检视图

接口说明
GET /api/v1/debug/owners失联 owner（remind_count > 0）展开应用/owner/提醒次数
POST /api/v1/owner-check手动触发巡检

巡检规则：owner 最近 7 天无活动 → 提醒 +1；达 3 次无响应 → 应用自动停用 → 新 owner 认领恢复。解决「应用失管」问题。

4. 踩坑复盘

  • 趋势 SQL 类型不匹配：(? || ' hours')::interval 传 int 参数返回空 → 改用 interval '1 hour' * ?。
  • source_dist 丢行：GORM 把 SQL NULL 扫进 string 字段时静默丢弃整行 → 用 COALESCE + 累加（dist[k] += v），否则归一后的 434 会被真实 remote=2 覆盖。
  • 验证路径陷阱：PEP 接口是 /v1/authz/check（无 /api/v1 前缀）+ X-PEP-Token；curl 错路径 404 但被 > /dev/null 吞掉，误判缓存没写入。

5. 小结

观测的价值在于「让黑盒显性化」：决策缓存为什么命中、指标为什么波动、数据面关系长什么样、Owner 是否失管——都能在系统观测中一览无余。既是运维排障入口，也是学习演示的绝佳素材。
