# 能力包全生命周期 · 设计讨论（多轮）

> 状态：**讨论中（Round 1）**，未实施。用户已选 **方案 A（云原生企业蓝）** 作为前端风格，暂缓落地。
> 本文档沉淀能力包相关 6 个架构问题的讨论，每轮更新。

## 总体框架（6 问的串联）

四个层次，六问分属其中：

```
┌─────────────────────────────────────────────────┐
│ ① 声明层 Manifest  — 能力包"是什么/谁能用/谁可见"      │
│    Q1 申请主体限制 · Q4 可见范围 · Q5 网络/开通/鉴权声明   │
├─────────────────────────────────────────────────┤
│ ② 创作层 Authoring — 能力包"怎么写"                 │
│    Q2 表单化配置（取代手写 JSON）                    │
├─────────────────────────────────────────────────┤
│ ③ 执行层 Enforcement — 权限"怎么执行/怎么保护"         │
│    Q3 PEP 位置/身份传播/认证方式 · Q6 保护边界界定       │
├─────────────────────────────────────────────────┤
│ ④ 开通层 Provisioning — 审批通过后"怎么落地"           │
│    Q5 网络打通/安全组/工单/凭证签发                    │
└─────────────────────────────────────────────────┘
```

核心原则：**授权（Authorization）与开通（Provisioning）分离**。
IAM 只负责"许可决策"；网络打通、安全组、凭证签发是"落地动作"，通过工单/自动化完成，完成后才激活授权。

## Q1 · 能力包控制申请主体类型

**现状**：`CapabilityManifest` 无主体限制；任何用户/组/应用都可申请。系统已有主体类型（user / group / org / client M2M），鉴权层主体是字符串（`client:cloud-mgmt` 已可用）。

**业界参考**：
- AWS IAM：策略带 `Principal`（谁可以使用这条策略）
- GCP IAM：角色授予 principal（user / group / serviceAccount / domain）
- K8s RBAC：subjects = user / group / serviceAccount

**设计选项**：
- **A1（简单）**：manifest 加 `allowed_subject_types: [user, group, app]`（白名单，默认全开）。仅枚举级控制。
- **A2（加强）**：A1 + 条件（如 `allowed_org_paths`、仅特定 M2M client / 特定应用可申请）。

**关键区分**：**可申请性（Q1）≠ 可见性（Q4）**。两个独立策略维度，可组合：
> 例：某能力"运维部可见 + 仅 M2M 应用可申请"。

**待讨论**：
- "只允许应用申请"的典型场景是什么？（如云管只允许 M2M 申请）
- 申请主体是"应用本身（M2M）"还是"应用 owner（人）代理申请"？需要区分。

## Q2 · 表单化配置能力包声明文件

**现状**：纯 JSON API 创建/更新（`createCapability`），seed 程序化写入；已有 OpenAPI 推断预填（`syncCapabilities`）；前端 AppDetail 能力编辑是 P2 未完成项。

**业界参考**：Backstage catalog（YAML + 校验 + scaffolder）；API 管理平台（APIM/Kong）的表单向导；schema-driven form（react-jsonschema-form / Vue JSON schema form）。

**设计建议**：
- **双视图**：表单向导（默认，面向能力 owner）+ 原始 JSON/YAML（高级用户）。
- **向导步骤**（schema-driven，从 JSON Schema 自动生成表单）：
  1. 基本信息（名称/描述/数据模型/标签）
  2. 权限点选择（从已有 actions/模板勾选）
  3. 数据模型字段（model_fields）
  4. 数据范围定义（scope_definitions，即"申请表单的模板"）
  5. 权限组合预设（presets）
  6. 申请策略（Q1 主体限制 + Q4 可见性 + Q5 网络/开通/鉴权声明）
  7. 预览（市场卡片效果）+ 校验 + 发布
- **OpenAPI 导入**作为起点预填（已有基础，增强）。
- 版本 + diff（已有 version 概念，可加历史对比）。

**待讨论**：表单是第一优先级吗？（工程量最大）；是否需要 YAML 视图？

## Q3 · 拦截器位置 / 转发到中心 / 认证方式（核心）

**现状**：Traefik 网关 = PEP，`forwardAuth` 每请求转发 `iam-server /v1/gateway/check`；`X-PEP-Token` 共享密钥信任；`X-User` 业务身份头透传；agent bundle（Casbin 本地决策）为已规划的"进阶"（§5.7）。

### 3.1 拦截器位置（三选）
| 位置 | 侵入性 | 说明 |
|------|--------|------|
| **网关集中式**（现状） | 零（应用不变） | 所有流量过网关，网关建立身份 + 调 PDP。前提：应用必须入网关（→ Q6） |
| 应用内 SDK/中间件 | 高 | 应用改造，可保护不入网关的应用 |
| 边车/服务网格 | 低-中 | Istio/SPIFFE，身份在 TLS 层，需网格基建 |

### 3.2 "每一次都认证？"
拆开两个概念：
- **认证（你是谁）**：JWT 签名校验是无状态廉价操作，**每请求可接受**。
- **鉴权（能不能）**：可缓存 / 本地 bundle 决策；**高风险写操作强制远程**（现有 §5.7 已规划"force-remote"）。

### 3.3 "临时 token？接收方验证？有多少种方法？"
**身份传播模型对比**：
| 方法 | 说明 | 侵入性 | 强项 | 弱项 |
|------|------|--------|------|------|
| a. 共享密钥头（现状） | 网关注入 X-PEP-Token | 零 | 简单 | 弱，仅信任边界内，无每请求身份 |
| b. 网关统一校验 JWT | 网关验签+aud+exp，注入规范化身份头 | 零（应用不变） | 标准、无状态、可吊销（黑名单） | 需密钥轮换 |
| c. Opaque token + introspection | 网关每请求查 IdP 校验 | 零 | 强吊销 | 每请求 RTT，需缓存 |
| d. mTLS / SPIFFE | TLS 层 workload 身份 | 低-中 | 最强、零 token 处理 | 基建复杂 |
| e. 审批受限令牌（已有概念 §5.8） | 审批后签发 scope+TTL 令牌 | 应用配合 | 精确到能力/数据范围 | 需要应用侧或网关配合校验 |

**转发到中心的方式**：远程每请求（+缓存）/ 本地 bundle / 混合（读本地、写远程）——三种都已有设计。

**推荐组合**：网关默认 PEP + **JWT（b）** 作身份载体 + 高风险强制远程（§5.7）+ **审批受限令牌（e）** 作"能力级临时令牌"；mTLS/SPIFFE 为演进方向。

## Q4 · 能力包可见范围

**现状**：`marketplaceCapabilities` 返回全部 Published，无筛选。

**业界参考**：应用商店/目录可见性策略（Azure AD gallery、内部 catalog）；Backstage catalog rules。

**设计**：manifest 加 `visibility`：
- `public`（默认，发布即全可见）
- `org_paths`（仅指定组织可见，如"运维部"）
- `groups` / `apps`（仅指定组/应用可见）

市场查询按当前用户身份过滤；**owner 主动控制**（符合自服务/弱管理员哲学）。

**待讨论**：可见性由 owner 自主即可，还是需平台管理员审批发布？

## Q5 · 能力包携带网络/鉴权信息 + 审批阶段网络打通/工单

**现状**：无网络概念；审批流为内部模拟（ApprovalTask）；AccessRequest 有 items / approval chain / TTL / 理由。

**业界参考**：
- 多云/混合云 IAM：授权（许可）与资源开通（落地）分离
- 大厂内部：权限申请单自动带出申请方/提供方网络信息 → 转网络工单（防火墙/安全组/VPC peering）→ 打通后激活
- Vault 类凭证管理：授权通过后签发短期凭证

**设计（授权与开通分离）**：
1. **声明层**：
   - `App` 加 `network_info`：出站 CIDR、服务端点、region、负责人
   - `CapabilityManifest` 加 `provisioning`：开通要求（是否需网络打通/安全组/凭证）+ `auth_method`（JWT / mTLS / 共享密钥）
2. **申请层**：申请单自动附带**申请方（源）+ 提供方（目标）网络信息快照**
3. **审批层**：内部审批链通过 → 生成**工单**（demo 用模拟表；生产对接真实工单系统 webhook）
4. **开通层**：工单办理（人/自动化）→ 回调 → IAM **激活授权**（建策略 + OpenFGA tuple + 必要时签发凭证）

**"鉴权怎么办"（核心回答）**：
授权决策始终在 **IAM 令牌体系闭环**；网络打通是**前置条件/开通动作**而非鉴权本身。
- 受保护方网关校验调用方令牌（网关/PDP）
- 能力级凭证（如需）由 IAM 在开通后签发（= 审批受限令牌的落地形态）

**待讨论**：工单要对接真实系统还是 demo 模拟？鉴权倾向令牌（JWT/受限令牌）还是 mTLS？

## Q6 · 接入应用发布能力的能力 & 保护范围界定

**现状**：注册即可建能力（owner 门禁）；网关只保护 cmdb 一条路由。

**业界参考**：API 管理平台 onboarding（注册 + 路由接入后才被管理）；服务网格（入 mesh 才有 authz）。

**设计（enrollment 模型）**：
```
App 状态机： registered（注册=可申请/消费者）
          → onboarded（接入网关=被保护）→ active
```
- **只有 onboarded 的应用能发布能力**（你在我的保护范围内，我才能保证你的 API 被鉴权）。
- **未接入的应用只能申请能力**（消费者角色）。
- 能力发布时声明"网关保护路由"（路径前缀/域名），系统校验/生成网关配置。
- 保护范围**显式化、可审计**（受保护路由注册表）。

**与 Q3 绑定**：保护能力的前提 = 流量必须经过网关（网络拓扑约束）；无法入网关的应用需 SDK/边车备选（侵入性权衡）。

**争议点（需用户拍板）**：
- **严格**（必须入网关才能发布）vs **宽松**（自声明 + best effort）
- 出方向调用如何保护？→ 出方向由"对方网关"保护；IAM 管授权，拓扑管流量。

## Round 2 用户输入与收敛（2026-08-05）

### Q1 · 已收敛
- **典型场景**：cmdb 元数据只允许程序（M2M）增删改查；部分人员仅可查看（排查问题）。
- **双主体模型（关键）**：`grantee`（授权作用主体）= 应用/client（如 `client:cloud-mgmt`）；`applicant`（申请人）= 应用 owner（人代理，程序是死的）。请求单需区分这两个角色。
- **主体限制粒度**：不止能力包级，应到**预设（preset）/动作（action）级**——如"完整管理"预设 `grantee_types: [app]`、"只读查看"预设 `grantee_types: [user, app]`。
- 审批链：目标应用（能力提供方）owner 审批；申请人 ≠ 审批人（SoD 沿用）。

### Q2 · 已收敛
- 格式本身不重要（JSON/YAML 均可），核心是 **表单 ↔ 结构化配置（YAML/JSON）双向互转**。
- 用户给出 YAML 示例，结构与现有 `scope_definitions`（JSONMap）完全对应：
  - `type: select` + `source: api` + `api:`（选项来自 API）——需扩展现有静态选项/instance 两类
  - `type: expression` + `validation.pattern`（标签表达式+正则校验）
  - `type: instance`（复用现有实例选择器）
- 决策：**YAML 作为人可编辑的规范格式（canonical）**，DB 仍存 JSONB；后端 yaml.v3 ↔ JSON，前端 js-yaml；表单为默认 UX，原始 YAML 视图保留。向导第 6 步"申请策略"（Q1/Q4/Q5 声明）一并纳入。

### Q3 · 用户背景（重要）与我的建议
- **用户公司背景**：所有应用间访问都经过**公司安全网关**（前端→nginx 安全网关→EKS ingress→后端；后端间也如此）——这是公司级基础安全规范。但安全网关是基础网关，只能在上面"接入"有限能力，无法深度定制。
- **v1（用户所在期）**：自建 APISIX 网关，**每请求都在 IAM 认证** → 很重、性能差。
- **v2（用户离职后）**：应用自注册 → 别人申请能力 + 申请密钥 → 使用方先请求 IAM 拿临时 token → 调能力方，能力方验 token 有效期。优点：任意应用可接入；缺点：接入方都要改造（除非 IAM 提供常见后端 SDK，装即用）。
- **我的建议（详见对话）**：
  1. 认证（谁）与鉴权（能不能）解耦：JWT 无状态验签 = 廉价，每请求可接受；鉴权走缓存/本地 bundle，仅高风险写强制远程（治 v1 的痛）。
  2. **公司安全网关若支持 authz 钩子（ext-authz/forwardAuth）→ 把 IAM 作为外部鉴权后端接入公司网关**，全流量被保护且应用零改造（最佳形态）。
  3. 若不能 → 自建 IAM 网关（APISIX）部署在受保护应用前（v1 形态但做缓存优化）。
  4. v2 的"验有效期"偏弱 → 强化为 **JWT 验签（JWKS）+ audience + scope + 短 TTL**，高风险才 introspection；能力级临时令牌 = 审批受限令牌落地。
  5. SDK 作为任意应用接入的通道（thin SDK：验签 + 调 PDP 或嵌 bundle）。

### Q4 · 已定案（无争议）
- 完全 owner 控制；管理员是程序员，无法判断业务应用权限逻辑。manifest 定义"谁能看到、谁能申请"。
- 可申请性（Q1 grantee_types）≠ 可见性（Q4 visibility），两套独立策略。

### Q5 · 用户痛点与我的建议
- **v2 真实痛点**：申请了权限仍不通 → 找发布方问网络信息 → 打通 → 测试 → 鉴权不过 → 再拿 token → 重试。流程不透明、费事。
- 用户三个子选项：① 申请能力包前必须先申请网络打通工单（前置判断太多太麻烦）② 每次申请能力包都走网络工单（已打通也走，繁琐）③ 用户自己选择是否网络打通。
- **我的建议：基于"网络依赖自动判定"的中间态**（详见对话）：
  - App 预声明 `network_info`（出站 CIDR/端点/region/负责人）
  - 能力包声明 `network_requirements`（是否要求申请方网络已放行：源 CIDR 白名单/安全组/VPC peering/出站白名单）
  - 申请时**系统自动比对**：申请方声明的 CIDR 是否已满足提供方要求 → 已满足=网络就绪（不产生工单）；未满足=自动生成网络工单（自动附带源/目标网络信息快照）
  - 工单生命周期：`pending → processing(外部) → done`，done 回调 → IAM 激活授权
  - 前端：能力申请流中"网络打通"节点标记为外部工单，可点击/悬停模拟外部审批流
  - 授权与开通分离：网络是前置条件；鉴权始终在 IAM 令牌体系闭环

### Q6 · 已收敛为"双层接入模型"
- v1 = onboarding（网关）；v2 = 任意接入+临时 token（接入方重）。用户问：支持两种？严格/宽松取决于接入能力。
- **我的建议：严格管"保护必须存在"，宽松管"保护方式"**：
  - **Tier 1 网关托管**（受保护应用入 IAM 网关，零改造）→ 可发布能力
  - **Tier 2 SDK 自接入**（不入网关，装 SDK 验签）→ 可发布能力
  - **发布能力的前提 = 至少有一条强制路径**（网关 or SDK），manifest 声明 `enforcement_mode`。未接入任何强制路径的应用只能申请（消费者）。
  - 这同时回答了 Q3 的"SDK 要不要"：Tier 2 就是 SDK 通道。

## Round 3 用户澄清（2026-08-05）

### Q1 修正
- 我的"写操作只给程序、读给人"只是 cmdb 的例子，**不是规则**。主体限制必须**自由可定制、分层**——另一个应用完全可以"完整管理也可以给人"。
- 结论：`grantee_types` 是**owner 在声明文件里自由配置**的（能力包级默认 + 预设/动作级可覆盖），默认宽松，无硬编码。

### Q3 澄清
- 用户 v1 的真实做法：**JWT 认证在网关级别**，鉴权转发 IAM，**只是每次请求都转发**（重在这里）。
- 结论：痛点 = 每请求远程鉴权；解法 = 决策缓存 + 本地 bundle（读本地）+ 高风险写强制远程（§5.7），与之前分析一致。
- **放弃"接公司安全网关"路线**：公司多业务线各自为政无法全局控制，且系统要用于面试讲解，"全公司"范围太大说不清。
- **真实服务范围**：效能部门（3 小组）+ 兄弟运维部门若干小组。内部三小组都没统一网关（只有用户小组接了统一网关），运维部门开发能力弱（只做小应用）但也想接入。
- **结论：双模式（Tier 1 网关接入 / Tier 2 程序级接入=SDK）确认**。

### Q5 澄清
- 用户对"网络依赖自动判定"的实现存疑：**如何判断网络可达？需要双方提供什么信息/能力？**
- 结论：需要在 v6 demo 中把"判定逻辑"可视化表达清楚（申请方出站 CIDR/端点 vs 提供方放行规则/安全组/peering），并展示工单模拟。

## Round 4 用户反馈与收敛（2026-08-05）

### Q5 简化（网络依赖检查 → 网络信息声明）
- **不做网络可达性检查**（用户认同复杂度后放弃自动判定）。
- 要求**接入方（提供方）声明尽可能详细的网络信息**：所属云 / 账号 / 区域 / VPC / 子网 / 安全组 / 所属容器（主机或 EKS 等）/ 通信测试接口（无鉴权只返回状态）。由接入方自行判断。
- **网络打通工单加开关**：能力包配置 `network_ticket: none | user_choice | always`，申请时用户自行选择（推荐 user_choice）。

### Q2 入口改为"应用"
- **应用为中心**：点应用 → 接口树 + 数据模型（OpenAPI 同步元数据，owner 可核对同步结果）→ 该应用下能力包（草稿/待发布/已发布）。
- 权限市场同理：按应用浏览 → 点应用看已发布能力 → 申请。

### 数据级控制开关（新）
- 能力包配置 `data_control: true|false`。**false = 所选接口访问全部数据**（大多数应用场景，如 ITSM 自身有 assignee 分配人逻辑，开通"待办理"接口即可看到自己待办）。
- 能力表单需**尽可能自由、灵活、可配置**。

### 可见性 vs 可申请性（定案）
- **默认"都能看见、限制申请"**（public 可见 + 预设级 org_restrict 限制可申请），同时支持 `hidden` 隐身（敏感能力仅白名单/直链）。
- 关键：**同一能力包内多个预设**覆盖不同诉求——如"数据库管理"能力含"DBA 管理"预设（org_restrict=[DBA组]）+ "数据库查看"预设（全员可申请），小黄能申请查看、无需单独发能力。
- 被拒时给**友好提示 + 推荐可申请替代**。
