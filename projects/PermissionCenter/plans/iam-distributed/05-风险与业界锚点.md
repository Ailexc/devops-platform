# 05 · 风险登记册与业界锚点（防意淫专章）

> 本章就是你说的"对抗自己"的部分：每个设计点找业界出处（有据可查）+ 风险如实登记 + 纯理想化自检问答。

## 1. 业界锚点表（每件都有出处——是组装不是发明）

| 我们的设计 | 业界对应物 | 出处/说明 | 锚定强度 |
|---|---|---|---|
| 旁挂 Agent + bundle 本地判 | **OPA sidecar + policy bundle** | OPA 官方主打形态；Envoy ext_authz 同族 | 强（同款） |
| 策略按 app 切分分发 | OPA bundle 按 namespace/service 切 | 同上 | 强 |
| last-known-good / fail-closed | OPA/Envoy 策略加载失败语义 | 业内默认 | 强 |
| 判定数据自治（不探活业务） | **Google Zanzibar**（授权数据自维护）、AWS IAM 最终一致 | 论文/官方文档 | 强 |
| 声明驱动取材（QueryDecl） | **XACML PIP**（策略信息点）、AWS Cedar 实体按需拉取 | 访问控制标准架构 | 强 |
| 统一 SDK/客户端强制 | **Google 内部 Zanzibar 生态**（强制统一 client） | 大厂内部实践（我们能学因为它=企业内部） | 强 |
| 数据契约/查询接口声明 | Data Contract 运动、SCIM meta.lastModified | 清单 A2 对标表 | 中（体系级） |
| 发布门禁+试算自检 | 算不出指纹→拒+出路（我们既有 A2）+ 业内 schema registry 兼容性检查 | Kafka Schema Registry 试写校验同思路 | 中 |
| 网关只认证（认证/授权分离） | OAuth2/OIDC 网关模式、Zanzibar 客户端侧判定 | 认证在网关、授权在判定点 | 强 |
| 撤销传播窗口三道兜底 | K8s failurePolicy、短时效令牌（AWS STS）、force-remote=同步刷新语义 | 清单附录二八行表 | 强 |
| 防绕过三层（SDK+审计+审阅） | Spring Security 生态常态 + Google 内部强制 + DB RLS 备用 | 无完美解是共识 | 强 |
| 契约测试套件 | OAuth/OIDC 一致性测试 | 生态标准做法 | 强 |

**结论**：没有一件是"凭空"；组合（六件套闭环）是我们的集成设计——**创新点在组合与门禁的严谨度，不在零件**。

## 2. 风险登记册（S/M/L）

| 级 | 风险 | 缓解 | 状态 |
|---|---|---|---|
| **S** | Agent 数据级求值是**未开发**能力（P2 是本轮最大工程） | 契约测试 6 条 + 试点先行（P4 只接一个 Django） | 排期 10d，验收硬 |
| **S** | 试点被绕过（业务直连数据层不走 SDK） | 三层防线（统一 SDK/审计归因/审阅）+ 绕过=审计可见（有判定无日志一眼穿）；DB 行级安全备用 | 接受为已知边界（enforcement 物理上无法完全中心化）|

| L | 关系式范围边缘不判（预留形态） | 明确回源语义，无 UI 入口不产生 | 边界表 |

## 3. 纯理想化自检问答（"这套是不是意淫"压力测试）

**Q1：业界有没有完整这样玩的？** ——没有单个产品端出六件套闭环（开源无法强制用户装 SDK）；但每件都有强锚点（§1），且 Google 内部 Zanzibar 生态 = "统一 client+中心规则+边缘判定"的完整先例——**我们是在复制"大厂内部玩法"而非发明**。组合的合法性来自：企业内部可强制契约（这是开源产品没有的条件）。

**Q2：是不是为了自圆其说在硬凑？** ——检验法：每个设计对应一个已发生的真实痛点（老系统直查扇出/自循环/中心 QPS/投影新鲜度税），且删掉它痛点回来。逐件可回溯（README 叙事弧线）。

**Q3：工程量吹小了吗？** ——最大件是 Agent 数据级求值（P2 估 10d）+ SDK core（P3 估 10d）；合计 47d 对一人全职 9-10 周——**不便宜**，但 P1-P3 并行可压 7 周。若估时砍半才可接受，说明还在意淫区。

**Q4：哪天不成立？** ——三条件任一破即退化：企业强制力失效（外包/外部接入方多）→ 退化为自愿集成+审计；数据不可控且跨源聚合多 → 投影回主路径；发布方数量爆炸门禁成瓶颈 → 门禁自动化压力（试算引擎要扛）。

**Q5：为什么不用现成的（OPA/Keycloak）？** ——OPA 只有分发没治理生命周期（申请/审批/到期/审计）；Keycloak 只有认证+粗授权没数据级；我们要的"能力包+数据契约+门禁+定制需求卡"是 IGA 治理层，恰好是它们的空白——**这也是老系统立项动机的延续**。

**Q6：最弱证据支撑的最大结论是什么？** ——"零侵入接入"（说满即翻车）：准确表述是"业务代码零权限逻辑、接入动作=壳配置+声明填写"；接入壳本身仍是改动（部署文件+中间件挂载），按"最小侵入"表述。

**Q7：Demo 与叙事的差距？** ——Demo 现状=中心侧全部实装（A 层+同步加固），Agent 数据级/SDK/门禁是【设计定稿】——面试按 04 的边界表说，不越线。
