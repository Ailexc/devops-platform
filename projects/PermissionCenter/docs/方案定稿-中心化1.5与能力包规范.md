# 权限中心 1.5 方案定稿：中心化判定 + 通用点查约定（含能力包与预设规范）

> **版本**：v1.0（2026-10-03 定稿）｜ **来源**：中心化 vs 分布式多轮技术讨论收敛
> **性质**：方案定稿 + 规范成文——接手续接"中心化现状实装"，停掉投影扩张，2.0 分布式方案降为演进项
> **口径纪律**：每项标注【已实装】/【待小改】/【待成文】/【演进项】，面试表述以 §10 边界表为准

---

## 0. 一段话说清这个方案

> **中心化判定 + 点查自足**：网关拦接口级，**点操作（资源 ID 在 URL 里）连数据级也走网关链路即判**——中心按【通用点查约定】自取判定材料（每系统注册一次，不进能力包），**业务零配合**；剩余仅两处轻回调（列表过滤、创建参数校验各一次调用）+ 工单型写操作的执行侧收口。投影停在 CMDB 存量不扩张；**不引入 SDK、不引入分布式 Agent**（2.0 降为演进项，贴合真实工作量级）。能力包规范 = 五区块配置 + 预设场景（参数联动/层级编排）+ 从属三判据 + 黑白名单 + 多包申请 + 门禁三道。
> 一句话判据（贯穿全文）：**判定材料决定判定点**——点操作的判定点在网关链路、材料由中心自取，"行哪来"被结构性消灭。

## 1. 决策记录（为什么走到这一步）

### 1.1 三代演进

| 代 | 形态 | 病/痛 | 结局 |
|---|---|---|---|
| **老权限中心 1.0** | 中心化但**全量扇出**：判一次权限实时去上游/各家查一圈 | 性能差=程序间调用爆炸（不是中心化的锅）；只能"整模型放权 or 逐条勾选"，**无中间态** | 被重构 |
| **本系统 1.x（现状实装）** | 中心化 + **投影**（CMDB 判定字段投进中心）+ 确认制时钟三档 | 数据膨胀治了（只投判定字段），但**供数结构还在**：新应用数据在自己库就投不了（"上帝视角"前提） | **保留，投影停扩** |
| **2.0 分布式**（plans/iam-distributed） | 判定下沉业务侧：SDK+Agent+bundle | 撤销窗口/防绕过/工程量 51d/无实战；钩子拦不到"编辑=发工单"型副作用 | **降为演进项**（§7） |
| **1.5 定稿（本文）** | 中心化判定 + **通用点查约定** | —— | ✅ 本轮方案 |

### 1.2 三个关键决策

1. **走中心化**：请求量论（企业内部：多云管理+工单，量级不大——老系统差劲是扇出架构病不是中心化病）+ 时间紧 + 叙事稳（连续追问每条有成文答案）；
2. **投影停扩**：投影只配得上"数据天然集中"的场景（CMDB 共享权威源，多方访问同一批数据，税只付一次）；数据散在各业务库的场景，投影=上帝视角（老系统"全量灌库"同款结构），**停扩、存量保留**；
3. **2.0 降级**：企业强制力是它的成立前提、工程量大、无实战——记为演进项，其合理内核（**通用点查、fetch-and-bring**）被 1.5 吸收，其 SDK/Agent 本体不实施（语义守卫仅留极端场景备用）。

### 1.3 核心判据：判定材料决定判定点

| | 判定材料 | 材料来源 | 判定点 | 痛点 |
|---|---|---|---|---|
| 老 1.0（模型级+勾选） | 身份+动作+模型/实例ID | **请求自带** | 网关/中心，稳 | 无（但无条件式的灵活） |
| **条件式**（新增能力） | 多一样：**行属性**（account/owner…） | 请求里没有 | **被迫漂移到能看见行的地方** | 所有痛的根源：投影税（1.x）/ 语义守卫（SDK）/ 本地判（2.0）——**三套方案本质都在回答"行给谁、谁去拿"** |

**条件式的爽与痛是同一枚硬币**：换来区域授权的中间态（整模型放权 vs 逐条勾选之间唯一灵活档），代价=判定点跟着材料走。SDK/点查不是凭空负担，是这个能力的对价。

### 1.4 真实接入边界（工作实况——面试如实讲）

- **权限中心的管辖范围 = 内部网关体系**：我们这套接入了统一网关、管理体系、流量体系的**内部系统**（多云管理、工单、事件、认证等）——判定收口在网关 + 中心，这就是它的全部地盘；
- **发布系统的例外（真实案例）**：它来自**其他团队/小组**，转过来时**自带一套权限管理**；我接手时只做了**升级（改造成 ABAC 形式）**，**没有并入这一套**——当时进度紧、没做大改，就这样了。它技术上能不能接？**能**（接入=网关配置级），但工作场景下没必要为接而接；
- **面试讲法**："权限中心管的是内部这一套（接网关的）；发布系统是后来转来的，带着自有权限，我给它升级到 ABAC 就没再动——不是技术上接不进，是当时没有动它的必要，硬接反而引入变更风险。"——**贴合真实工作，不假大空，反而经得起追问**。

## 2. 目标架构

```
用户/程序请求
  │
  ▼
[网关] 接口级物理拦截（零业务配合）
  · JWT 认证 + 身份注入；forwardAuth 判"能否调此接口"（动作码级）
  · 保留流量防护（防爆破/TLS——免鉴权≠免防护）
  │
  ▼
[业务应用]（**点操作零配合**——网关链路已判完；仅两处轻回调）
  │  列表：候选行带回 / 或应用返回的范围条件（一次 filter 调用）
  │  创建：请求参数即"未来的行"（一次参数校验调用）
  │  工单型写操作：执行侧收口（本来就归执行器）
  ▼
[权限中心 · 数据级判定]（纯函数，零投影扩张）
  · 点操作材料：中心按通用点查约定自取（网关从路径提取 model+id）——业务不供材
  · 列表/创建材料：业务回调时带了就用带的，没带中心点查
  · 判定：动作策略 × 各域范围谓词（条件/集合/全量）× deny-overrides
  · CMDB 存量投影保留为取材快捷档（已实装）；新域一律走点查约定
  · 策略生命周期（申请/审批/版本/TTL回收/审计/能力包门禁）——中心不可替代的核心
```

**取材与发起的一条规则**：**点操作=网关链路发起、中心点查自足（业务零配合）；列表/创建=业务一次轻回调（带了就用带的，没带中心点查）**——点查读的就是实时行，**无新鲜度税**。

## 3. 通用点查约定（本方案核心新增——"编辑删除行哪来"的答案）

### 3.1 约定内容

```
应用注册时配一次（系统级，不进能力包）：
  ├── 查询语义：按 (model, resource_id) 返回该行
  │     POST {系统内部地址}/__perm/query   （或 GET /{model}/{id}，系统自定）
  │     body: { model: "disk", id: "d-500" }  →  { row: {account:123, host_id:...} }
  ├── 模型白名单：只允许已登记数据契约的域（防"查任意表"越权）
  ├── 独立凭证：M2M 只读、仅此用途、不上能力市场、不给用户走
  ├── 网络/豁免：路由进网关与 SDK 豁免清单（防递归），审计留痕
  └── 能力包/数据契约侧只登记【判定要哪几个字段】（fields，现契约字段不变）
```

**配置位置的规范修正**：查询约定是**应用注册**的一部分（一系统一约定），**不是能力包的字段**——包只管"哪些域、什么范围"，"怎么取行"归应用注册。

### 3.2 取材流水线（中心视角）

```
数据级判定请求
 ├─ 请求里带了行属性（fetch-and-bring）→ 直接验谓词 → 完
 └─ 没带（编辑/删除典型）→ 查应用注册表得约定 → 按 (model, id) 点查
      ├─ 查到 → 挑 fields → 验谓词 → allow/deny（行用完即丢，不落库）
      ├─ 查不到该行 → deny reason=data_missing（fail-closed）
      └─ 点查失败（应用挂）→ deny/降级（对称依赖，见 3.3）
```

### 3.3 两笔账（如实）

| 账 | 结论 |
|---|---|
| **可用性** | 中心→应用点查 vs 应用→中心判定：**写操作本来就有这个依赖**（应用挂了编辑也做不了）——对称依赖，不新增风险；对比老系统"判 CMDB 权限问 CMDB 拿人数据"的全域自循环，这是写操作的必然链路，不算耦合病 |
| **安全** | 通用接口=凭证可读任何行（白名单内）——"开自己家门给自己人"前提下可接受，**白名单+只读+审计三件不能省**（这是省事方案唯一付的规范成本） |

### 3.4 业内锚点

XACML PIP 的 HTTP 属性源（判定方按登记的属性源取材——本约定是它的标准化单点变体）；k8s/云厂商 Describe API（内部服务按 ID 取资源描述是标准习惯，此处立为对权限中心的专用通道）；AWS "服务必须调 IAM"的镜像（那边 IAM 在服务侧被调，这边中心按约定回调服务）。

### 3.5 谁发起判定——点操作为什么业务零配合

资源 ID 在 URL 里的查/改/删（REST 主流形态），**网关链路全程判完，业务一行代码不写**：

```
PATCH /disks/d-500
  → 网关 forwardAuth 回调中心（接口级回调，链路现成）
  → 中心路由表（OpenAPI 生成）得动作码 cmdb:disk:edit + 从路径提取 (model=disk, id=d-500)
  → 按通用点查约定回调应用取 d-500 行 → 验谓词（account==123?）
  → 2xx 放行 / 403 拒
```

网关本来就在这条链上（接口级回调现成），数据级等于**顺带多判一步**（多一次中心→应用点查，索引命中 ms 级）。**需要业务配合的只剩三处、且都是轻量级**：列表（行过滤网关改不了响应体，一次 filter 回调）、创建（条件校验看请求体，一次参数校验回调）、工单型（执行侧收口）——**不存在 SDK 植入、不存在中间件改造**，配合面比业内"服务必须调 IAM"还小。

### 3.6 点查缓存（可选优化——量级需要再上）

中心侧可对 `(app, model, id) → 行` 加**短 TTL 缓存**（秒级，如 5s）：

- **收益**：详情页反复编辑、热点行判定少一跳点查（点操作高频场景的唯一延迟点）；
- **代价（如实）**：重新引入一个**微缩新鲜度窗口**——正是点查甩掉的那张税的回归；
- **决策：默认不缓存**；出现真实热点（点查耗时进 SLA 红线）再加，且 TTL 必须秒级 + 可关 + 决策日志标注材料来自缓存（审计能区分"实时行 vs 秒级缓存行"）；
- **写后失效不做**（复杂度不配收益）——靠 TTL 自然过期，**最大陈旧度 = TTL**。

## 4. 能力包与预设规范（包规范成文——本节是主交付）

### 4.1 配置页五区块（必填标 ★，配置页=规范主载体）

```
┌─ 能力包发布 ·「主机管理」─────────────────────────────┐
│ ① 基本信息   名称★ / 所属应用★ / 关联 OpenAPI          │
│ ② 能力点（接口维度）★ 按板块分组：主机查改删/下钻、磁盘、   │
│    网口、判断类接口（如"密码按钮可见"）——想给就勾          │
│ ③ 数据范围（数据维度）★ 逐数据域一个范围选择器：           │
│    host: ○全量 ●条件{account=123} ○勾选实例 ○自己的      │
│    disk:（层级/联动自动带出，见 4.2）                    │
│ ④ 数据契约 ★条件触发：任一域选条件式才弹——判定字段/SLA     │
│ ⑤ 自检与发布：四问自检 → [发布] → 门禁三道自动跑          │
└──────────────────────────────────────────────────────┘
```

**条件必填逻辑**：勾数据级 → ③必填；任一域条件式 → ④该域必填；纯接口包 → ③④隐藏（合法）。

### 4.2 预设 = 场景（含两项升级设计）

**现状【已实装】**：预设 = 包内的场景化方案（查看/管理/最小授权……），每预设含 `{name, status(draft/published·独立上下架), interfaces(勾选动作), grantee_types, apply_scope, data_control, data_models}`；申请时选预设 → 填范围 → 生成判定表达式（demo 场景 14/15 全链可演）。

**升级一：参数联动【待小改】——防"host 选 123、disk 选 456"错位**

```
预设「主机管理·123」声明场景参数 {account}
  host 域条件 {account: $param}   ← 申请时只选一次 account=123
  disk 域条件 {account: $param}   ← 同一参数带出全域，结构上不可能错位
（预设配置项：共享参数=联动模式 / 各域独立=独立模式——真独立的域才允许独立选）
```
判定层不假设域间一致（各域独立判定是合法的），联动纯粹是**申请体验的防错**。

**升级二：层级编排【待小改】——data_models 从平面数组升级为树**

```
预设 data_models 树：
  host（account=123）
    └─ disk（随 host：从属条件）   ← Markdown 缩进式声明层级
      └─ nic（随 host）
· 向导层：层级=联动（选父域范围，从属子域自动带出）
· 落底层：各域仍是【独立策略】——层级是编排不是存储结构
· 跨出层级（管其他账号的磁盘）→ 不在树里 → 单独申请
```

### 4.3 从属三判据（"什么情况可以从属"判死）

1. **从属事实必须在子行字段上**（`disk.host_id` / `disk.account` 行属性）→ 可用从属条件式 `{field: host_id, op: in, value: …}` 一条策略覆盖一族（单行点查可验）；
2. **必须显式声明**：发布方勾子域 + 写谓词，**系统零推导**（没有"主机有权限自动算磁盘有权限"）；
3. **缺字段/表达不了 → 禁止从属，单独授权**——不许硬凑。CMDB 建模若无从属字段，**数据建模加冗余字段**（一行字段换一条简单谓词）是本方案的隐藏依赖。

**包永远只有接口×数据两维度**——关联/下钻/整体感全部由两维度勾选组合 + 条件式表达；从属不另设机制（行有字段→条件式；是人的集合→组；真关系图→关系式预留）。

### 4.4 黑白名单

| 语义 | 机制 | 状态 |
|---|---|---|
| 白名单（默认） | deny-by-default + allow 策略 = 系统底色 | 【已实装】 |
| "直接放行" | allow 策略条目 | 【已实装】 |
| **黑名单（显式禁止）** | **effect=deny 策略** → 构建物化 deny 规则 → Casbin **deny-overrides**（`allow && !deny`：任一 deny 命中，再多 allow 也拒） | 【已实装】UI 直授可选、builder、model.conf 三处实证 |

**deny 治理规范【待成文】**（能力有、规矩没有）：deny 必须比被禁 allow 更精确（防宽 deny 全局误伤）；走同一审批链；配额+审计。deny 演示样例【待补】进 demo。

### 4.5 包边界正反表 + 四问自检

**能进包**：多数据域的接口清单 × 各域范围；下钻（显式勾子域接口+范围，整包申请=用起来像整体、落库每条可指认）；判断类接口（动作级）。

**不能进包**：

| 禁 | 为什么 | 替代 |
|---|---|---|
| 隐式推导（主机有→磁盘有） | 判多温床，审计指不出记录 | 显式勾子域 / 从属条件式 |
| 跨源聚合条件（成本>1000 才看） | 业务逻辑塞不进能力包（包只装**资源元数据维度**范围） | 出圈，不支持 |
| 关系式判定 | 材料在中心关系图，预留无入口 | 组/条件式 |
| 聚合接口判定（count/sum 非行） | rows 模型套不上 | 默认拒+显式声明改写 |

**四问自检**（发布方填包照答 + 门禁复核）：引用了哪几个数据域？每域什么范围形态？条件式的域字段在行上吗（契约 fields）？下钻子域/模型勾全了吗？

### 4.6 组合自由度三件套（明确不搞包嵌套）

| 需求 | 方案 | 状态 |
|---|---|---|
| 包内多方案 | **预设**（多套勾选组合，申请时选） | 【已实装】 |
| 跨包组合（主机+安全组+子网） | **多包一次性申请**：申请页多选 N 包 → 单一审批视图 → 批量开通 + 关联推荐（推荐非依赖） | 【待小改】 |
| 组合不到的缺口 | **定制需求卡**（owner 直授/补包，A8） | 【已实装】 |

**为什么不做链式/嵌套（包引用包）**：引用图→循环引用、版本传播、影响面递归爆炸；**包是发布方的策展单元（分发时展开成原子策略），组合是申请方的选择权**——组合发生在申请时，不发生在包结构里。**包粒度原则 = 能力域**（主机/安全组/子网各一包；大而全包 → 一系统一包+堆预设 → 包失去策展意义）。

### 4.7 发布门禁三道（机器强制，声明不合格挡在发布期）

| 门 | 校验 | 不过 |
|---|---|---|
| ① schema 完整性 | 范围/契约必填项齐 | 拒发 |
| ② **试算自检** | 条件式域真取一次行（现契约=指纹试算；1.5=点查试取） | 不可算→400 拒+出路（降接口级）；不可达→502 重试 |
| ③ 语义档位 | 声称数据级无契约/条件字段不在行上/名单超限（500，治理阈值） | 拒或降级接口级 |

**规范三层载体**：配置页条件必填（②引导）+ 门禁代码（①兜底强制）+ 边界文档（③解释）——**能强制的绝不靠自觉，文字只解释不承担强制**。

## 5. 接入与拦截（贴合真实：不搞 SDK、不搞 Agent）

**本方案明确不实施 SDK 与分布式 Agent**——点查自足后，需要业务配合的只剩两处"一次 API 调用"级的轻回调，不构成引入 SDK 的理由（2.0 的 SDK/Agent 设计保留作演进项参考，见 §7）。

### 5.1 三处配合面（全集，就这些）

| # | 场景 | 配合形态 | 量 |
|---|---|---|---|
| 1 | **点操作（查/改/删，ID 在 URL）** | **零配合**——网关链路判完，中心点查自足（§3.5） | 无 |
| 2 | **列表** | 一次 `filter` 回调（候选行带回 或 应用返回的范围条件） | 一次调用 |
| 3 | **创建** | 一次参数校验回调（请求参数即"未来的行"） | 一次调用 |

（工单型写操作第四处 = 执行侧收口，本来就归执行器，不算对业务的新增配合。）

### 5.2 拦截分层四道（"业务不配合怎么办"的标准答案）

| 层 | 拦什么 | 需要业务配合？ | 状态 |
|---|---|---|---|
| ① 网关 | **接口级 + 点操作数据级**——请求进不了业务 | **不需要（物理在路径上）** | 【已实装】接口级；点数据级【待小改】（中心路由表提取路径参数） |
| ② 业务轻回调 | 列表行过滤、创建参数 | **需要——但只是一次 API 调用**（无 SDK 无改造） | 设计定稿 |
| ③ 数据层（DB 行级安全/SQL 网关） | 数据级绝对拦截——SQL 自动过滤 | 不需要（物理强制） | 重手段备用 |
| ④ 执行侧（工单任务平台执行前判） | 队列型写操作最终防线 | 执行器配合（本来就归它） | 【已实装】 |

**面试口径**："点操作网关全包（ID 在 URL 里，中心点查取材，业务零配合）；列表和创建各一次轻回调；真正的强制面在网关——绕过网关直连业务的流量，接口级和点操作数据级根本进不来。我们不承诺防住铁了心绕过网关直连数据库的代码，承诺**绕过必留痕、留痕必被审出**。"

## 6. 完整场景走查（编辑磁盘 d-500，账号 123 授权）

```
申请期：选包「主机管理」→ 预设「管理·123」→ 参数 account=123 选一次
        → 层级带出 host+disk 域 → 各域范围落成独立策略（host{account=123}, disk{account=123}）

运行期：
  ① PATCH /disks/d-500
  ② 网关 forwardAuth → 中心：路由表得 cmdb:disk:edit + 路径提取 (disk, d-500)
  ③ 中心点查 d-500（按 (cmdb,disk) 约定）→ disk.account==123？ → ✅ → 2xx
       · 属账号 456 → account≠123 → 403（各域独立判定；防错位靠预设联动）
  ④ 业务收到放行请求 → 落库（业务全程零权限代码）
  ⑤ 兜底：绕过网关直连业务 = 进不了正常链路；工单型写操作在执行侧另判
```

**动作码锚定数据域**（复述钉死）：`cmdb:disk:edit` → model=disk → 契约 (cmdb,disk) → **disk 自己的取材路径**——从不"拿主机接口查磁盘"。

## 7. 与 2.0 的关系（演进项定位）

- 2.0（`plans/iam-distributed/`，六文件+对抗审查修订）**保留为演进项，本方案不实施其 SDK 与分布式 Agent**——点查自足把配合面缩到两处轻回调后，SDK/Agent 的存在理由（低侵入材料供给）已被消解；
- 其被 1.5 吸收的部分：**通用点查**（比 2.0 的按域 QueryDecl 更简，一系统一约定）、fetch-and-bring（业务回调顺带带材料）；其"语义守卫/SDK 中间件"仅作为"目标不在 URL 里"的极端场景备用手段记录，不排期；
- 其已知边界如实记录：ORM 钩子拦不到"编辑=发工单"型副作用（1.5 下工单型由执行侧收口，天然覆盖）；撤销传播窗口是分布式固有代价（1.5 中心化即时撤销反而更优）。

## 10. 面试叙事与边界表

**三段弧线**："老系统 = 中心化做成了全量扇出（性能病）→ 重构 = 中心化判定 + 投影（治了数据膨胀，但供数结构有前提）→ 1.5 = **投影停扩 + 通用点查**（中心判定、材料就近供给、判定字段随契约登记）——判定集中（叙事稳/审计无损/即时撤销），数据零汇聚（无上帝视角/无新鲜度税扩张）。"

**边界表（说/不说）**：

| 说 | 不说 |
|---|---|
| "条件式的判定点跟着材料走，三套方案都是在回答材料问题" | 不说"某一套是唯一正解" |
| "投影停在共享权威源存量，新域走点查" | 不说"投影全删"（CMDB 存量在跑） |
| "点操作零配合（网关+点查自足），列表/创建各一次轻回调；绕过网关直连=进不了正常链路" | 不说"业务零改造全覆盖"（两处轻回调如实讲）；不说"技术上绝对防绕过" |
| "发布系统自带权限、仅升级 ABAC 未并入——进度紧且无必要" | 不说"全部系统已接入"；不说"接不进"（是没接的必要） |
| "黑名单 deny-overrides 已实装，治理规范在补" | 不说"黑白名单体系已完善" |
| "2.0 是演进项，吸收了它的 SDK 与点查" | 不说"已实施分布式" |
| "零 X 类词带范围限定"（core 零系统知识/业务零权限逻辑） | 不裸说"零侵入/零风险" |

**一句话收束**：**判定跟着材料走、材料就近供给（带了就用带的，没带就点查）、包是策展预设是场景、组合在申请侧、门禁挡不合格、强制靠组织**——这套就是 1.5。
