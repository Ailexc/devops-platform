# 兜底接入规范（业务轻回调：列表 filter + 创建带体调用）

> 版本：v1.0（2026-10-17）｜状态：已成文；带体调用【已实装 T2】，filter 回调【契约定稿，档 c 启用时实装】
> 权威源：方案 §5.1 配合面账目 / §5.2 判定两步 / §5.3 拦截分层②｜适用：内部接入面的历史系统与边角场景

## 0. 先定位：什么时候需要本文档的契约

**主路永远优先**——绝大多数接入根本不需要业务回调：

| 场景 | 主路 | 业务配合 |
|---|---|---|
| 点操作（id 在 URL） | 网关链路即判，中心点查自足 | **零** |
| 列表（维度翻得成 query 参数，档 b） | 判定两步：中心从 X-Forwarded-Uri 读参做缺参拒/子集校验 | **零**（前端强制携带是一次性改造，非运行期） |
| **创建 / 存量 body-id** | — | **一次带体调用/接口**（§本文 §2，已实装） |
| **列表兜底（档 c：维度翻不成查询参数/无契约）** | — | **一次 filter 回调/列表接口**（§本文 §3，契约定稿） |

**总原则：谁持有请求，谁抠材料**。判定永远在中心（PDP），但材料（id/信封/范围参数）在请求里——请求在谁手里，谁负责把它抠出来送到判定点。与 V1 SDK/中间件示例是**同一逻辑的两种形态**：V1=代码贴中间件代抠；兜底=业务在现有代码里加**一处调用点**代抠（无 SDK、非中间件改造）。

## 1. 三不原则（防过度接入）

1. **不引入 SDK/Agent**：内部接入面不发 SDK、不部署 Agent——配合形态只有"一处调用点"
2. **不做语义守卫**：中心不猜业务语义；业务不实现权限逻辑——业务只负责"把材料带到判定点"
3. **不搞对抗性设计**：内部自用，规范+门禁+契约测试到位即可；防绕网关=网内端口收敛+日志缺口对账（§5.2 诚实边界），不做渗透级对抗

## 2. 带体调用契约【已实装】（创建 / 存量 body-id）

**什么时候用**：材料在请求体里、网关链路拿不到（Traefik forwardAuth 不转发 body；APISIX 链内插件形态则业务仍零调用——本契约是**无插件网关的补通道**，与创建场景共用）。

**契约**（实现在 `POST /v1/authz/check-material`，PEP 共享密钥）：

```
POST {中心}/v1/authz/check-material
X-PEP-Token: {pep-shared-secret}
Content-Type: application/json

{
  "user": "alice",              // 业务侧透传的用户身份（与网关 X-User 同源）
  "app": "cmdb",                // 应用 code
  "action": "cmdb:disk:update", // 三段式动作码（路由表登记过——未登记=拒，纯查表）
  "material": { ... },          // 原始请求体（或信封）——中心按取材声明自取，业务不解析
  "path": "/api/v1/disks/8",    // 可选：id_path=path.* 声明时必带（或直接走网关链路）
  "query": { "region": "hz" },  // 可选：id_path=query.* 声明时带
  "trace_id": "…"               // 可选：链路追踪
}
```

**响应合同**（与网关 forwardAuth 同一二值语义）：

| 状态 | 含义 | 业务动作 |
|---|---|---|
| `200 {"decision":"allow"}` | 放行 | 继续执行 |
| `403 {"decision":"deny","code":…}` | 拒绝 | **返回 403，不执行** |

deny code 家族（fail-closed 全家福）：

| code | 含义 |
|---|---|
| `NO_PERMISSION` | 动作级无授权 |
| `DATA_MISSING` | 按 id 点查权威行不存在（行删了=幽灵授权，判少不判多） |
| `DATA_SOURCE_UNAVAILABLE` | 点查/回源失败（应用挂/超时）——**无隐式降级**，拒绝 |
| `MATERIAL_MISSING` | 信封字段取不到（创建类 fail-closed） |
| `MATERIAL_DECL_INVALID` | 取材声明配置错（回源绑定缺等） |
| `MODEL_NOT_REGISTERED` | 点查模型不在数据契约白名单（防"查任意表"） |

**调用位置**：**落库前**（网关接口级放行之后、业务写库之前）——一次调用，一行代码量级：

```python
# Python 示例（Flask）：创建磁盘
resp = requests.post(f"{IAM}/v1/authz/check-material",
    headers={"X-PEP-Token": PEP_TOKEN},
    json={"user": g.user, "app": "cmdb", "action": "cmdb:disk:create",
          "material": request.get_json()},          # 整包请求体，业务不解析
    timeout=2)
if resp.status_code != 200:
    return jsonify(resp.json()), 403                # fail-closed：中心拒=业务拒
# …继续创建
```

**未调用的后果**：创建/存量 body-id 的数据级判定**根本不会发生**（接口级放行≠数据级放行）——归缺口对账管（业务请求日志 vs 中心判定审计），**必被报出**。这不是可选项：凡能力包对该接口勾了数据级，带体调用就是上线前置。

**判定字段=落库字段**（契约测试钉死）：信封判定用的字段（如 `.meta.account`）业务落库必须消费同一个字段——否则"判的时候是 123、存的是 456"。一次性契约测试断言这一点（`scripts/contract-test.sh` 同族）。

## 3. filter 回调契约【契约定稿，档 c 启用时实装】

**什么时候用**（档 c，仅此两种情况）：

1. 维度**翻不成查询参数**——如 bk-cmdb 式全 POST 查询（过滤条件在 body 里，网关读 X-Forwarded-Uri 拿不到）；
2. **无契约系统**——历史系统连 OpenAPI 都没有，登记不了列表范围字段。

**契约设计**（= 判定两步的业务侧调用形态——同一引擎、只是取参执行方从网关换成业务）：

```
POST {中心}/v1/authz/filter
X-PEP-Token: {pep-shared-secret}
Content-Type: application/json

{
  "user": "alice",
  "app": "itsm",
  "action": "itsm:ticket:list",
  "params": { "account": "acc-ops-001" }   // 业务从请求里抠出的范围参数——谁持有请求谁抠材料
}
```

**响应合同**（与判定两步三态一一对应）：

| 状态 | 场景 | code |
|---|---|---|
| `200 {"decision":"allow"}` | params ⊆ 授权范围 | — |
| `403` | 必填范围参数缺失 | `MISSING_SCOPE_PARAM` |
| `403` | 参数值超出授权范围 | `NO_PERMISSION` |

**核心保证（与主路同权重）**：授权集=回调时**实时按策略计算**（不依赖前端诚实、不落授权集缓存）；语义与网关链路判定两步**完全一致**——只是取参执行方不同（网关读 URI 头 vs 业务读自己看得见的请求）。

**调用位置**：业务列表接口的**入口处**（拿到请求、还没查询数据源之前）——一次调用，拒了直接 403 不查库：

```python
# Python 示例（bk-cmdb 式全 POST 查询）
@app.route("/api/v1/tickets/query", methods=["POST"])
def query_tickets():
    body = request.get_json()
    resp = requests.post(f"{IAM}/v1/authz/filter",
        headers={"X-PEP-Token": PEP_TOKEN},
        json={"user": g.user, "app": "itsm", "action": "itsm:ticket:list",
              "params": {"account": body.get("account")}},   # 从 body 抠范围参数
        timeout=2)
    if resp.status_code != 200:
        return jsonify(resp.json()), 403
    # …正常查询
```

**档 c 的代价**（为什么它是"兜底"不是"推荐"）：每列表请求多一次回调（中心挂=列表挂，对称依赖）；且**业务持有参数=业务可以选择不调**——契约测试（受限用户请求结果 ⊆ 授权范围）就是钉这个的：**不过=该域不得用档 c，收紧到接口级**。

## 4. 契约测试（两种回调共同的上线闸门）

档 b（判定两步）与档 c（filter 回调）上线前，中心出对测脚本（`scripts/contract-test.sh` 同族），两个断言：

1. **受限用户请求结果 ⊆ 授权范围**——业务真按该字段过滤了（防"判了但业务无视"）；
2. **判定字段=落库字段**——信封/回源判定用的字段与业务落库消费的是同一个（防"判 123 存 456"）。

**不过=该域降档 c 或收紧到接口级**——契约测试是档位的准入证，不是事后补票。

## 5. 与 V1 SDK/中间件示例的关系

| | V1（代码/SDK 贴中间件） | 兜底（本文契约） |
|---|---|---|
| 形态 | 中间件代抠材料，实时回中心 | 业务现有代码里加**一处调用点** |
| 谁配 | 对方开发排期 | 对方开发排期（量级更小：一处 vs 一层） |
| 适用 | 第三方口子 V1 档 | 内部接入面历史系统 |
| 判定权威 | 中心 | 中心（同一套 PDP/引擎/审计） |

**同一逻辑**：谁持有请求谁抠材料、抠完送中心判、中心拒=业务拒。V1 是"框架层代劳"，兜底是"手工一处"——不是两套机制，是同一机制的两种接入姿态。
