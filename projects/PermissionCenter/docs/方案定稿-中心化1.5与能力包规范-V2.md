## 0. 一段话说清这个方案

> **中心化判定 + 点查自足**：网关拦接口级，**点操作连数据级也即判——材料随请求到达判定点**（在 URL → 网关链路即判零配合；在请求体 → 信封登记制、按供材通道送中心：真实 APISIX 插件整包转发=同一条链路内完成，无插件网关=带体调用，§2/§5.1）——中心按【通用点查约定】自取权威行（每系统注册一次，不进能力包）；运行期配合仅"创建/存量 body-id 各一次带体调用 + 列表兜底时一次 filter"——**列表主路=判定两步（不带范围参数=非法拒；带了超授权=拒，元组集合语义），业务零过滤代码（前提=业务 API 真按该字段过滤，契约测试钉死），前端展示是应用自己的事**；工单型写操作执行侧收口；一次性面见 §5.1 唯一账目表（回查端点/契约两件登记/带体调用接入/动作码登记/档 b 前端改造/契约测试）。**接口动作=三段式登记（应用:资源:动作）、数据级取材=必填声明（id 路径/信封字段路径/补救回源），运行期纯查表零推断**（§3.7/§3.8）。**投影退役**（CMDB 取材切点查后同步管道整条**干净移除**、不留灰态，待办 #1）；**内部接入面（接网关的内部系统）不引入 SDK、不引入分布式 Agent**（2.0 降为演进项，贴合真实工作量级）；第三方接入口子另立**三级版本**（V1 代码/SDK → V2 挂网关 → V3 本地 Agent——治理深度逐级加深、判定执行位至 V3 才下沉，**权威始终在中心**，三级均成文未实施，§1.5）。能力包规范 = 五区块配置 + 预设场景（参数联动/层级编排）+ 从属三判据 + 黑白名单 + 多包申请 + 门禁三道。
> 一句话判据（贯穿全文）：**判定材料决定判定点**——点操作的判定点在网关链路、材料由中心自取，"行哪来"被结构性消灭。

## 1. 决策记录（为什么走到这一步）

### 1.1 三代演进

| 代 | 形态 | 病/痛 | 结局 |
|---|---|---|---|
| **老权限中心 1.0** | 中心化但**全量扇出**：判一次权限实时去上游/各家查一圈 | 性能差=程序间调用爆炸（不是中心化的锅）；只能"整模型放权 or 逐条勾选"，**无中间态** | 被重构 |
| **本系统 1.x（现状实装）** | 中心化 + **投影**（CMDB 判定字段投进中心）+ 确认制时钟三档 | 数据膨胀治了（只投判定字段），但**供数结构还在**：新应用数据在自己库就投不了（"上帝视角"前提） | **退役**（切点查后下线） |
| **2.0 分布式**（plans/iam-distributed） | 判定下沉业务侧：SDK+Agent+bundle | 撤销窗口/防绕过/工程量 51d/无实战；钩子拦不到"编辑=发工单"型副作用 | **降为演进项**（§7） |
| **1.5 定稿（本文）** | 中心化判定 + **通用点查约定** + **动作码登记** | —— | ✅ 本轮方案 |

### 1.2 三个关键决策

1. **走中心化**：请求量论（企业内部：多云管理+工单，量级不大——老系统差劲是扇出架构病不是中心化病）+ 时间紧 + 叙事稳（连续追问每条有成文答案）；
2. **投影退役（2026-10-03 裁决）**：投影只配得上"数据天然集中"的场景，数据散在各业务库时=上帝视角（老系统"全量灌库"同款结构）——**裁决下线：判定取材一律走通用点查，CMDB 切点查（待办 #1）后同步管道整条下线**；切换期间代码在跑，如实说"裁决退役、切换中"；
3. **2.0 降级**：企业强制力是它的成立前提、工程量大、无实战——记为演进项，其合理内核（**通用点查、fetch-and-bring**）被 1.5 吸收，其 SDK/Agent 本体在**内部接入面**不实施（第三方口子三级另见 §1.5；语义守卫仅作判定通道完全不可得时的备用手段）。

### 1.3 核心判据：判定材料决定判定点

| | 判定材料 | 材料来源 | 判定点 | 痛点 |
|---|---|---|---|---|
| 老 1.0（模型级+勾选） | 身份+动作+模型/实例ID | **请求自带** | 网关/中心，稳 | 无（但无条件式的灵活） |
| **条件式**（新增能力） | 多一样：**行属性**（account/owner…） | 请求里没有 | **被迫漂移到能看见行的地方** | 所有痛的根源：投影税（1.x）/ 语义守卫（SDK）/ 本地判（2.0）——**三套方案本质都在回答"行给谁、谁去拿"** |

**条件式的爽与痛是同一枚硬币**：换来区域授权的中间态（整模型放权 vs 逐条勾选之间唯一灵活档），代价=判定点跟着材料走。SDK/点查不是凭空负担，是这个能力的对价。

### 1.4 真实接入边界（工作实况——面试如实讲）

- **权限中心的管辖范围 = 内部网关体系**：我们这套接入了统一网关、管理体系、流量体系的**内部系统**（多云管理、工单、事件、认证等）——判定收口在网关 + 中心，这就是它的全部地盘；
- **发布系统的例外（真实案例）**：它来自**其他团队/小组**，转过来时**自带一套权限管理**；我接手时只做了**升级（改造成 ABAC 形式）**，**没有并入这一套**——当时进度紧、没做大改，就这样了。它技术上能不能接？**能**（接入=网关配置级），但工作场景下没必要为接而接；
- **面试讲法**："权限中心管的是内部这一套（接网关的）；发布系统是后来转来的，带着自有权限，我给它升级到 ABAC 就没再动——不是技术上接不进，是当时没有动它的必要，硬接反而引入变更风险。"——**贴合真实工作，不假大空，反而经得起追问**。

### 1.5 第三方接入口子（三级版本：V1 代码/SDK → V2 挂网关 → V3 本地 Agent）

**本质一句话**：口子不是新机制——三级递进回答同一个问题的三个深度：**判定执行位放哪、强制力多强、平台背多重建**。**排序轴 = 平台治理深度（不是对方接入成本）**：越往上平台背的组件与运维越重，换来的强制力与性能越多（对方视角 V1 反而最轻——先声明这个轴，否则顺序会被"装网关不是更麻烦吗"问反）。

| 版本 | 形态（谁配） | 判定在哪 | 存在理由/升级动因 | 代价 |
|---|---|---|---|---|
| **V1 基础版** | **代码片段/SDK**——对方贴中间件或引库，全路由先拦一道（对方配） | **实时回中心** | 零基建：核心判定调用十行级、语言无关，双方成本最低，买到"接上了" | 防绕过靠信任、逐家发版管版本；判定审计集中在中心，缺的是旁路检测（有数据写操作无判定记录=一眼穿） |
| **V2 进阶版** | **挂网关**三形态——我方接入网关实例（我们运维，强）/ 他家网关认证插件**回调地址下发**（对方配置）/ 反代容器（我们发、他部署，**PEP 转发器不是判定器**） | **实时回中心** | 物理强制：判定点在请求必经之路，买到"强制"，业务侧零代码 | 要改链路；判定仍逐请求回中心（网络路径未减）；**他家插件被关掉 = 退回 V1 且无实时检测**——靠配置比对 + 审计兜底（信任假设如实说） |
| **V3 高阶版** | **下发本地 Agent**（伴生进程），通用接口配置进 Agent，应用只调本地（我们发运维） | **本地判定**（规则**轮询下发**） | **判定主路径**零跨网（取材走应用本地点查端点）+ 中心不可用时 **stale 窗口内**仍能判，买到"性能与可用性" | 撤销有界延迟（轮询周期 + stale 上限）、审计要回传、平台背一套规则分发体系 |

> **V2+V3 可共存的裁决**：网关管拦截、Agent 管判定；共存时**网关链路仍问中心（权威裁决）**，Agent 只服务应用内嵌的判定调用——两处结论不一致以中心为准，Agent 的 stale 放行被网关兜住。

**V1 示例（代码片段形态，贴进任意 Web 框架的请求入口；SDK 形态 = 同一逻辑的库封装）**：

```python
def perm_middleware(request):
    if is_exempt(request.path):
        return next(request)        # 点查/回源豁免（§3.1——凭证绑定跳过，防递归，同一套规则）
    action = route_to_action(request.method, request.path)   # 查路由表得动作码（§3.8，纯查表）
    payload = {"user": who(request), "action": action}
    if is_point_op(request):        # 点操作（ID 在 URL）：带上 model+id 即可
        payload.update(model=..., instance_id=extract_id(request.path))  # 中心点查取材，无需自己查
    try:
        r = post(f"{IAM}/v1/authz/check", headers=token, json=payload)
    except NetworkError:
        return 403                  # fail-closed：判定不可达=拒
    if r.status != 200:
        return 403                  # 合同：deny 一律非 2xx、200 恒 allow（与网关 forwardAuth 同一合同）
    return next(request)            # 判过才进业务
```

> **列表与创建不在中间件里做**：列表主路=前端**强制携带**范围参数（授权与选项展示=应用自己的事，中心不下发授权集），中间件 check 时顺带按契约参数位置判子集（有列表数据级包才需要，§5.2；无契约系统=业务 filter 回调兜底）；创建/存量 body-id=一次带体调用（V1 形态统一如此，中间件持有请求体、内联判定亦可）。中间件这道管接口级 + 点操作 + 列表子集。

**V3 本地判定的对价（成文即如实报，不藏代价）**：
- **撤销有界，界要写死**：撤销上界 = 轮询周期（正常态）+ stale 窗口上限（N×轮询周期，秒级）——上界内用旧规则保可用，**超界 fail-closed**；"中心挂了仍能判"只在 stale 窗口内成立，超窗一律拒，不含糊；
- **取材就近——通道换、语义不换**：点操作行属性由 Agent 按**同一条点查约定**直查应用本地查询端点（约定的提供方是应用，不是中心）——零跨网与"中心不可用仍能判"都由此成立；应用没配本地端点、取材回中心时，中心不可用则点操作 fail-closed（接口级仍可判）；
- **审计回传（"权威在中心"的底线不许断）**：本地判完日志流回中心、断网本地缓冲、恢复补传；**每条带 rule_version（规则版本号）与连续序号，中心侧校验缺口**——缓冲在对方容器里可删可改，防篡改靠这手（顺带解决"当时按哪版规则判的"复现问题）；
- **本地接口防伪造 + 时钟**：Agent 的本地判定接口仅本进程/本地 socket 可调（peer 认证）——容器内任意进程直调拿 allow 就是伪造判定；stale 判定与日志时间戳依赖本地时钟，带偏差容忍（超差拒判）；
- **心跳**：Agent 心跳进中心看板，被对方停掉要看得见——这是 V3 唯一防绕不牢的地方（Agent 在他容器里），要硬拦叠加 V2，即 V2+V3 共存。

**三级判据**：
- **选级三问：信任 × 防绕过要求 × 性能敏感度**——对方工程能力强、关系可信 → V1 够用；要物理强制 → V2；判定量大/延迟敏感/要兜底中心可用性 → V3；
- **与 1.5 底线的关系**：V1/V2 判定实时回中心（即时撤销 + 集中审计不丢）；**V3 = 2.0 判定型 Agent 的正式入口形态**——底线句在 V3 改述为：**权威在中心（规则定义、版本、审计），判定执行位至 V3 按级下沉；下沉不改权威、但带撤销延迟**；
- **与 2.0 的边界**：三级**均成文未实施**；2.0 全量（SDK 本体、语义守卫、bundle 全量下发）仍是演进项——V3 是它们的按需入口，不排期；
- **配套三件（三级通用）**：① 凭证=M2M 客户端凭证（client_credentials 换令牌，最小 scope 只给判定）；② 第三方数据的**通用点查登记**（应用注册一环，与内部应用同一条约定）；③ 公网只暴露**判定端点白名单**（TLS + token + rateLimit，`app.oc` 公网暴露即此清单——管理面/数据面一概不出）；V3 取材走应用本地端点时退化为规则下发通道白名单，取材回中心时还含点查回程。

**面试口径**：老系统当年"外部系统计划接入"，**停在方案设计**——做的前半段是方案，实施没启动；本文三级是**重新成文的规范，均未实施**。真实情况：**规范就绪、没来得及接**——原计划把另外两个组统一接进来（发布系统是另一回事：自带权限、主动不并入，见 §1.4），规范设计好了、实施没启动我就离开了。讲的是扩展性与进阶思考：**平时主动不铺开，被问才聊一两句方向，答到"设计就绪、未实施"为止——没做过的不扯**；不说"已接入"、不说"V3 已实施"、不把"规范就绪"说成"能力就绪"。

## 2. 目标架构

```
用户/程序请求
  │
  ▼
[网关] 接口级物理拦截（零业务配合）
  · JWT 认证 + 身份注入；判"能否调此接口"（动作码级）
  · 形态分两种：真实=链内插件（APISIX Lua，看得见全请求，查表+取材料+问中心一体）；
    Demo/无插件网关=forwardAuth（另发请求问中心，只带 path/query 不带体 → body 材料走带体调用，§5.1）
  · 应用归属按域名/路由自定（不靠请求携带）；转发头 X-App 供后端用
  · 保留流量防护（防爆破/TLS——免鉴权≠免防护）
  │
  ▼
[业务应用]（点操作与列表主路**零配合**——网关链路已判完）
  │  列表：前端强制携带范围参数（query，契约登记）→ 中心链路子集校验；filter 回调仅兜底
  │  创建：请求参数即"未来的行"（一次带体调用，业务→中心）
  │  工单型写操作：执行侧收口（本来就归执行器）
  ▼
[权限中心 · 数据级判定]（纯函数，取材一律点查）
  · 动作码：路由表查表所得（登记制，运行期零推断，§3.7/§3.8）
  · 点操作材料：中心按通用点查约定自取——path 材料=中心读 X-Forwarded-Uri 按路由表模板提取；
    body 材料=供材通道（插件抠取带入 或 带体调用按取值路径自抠）——业务不供材权威行
  · 列表材料：请求范围参数 ⊆ 授权范围（实时计算，元组集合语义；缺参 deny——限已登记契约的路由）
  · 创建材料：带体调用带参（业务→中心），按登记的信封路径取范围字段（行未存在，点查必空→deny，天然逼出带参）
  · 判定：动作策略 × 各域范围谓词（条件/集合/全量）× deny-overrides
  · 取材一律走点查约定；投影机制退役——CMDB 切点查（待办 #1）后同步管道下线
  · 策略生命周期（申请/审批/版本/TTL回收/审计/能力包门禁）——中心不可替代的核心
```

**取材与发起的一条规则**：**点操作（URL 材料）=网关链路发起、中心点查自足；点操作（body 材料，存量）与创建=一次带体调用（业务→中心，共用同一通道）；列表=判定两步（前端强制携带范围参数→中心缺参即拒、越权即拒，业务零调用）**——点查读的就是实时行，**无新鲜度税**；列表的范围参数本就在查询里，**过滤=查询本身，分页天然正确**。

**与网关的配合形态（三选一，本文选第三种）**：

| 做法 | 是什么 | 取舍 |
|---|---|---|
| 规则打包下发网关（网关本地判） | 规则进数据面（Envoy 本地规则、OPA push 类） | **不用**——规则离中心=背规则同步/撤销延迟/审计回传三件套（即 V3/2.0 的代价清单），网关变有状态 |
| 网关旁挂 Agent | 即 V3 本地判定 | **内部系统不用**——第三方口子高阶档专用（§1.5） |
| **认证供材回中心（选定）** | 真实=**链内插件**（APISIX Lua：拦截→查表→取材料→问中心→放行/拒——整包 body 转发即此形态，内部量级够用，演进=插件就地抠 meta）；无插件网关=**forwardAuth**（另发请求问中心，只带 path/query 不带体——body 材料走带体调用补通道，§5.1） | **本网关形态**：网关零规则零状态、判定实时回中心（即时撤销+集中审计）；一次内网回调 ms 级，请求量论可承受（§1.2）——**同一判定契约，供材通道按网关能力选，语义无差** |

**这不是我们发明的**：认证转发是网关的**标准扩展点**——Nginx `auth_request`、Traefik `forwardAuth`、Envoy `ext_authz`、APISIX 的 Lua 插件/external plugin、Kong 类插件生态，自研网关则等价物=一个十几行的认证 filter。**网关侧动作=一次性配置指向中心**（配的是"每请求问一次"的回调，不是静态转发规则）；中心侧登记网关凭证与信任；配套的头清洗（X-Forwarded-* 只信网关自产）见 §5.2。

**中心不可用 = fail-closed（如实记账）**：每请求问一次中心 → **中心挂 = 全平台判定面 403**（接口级+数据级全拒）——这是"判定集中"的对价，换即时撤销与审计无损；企业内部量级下用**中心高可用（双副本+重启自愈）**兜可用性，不做网关本地缓存规则（那会把撤销延迟带回系统，即三选一表第一行的病）。延迟账：每请求固定一次内网回调（ms 级）；点操作 = 回调+点查两跳；创建/带体调用 = 业务→中心一跳（材料在包里；变更类权威行另有一次中心→应用点查）；健康检查/静态资源按路由声明免判定（公开路由三分类，§5.3）。

## 3. 判定材料与接口登记（点查约定 + 动作码）

### 3.1 约定内容

```
应用注册时配一次（系统级，不进能力包）：
  ├── 查询语义：按 (model, resource_id) 返回该行
  │     POST {系统内部地址}/__perm/query   （或 GET /{model}/{id}，系统自定）
  │     body: { model: "disk", id: "d-500" }  →  { row: {account:123, host_id:...} }
  ├── 模型白名单：只允许已登记数据契约的域（防"查任意表"越权）
  ├── 独立凭证：M2M 只读、仅此用途、不上能力市场、不给用户走
  ├── 回查通道：优先走【系统内部地址】不过网关（中心→业务回调不经网关 = 无豁免需求，Demo 即此）
  │     确需过网关的：豁免主语=【中心 M2M 凭证】不是路由——凭证匹配才跳过判定，
  │     普通用户同接口照常判；【裸豁免（只配路径不绑凭证）=体检阻断】（§3.9）
  │     ★ 回源接口（§3.7 自登记）与点查共用同一套凭证与豁免规则，审计留痕
  └── 能力包/数据契约侧只登记【判定要哪几个字段】（fields，现契约字段不变）
```

**配置位置的规范修正**：查询约定是**应用注册**的一部分（一系统一约定，**标配必配**——凡有变更/删除类数据级判定的系统必须具备这个通用回查地址），**不是能力包的字段**——包只管"哪些域、什么范围"，"怎么取行"归应用注册；每个接口的**取材声明**（id 路径/信封字段路径/补救回源）登记在能力点（§3.7）。

### 3.2 取材流水线（中心视角）

```
数据级判定请求（材料按接口的【取材声明】，§3.7）
 ├─ 创建类（目标行不存在）→ 信封/请求自带字段即"未来的行" → 直接验谓词
 │    ├─ 字段取到 → 验谓词 → allow/deny；【取值路径不存在/字段缺失 → deny】（fail-closed）
 │    └─ ★判定字段=落库字段：业务落库必须消费同一字段，契约测试钉死（§5.1）
 ├─ 变更/删除类（目标行存在）→ 按 id 取值路径取出 id → 通用回查取【权威行】
 │    （信封 meta 只做审计上下文，不做判定依据）
 │    ├─ 取到 → 挑 fields → 验谓词 → allow/deny（行用完即丢，不落库）
 │    ├─ 查不到该行 → deny reason=data_missing（fail-closed）
 │    └─ 取材失败（应用挂/超时）→ 【deny，fail-closed，无隐式降级】（对称依赖，见 3.3）
 └─ 补救档（历史接口 id/信封都摸不着）→ 自登记回源取行（绑定字典，§3.7）
```

### 3.3 两笔账（如实）

| 账 | 结论 |
|---|---|
| **可用性** | 中心→应用点查 vs 应用→中心判定：**写操作本来就有这个依赖**（应用挂了编辑也做不了）——对称依赖，不新增风险；对比老系统"判 CMDB 权限问 CMDB 拿人数据"的全域自循环，这是写操作的必然链路，不算耦合病 |
| **安全** | 通用接口=凭证可读任何行（白名单内）——"开自己家门给自己人"前提下可接受，**白名单+只读+审计三件不能省**（这是省事方案唯一付的规范成本） |

### 3.4 业内锚点

XACML PIP 的 HTTP 属性源（判定方按登记的属性源取材——本约定是它的标准化单点变体）；k8s/云厂商 Describe API（内部服务按 ID 取资源描述是标准习惯，此处立为对权限中心的专用通道）；AWS "服务必须调 IAM"的镜像（那边 IAM 在服务侧被调，这边中心按约定回调服务）。

### 3.5 谁发起判定——点操作为什么业务零配合

资源 ID 在 URL 里的查/改/删（REST 主流形态），**网关链路全程判完，业务一行代码不写**：

```
PATCH /disks/d-500
  → 网关 forwardAuth 回调中心（接口级回调，链路现成）
  → 中心路由表（登记制）得动作码 cmdb:disk:edit + 从路径提取 (model=disk, id=d-500)
  → 按通用点查约定回调应用取 d-500 行 → 验谓词（account==123?）
  → 2xx 放行 / 403 拒
```

网关本来就在这条链上（接口级回调现成），数据级等于**顺带多判一步**（多一次中心→应用点查，索引命中 ms 级）。**id 在请求体的接口（存量，云管主流如 `POST /instances/reboot`）**：URL 里没有材料——由**看得见请求的那一层供材**（真实=APISIX 链内插件按取材声明取值路径抠出 id 随判定带给中心；无插件网关=业务一次**带体调用**，与创建共用同一通道）——**不立"id 进 URL"规范**（业界亦无此标准，RebootInstance 类接口全 POST body）。**需要业务配合的都很轻**：列表（主路判定两步零调用，§5.2——"网关改不了响应体"只约束过滤位置、不约束判定位置，判定照样在网关链路）、创建/存量 body-id（各一次带体调用）、工单型（执行侧收口）——**（内部接入面）不存在 SDK 植入、不存在中间件改造**，配合面比业内"服务必须调 IAM"还小（第三方口子三级另见 §1.5）。

### 3.6 点查缓存（可选优化——量级需要再上）

中心侧可对 `(app, model, id) → 行` 加**短 TTL 缓存**（秒级，如 5s）：

- **收益**：详情页反复编辑、热点行判定少一跳点查（点操作高频场景的唯一延迟点）；
- **代价（如实）**：重新引入一个**微缩新鲜度窗口**——正是点查甩掉的那张税的回归；
- **决策：默认不缓存**；出现真实热点（点查耗时进 SLA 红线）再加，且 TTL 必须秒级 + 可关 + 决策日志标注材料来自缓存（审计能区分"实时行 vs 秒级缓存行"）；
- **写后失效不做**（复杂度不配收益）——靠 TTL 自然过期，**最大陈旧度 = TTL**。

### 3.7 动作码：三段式登记（配置页五格模板）

**动作码 = 唯一标识符，不是语义分类。**

```
cmdb:disk:edit                编辑磁盘
cmcloud:instance:start        开机        ← 不是"更新"，它就是 start，自己一个动作
cmcloud:instance:resize       变更实例类型  ← 也不硬塞"更新"（资源级变更，与改一个字段两回事）
cmcloud:instance:reboot       重启
cmdb:disk:list                看列表
```

- 三段 = **应用 : 资源 : 动作**——应用段回答"哪个系统的"（网关按域名/路由已定应用，不靠请求携带）；动作段是**被策略引用的字符串**；
- **系统不消费"这是增是删"**。唯一被消费的分类 = **读 / 写这一个 bit**，用途只有四个：UI 分组、只读角色聚合（只读预设=全部读动作）、审计分级（写=高危）、默认策略——增删改的"分类问题"在业内就被压缩成这一个 bit；
- **为什么不用 CRUD 分类学**：真实项目接口动作与 HTTP 词不对齐——PUT=更新那套 REST 语义靠不住（bk-cmdb 全 POST、云管的关机/重启/变更实例类型全 POST、查询也可能 POST）。业界同款做法：阿里云 `RebootInstance`、GCP `compute.instances.start`、Azure `.../virtualMachines/start/action`、K8s 的 `pods/exec` subresource 动作——**动作靠登记，不靠推断；开机算什么？算 start，完事**。

**配置页五格（选中一个 API 端点后配这些）**：

```
┌─ 登记接口 ───────────────────────────────────────────┐
│ 接口    POST /api/v1/instances/reboot                │ ← 自动带出（OpenAPI），不手填
│ 动作    cmcloud:instance:reboot                      │ ← 三段式；预填可改
│ 读/写   ● 写    ○ 读                                  │ ← 唯一的"分类"，完事
│ 数据级  ● 需要（条件式）→【取材声明】★必填，三选一：      │
│         ● 目标行存在 → id 取值路径 body.instance_id    │ ← 按 id 走通用回查取权威行
│         ○ 创建类     → 字段取值路径 .meta.account      │ ← 信封规范默认预填
│         ○ 补救       → 自定义回源（url+绑定+pick）      │ ← 前两档兜不住才展开
│ 资源    instance（关联数据契约 model，可选）             │
│—— 按动作类型扩展 ——                                   │
│ 登记 list 动作  → 多一格【范围参数】account / query      │ ← 列表判定两步用（§5.2）
│ 登记 create    → 取材声明②即【范围字段路径】（默认 .meta.account）│ ← 创建越权检查用
└──────────────────────────────────────────────────────┘
```

- **契约两件都在应用接入侧一处配完**：通用回查地址=应用级标配（§3.1）、列表范围字段=list 动作扩展格；自定义回源=补救档——系统只按登记取数验证，不猜；
- **create 的范围字段路径**：判断"他能不能在这创建"的字段（如 `.account`），应用方必须把取用路径填出来——嵌套点号路径（`.meta.account`）、数组 `items[0].account`，表单/工单配置同款写法；不填=中心不知道去 body 哪拿账号=无法防越权（配置页必填提示）——**与取材声明②同格**：同一个路径两处消费（验条件 + 创建越权比对）；
- **list 的范围参数**：告诉系统"这个列表接口的范围看哪个参数、在什么位置"——系统凭它做缺参与子集校验。

**取材声明（每个数据级接口 ★必填——既规范又自由：规范钉死"必须显式登记"，自由留给"登记成什么形态"）**：

```
按序命中即停：
① 目标行存在（变更/删除/操作）→ 配【id 取值路径】→ 按 id 走通用回查取【权威行】
     path.id            ← CMDB 风格（路径带 ID）——中心读 X-Forwarded-Uri 自行提取
     body.instance_id   ← 云管风格（POST body 带 ID，主流）——供材方=看得见 body 的那一层：
                           真实=APISIX 插件抠出带给中心；无插件=业务带体调用，中心按此路径自抠
     body.ids[*]        ← 批量操作逐个取：【任一行 deny=整批 403】（判定通道只有 2xx/403 二值）
                           且批量上限 20，超限拒绝
     ★ 信封 meta 不做判定依据——前端自报、与目标行对不上=越权通道；
       权威行是 ms 级索引查询（§3.5 的账），没有省的必要
② 目标行不存在（创建）→ 配【字段取值路径】→ 信封自带材料即"未来的行"
     .meta.account      ← 信封规范默认值，预填零手填
     .payload.xxx       ← 历史接口自定义点号路径（数组 items[0].x 同款）
③ 两档都兜不住（历史接口 id 摸不着、信封不合规）→ 【自定义回源】= 补救档
     展开下方绑定字典（url + bind + pick）——新系统按规范开发，此档配置率≈0
```

**请求信封规范（组内开发规范——判定材料随请求到达）**：

```json
POST /api/v1/instances/reboot
{
  "meta":  { "cloud_type": "cvm", "account": 123, "region": "cn-hz", "owner": "u1" },
  "spec":  { "instance_id": "i-999", "action": "reboot" }
}
```
· meta 板块 = 权限判定字段（约定必含）：创建类直接当判定材料（②）；变更类做审计上下文落审计日志（判定依据仍是按 id 查的权威行）
· spec 板块 = 业务内容（权限不看）；id 放 body 是云管主流 → id 取值路径默认从 body 取
· 收益：材料结构固定 → 审计可复现（哪次放行依据了哪个字段一目了然）+ 新接口按规范零逐格手填
· 实现传输量由网关能力定：真实 APISIX 整包 body 转给中心、中心按登记路径抠（内部量级够用，合规）；
  演进=插件就地抠 meta 再传——**规范只钉【材料位置】，不钉【实现传多少】**

**信封防伪边界（meta 一定会被伪造——设计是"不把信任放在 meta 上"）**：
· **身份永远来自 JWT**（网关认证），body 里的任何身份字段不认——伪造身份字段无效；
· **变更/删除类不信 meta**：判定依据=按 id 点查的权威行（你说你是谁不算数，查你名下那行才算数）；
  伪造 id 只是换目标，每个目标照样被权威行罩着；残留=审计上下文被自报字段污染 → 审计中该类字段标注"自报"；
· **创建类 meta 是唯一材料**（行不存在只能自报），但伪造被授权集封顶：伪造 account=123 只能
  "申请一个你本来就有的范围"或被 403，无收益；
· **判定字段=落库字段**（唯一真突破口）：业务落库若消费别的字段，判定形同虚设——
  契约测试钉死（§5.1），不过=不得上判定两步主路。

**补救档：绑定字典（自定义回源的参数从哪来）**——仅取材声明选③才展开；每个值从**本次请求**哪里取，五种来源（**通用回查=应用级标配，本字典=接口级补救，两者共用同一套凭证与豁免规则**）：

```yaml
route:  { method: PATCH, path: /api/v1/disks/{id}, action: cmdb:disk:edit, rw: write }
fetch:                          # 条件式才配
  url:  GET /api/v1/disks/{disk_id}
  bind:                         # 回源参数 ← 本次请求（字典式对应）
    disk_id: { from: path,   key: id }          # 路径参数
    region:  { from: query,  key: region }      # 请求参数 query
    owner:   { from: body,   key: meta.owner }  # 请求 Body，点号下标取值
    tenant:  { from: const,  value: t-1 }       # 固定值
    acct:    { from: ctx,    key: account }     # 身份上下文变量（复用 $user/$org/$group/$account）
  pick: account                 # 回源返回的行里，拿哪个字段去验条件
```

三条规则：**回源模板的每个占位符必须有绑定（缺=配置页不让存）；来源就这五种；`pick` 指定验条件的字段**。

### 3.8 路由表：动作码怎么来、请求怎么查

**建表三种方式（能自动就自动，拿不准人确认）**：

| 方式 | 谁做 | 准确度 |
|---|---|---|
| **x-action 源头标注**：OpenAPI 每个接口挂 `x-action: cmdb:disk:edit`（`x-` 扩展字段是 OpenAPI 官方后门，工具都认识） | 应用方 | 100%，导入即用零人工 |
| **导入推断预填**：按下面四条规范猜，**人确认后落表** | 系统+人确认 | 建议性质——猜错了确认时改掉，**预填永远不直接生效** |
| 人工从下拉登记 | 管理员 | 存量不规范系统兜底 |

**应用方怎么带出 x-action（代码即清单）**：

```python
# Django（drf-spectacular）
# ① 装饰器（推荐）——动作码跟代码走，重构不漂移
@extend_schema(operation_id="edit_disk", extensions={"x-action": "cmdb:disk:edit"})
def patch(self, request, *args, **kwargs): ...

# ② 中央字典钩子（存量项目次选）：POSTPROCESSING_HOOKS 按 (方法, 路径) 逐接口补 x-action
#    弱点=urls 改了字典会失配——失配在【重新导入时被接入体检报错】+ 运行期未命中默认拒
#    并打告警日志（发现靠导入体检与告警，不靠自动巡比——触发权在应用方）
```

```go
// Gin
// ① 注册即登记（推荐）——注册路由与动作码同一行，注册表=动作清单
app.P("PATCH", "/api/v1/disks/:id", "cmdb:disk:edit", h.EditDisk)

// ② 存量零改动：gin 自带 router.Routes() 吐出全部 (方法, 路径)
//    脚本按字典补 x-action → 调中心导入接口（同一份数据两个出口：openapi.json / 导入 API）
```

推荐顺序：新代码用 ①（就近原则）；存量项目用 ②（不动业务代码）；已有生成流水线再考虑回填脚本。

**推断规范：四条 + 一兜底（内部标准，可对组内推广）——判定顺序写死：先③后②**：

```
① 路径 = /资源集合/{资源id}/{动作段?}，段位固定
② create = POST 集合路径，【不允许带路径参数】且【末段 ∉ 动作词表】才成立
   （判定顺序：③业务动作先判——POST /instances/reboot 末段 ∈ 词表 → 推断为 reboot，
     不会被②抢成 create；词表 = 平台内置通用动作词表 + 应用登记动词（导入时可编辑）；
     自家新接口 100% 合规，存量不规范走人工档：规范管增量、存量兜底）
③ 业务动作 = 写方法(POST/PUT/PATCH/DELETE) + 末段 ∈ 动作词表
     POST /instances/{id}/reboot   ✓ 动作段（id 在路径）
     POST /instances/reboot        ✓ 也认——id 在 body 无所谓：匹配按整条模板命中，
                                          绑定字典从 body 取 id（五来源存在的意义）
     GET  一律不认动作段——读动作只有 list/get，形态表直接给，
          GET /disks/status 安全（status 只是普通路径段）
④ 单资源形态表：GET 集合=list / GET 单个=get / PATCH|PUT {id}=edit / DELETE {id}=delete
⑤ 推不出唯一结果 → 不猜 → 待确认队列（应用方补 x-action 或人工选）
```

**运行期 = 纯查表，零推断**：

```
请求: POST /api/v1/servers/s-001/reboot   (Host: cvm.example.internal)
  ① 域名/前缀 → 定应用: cvm            ← 两个系统的动作词再撞也互不可见（先隔离）
  ② 该应用路由表内，方法+路径模板匹配——【specificity 钉死】：方法先比 → 静态段数多者优先 →
      同数按最左参数段靠前 → 全等按登记序（中心匹配器为准；与应用真实路由的差异由导入一致性体检收口）
        cvm 表: POST /servers/{id}/reboot  ✓ 命中
  ③ 命中 → 整串取出登记好的动作码: cvm:server:reboot
  未命中 → 未登记 → 默认拒（deny-by-default）
```

- **词表不参与匹配**（不是"在路径里找动词"）——动作码是登记时人确认存下的，运行期只查表，**推断永远不活在运行期**；
- 模板撞车（`GET /disks/list` vs `/disks/{id}`）→ **静态段优先**（gin/express/k8s 同款规则）；
- 同一系统内动词重复无歧义：路径模板不同=两条路由（`POST /disks/{id}/reboot`→disk:reboot、`POST /volumes/{id}/reboot`→volume:reboot），动作段只是被"取出"的结果；
- **导入一致性校验**：三段码的资源段要和路径对得上——`cmdb:disk:edit` 挂在 `/volumes/{id}` 上=明显配错，体检报错。

### 3.9 接入体检与动作码规矩

**接入体检（应用注册 / 导入 / 发版重新导入时自动跑，报告回执）**：

```
┌─ cmcloud 接入体检报告 ─────────────────────────────────┐
│ ✅ 路由 42 条，动作码已登记 40 条                        │
│ ❌ 阻断（不修完不能接入，网关路由不放进来）                  │
│   · POST /disks/{id}        无动作码且推断不出（POST 带 id）│
│   · PATCH /instances/reboot  勾了条件式但没配取材声明         │
│   · 裸豁免：豁免只配路径未绑中心 M2M 凭证（自锁或裸奔）        │
│   · create 缺范围字段路径 / 回源占位符无绑定 / pick 不在 schema│
│   · 动作码格式错 / 同一路由挂多码 / 同码多路由（别名路由例外）  │
│   · 导入一致性：三段码资源段与路径模板不符（disk:edit 挂 /volumes）│
│ ⚠️ 待确认                                               │
│   · 5 条路由推断预填未人工确认 → 接入停在"未完成"状态         │
└──────────────────────────────────────────────────────┘
```

- **只做硬的五类**：① 缺动作（推断不出）② 格式错（非全小写三段）③ 重复（同码多路由/同路由多码，别名路由显式登记为例外）④ 配置自洽（**取材声明缺失**、补救回源占位符没绑定、`pick` 不在回源 schema、**裸豁免未绑凭证**、create 缺范围字段路径）⑤ 导入一致性（三段码资源段 vs 路径模板对得上）→ 阻断；
- **不当保姆**：起名好不好、同义词（reboot vs restart）一律不管——**检测不是治理**，业务方自己的事（动作词在他的业务代码里就是个短字符串，中心管不着也不该管）；
- **发版即更新**：应用方接口改版/新增后**自己重新导入**（跑一遍体检），登记跟着更新；平台不做自动巡比（巡检机制砍掉，触发权交应用方）；
- 设计原则 = 门禁思想从"包发布"（§4.7）延伸到"应用接入"的第一道：**能强制的绝不靠自觉**。

**词表规矩三条**：
1. **格式统一**：全小写三段 `app:resource:verb`——格式不统一没法比对；
2. **机器校验，无审批流**：格式不对→报错；同码/同路由重复→报错；下拉=配置页从登记表读（登记通过即出现在下拉，顺手复用已有动作）；
3. **改名不存在**：中心只有【新增动作】和【归档动作】两个操作，**rename 根本没有 API**——想改没门。导入发现动作码变了（`edit`→`update`）→ **默认阻断** + 受影响清单（包A、包B、3 条策略引用）→【确认同步迁移】按钮：批量替换引用 + 留迁移记录（旧码/新码/谁/何时/清单）→ 放行。**语义等价的改名才迁移；语义变了=新增+归档**——迁移只换词，接口行为对不对必须人判断，所以默认阻断永远在。

**动作码生命周期**：只增不改；接口下线=动作码**归档不删**（可查不可用）；还有包/预设在引用 → 拒删并列引用方（与 A9 策略影响面是同一家族）。**路由表版本**：每次导入/迁移即版本递增；**判定审计写 (action_code, route_version) 快照**——判定可复现："当时那条请求按哪版路由表判的"查得出，迁移后旧版本仍可查。

## 4. 能力包与预设规范（包规范成文——本节是主交付）

### 4.1 配置页五区块（必填标 ★，配置页=规范主载体）

```
┌─ 能力包发布 ·「主机管理」─────────────────────────────┐
│ ① 基本信息   名称★ / 所属应用★ / 关联 OpenAPI          │
│ ② 能力点（接口维度）★ 按板块分组：主机查改删/下钻、磁盘、   │
│    网口、判断类接口（如"密码按钮可见"）——想给就勾          │
│    （能力点的动作码/读写/回源/范围参数等登记内容见 §3.7——   │
│      登记发生在【应用接入】侧，本包配置页只勾选已登记的能力点）│
│ ③ 数据范围（数据维度）★ 逐数据域一个范围选择器：           │
│    host: ○全量 ●条件{account=123} ○勾选实例 ○自己的      │
│    disk:（层级/联动自动带出，见 4.2）                    │
│ ④ 数据契约 ★条件触发：任一域选条件式才弹——判定字段/SLA     │
│ ⑤ 自检与发布：四问自检 → [发布] → 门禁三道自动跑          │
└──────────────────────────────────────────────────────┘
```

**条件必填逻辑**：勾数据级 → ③必填；任一域条件式 → ④该域必填；纯接口包 → ③④隐藏（合法）。

**范围字段白名单门禁【待小改】**：③ 的条件字段只能从**应用契约白名单**选（OpenAPI 参数供候选 → 应用注册勾选"权限维度+必填"）——白名单外禁配、勾不出维度的域降兜底档，防"配了验证不了的字段"（§5.2）。

### 4.2 预设 = 场景（含两项升级设计）

**现状【已实装】**：预设 = 包内的场景化方案（查看/管理/最小授权……），每预设含 `{name, status(draft/published·独立上下架), interfaces(勾选动作), grantee_types, apply_scope, data_control, data_models}`；申请时选预设 → 填范围 → 生成判定表达式（demo 场景 14/15 全链可演）。

**升级一：参数联动【待小改】——防"host 选 123、disk 选 456"错位**

```
预设「主机管理·123」声明场景参数 {account}
  host 域条件 {account: $param}   ← 申请时只选一次 account=123
  disk 域条件 {account: $param}   ← 同一参数带出全域，结构上不可能错位
（预设配置项：共享参数=联动模式 / 各域独立=独立模式——真独立的域才允许独立选）
```
判定层不假设域间一致（各域独立判定是合法的），联动纯粹是**申请体验的防错**。

**升级二：层级编排【待小改】——data_models 从平面数组升级为树**

```
预设 data_models 树：
  host（account=123）
    └─ disk（随 host：从属条件）   ← Markdown 缩进式声明层级
      └─ nic（随 host）
· 向导层：层级=联动（选父域范围，从属子域自动带出）
· 落底层：各域仍是【独立策略】——层级是编排不是存储结构
· 跨出层级（管其他账号的磁盘）→ 不在树里 → 单独申请
```

### 4.3 从属三判据（"什么情况可以从属"判死）

1. **从属事实必须在子行字段上**（`disk.host_id` / `disk.account` 行属性）→ 可用从属条件式 `{field: host_id, op: in, value: …}` 一条策略覆盖一族（单行点查可验）；
2. **必须显式声明**：发布方勾子域 + 写谓词，**系统零推导**（没有"主机有权限自动算磁盘有权限"）；
3. **缺字段/表达不了 → 禁止从属，单独授权**——不许硬凑。CMDB 建模若无从属字段，**数据建模加冗余字段**（一行字段换一条简单谓词）是本方案的隐藏依赖。

**包永远只有接口×数据两维度**——关联/下钻/整体感全部由两维度勾选组合 + 条件式表达；从属不另设机制（行有字段→条件式；是人的集合→组；真关系图→关系式预留）。

### 4.4 黑白名单

| 语义 | 机制 | 状态 |
|---|---|---|
| 白名单（默认） | deny-by-default + allow 策略 = 系统底色 | 【已实装】 |
| "直接放行" | allow 策略条目 | 【已实装】 |
| **黑名单（显式禁止）** | **effect=deny 策略** → 构建物化 deny 规则 → Casbin **deny-overrides**（`allow && !deny`：任一 deny 命中，再多 allow 也拒） | 【已实装】UI 直授可选、builder、model.conf 三处实证 |

**deny 治理规范【待成文】**（能力有、规矩没有）：deny 必须比被禁 allow 更精确（防宽 deny 全局误伤）；走同一审批链；配额+审计。deny 演示样例【待补】进 demo。

### 4.5 包边界正反表 + 四问自检

**能进包**：多数据域的接口清单 × 各域范围；下钻（显式勾子域接口+范围，整包申请=用起来像整体、落库每条可指认）；判断类接口（动作级）。

**不能进包**：

| 禁 | 为什么 | 替代 |
|---|---|---|
| 隐式推导（主机有→磁盘有） | 判多温床，审计指不出记录 | 显式勾子域 / 从属条件式 |
| 跨源聚合条件（成本>1000 才看） | 业务逻辑塞不进能力包（包只装**资源元数据维度**范围） | 出圈，不支持 |
| 关系式判定 | 材料在中心关系图，预留无入口 | 组/条件式 |
| 聚合接口判定（count/sum 非行） | rows 模型套不上 | 默认拒+显式声明改写 |

**四问自检**（发布方填包照答 + 门禁复核）：引用了哪几个数据域？每域什么范围形态？条件式的域字段在行上吗（契约 fields）？下钻子域/模型勾全了吗？

### 4.6 组合自由度三件套（明确不搞包嵌套）

| 需求 | 方案 | 状态 |
|---|---|---|
| 包内多方案 | **预设**（多套勾选组合，申请时选） | 【已实装】 |
| 跨包组合（主机+安全组+子网） | **多包一次性申请**：申请页多选 N 包 → 单一审批视图 → 批量开通 + 关联推荐（推荐非依赖） | 【待小改】 |
| 组合不到的缺口 | **定制需求卡**（owner 直授/补包，A8） | 【已实装】 |

**为什么不做链式/嵌套（包引用包）**：引用图→循环引用、版本传播、影响面递归爆炸；**包是发布方的策展单元（分发时展开成原子策略），组合是申请方的选择权**——组合发生在申请时，不发生在包结构里。**包粒度原则 = 能力域**（主机/安全组/子网各一包；大而全包 → 一系统一包+堆预设 → 包失去策展意义）。

### 4.7 发布门禁三道（机器强制，声明不合格挡在发布期）

| 门 | 校验 | 不过 |
|---|---|---|
| ① schema 完整性 | 范围/契约必填项齐 | 拒发 |
| ② **试算自检** | 条件式域真取一次行（现契约=指纹试算；1.5=**按取材声明真取一次**：id 路径→通用回查 / 信封→字段路径 / 补救→绑定回源——机制同一条，来源泛化） | 不可算→400 拒+出路（降接口级）；不可达→502 重试 |
| ③ 语义档位 | 声称数据级无契约/条件字段不在行上/名单超限（500，治理阈值） | 拒或降级接口级 |

**规范三层载体**：配置页条件必填（②引导）+ 门禁代码（①兜底强制）+ 边界文档（③解释）——**能强制的绝不靠自觉，文字只解释不承担强制**。

## 5. 接入与拦截（贴合真实：内部接入面不搞 SDK、不搞 Agent）

**本方案的内部接入面明确不实施 SDK 与分布式 Agent**——点查自足 + 列表判定两步后，运行期配合只剩"创建/存量 body-id 各一次带体调用 + 列表兜底时一次 filter"，不构成引入 SDK 的理由（2.0 的 SDK/Agent 设计保留作演进项参考，见 §7）。

**边界注**：本节结论管**内部接入面**（接网关的内部系统）；第三方接入口子的三级版本另立 §1.5——V1 的 SDK 是对方项目内的库封装形态、V3 是"本地判定 Agent"的按需形态，均**成文未实施**，不与本节矛盾。

### 5.1 配合面（全集，就这些）

| # | 场景 | 配合形态 | 量 |
|---|---|---|---|
| 1 | **点操作（URL 材料：id 在 path/query）** | **零配合**——网关链路判完，中心点查自足（§3.5） | 无 |
| 1b | **点操作（body 材料：存量 POST body-id）** | 供材通道二选一：真实=网关链内插件按取材声明抠材料（业务仍零配合）；无插件网关=一次**带体调用**（与创建共用通道） | 真实=无；无插件=一次调用/接口 |
| 2 | **列表（主路）** | **判定两步零调用**：前端强制携带范围参数（query，契约登记）→ 中心链路缺参 deny/元组子集校验（§5.2） | 业务对中心运行期调用为零 |
| 3 | **列表（兜底）** | 一次 `filter` 回调——仅契约表达不了/无契约的系统 | 一次调用（按档启用） |
| 4 | **创建** | 一次**带体调用**（业务→中心，请求参数即"未来的行"；参数天然在请求体、网关判定通道不带体，故留这一次） | 一次调用/接口 |
| 5 | **前端改造（档 b）** | 范围参数强制携带（选项展示/账号配置=应用自己的事） | 一次性改造（非运行期） |

（工单型写操作 = 执行侧收口，本来就归执行器，不算对业务的新增配合。）

**一次性面唯一账目（全集，就这些——防"还有没有别的"追问）**：

| # | 一次性工作量 | 谁做 | 何时 |
|---|---|---|---|
| 1 | 通用回查端点实现（`__perm/query`）——凡有变更/删除类数据级判定的系统标配 | 应用方 | 接入时 |
| 2 | 契约两件登记：通用点查接口 + 列表范围字段（维度/位置/必填，登记于 list 动作，§3.7 一处配完） | 应用方 | 接入时 |
| 3 | 创建/存量 body-id 的带体调用接入（每接口一处调用点，无 SDK、非中间件改造） | 应用方 | 上线对应接口前 |
| 4 | 动作码路由表登记（x-action 导入 + 人工确认） | 应用方 | 接入时 |

| 6 | **一次性契约测试**：受限用户请求结果 ⊆ 授权范围 + **判定字段=落库字段断言**（中心出脚本；不过=该域降档 c） | 应用方跑、中心出脚本 | 档 b 上线前置 |

### 5.2 列表数据权限主路（判定两步 + 契约分档）

**判定两步（主路，业务零过滤代码——前提=业务 API 真按该字段过滤（契约测试钉死），否则降档 c；【设计定稿】）**——中心的职责到此为止：

```
① 不带范围参数 → deny（missing_scope_param，默认拒绝，不进业务）
     触发条件=契约标注 required 的范围参数；未登记契约的路由不触发查参，档 a 零登记=零影响
② 带了 → 子集校验（请求范围 ⊆ 授权范围）→ 超授权 = 拒
     授权范围 = 本次回调实时按策略计算（不缓存、不下发，撤权即时生效）
     通过 → 业务照常查询——范围参数本就在查询里，过滤=查询本身，分页天然正确
```

**边界（越俎代庖不做）**：前端展示什么、选项怎么管理、"选全部"怎么展开——**全是应用自己的事**（账号配置是人家系统的，中心做不清楚也不该做）；中心**不提供**授权集下发/查询接口，只保证"不带不行、带错不行"。

**子集校验语义（钉死——元组集合语义）**：
- **授权范围 = 各策略展开的【组合元组集合】取并**——`(账号, 区域)` 成对保留，**跨策略只并集合、不打散维度重组**：授权 `{(1,hz),(2,bj)}` 拒绝 `(1,bj)`（投影并集会误放行，此处堵死；K8s RBAC 的授权也是 (角色, 命名空间) 成对存的同款锚点）；
- 请求参数元组 ∈ 集合 → 过；不在 → 拒；单条策略内部"账号∈{1,2}×区域∈{hz}"展开为组合是它自己的意思，合法；
- **逐维 ⊆ 仅用于缺参判定**（契约内 required 维度缺任一=缺参 deny）；
- **"全量"=通配组合** `(123, *)`，比对时通配匹配；**组合数上限 500**（与门禁③同值），超上限该系统列表**降档 c**（参数表达不了全量）；
- 子集计算异常 → fail-closed（默认拒绝）。成本：策略数×每条组合数一般在数百内，集合查一次毫秒级，仍在网关那一次回调内完成。

**范围参数位置规范**：**query string，与 HTTP 动作无关**——`POST /search?account=123` 完全合法，**全 POST 查询（bk-cmdb 式）照走判定两步**；连 query 都不认、查询条件只在 body 的极端接口 → 退档 c 兜底。

**为什么判定能放网关链路**：列表接口的接口级判定本就在网关（forwardAuth 逐请求回调中心），范围子集校验=同一次回调顺带多判一步（**按契约参数位置读取——query 或历史头**）——「网关改不了响应体」只约束**过滤位置**（响应侧过滤发生在分页后=错），不约束**判定位置**。**通道与配置前提**：Traefik 认证回调恒 GET、不带原 query，原 URI/方法在 `X-Forwarded-Uri/Method` 头里，中心自该头解析范围参数；部署要求入口清洗或 `trustForwardHeader=false`，**X-Forwarded-* 只信网关自产**——这是"不依赖前端诚实"的前提（防客户端自带头伪造）。

**契约分档（按系统登记，不搞一刀切）**：

| 档 | 条件 | 做法 | 实态落点 |
|---|---|---|---|
| a 不需要 | 行级无语义 / 天然域隔离 | 接口级+域级完事，什么都不用做；**存量条件式仅作用于点操作/云管路径——CMDB 直连列表=模型级授权、无行级条件式**；**档 a 行级暴露面如实承认**："改不了别人的盘但列得出来"（列表可见性=模型级）——已接受的边界，非漏洞 | 工单（表单组件查询）、事件/任务（不对外）、CMDB 直连（模型级授权、对外少、行级主要经云管） |
| b 可强制（判定两步主路） | 维度翻得成查询参数 | 契约登记 → 判定两步 | 云管账号/区域、Secret 按组 |
| c 兜底 | 维度翻不成查询 / 无契约 | 一次 filter 回调，或收紧到接口级 | 历史系统、边角场景 |

**配置门禁（白名单三步链，【待小改】）**：OpenAPI 供候选字段（路由表本就 OpenAPI 生成，顺手抽 parameters 参数表）→ 应用注册勾选"权限维度 + 必填（required）" → 包③区只能引用白名单（§4.1）——配了勾不出的字段 UI 禁配，三态：可强制 / 可兜底 / 不可达禁配。**包的范围字段必须与前端强制携带字段一致，否则配了验证不了的包=给自己挖坑**。

**诚实边界（防深挖）**：防**前端越权**（中心缺参/子集强制，不依赖前端诚实）与**防绕网关**（物理链路）；防不了"业务 API 无视该参数全量返回"——那是业务 bug，靠**一次性契约测试**兜住（受限用户请求结果 ⊆ 授权范围 + 判定字段=落库字段断言；**归属=档 b 系统上线前置检查，中心出对测脚本，不过=该域不得选判定两步主路、降档 c**）。**不搞对抗性设计**（内部自用，规范+门禁到位即可）。**机器调用方（脚本/服务间调用/定时任务）**：走**服务身份**（M2M 凭证+其自身策略），范围参数照契约携带——与前端同一判定两步，无特殊通道（没有"前端"的调用方，授权范围来自服务身份自己的策略）。

**头 vs 参数（历史口径）**：规范=**查询过滤条件放 query 参数、头只放身份/认证**；云管历史范围头（account/region 塞请求头）是第一版分头开发的土办法（非我做的），接手后规范成查询参数+包字段对齐——历史头登记为契约兼容通道；不断言老系统细节，只讲规范与机制。

**业界锚点（§8）**：强制参数+子集校验=多租户 tenant_id/claims 校验同款、fail-closed 常规；注入/RLS（行级安全）/查询改写=另一流派——锚点备查，不进正文主路。

### 5.3 拦截分层四道（"业务不配合怎么办"的标准答案）

| 层 | 拦什么 | 需要业务配合？ | 状态 |
|---|---|---|---|
| ① 网关 | **接口级 + 点操作数据级（URL 材料）+ 列表范围子集校验（档 b）**——请求进不了业务 | **不需要（物理在路径上）** | 【已实装】接口级；点数据级+列表子集【待小改】（中心读 X-Forwarded-Uri 头按路由表模板提取路径/查询参数——网关只转发头，提取执行方=中心） |
| ② 业务轻回调 | 列表兜底 filter、创建/存量 body-id 带体调用 | **需要——无 SDK、仅一处调用点/接口**（列表主路已零调用） | 【设计定稿】 |
| ③ 数据层（DB 行级安全/SQL 网关） | 数据级绝对拦截——SQL 自动过滤 | 不需要（物理强制） | 重手段备用 |
| ④ 执行侧（工单任务平台执行前判） | 队列型写操作最终防线 | 执行器配合（本来就归它） | 【已实装】 |

**面试口径**："点操作网关链路全包（材料在 URL=零配合、中心点查自足；材料在 body=供材通道分形态：真实网关插件整包转发、无插件带体调用补通道）；列表=判定两步（前端强制携带范围参数，缺参拒、越权拒），创建/存量 body-id 各一次带体调用；真正的强制面在网关——绕过网关直连业务的流量，接口级、点操作数据级、列表范围校验根本进不来。我们不承诺防住铁了心绕过网关直连数据库的代码，承诺**绕过必留痕、留痕必被审出**（网内端口收敛 + 业务请求日志与中心判定审计的缺口对账）。"

## 6. 完整场景走查（编辑磁盘 d-500，账号 123 授权）

```
申请期：选包「主机管理」→ 预设「管理·123」→ 参数 account=123 选一次
        → 层级带出 host+disk 域 → 各域范围落成独立策略（host{account=123}, disk{account=123}）

运行期：
  ① PATCH /disks/d-500
  ② 网关判定通道 → 中心：路由表查表得 cmdb:disk:edit（登记制零推断）+ 从请求头按模板提取 (disk, d-500)
  ③ 中心点查 d-500（按 (cmdb,disk) 约定）→ disk.account==123？ → ✅ → 2xx
       · 属账号 456 → account≠123 → 403（各域独立判定；防错位靠预设联动）
  ④ 业务收到放行请求 → 落库（业务全程零权限代码）
  ⑤ 兜底：绕过网关直连业务 = 进不了正常链路；工单型写操作在执行侧另判
```

**动作码锚定数据域**（复述钉死）：`cmdb:disk:edit` → model=disk → 契约 (cmdb,disk) → **disk 自己的取材路径**——从不"拿主机接口查磁盘"。

## 7. 与 2.0 的关系（演进项定位）

- 2.0（`plans/iam-distributed/`，六文件+对抗审查修订）**保留为演进项，本方案的内部接入面不实施其 SDK 与分布式 Agent**——点查自足 + 列表判定两步把运行期配合面缩到"创建一次调用+兜底"后，SDK/Agent 在内部接入面的存在理由（低侵入材料供给）已被消解（第三方口子三级另见 §1.5）；
- 其被 1.5 吸收的部分：**通用点查**（比 2.0 的按域 QueryDecl 更简，一系统一约定）、fetch-and-bring（**存量 body-id 与创建的带体调用即此思想的正式通道**——材料随请求到达判定点）；其"语义守卫/SDK 中间件"仅作为判定通道完全不可得时的备用手段记录，不排期（存量 body-id 已由带体调用覆盖，不再算"极端场景"）；
- **V3 与 2.0 的承接**：第三方口子三级（§1.5）的 V3 本地 Agent 就是判定型 Agent 的**正式入口形态**——2.0 由此是"按需可启的最高档"而非"被否掉的方案"；但判定下沉三件套（规则同步/审计回传/撤销窗口）的代价口径不变，且三级均成文未实施；
- 其已知边界如实记录：ORM 钩子拦不到"编辑=发工单"型副作用（1.5 下工单型由执行侧收口，天然覆盖）；撤销传播窗口是分布式固有代价（1.5 中心化即时撤销反而更优）。

## 10. 面试叙事与边界表

**叙事弧线（面试主动讲的版本）**："老系统 = 中心化做成了全量扇出（性能病）→ 这套权限中心（1.5）= **中心化判定 + 通用点查 + 列表判定两步，自设计即无投影**（数据零汇聚、材料就近供给/点查自取、范围强制携带，判定字段随契约登记）——判定集中（叙事稳/审计无损/即时撤销），数据零汇聚（无上帝视角/无新鲜度税）。"

**分层纪律（2026-10-03 定，防叙事与开发史混残留）**：**面试主动叙事不含投影兴废**——这套权限中心自设计即无数据投影；投影的中间试用与裁决下掉（太复杂、不好控制）属**开发层面历史**（§1.1 表 / §1.2 决策 2 / §9 #1），仅被追问数据同步时才按开发层答法讲；**Demo/开发过程细节一律不进主动话术**——叙事层与开发层分开维护，避免文档冲突不一致。

**边界表（说/不说）**：

| 说 | 不说 |
|---|---|
| "条件式的判定点跟着材料走，三套方案都是在回答材料问题" | 不说"某一套是唯一正解" |
| 主动叙事："**这套权限中心自设计即无投影**（数据零汇聚、取材点查）"；被追问数据同步才答开发层："中间阶段搞过投影，太复杂不好控制，最终裁决下掉、取材改点查，CMDB 切换中" | 不把投影兴废写进主动话术（开发史不进叙事）；不说"投影已删干净"（代码在跑、切换=待办 #1）；不说"存量保留"（口径已改） |
| "点操作零配合（URL 材料：网关+点查自足）；列表主路=判定两步（前端强制携带、缺参拒越权拒）；创建/存量 body-id 各一次带体调用；**点操作与列表主路运行期对中心零调用（带体调用除外）**；绕过网关直连=进不了正常链路（契约两件登记+一次性契约测试在前）" | 不说"业务零改造全覆盖"（带体调用接入+契约两件登记+档 b 前端改造如实讲）；不说"运行期绝对零调用"（带体调用如实讲）；不说"防住业务 API 不按字段过滤"（一次性契约测试兜住）；不说"技术上绝对防绕过" |
| "材料随请求到达判定点：真实 APISIX 链内插件整包转发 body（内部量级够用）、Demo Traefik=URL 材料走 forwardAuth+body 材料走带体调用——同一判定契约，供材通道按网关能力选；信封规范钉死材料位置，传输实现按成本选" | 不说"所有网关都能转发 body"（forwardAuth/auth_request 都不带体）；不说"id 必须放 URL"（业界无此标准）；不把"整包转发"说成安全设计（真实=够用，规范=信封位置） |
| "meta 谁都能填所以不信它：变更类按 id 点查权威行、身份只认 JWT；创建类伪造被授权集封顶；判定字段=落库字段由契约测试钉死" | 不说"信封防伪造是技术保证"（是设计姿态：不把信任放在自报材料上） |
| "动作码=三段式唯一标识（应用:资源:动作），开机=start 不硬塞'更新'；唯一被消费的分类=读/写一个 bit；运行期纯查表零推断，推断只在导入且需人确认；接入体检硬校验（缺码/重复/配置自洽/回源豁免）" | 不说"接口按增删改分类做授权"（业内没人这么做：RebootInstance/compute.instances.start/K8s subresource 都是独立动作）；不说"动作全自动零人工"（预填需确认，存量走人工档）；不起名保姆（同义词不管，机器只报硬错） |
| "列表范围字段有白名单配置门禁（OpenAPI 供候选、契约勾选、配不出验证不了的字段）；范围放 query 参数是接手后规范，历史头登记兼容通道" | 不说"老系统一直规范"（第一版分头开发塞请求头，非我做的）；不说"业界都这么干"（注入/RLS 只是流派锚点，我们按系统分档） |
| "发布系统自带权限、仅升级 ABAC 未并入——进度紧且无必要" | 不说"全部系统已接入"；不说"接不进"（是没接的必要） |
| "第三方口子三级成文（V1 代码/SDK → V2 挂网关 → V3 本地 Agent）：V1/V2 判定实时回中心，V3 本地判定（撤销上界+审计回传如实报）；**规范就绪**、没来得及接（发布系统=自带权限主动不并入、另两个组=想接没启动，两回事）" | 不说"外部系统已接入"；不把"规范就绪"说成"能力就绪"；不把 V2 网关/反代说成本地判定（它们回中心）；不说"V3 已实施/2.0 已上"（三级均成文未做）；不把"省网络路径"安到 V1/V2 头上（只有 V3 本地判定省） |
| "黑名单 deny-overrides 已实装，治理规范在补" | 不说"黑白名单体系已完善" |
| "2.0 是演进项，吸收了它的 SDK 与点查" | 不说"已实施分布式" |
| "零 X 类词带范围限定"（core 零系统知识/业务零权限逻辑） | 不裸说"零侵入/零风险" |

**一句话收束**：**动作靠登记不靠猜、判定跟着材料走、材料就近供给（带了就用带的，没带就点查）、列表两步带参即判、包是策展预设是场景、组合在申请侧、门禁挡不合格、强制靠组织**——这套就是 1.5。
