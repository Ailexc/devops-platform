## 二、为什么会这样？根因分析

### 根因 1：选错了工具

**错误**：试图在 `node -e` 内联脚本中做大量字符串替换。

**后果**：
- shell 引号转义地狱（`\"` 在单引号内不转义）
- 超长命令行难以调试
- 每次失败都要重新构造整个命令

**教训**：**涉及复杂字符串操作时，永远先写 `.js` 脚本文件，再 `node xxx.js` 执行。**

### 根因 2：没有先验证最小可行性

**错误**：一次性尝试替换所有函数（scopeOptRowHTML + pEdit + composeExpr + apStepHTML step3 + helpers），失败后无法定位是哪一步出了问题。

**后果**：花了 40+ 分钟在"到底是哪个替换导致语法错误"的排查上。

**教训**：**每做一步改动，立即验证（`node --check` 或浏览器刷新），确认 OK 再做下一步。**

### 根因 3：过度依赖正则匹配大段代码

**错误**：用正则匹配整个函数体（如 `h.match(/function scopeOptRowHTML[\s\S]*?(?=\nfunction composeExpr)/)`）。

**后果**：
- 正则对嵌套模板字面量不可靠
- 匹配结果可能包含多余或缺少内容
- 调试正则本身就是灾难

**教训**：**大段代码替换用精确字符串匹配（`str.replace(oldStr, newStr)`），不用正则。oldStr 取函数的第一行即可定位。**

### 根因 4：没有在执行前评估难度

**错误**：没有提前判断"修改 5 个函数 + 1 个数据结构"的工程量，直接开干。

**后果**：2 小时后发现只完成了 20% 的工作。

**教训**：**开始前先评估每一步的复杂度和风险，设定时间上限。超时就停下来重新评估。**

## 三、已经验证的正确路径

经过反复试错，我们找到了一条**验证过的、可靠的路径**：

```
1. scripts/build-v12.js 从 v10 读取
2. 用 str.replace() 做精确字符串替换（不用正则）
3. 每替换一个，立即 vm.compileFunction() 验证
4. 全部替换后，浏览器打开验证
```

**这条路径已经跑通了 Phase 1（数据+CSS+helpers）。**

## 四、剩余工作与可行路线

### 已确认的可行方法

```js
// build-v12.js 的模式：
function rep(js, label, search, replacement) {
  if (js.includes(search)) {
    js = js.replace(search, replacement);
    console.log(`  ✅ ${label}`);
  } else {
    console.log(`  ❌ ${label}: NOT FOUND`);
  }
  return js;
}
```

### 剩余 5 个任务（按依赖顺序）

| # | 任务 | 预估 | 风险 |
|---|------|------|------|
| 1 | 移除 `composeExpr` 函数 | 2 分钟 | 低（精确匹配删除） |
| 2 | 重写 `scopeOptRowHTML` | 15 分钟 | 中（长函数，需仔细匹配边界） |
| 3 | 重写 `pEdit` | 10 分钟 | 中（新增操作分支） |
| 4 | 重写 `apStepHTML` step3 | 15 分钟 | 高（最长最复杂的函数） |
| 5 | 更新 step4 预览逻辑 | 5 分钟 | 低（只改一处） |

**预估总耗时：45-50 分钟**（如果每步都验证通过）

### 执行策略

**关键原则：每步验证，超时止损**

```
Step 1: 移除 composeExpr → vm.compileFunction → OK → 继续
Step 2: 替换 scopeOptRowHTML → vm.compileFunction → OK → 浏览器验证编辑器
Step 3: 替换 pEdit → vm.compileFunction → OK → 浏览器验证编辑器保存
Step 4: 替换 apStepHTML step3 → vm.compileFunction → OK → 浏览器验证申请人
Step 5: 更新 step4 → vm.compileFunction → OK → 浏览器端到端验证
```

**止损规则**：
- 每步最多花 10 分钟
- 如果 10 分钟内无法完成，停下来，记录卡点，寻求其他方案
- 不要在同一步骤中同时修改多个函数

### 关于 `scopeOptRowHTML` 和 `apStepHTML` 的策略

这两个是最长最复杂的函数（各 50+ 行模板字面量）。直接在 build 脚本中写完整替换字符串风险高。

**更安全的策略**：
1. 先在浏览器控制台手动测试新函数逻辑（`page.evaluate()`）
2. 确认逻辑正确后，再写入 build 脚本
3. 写入后立即浏览器验证
