## 1. 背景与目标

**现状问题**

- 工作台是统计面板：各模块（我的申请 / 我的应用 / 我的组）只是展示列表，条目不可点击、不可跳转，交互价值低。
- 菜单按"对象"平铺（组织/组、策略、应用、主体、市场、审计），本质是管理员视角的功能清单，没有围绕当前登录用户组织。
- 用户实际心智是：**我是谁 → 我有什么权限 → 我要什么权限 → 我管理什么 → 我审批什么**。

**目标**

- 系统中心从"管理员控制台"转为"以我为中心的个人权限工作台"。
- 普通用户、应用 owner、组 leader、审批人共用同一套导航，靠**上下文过滤**浮现各自能力，无角色切换按钮。

## 2. 设计原则

1. **一切围绕"我"**：每个菜单默认呈现与我相关的数据。
2. **上下文过滤替代角色切换**：同一页面按我的身份显示不同操作（owner 显管理，普通用户显申请）。
3. **权限是聚合视图**：个人权限不是一张静态表，而是组织继承 + 个人 + 自建组 + 临时（TTL）多个维度的合并视图，且每条可溯源。
4. **应用双角色**：应用既是"被申请的资源方"，也是"可申请别家能力的主体方"。
5. **管理能力浮现式**：我是应用 owner / 组 leader 时才出现对应管理入口。
6. **全流程闭环**：申请 → 审批 → 开通 → 回收，每个状态可见、可追溯。

## 3. 信息架构（导航重组）

```
工作台（我的首页）
├─ 个人权限
│   ├─ 我的权限（权限展示）
│   │   ├─ 组织权限（仅末级组织可配置；组内/组外应用权限、组织成员）
│   │   ├─ 个人权限（多维度聚合视图：组织继承 / 个人直接授权 / 自建组 / 临时 TTL）
│   │   ├─ 自建组权限（我加入的自建组及其成员、权限、我的身份）
│   │   └─ 我的身份（组 leader / 成员 / 应用 owner / 审批人）
│   ├─ 权限申请（为自己 / 我的组织 / 我的自建组）
│   └─ 自建组（创建组 / 申请加入 / 退出 / 成员与权限管理）
├─ 应用权限
│   ├─ 应用管理（注册应用 / 我的应用清单 / 应用详情）
│   │   └─ 应用详情：全部权限（动作+数据）、对外暴露的权限、策略清单、分发记录、被申请记录
│   ├─ 策略管理（为应用配置策略 / 绑定应用 / 策略模板 / 发布 / 发布记录）
│   └─ 权限管理（谁在访问我的应用：程序 / 人 / 组织 / 自建组，查看与回收）
└─ 审计中心
    ├─ 我的申请（我发起的所有申请与状态）
    ├─ 我的发布（我发布的策略 / 授权记录）
    └─ 我的审批（待我审批 / 我审批过的）
```

> 建议：保留"全局入口（主体目录 / 全局审计）"作为权限到位才可见的只读合规入口，不放入主导航（对齐 `refactor-plan.md` §4）。

## 4. 功能需求

### FR-1 工作台（我的首页）

- 身份卡：姓名、所属组织、组织内身份、自建组身份、应用 owner 身份。
- 权限概览：按维度汇总（组织权限数、个人权限数、自建组权限数、临时权限数）。
- 待办：待我审批数、进行中的申请数。
- 快捷入口：我的应用、我的自建组、权限申请。
- **交互要求：所有卡片、列表条目均可点击跳转到对应详情页；数字即入口**（本次改造的直接诉求）。

### FR-2 权限展示

#### FR-2.1 组织权限

- 展示我的组织树与我的组织节点。
- 组织权限 = 该组织配置的权限，拆分为**组内应用权限**与**组外应用权限**。
- 组织人员：组织成员列表。
- 规则：**仅末级（叶子）组织可配置权限**；非末级组织只读查看（继承规则待确认，见 §7）。

#### FR-2.2 个人权限（聚合视图）

- 聚合维度：
  - 组织继承：组织配置后继承到我的权限；
  - 个人直接授权：我为自己申请并通过的权限；
  - 自建组权限：我加入的自建组挂载的权限；
  - 临时权限：TTL 临时授权，含到期时间。
- 每条记录字段：权限名称、动作、数据范围、来源（哪个组织/组/申请单）、授予人、时间、有效期、状态。
- 交互：支持按维度筛选、搜索；点击记录 → 查看**授权链**（谁给我、经由哪张申请单、审批人是谁）。

#### FR-2.3 自建组权限

- 我加入的自建组列表：组名、组长、成员数、我的身份。
- 组详情：成员列表、组权限、组有效期、我的身份（组长/成员）。
- 组长能力：成员管理、权限配置、转让/解散。
- 成员能力：查看、退出。

#### FR-2.4 我的身份

- 身份维度汇总：组织身份（leader/成员）、自建组身份（组长/成员）、应用身份（owner/使用者）、审批人身份。
- 说明我的管理范围：我能管理哪些组织、哪些应用、哪些自建组。

### FR-3 权限申请

- 申请对象三选一：**我自己 / 我的组织 / 我的自建组**。
- 申请内容：应用 + 动作 + 数据范围（从能力目录选择，建议联动 `plans/capability-manifest.md` 的智能申请表单）。
- 申请单：风险等级、审批链、状态流转（待审批 / 通过 / 驳回 / 已回收）。
- 我的申请列表在审计中心可见。
- 规则：申请人不进入自己的审批链；高风险自动追加审批节点。

### FR-4 自建组管理

- 创建自建组：组名、成员、挂权限、有效期（TTL）。
- 申请加入自建组：浏览可加入的组 → 申请 → 组长审批。
- 退出自建组：成员可主动退出；组长转让或解散。
- 规则：创建 / 加成员 / 挂权限均走审批（对齐 `refactor-plan.md` §3.1）。

### FR-5 应用管理

- 应用注册：应用信息、能力声明（动作 + 数据）、owner（建议 ≥2）。
- 我的应用清单：我注册 / 拥有的应用。
- **应用详情页**：
  - 应用全部权限（动作、数据）；
  - 对外暴露的权限（能力目录 / 权限市场可见）；
  - 策略清单（我发布的策略及绑定关系）；
  - 分发记录（策略分发、bundle 状态，对齐 OPA bundle 设计）；
  - 被申请记录（谁申请了我的应用权限）。

### FR-6 策略管理

- 为我的应用配置策略：动作 + 数据范围 + 效果（允许 / 拒绝）。
- 绑定应用：策略与应用的关联；从应用视角看到"发布了哪些策略"。
- 策略模板：可复用的策略 → 发布 → 他人可申请（形成模板化资产）。
- 发布记录：版本、发布人、时间、状态、被申请次数。
- 规则：策略变更走审批；版本可回滚（对齐 policy_versions 设计）。

### FR-7 权限管理（我的应用被谁访问）

- 访问者视图：**程序（M2M client）/ 人 / 组织 / 自建组**。
- 每个访问者可查看：授予的权限、来源（owner 发布 / 申请审批）、有效期、状态。
- 管理操作：调整、回收（回收走审批）、查看访问记录。
- 建议：同时提供反向视图"我的应用申请了谁"（应用作为主体方），形成双向账本。

### FR-8 审计中心

- **我的申请**：我发起的全部申请，状态、审批链、结果。
- **我的发布**：我发布的策略 / 授权 / 模板记录。
- **我的审批**：待我审批的 + 我审批过的；审批操作入口。

## 5. 页面可见性规则（上下文过滤）

| 身份 | 可见能力 |
|---|---|
| 普通用户 | 我的权限（只读）、权限申请、自建组加入/退出、审计中心（我的） |
| 组 leader | + 组成员管理、组权限配置（自建组；组织权限按末级规则） |
| 应用 owner | + 应用管理、策略管理、权限管理（仅我的应用） |
| 审批人 | + 审批中心（按审批链路由） |

## 6. 交互规范（前端统一要求）

- 工作台所有模块条目必须可点击跳转。
- 列表统一：点击行 → 详情页或抽屉；数字 / 徽标 → 过滤后的列表页。
- 空态、加载态、错误态完整。
- 权限类操作给出**影响范围提示**（授予谁什么权限、影响哪些人 / 应用）。

## 7. 待确认问题（需业务拍板）

1. 末级组织的定义：以组织树叶子节点为准？父组织能否查看 / 管理子组织权限？
2. 组织权限继承：父级配置自动继承给子级，还是各叶子独立配置？
3. "组外应用权限"的范围：兄弟组织、整个系统，还是仅"非本组应用"？
4. 个人权限的"个人"维度：是否包含个人直接申请 + 临时授权两部分？
5. 权限管理中的"程序"：是否对应现有 OAuth2 client / service？是否要求 owner ≥2？
6. 策略与模板关系：策略 = 能力 + 数据范围 + 来源；模板 = 可复用策略并发布到市场？
7. 审批链规则是否沿用 `refactor-plan.md` §3.1（申请人退出、双 owner 互批、自动路由）？
8. 是否需要保留全局只读入口（主体目录 / 全局审计）？权限如何控制？
