第一章 · 市面常见应用间鉴权方式

应用之间（机器对机器，M2M）的主流做法，本质都是「出示一个身份凭据，让对方验证后放行」，区别在于凭据的形态、签发方与校验方式。

1.1 静态 Token / API Key 最简单

  • 怎么做：平台给调用方签发一个固定字符串（如 X-API-Key: k_xxxx），调用时放在请求头；服务端查表/比对后放行。
  • 优点：实现简单、接入快；缺点：无状态性弱（要查签发记录）、泄漏面大、难以精细化控制（scope）。
  • 典型场景：内部工具脚本、低频调用、只读接口。

1.2 OAuth 2.0 Client Credentials M2M 主流标准

  • 怎么做：应用以 client_id + client_secret 向授权服务器换取 短期 access_token（通常是 JWT）；后续请求携带 Authorization: Bearer <token>；服务端验签（JWKS）+ 校验 aud / scope / exp。
  • 优点：标准化、令牌无状态（验签即可）、可吊销（黑名单/短 TTL）、支持 scope 最小权限；缺点：需要一套授权服务器与密钥轮换。
  • 典型场景：云厂商 SDK（AWS/GCP）、企业服务间调用的事实标准。

1.3 mTLS / SPIFFE 最强身份，最重基建

  • 怎么做：调用方与服务端互验证书，身份在 TLS 握手层建立，不依赖 token 字符串；SPIFFE 进一步为每个工作负载签发标准化身份（SPIFFE ID）。
  • 优点：最强、零 token 处理、天然防重放；缺点：证书生命周期管理（签发/轮换/吊销）成本高，需要 PKI 基建。
  • 典型场景：服务网格（Istio）、高安全合规环境。

1.4 OIDC / 委托令牌 涉及"人"的场景

  • 怎么做：用户经企业 SSO 登录后，应用获得 ID Token / Access Token（OIDC 标准），代表「某个用户」访问下游；可叠加 on-behalf-of 流在服务间传播身份。
  • 适用：需要用户级身份与审计的应用间调用（区别于纯 M2M）。

1.5 对比表

第二章 · 认证 vs 鉴权：谁先谁后

两个概念必须分开，顺序也不能反。

🔐 认证 AuthN（你是谁）

  • 验证凭据有效：JWT 验签、secret 比对、证书校验
  • 产出可信身份（如 client:xxx / u:alice）
  • 无状态、廉价，每请求可做

🛡️ 鉴权 AuthZ（你能不能）

  • 基于可信身份做授权决策：动作级（RBAC/ABAC）+ 数据级（实例/条件）
  • 可缓存 / 本地 bundle，高风险写强制远程
  • 决策结果：allow / deny + 理由留痕

为什么认证必须在前

  1. 决策前提：不知道「你是谁」，就无法判断「你能不能」——鉴权的主体输入来自认证结果；
  2. 防绕过：若先鉴权后认证，攻击者可用伪造身份绕过授权检查；
  3. 审计完整：决策日志需要记录「谁」被拒绝/放行，身份必须先被确认。
顺序铁律：认证 → 鉴权 → 放行/拦截。身份不可信之前，任何授权决策都无效。

身份如何在链路中传播

在我们的系统中，身份通过标准化主体键传播：

// JWT 载荷（IAM 签发）
{
  sub: "s:client-cmdb-xxxx",   // 程序身份
  st: 2,                          // 1=user 2=service
  sk: "s:client-cmdb-xxxx",     // 决策主体 key
  scope: "app:cmdb",             // 已授权范围
  iss: "iam", exp: …        // 签发方 + 过期
}

// 网关模式：身份头由网关注入/透传
X-User: client:cmdb        // PEP → PDP 决策主体
X-App: cmdb                // 目标应用

第三章 · 我们的系统支持哪些鉴权方式 & 为什么

回到权限中心：接入方式 = 网关（Tier 1）或 SDK（Tier 2），凭据形态由 IAM 统一签发。

3.1 支持矩阵

方式支持状态凭据为什么能支持
OAuth2 Client Credentials✅ 支持（已实现）client_id + client_secret → JWTIAM 内置 POST /v1/oauth/token，签发 HS256 JWT（短 TTL、带 scope），网关/SDK 验签即可
静态 Token✅ 支持（已实现）X-Auth-TokenIAM 签发固定 Token（一次性展示、存哈希、可吊销轮换），PDP 查签发记录映射授权范围
API Key✅ 支持（已声明）X-API-Key与静态 Token 同机制，适合 SDK/脚本轻量接入
mTLS / OIDC🔶 演进方向（仅声明，不承诺执行）证书 / IdP 令牌依赖 PKI / 企业 IdP 基建，本期展示声明，接口已预留

3.2 为什么能支持多种方式

  1. 统一凭证体系：所有方式都收敛到「IAM 签发 → 网关/SDK 校验 → PDP 决策」一条主链路，凭据只是入口形态不同；
  2. JWT 无状态验签：OAuth2 令牌验签廉价、每请求可做（解决「v1 每请求远程鉴权太重」的历史痛点）；
  3. 鉴权与凭据解耦：凭证 = 身份（一次），能力包申请 = 追加 scope（多次）；每次换取的 JWT 只含已授权 scope——支持多少种鉴权方式，都不影响授权模型；
  4. 双执行点：网关集中校验（零改造）或 SDK 本地校验（任意接入），执行点可换、决策不变。
🔄 关键叙事：这不是"每加一种鉴权方式就加一套鉴权逻辑"，而是把复杂度收敛到统一令牌体系——鉴权方式只解决「身份怎么来」，权限怎么给始终由能力包/预设/scope 决定。

3.3 既然 token 都是 IAM 签发的，应用为什么还要声明支持哪些鉴权方式？

签发方统一 ≠ 受理方不需要声明。「谁签发」是供给侧的事，「我接受哪种方式接入」是应用自己的受理契约——这是两个层面。

💡 类比：银行统一发卡（签发方只有一个），但每个商户要声明支持银联 / Visa / 支付宝——发卡统一，但「我接受哪种支付方式」是商户的受理契约。
  1. 接入向导的选项来源：应用市场发起接入申请时，可选的鉴权方式列表 = 提供方 app.auth 声明；不声明，消费方就不知道该选什么、流程怎么走；
  2. 执行点兼容性（最关键）：网关模式由网关统一验 JWT/Token，应用零改造；SDK 模式验签发生在应用内部——SDK 验 JWT 需要 JWKS/密钥、查静态 Token 需要查签发表，应用必须声明它实际能处理哪种，否则接进来也验不了；
  3. owner 自主控制：有的应用只愿意开放某一种方式（如只允许 OAuth2、拒绝固定 Token），声明就是契约边界；
  4. 演进展示：mTLS / OIDC 目前 IAM 并不签发，但应用可以声明「未来支持」——如果声明等于「当前能签发」，演进方向就永远不会出现在市场里，叙事就断了。
一句话：签发能力 = IAM 供给侧统一；鉴权方式声明 = 应用侧受理契约 + 消费方引导 + 执行点能力 + 演进 roadmap，缺一不可。

第四章 · 双方各自要做什么

一次应用间接入 = 提供方（能力方）声明 + 使用方（消费方）申请，双方职责分离。

🏛️ 提供方（能力方）

  • 注册应用：声明 OpenAPI / 网络信息 / 鉴权方式（云、账号、区域、VPC、安全组、支持哪些鉴权方式）
  • 接入执行点：入网关（Tier 1，零改造）或集成 SDK（Tier 2）——发布能力的前提
  • 声明能力包：接口 + 预设 + 数据范围（owner 配置 applicant 可选类型）
  • 审批：接入申请、能力申请、上架下架的 Owner 确认

🔧 使用方（消费方）

  • 发起接入申请（一次）：选目标应用 + 鉴权方式 + 网络打通 → 审批 → 拿到凭证
  • 申请能力包（多次）：选预设 + 主体 + 数据范围 → 审批 → 追加 scope
  • 调用：凭证换令牌 → 携带令牌调目标接口 → 被网关/SDK 放行或拦截
  • 凭证维护：轮换、吊销、监控授权状态
事项提供方使用方系统（IAM）
应用注册/声明✅ 填写—存储 + 校验
执行点接入✅ 网关/SDK—校验强制路径
能力包/预设✅ 配置—校验 + 发布
接入申请✅ 审批✅ 发起✅ 签发凭证
能力申请✅ 审批✅ 发起✅ 追加 scope / 写策略
调用校验网关/SDK 执行✅ 携带令牌✅ PDP 决策 + 留痕

第五章 · 网关接入 vs SDK 接入

两者共享同一套凭据体系与决策逻辑，差异在执行点位置与改造量。

维度🌐 网关接入（Tier 1）📦 SDK 接入（Tier 2）
执行点位置集中（Traefik 网关，forwardAuth → PDP）应用内（SDK/agent 验签 + 本地决策）
应用改造量零（网关统一处理）集成 SDK（验签 + 调 PDP / 嵌 bundle）
认证（你是谁）网关层校验/透传 X-User应用内验 JWT（JWKS）或信任网关注入头
动作级鉴权远程 PDP（决策缓存加速）本地 bundle（Casbin 快照，低延迟/可离线），高风险强制远程
数据级鉴权远程 OpenFGA（实例/条件）同左（远程 OpenFGA）
降级行为网关集中，PDP 不可用即拦截（fail-closed）本地 bundle 仍可动作级决策（stale-but-available）
绕过防护网关外无法直连受保护应用应用自身校验，无网关兜底

5.1 流程对比

🌐 网关模式

  1. 调用方带令牌/身份头请求
  2. Traefik forwardAuth → PEP：解析 method/path → 权限点 action
  3. PDP 决策（缓存/Casbin/条件）→ 200 放行 / 403 拦截
  4. 放行后转发业务请求到目标应用

📦 SDK 模式

  1. 调用方带 JWT 请求
  2. 应用内 SDK 验签（认证）
  3. 动作级：本地 bundle（Casbin）决策；高风险/数据级：远程 PDP / OpenFGA
  4. 应用内拦截或放行
相同点：认证在前、凭据体系一致、最终都由同一套策略（Casbin + OpenFGA）做决策。不同点：执行点位置（集中 vs 本地）与可用性策略（fail-closed vs stale-but-available）。

5.2 一个签发方、多个验签方：为什么能成立

核心原理：验签不需要「问签发方」，验签者只需持有「验证材料」，本地就能算出来。这是密码学签名的性质。

实现签发验签说明
对称 HS256（本系统 demo）共享密钥同一共享密钥本地重算签名谁拿到密钥谁就能验；密钥需安全下发到各可信组件（JWT_SECRET）
非对称 RS256 / ES256 + JWKS（生产标准）私钥（仅 IAM 持有）公钥（可公开分发，经 JWKS 端点下发）公钥不保密，复制一万份也安全；私钥只有 IAM 有，别人伪造不了
💡 类比：央行统一印钞（签发方一个），但每个商户都有验钞机（验签方无数）——验钞是本地动作，不需要打电话问央行；印钞母版（私钥）只有央行有，验钞特征（公钥/验钞机）大家都有。
  • 验签 = 本地计算（哈希 + 签名算法验证），零网络往返、无状态、廉价；
  • 令牌可信 = 验签通过 + exp / aud / iss 检查通过，不需要查数据库、不需要每次回源 IAM；
  • 这就是 JWT 的设计目的：签发一次、到处验证——认证本地化（治 v1「每请求远程鉴权太重」的痛点），鉴权才需要决策。
IAM（签发）                           网关 / SDK（验签）
私钥 / 共享密钥 ──签发──▶ JWT ──验证──▶ 本地算签名一致 + exp 未过期
（只有 IAM 能造）                      （任何持验证材料者都能验）

5.3 执行点 PEP 位置是什么意思

PEP（Policy Enforcement Point，策略执行点）= 「拦截请求、发起鉴权、执行放行/拦截」的那段逻辑跑在哪。

🌐 网关接入📦 SDK 接入
PEP 在哪网关（Traefik forwardAuth 中间件）应用内部（应用进程里的 SDK）
请求路径Client → 网关拦截 → 调 IAM 决策 → 放行才转发给应用Client → 应用内 SDK 拦截 → 决策 → 应用自己放行/拦截
应用改造零（应用无感知）要集成 SDK
流量约束 / 降级必须过网关（否则可绕过）；PDP 挂了 fail-closed 全拦无集中点，应用自己兜底；本地 bundle 可 stale-but-available
 
网关模式： Client → [ 网关 = PEP：验签 + 调 IAM ] → 应用（不感知鉴权）
SDK 模式： Client → 应用内 [ SDK = PEP：验签 + 本地bundle/远程IAM ] → 业务逻辑
三者各司其职：签发（IAM）集中、验签（PEP 本地化）分散、决策（PDP）集中——IAM 只管发 token 和做决策，验签是任何持验证材料者都能做的廉价本地动作，所以网关能做、应用内 SDK 也能做。

第六章 · 端到端工作流（从头到尾）

三个阶段：接入（一次）→ 授权（多次）→ 调用（每次）。

阶段一 · 接入：身份与网络就绪（一次）

① 提供方注册应用并声明
OpenAPI / 网络信息（云/账号/VPC/安全组）/ 鉴权方式；接入网关或 SDK（发布能力的前提 = 至少一条强制路径）
② 使用方发起接入申请
在「应用市场」选择目标应用 + 鉴权方式（如 OAuth2 Client Credentials）+ 网络打通（并入本次申请）
③ 提供方 Owner + 平台审批
SoD：申请人 ≠ 审批人；审批通过即生效
④ IAM 签发凭证
生成 client_id/client_secret（明文仅展示一次，库中只存哈希）；凭证 = 身份，长期有效可轮换

阶段二 · 授权：追加 scope（多次）

① 使用方在「能力市场」申请能力包
选预设 → 主体（双主体：grantee=程序，applicant=人代理）→ 数据范围（6 类型表单，自动生成 CEL 表达式）
② 提供方审批
审批链按风险分级（删除=高、M2M=至少中、数据级=中+）
③ 生效：追加授权
Casbin 策略（动作级）+ OpenFGA 关系/条件（数据级）写入；凭证不变，scope 增加

阶段三 · 调用：认证 → 鉴权 → 放行（每次）

① 换取令牌（认证起点）
POST /v1/oauth/token（client_credentials）→ 短 TTL JWT（含已授权 scope）
② 请求进入执行点（认证校验）
网关验签/透传身份，或 SDK 验 JWT → 得到可信主体 client:xxx
③ 鉴权：动作级
PEP 解析请求 → action → PDP：决策缓存 → Casbin（RBAC）→ ABAC 条件；高风险写强制远程
④ 鉴权：数据级
OpenFGA：tuple 关系（实例）/ condition（CEL 条件，variable 按 grantee 解析）
⑤ 放行 / 拦截 + 留痕
200 转发业务请求；403 deny-by-default；决策日志（TraceID 贯穿 PEP→PDP）

6.3 凭证签发：到底谁来做（职责边界）

结论：凭证签发必须是 IAM（身份平台）来做；工单是编排载体；办理人（应用负责人）只做审批决策、不做密钥操作。这是「授权与开通分离」最关键的分界。

选项结论理由
A · 工单通过后 IAM 签发✅ 推荐（业界标准）凭证涉及密钥生成/哈希存储/轮换/吊销，必须由身份平台做；且凭证要绑定 IAM 的身份与 scope、进审计
B · 工单调用某系统签发本质是 A 的变体ITSM 是流程状态机+审计载体，不持有密钥能力；「某系统」= IAM/Vault 时等价于 A（工单只触发、不生成）
C · 办理人（应用负责人）签发❌ 不推荐人工接触明文（泄漏面）、无自动轮换/吊销、绕过审计、secret 流转不可控——负责人只做审批决策

✅ 正确顺序

  1. 接入申请 → 提供方 Owner + 平台审批（SoD）
  2. 前置工单：网络打通等落地动作（ITSM 编排）
  3. 工单 done → 回调 IAM
  4. IAM 签发凭证（client_id/secret，哈希存储、一次性展示）→ 激活授权

业界佐证

  • OAuth2：client 凭证由授权服务器（AS）签发，审批走管理面、签发永远在 AS
  • HashiCorp Vault：审批通过后由平台调用 Vault 生成动态凭证，ITSM 不碰密钥
  • AWS：policy attach（审批）与 STS 签发临时凭证（签发）天然分离
审批通过 ≠ 立即签发：要等前置工单 done 回调后，IAM 才签发并激活——签发归 IAM、编排归工单、审批归负责人，三者不越界。

第七章 · 业内怎么做 & 我们的定位

"全包"在商业产品里少见，但在"企业内部一体化权限平台"里是业界主流形态——我们的定位是后者，而且每个模块都有清晰的业内对应物。

7.2 我们的定位：企业内部统一权限平台

大厂内部自研的 IAM / 权限中台（Google Zanzibar 只是其中"授权"一块，Stripe / 字节 / 美团都有）正是这种形态：内部可以强约束（所有应用必须接入平台），所以能把 认证 + 授权 + 目录 + 审批 + 开通 串成一条主链路。我们不是"大包大揽"——网络打通由用户在 ITSM 提单、验签由双方系统开发协商，平台只提供便利性入口。

7.3 真正值得强调的三个设计理念

  1. 授权与开通分离：许可决策永远闭环在 IAM；网络打通、凭证签发是"落地动作"走工单（demo 模拟 + 预留 webhook）——业界共识，权限平台不负责网络、但可与网络平台联动；
  2. 决策统一、执行分散：一套策略（Casbin + OpenFGA），网关或 SDK 两种执行点——对应业界"PDP 集中 + PEP 多处"的标准架构；
  3. 凭证与授权分离：接入签发凭证一次、能力包追加 scope 多次——对应 OAuth client registration + APIM subscription 模式。
🎤 标准答法："商业产品是分域的（IdP / 授权引擎 / API 网关 / ITSM 各自独立），靠集成拼装；我们的系统对标企业内部一体化权限平台——把身份、授权、目录、审批、开通串成一条主链路，同时严格保持授权与开通分离，网络/工单这类落地动作通过对接外部平台完成（demo 用模拟 + webhook 预留体现这个边界）。"

第八章 · OAuth2 与 SSO：协议、模块与单点登录

把"OAuth2 是不是一个独立系统"、"人的登录（SSO）和程序调用（client_credentials）是什么关系"讲清楚。

8.1 OAuth2 是协议，不是系统

OAuth2 是一份协议（规范），不是一个系统。业界说的"OAuth2 系统"，本质都是内置 OAuth2 能力的身份平台（IdP / 授权服务器 AS）——Okta、Auth0、Keycloak、Azure AD 都是"身份平台里带一个 OAuth2/OIDC 模块"，而不是单独部署一套"OAuth2 系统"。

资源所有者(人/owner) ──授权──▶ 授权服务器 AS（签发 token）◀──拿令牌── 客户端 Client
                                    │ 校验 / 放行                │ 带 token 访问
                                    ▼                           ▼
                              资源服务器 RS（被访问应用）◀──────────┘
AS 能力清单我们的现状
Client 注册（client_id/secret、哈希存储、轮换）✅ 已有
Token 端点（client_credentials）✅ 已有
JWT 签发（短 TTL、带 scope）✅ 已有
JWKS 端点（资源服务器拉公钥验签）⏳ 生产化补齐（demo 用 HS256 共享密钥）
授权码流（人登录）⏳ 可对接公司 IdP 替代，不自建
Introspection / 吊销⏳ 演进
IAM 内置 OAuth2 模块 = IAM 就是授权服务器；不需要为 M2M 单独上 Keycloak/Auth0——多一个独立 AS 就多一个身份源，违背统一身份。分工建议：程序身份走 IAM 自建 AS（client_credentials），人的身份走公司统一 IdP（OIDC 对接）。

8.2 SSO：一次登录、处处免登（企业真实架构）

典型企业流程：用户经 EAA（企业应用接入层/网关） → Okta（IdP 身份提供商） 认证 → 门户统一认证系统（SP/RP + 会话代理） 把认证结果换成门户会话/JWT → 进入平台中心 → 访问任意内部应用免登。

你的组件标准角色
EAA 平台企业应用接入层 / 零信任网关（网络接入 + 代理）
OktaIdP 身份提供商：认证，签发身份断言
门户 auth 认证系统SP/RP + 会话代理：对接 Okta，向内部应用分发信任
内部应用SP/RP：信任门户/IdP 的认证结果，不再自己登录

概念层级：SSO 是目标（体验），SAML 2.0 / OIDC 是实现它的协议；OIDC = OAuth2 + 身份层（ID token 携带"人是谁"）。

8.3 SSO 与 OAuth2 的重合与分工

维度门户 SSO（人的场景）我们当前的 OAuth2（程序场景）
对象人（浏览器会话）程序（M2M）
流程OIDC 授权码 / SAML + 会话 Cookieclient_credentials + JWT
身份载体ID token / 门户会话 JWTaccess token（程序身份）
验签/传播门户注入身份头 / 应用校验 token网关/SDK 验签 + X-User 注入
与权限中心关系认证（你是谁）——上游认证 + 鉴权（全链）
🔗 关键衔接：门户 SSO 的"认证后给各应用注入身份"与我们网关的 X-User 身份头注入是同一套思想。落地：门户认证成功 → 向各应用/网关注入 X-User → 我们的网关/PDP 继续做鉴权——SSO 解决"人怎么登录"，权限中心解决"能不能访问"，零重叠、严丝合缝。
统一身份（SSO：人登录）+ 统一授权（权限中心：能不能）+ 统一执行（网关/SDK）——认证与鉴权分离叙事的完整闭环。

第九章 · 面试叙事要点

把上面的细节压缩成可讲的叙事主线。

  • 外部化授权四组件：PEP（网关/SDK 执行点）→ PDP（iam-server 决策）→ PAP（管理面：能力/预设/策略）→ PIP（身份与数据源）；
  • 认证与鉴权分离：JWT 验签无状态每请求可做（治 v1 每请求远程鉴权的痛点）；鉴权走缓存/本地 bundle，仅高风险写强制远程；
  • 凭证与授权分离：接入申请签发凭证（一次），能力包申请追加 scope（多次），每次 JWT 只含已授权 scope——OAuth client registration + subscription 模式；
  • 数据级条件授权：OpenFGA（Zanzibar 系）+ CEL condition，范围字段类型系统把表达式收敛为 6 种表单、系统生成并 cel-go 真解析；
  • 双模式接入：Tier 1 网关（零改造、fail-closed）与 Tier 2 SDK（本地 bundle、stale-but-available），同一套策略两种执行；
  • 授权与开通分离：网络打通/凭证签发是落地动作（工单），授权决策始终闭环在 IAM 令牌体系。
🎤 一句话总结：身份来自 IAM、决策来自 PDP、执行在网关或 SDK，凭证一次、scope 多次、审计全程。
