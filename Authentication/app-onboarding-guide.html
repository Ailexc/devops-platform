2第 ③ 步的关键：两种接入方式

应用的前端请求后端，怎么经过网关？关键看应用部署在不在网关后面

方式 A：经统一网关 forwardAuth · 推荐

应用挂在网关后面，所有 /api 请求都被网关先"过一道验票闸机"

🌐浏览器打开 app.xxx.orb.local
↓
🛡️统一网关Traefik 先拦截所有 /api/*
↓
🔍校验 JWTforwardAuth → 认证中心 /verify
↓ 通过则注入 X-Auth-* 头
📦业务后端零鉴权，读 X-Auth-* 头即知是谁
✅ 特点：业务系统几乎不用写鉴权代码；网关统一管所有应用的"验票"。适合网关能覆盖到的应用。
本 Demo mock-app 就是这种方式，已验证：无 token → 401，带 token → 放行。

方式 B：不经网关 JWKS 自验签

应用在网关外面（外部部署 / 后端互调），自己验 JWT

📦业务后端直接收到带 Bearer JWT 的请求
↓
🔑本地验签拉认证中心公钥 JWKS 验 JWT 签名
↓
👤读身份从 JWT 取 uid / name / source
↔
🔐认证中心只发布公钥，不参与每次请求
✅ 特点：因为 JWT 用 RS256 非对称签名，公钥公开，任何系统都能独立验签，不依赖网关。适合外部/内部服务。
每语言 加 20-30 行中间件即可（Go / Python / Node 都有 jose 库）。

两种方式对比

维度方式 A：网关 forwardAuth方式 B：JWKS 自验签
谁校验 JWT统一网关（业务后端零鉴权）业务后端自己（本地验签）
业务后端改动几乎零（读 X-Auth-* 头即可）加一个验签中间件（20-30 行）
适用场景应用在网关后面外部部署 / 后端到后端互调
优点集中管控、业务改动最小、一处升级全局生效不依赖网关、适合异构外部系统
代价需要网关能路由到该应用（跨项目较繁琐）每个系统都要维护验签依赖
本 Demo✅ mock-app 已实现机制已具备（JWKS 公钥已发布），可补示例

3方式 A 细看：一次请求怎么走

以"用户从门户点进应用 → 应用前端调后端 API"为例（泳道图）

👤 浏览器 🏠 门户 📦 业务前端 🛡️ 网关 📦 业务后端 🔑 认证中心
登录门户（一次）
拿到统一 JWT
点击应用 → 带 token 跳转
前端把 token 存好，调 API 时带 Authorization: Bearer JWT
拦截 /api/* → 转发给认证中心校验
200 + 注入 X-Auth-* 头
放行，转发请求 + X-Auth-* 头
返回数据（后端读 X-Auth-* 头就知道是谁）
→ 全程免登录，用户无感知
⚠️ 注意：用户访问的业务页面本身（静态资源）可以不经过 forwardAuth（SPA 先加载再带 token 调 API）；业务 API 才是被网关真正保护、需要验票的部分。

4client_id / client_secret 到底干嘛的？

这俩凭证在"token 跳转"模式下用不上，在"OIDC 授权码"模式才是主角

SSO 类型需要 client_secret 吗为什么
token 跳转
本 Demo 现状		 ❌ 不需要 门户直接签发 JWT 带过去，网关/后端验 JWT 签名即可。"凭证"就是 JWT 本身，用不到 client_secret。
OIDC / OAuth2 授权码
真实企业 SSO 主流		 ✅ 必须 见下方流程图：client_id 标识"是哪个应用"；client_secret 证明"我是这个应用的后端"，用于拿授权码换 token。

OIDC 授权码模式里它们怎么用

👤 用户 📦 业务前端 📦 业务后端 🔑 认证中心
访问业务系统（未登录）
302 → 认证中心 /authorize?client_id=xxx
client_id = 应用身份证（公开）
用户登录授权
302 带回授权码 code
后端 POST /token?code + client_secret
client_secret = 应用后端的密钥（机密，只存后端）
校验通过 → 发 access_token + id_token
建立会话 → 正常访问
✅ 一句话总结：client_id 是"我是谁"，client_secret 是"我真的是我"。它俩用于 OIDC/OAuth2 场景——应用后端向认证中心换取 token 时的身份凭证。我们 Demo 先自动生成它们，是为接 OIDC 预留的完整应用凭证模型（面试正好讲这个知识点）。

5一份接入前的自查清单

把上面的内容浓缩成可执行的核对项

  1. 确定接入方式：应用部署在我们网关后面？→ 选 A（forwardAuth）；在外部/内部服务？→ 选 B（JWKS 自验签）
  2. 注册应用：在门户「应用管理」填写信息，拿到 client_id / client_secret 和统一 JWT 的验签公钥地址 /.well-known/jwks.json
  3. 前端改造：登录流程改为"从门户跳转读统一 JWT"（存好 token，调 API 时带 Authorization 头）；401 时跳回门户登录
  4. 鉴权打通：方式 A → 网关加一条路由 + forwardAuth；方式 B → 后端加 JWKS 验签中间件
  5. 验证闭环：门户登录 → 点应用 → 无感进入；无 token 直访 → 401
💡 面试可以这样讲：先讲"统一门户 + 统一 JWT"，再讲"两种接入模式（网关/自验签）"，最后用 client_id/client_secret 引出 OIDC 授权码流程——一条线把整个 SSO 串起来。
