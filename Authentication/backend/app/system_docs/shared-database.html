为什么数据库要"外部共享"

本项目的数据库（PostgreSQL，容器名 devops-postgres）独立于认证中心容器运行，是一个"外部共享库"。这样设计的原因：

  • 数据不随容器销毁：容器重建、镜像升级不会丢数据；
  • 多服务可共享：门户、认证中心、后续服务都能访问同一份数据；
  • 贴近生产：真实系统里数据库就是独立基础设施，高可用、备份、扩容都与应用解耦；
  • 对比进化：早期 Demo 用 SQLite（单文件、零依赖），标准化后迁移到 PostgreSQL 共享库，也是本项目的演进亮点。

连接方式

认证中心通过环境变量 DATABASE_URL 连接外部共享库：

# docker-compose.yml 中 auth-backend 的配置
DATABASE_URL=postgresql://devops:devops@devops-postgres:5432/devops_auth

# devops-postgres 是独立的外部容器（不在本 compose 内），
# 通过 OrbStack 的容器网络（devops-net）互通

启动时认证中心会等待数据库就绪（wait_for_db.py），再执行建表与种子数据。

数据库表结构

表名作用关键字段
users用户账号username / password_hash(bcrypt) / is_admin / source
app_registrations应用注册表（接入配置）client_id / client_secret / redirect_uris / token_mode / is_public
auth_codesOIDC 一次性授权码code(哈希) / client_id / user_id / code_challenge / expires_at / used_at
refresh_tokens刷新令牌（轮换 + 复用检测）token(哈希) / client_id / user_id / family_id / revoked_at / replaced_by
auth_logs认证审计日志username / source / success / ip / created_at
安全设计：授权码与刷新令牌均以哈希形式入库（不是明文）。即使数据库泄露，攻击者也无法直接拿这些哈希去换取 token。

Schema 迁移

老库升级新字段由 migrate.py 处理：

  • 每个新列在独立事务中执行，单列失败只告警、不影响其他列（避免 PostgreSQL 单事务整体回滚）；
  • PostgreSQL 布尔列默认值必须写 BOOLEAN DEFAULT FALSE（不能用 0，否则类型不匹配报错）；
  • 启动流程：ensure_schema() 补齐列 → create_all() 建新表 → seed_all() 写种子数据。

小结

  • 外部共享库 = 独立于应用容器的数据库，数据安全、可共享、贴近生产。
  • 统一 JWT / OIDC 相关的授权码、刷新令牌都落库且哈希存储。
  • 老库迁移用 migrate.py，独立事务逐列升级，稳妥可复现。
