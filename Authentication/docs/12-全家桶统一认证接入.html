01一句话结论

认证中心完成 OIDC 标准改造后，本轮把 六大真实业务系统（云管 / 工单 / 权限 / 任务 / 事件 / 发布）全部接入统一认证：其中三个内部系统走网关 forwardAuth（方式一）、两个走直连 JWKS 验签（方式二）、发布系统走标准 OIDC 客户端（方式三）——三种企业级接入模式在一个项目里全部落地。身份统一到 OpenLDAP（12 个用户、固定演示密码、按组织归属），并补齐了每个系统的前端 SSO 令牌消费与用户可见性，做到"门户登录一次、全家桶到处通"。

02背景与目标

此前各业务系统是独立开发、独立登录（各自维护一套模拟用户，互不相同），与"统一入口 + 单点登录 + 多点访问"的设计目标割裂。本轮目标是：

  • 身份统一：全家桶用户集中到统一身份源（OpenLDAP），登录一次全局通行；
  • 接入规范：按系统特点分配三种标准接入方式，而不是自研一套；
  • 前端闭环：每个系统前端都要真正消费统一令牌并展示当前用户，而不是"API 通了但界面没串起来"；
  • 认证 / 授权分离：认证统一到认证中心；授权（权限申请）仍在各系统/权限中心自治。

04身份统一：OpenLDAP + LAM

改造前（各系统独立用户）

  • 每个系统各自一套模拟用户，互不相同、互不通用
  • 演示时要在每个系统分别登录、记多套账号密码
  • 没有"一个人的统一身份"概念

改造后（统一身份源）

  • 12 个全家桶用户灌入 OpenLDAP，密码统一 demo1234
  • 用户隶属组织（研发部/运维部…），不隶属某个系统
  • 认证中心启用 LDAP 认证源（AUTH_PROVIDER_ORDER=ldap,local）
  • 登录页：选择系统 → 选择用户（按组织分组）→ 固定密码
  • 管理界面：LDAP Account Manager（LAM，替换过时的 phpLDAPadmin）
设计要点：用户"隶属于组织而非系统"——demo_systems 字段仅用于登录下拉按系统分组，方便演示快速切换用户，不改变"用户属于组织"的身份语义。

05三种接入方式的链路

方式一 · 经网关 forwardAuth（工单/云管/权限）

  1. 用户经门户/统一入口访问业务系统（域名由统一网关接管）；
  2. 前端消费 SSO 令牌（?token= → localStorage → 请求带 Authorization: Bearer）；
  3. 网关 Traefik forwardAuth 拦截，转发认证中心 /api/auth/verify 验签；
  4. 通过后注入 X-Auth-User / X-Auth-Username / X-Auth-Name / X-Auth-Source 头放行；
  5. 业务后端 零鉴权代码，读注入头即知当前用户（on-the-fly 映射本地用户）。

方式二 · 直连 JWKS 验签（任务/事件）

  1. 前端消费 SSO 令牌，请求直接到业务后端（不经网关）；
  2. 后端从 /.well-known/jwks.json 拉取公钥（5 分钟缓存）；
  3. 本地验 RS256 签名 + kid + 有效期（verify_aud=False）；
  4. 通过后从载荷读 uid 映射本地用户。

方式三 · 标准 OIDC 客户端（发布）

发布系统作为标准 OIDC 客户端，走授权码 + PKCE：门户注册应用、配置 redirect_uri 白名单、换取令牌建立用户会话——完整模拟外部第三方系统接入。

07网关关键配置与踩坑

域名接管

内部系统前端纳入统一网关后，改用 *.authentication.orb.local 域（网关 label 声明）：

  • cloud / workflow / iam .authentication.orb.local → 统一网关按 Host 分发到各前端；
  • 后端 API 也走同一网关路由并挂 auth-forward 鉴权；
  • 老域名 *.devops.orb.local 由 OrbStack 默认直连各前端容器，网关 label 抢不过（实测），故新域名更可控。

两个必须修的坑

现象根因修复
新域名 /api/ 请求被后端当"invalid token"拒mock-app-api 是无 Host 的 PathPrefix(/api/) 兜底路由，抢占了业务系统域名请求mock-app 路由限定 Host(mock.authentication.orb.local)
加了 Host 仍绕过 forwardAuth业务 API 路由与前端 home 路由 priority 相同（10），/api/ 被 home（前端 nginx 同源反代）抢占，直连后端绕过网关鉴权业务 API 路由 priority 提到 100
教训：这两个坑只有新域名会踩——老域名因不匹配 home 路由的 Host 反而"侥幸正常"，这就是为什么老域名验证全通、接新域名才暴露。此类问题任何环境（含 Linux 直接 Docker 部署）都可能出现，与 OrbStack 无关，是网关路由配置的通用问题。

09面试叙事要点

  • 为什么三种方式？统一认证不是"一个接口接所有"，企业里内部应用、跨网应用、外部第三方天然分三类；本项目每种都真实落地，讲得出选择依据。
  • 认证 / 授权分离：认证中心只回答"你是谁"，权限中心回答"你能做什么"——这是企业 IAM 的基本架构观。
  • 身份源选型：LDAP 是企业的身份目录事实标准（AD/OpenLDAP），配 LAM 可视化运维，比"数据库存用户"更贴近生产。
  • 网关 forwardAuth 的价值：业务系统零鉴权代码，网关统一拦截/审计——内部系统首选。
  • 直连 JWKS 的取舍：不经网关但要多写一次验签，认证中心宕机不影响已发令牌——跨网络/高可用场景。
  • 前端闭环的工程细节：令牌放 localStorage 的取舍、URL 清理防泄漏、异步 bootstrap 防竞态、中文显示名 HTTP 头 latin-1 必须 quote/unquote。

10如何运行验证

  1. 在 Authentication 目录 docker compose up -d --build 启动认证中心、统一网关、LDAP + LAM；
  2. 启动各业务系统（各自 docker compose），确认域名接管与网关路由生效；
  3. 门户登录（如 alice / demo1234）→ 应用广场点各系统 → 应直接进入并显示 alice；
  4. 地址栏不应残留 ?token=；无权限系统空白，走权限中心申请即可。
