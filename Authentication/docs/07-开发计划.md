# 统一认证中心 — 开发计划（Roadmap）

> 基于当前已交付的 P0，规划后续开发。定位仍是「知识点学习 + 面试演示」的 Demo，
> 计划的取舍原则：**演示价值最大化，改造成本可控，符合真实架构认知**。

## 一、现状总结（P0 已交付 ✅）

| 模块 | 内容 | 状态 |
|------|------|------|
| 认证中心 | FastAPI：登录/登出/刷新/改密、RS256 JWT + JWKS、应用注册表、用户管理、审计日志 | ✅ |
| 身份源 | Local / LDAP（OpenLDAP 容器）/ Okta（预留）+ 降级链（认证失败不降级） | ✅ 已实测 |

## 三、P1：应用生命周期管理（开发者控制台）— ★★★★★ 最优先

**为什么排最前**：这是把「接入应用」从改代码变成**界面操作**的关键，也是 docs/01~06 与《应用接入指南》的落地载体；后端 CRUD 已具备，成本集中在门户前端。

### 任务清单
- [x] **应用管理页面** `/admin/apps`（管理员可见）：
  - 应用列表表格：名称 / 图标 / 首页 / SSO 类型 / client_id / 状态 / 排序
  - 新增、编辑、启用/禁用、删除
- [x] **注册向导**（分步）：
  - Step1 基本信息：应用标识、名称、描述、图标选择、首页 URL、SSO 类型（token / oidc 预留）
  - Step2 凭证发放：展示自动生成的 `client_id` / `client_secret`（secret 一次性展示 + 提示保密）
  - Step3 接入配置说明：按 SSO 类型给出接入指引（网关地址 / JWKS 公钥地址）
  - Step4 完成：应用上架，出现在应用广场
- [x] 应用表新增 **`access_mode`（gateway / direct）** 字段：标注该应用走网关还是直连自验签
- [x] 门户入口：管理员下拉出现「应用管理」；应用广场卡片标注「网关接入 / 直连接入」
- [x] 复用后端 `/api/apps` CRUD；补充创建响应返回 `client_id/client_secret`

> ✅ **P1 已完成并实测**：admin 在门户「应用管理」注册新应用 → 凭证发放 → 接入配置 → 上架 → 应用广场立即出现（已验证 NoteManager 演示）。

### 验收标准
1. 管理员在门户「应用管理」新增一个应用（填表单 → 向导完成）
2. 应用**立即出现在应用广场**（数据驱动，无需重启）
3. 点击新应用 → SSO 携带统一 JWT 跳转 → 目标页收到凭证
4. 可编辑、禁用（广场隐藏）、删除

## 四、P2：直连模式示例 + 业务系统试点接入 — ★★★★

**为什么做**：文档已讲「两种接入方式」，但 Demo 只演示了网关模式（A）。补上**直连自验签（B）**示例，并选 1 个业务系统真接入，回答面试官「怎么接入」。

### 任务清单
- [x] **直连模式示例**：新增 `direct-app`（`direct-app/jwks_auth.py` 可复用 JWKS 验签中间件），不经网关、用认证中心公钥本地验统一 JWT（`/.well-known/jwks.json` + pyjwt 验 RS256），实测通过
- [x] **试点系统**：以**项目内模拟试点系统**落地（`pilot-app`「工单中心」）——经统一网关 forwardAuth 接入，SPA 从门户跳转读统一 JWT，后端读 `X-Auth-*` 头生成"当前用户的业务数据"，零鉴权代码
- [x] 统一网关为试点应用加独立入口（`pilot` entryPoint :8004）+ forwardAuth 保护其 `/api/*`
- [x] 试点应用前端：从门户 SSO 读统一 JWT，401 由网关注入（已实测：门户登录 → 点 PilotApp → 无感进入工作台显示当前用户）
- [x] 应用广场新增 `direct-app`（直连接入）、`pilot-app`（网关接入）两个演示应用

> ✅ **P2 已完成并实测**：
> - 直连模式：带统一 JWT 访问 `direct-app`（不经网关）→ 本地验签通过返回用户；无 token → 401
> - 网关模式：门户点「工单中心 PilotApp」→ SSO 跳转 → 网关 forwardAuth 放行 → 工作台显示"当前用户：张三"及业务数据
> - 两种接入方式在应用广场均有对应应用（标注 网关接入/直连接入）
> - 真实业务系统（WorkFlowCenter/CloudManager）接入 = 按 pilot-app 的接入方式改造（网关路由 + 前端读统一 JWT + 后端读 X-Auth-* 头），可随时按需接入

### 验收标准
1. 门户登录 → 点试点系统 → **无感进入**（不再出现其自己的登录页）
2. 无 token 直访试点系统受保护 API → 401
3. 直连模式示例：携带统一 JWT 请求不经网关的服务 → 本地验签通过，返回用户信息

## 五、P3：OIDC 授权码模式（mock OIDC Provider）— ★★★

**为什么做**：让 `client_id / client_secret` 真正派上用场，完整还原企业 SSO 的 OIDC 授权码流；同时把预留的 `OktaAuthenticator` 落地（对接 mock OIDC 而非真实 Okta）。

### 任务清单
- [x] **认证中心作为 OIDC Provider**（`backend/app/api/oauth.py`）：`/.well-known/openid-configuration`、`/oauth/authorize`、`/oauth/token`、`/oauth/userinfo`
- [x] 完整授权码流：authorize（带统一 JWT + client_id）→ 一次性 code → token（code + client_secret）→ userinfo（Bearer access_token）
- [x] 门户登录页支持 `?return=` 回跳：OIDC 场景未登录 → 跳门户登录 → 登录后带统一 JWT 回跳 authorize，自动继续
- [x] 新增 `oidc-demo` 演示应用：可视化展示授权码 4 步（client_secret 只在应用后端换 token）
- [x] 应用注册表 `sso_type=oidc`（seed 中 oidc-demo 已注册，固定 client_id/secret）；接入向导已含 OIDC 配置说明
- [ ] （可选补充）`OktaAuthenticator` 对接外部 OIDC 身份源：认证中心作为 OIDC 客户端去 Okta/mock-Okta 认证（与"作为 IdP 对外提供 OIDC"是两个方向，可后续实现）

> ✅ **P3 已完成并实测**：浏览器完整走通授权码流 —— oidc-demo 点登录 → 跳认证中心 authorize → 门户登录 → 回跳 → 一次性 code → 后端用 `client_secret` 换 access_token → userinfo 拿到用户（张三/研发部），`client_id / client_secret` 真正派上用场。

### 验收标准
1. 走完整授权码流：业务系统 → /authorize（带 client_id）→ 用户登录 → 授权码 → 后端用 client_secret 换 token → userinfo 拿用户信息
2. 身份源降级链中 `okta`（mock OIDC）可用

## 七、优先级与取舍说明

| 问题 | 我们的选择 | 理由 |
|------|-----------|------|
| 6 个业务系统全量接入？ | **否**，先做 1 个试点 | Demo 定位：1 个真接入足够证明可行性，成本聚焦 |
| 接真实 Okta/Keycloak？ | **否**，自建 mock OIDC | 成本与定位不符；文档说明 + 接口预留即可 |
| 网关管理页面？ | **不做**（放门户应用管理） | 应用接入入口在门户；网关运维面超出 Demo 范围 |
| 每种接入方式都演示？ | **是**（P1+P2） | 两种方式都是面试高频考点 |
