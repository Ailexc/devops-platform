## 三、任务执行粒度对齐（真实场景还原）

### 3.1 真实场景的三种任务粒度

```
┌─────────────────────────────────────────────────────────────┐
│  ① 区域级任务（最大粒度，无账号级全量同步）                    │
│     区域下所有资源类型，按分组下发                             │
│     原因：账号级数据量太大，不好控制                          │
│                                                              │
│  ② 资源组级任务                                              │
│     只同步某类资源（如 EC2 组），逻辑同①                      │
│     场景：只想同步某几类资源                                  │
│                                                              │
│  ③ 资源级任务                                                │
│     针对单个资源/关联关系同步                                 │
│     场景：出问题了，针对性修复（如单独同步 EC2 主机、          │
│           EC2↔子网关联关系）                                  │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 区域级任务的内部结构（两波次调度）

```
区域级任务（定时同步，夜间跑）
  Wave 1: 全部资源任务（跨组并行，最大化并发）
    计算组: EC2 ║ 网络组: VPC ║ 数据库组: RDS ║ ...
    每个资源类型一个"进程"，进程内大量协程做子任务（对比类）→ 批量写
  ── 全部资源完成（Chord）──
  Wave 2: 全部关系任务（跨组并行）
    ec2_belong_vpc ║ ec2_belong_subnet ║ ...
    每个关系一个"进程"，内部协程计算 → 批量写入
  ── 全部关系完成 ── 区域任务完成
```

**正确性**：Wave 2 启动时所有资源已同步到位 → 关系绑定一定找得到目标，无需兜底逻辑。
**效率**：两波内部都是全局并行，比旧 chain 完全串行快一个量级。
**解耦**：资源任务与关系任务彻底独立，无组内/跨组依赖纠缠。

### 3.3 关键设计点

- **两波次 = 先资源后关系**（全局顺序保证正确性）
- **两波内部全并行**（效率最大化）
- **单资源失败不阻塞**：关系基于库中旧数据绑定，幂等 + 周期性修正
- **并发规模可接受**：定时同步一天一次、夜间跑，单个任务处理快，有排队影响不大（综合考量）
- **每个粒度独立可调度**：区域/资源组/资源/关系各自可配 cron
- **层级触发语义统一**：
  - 区域级 → 全资源并行 → 全关系并行
  - 资源组级 → 该组资源并行 → 该组源端关系并行
  - 资源级 → 单资源；关系级 → 单关系

## 四、Celery 实现映射方案

### 4.1 两波次调度映射（最终确认）

真实场景是**任务（进程）级并行 + 进程内协程级并发**，区域同步采用**两波次**调度，用 Celery 原生能力映射：

```python
# 区域级两波次调度
resource_tasks = [每个资源类型一个 task.s(account, region)]
relation_tasks  = [每个关系一个 task.s(account, region)]

wave1 = group(resource_tasks)   # 第一波: 全部资源并行
wave2 = group(relation_tasks)   # 第二波: 全部关系并行
workflow = chain(wave1, wave2)  # group 在 chain 中，第一个完成才执行第二个
```

| 真实模型 | Celery 实现 | 说明 |
|----------|-------------|------|
| 区域级任务下发 | 区域编排任务（orchestrator task） | 顶层入口 |
| Wave 1：全部资源并行 | **Celery Group**（跨组） | 所有资源类型并行 |
| 每个资源类型一个"进程" | 每个资源类型一个 **Celery Task** | prefork 池天然"一任务一进程"，完美对应 |
| 进程内协程做对比子任务 | Task 内部 **asyncio.gather** | 并发对比/计算 |
| 资源全部完成 → 关系开始 | **chain(group, group)**（前组完成才跑后组） | 两波次衔接 |
| Wave 2：全部关系并行 | **Celery Group**（跨组） | 所有关系并行 |
| 每个关系类型一个"进程" | 每个关系类型一个 Celery Task | 同资源类 |

### 4.2 核心洞察

> **Celery prefork 池本身就是"一个任务一个进程"，正好等于真实场景的"一个资源一个进程"；"进程内协程"就是 Task 内部用 `asyncio.gather`。两波次调度用 `chain(group, group)` 实现"先资源后关系"的全局顺序，同时保证两波内部最大化并行。**

这个映射让 Celery 方案成为真实架构的直接翻译，无需任何 hack。

### 4.3 关系解耦与最终一致

- 关系任务基于**全局 CMDB**（读），不依赖本次同步的临时状态
- 单资源失败不阻塞：关系基于库中旧数据绑定，幂等 + 周期性修正
- 相比旧方案（django-q chain 完全串行保证顺序）：**放弃强顺序，靠幂等重跑 + 周期性达到最终一致**，换取两波内并行

### 4.4 技术栈演进叙事

> 真实生产环境最初用 django-q + 自研协程池实现；为技术沉淀和可维护性，迁移/对齐到 Celery。Celery 的 prefork 进程池天然对应"每资源一进程"模型，任务内部用 asyncio 实现协程并发，迁移成本低，还获得 Group/Chord/chain/retry 等成熟能力。

将"为什么用 Celery"讲成一次架构演进，而非凭空引入，面试观感更好。

### 4.5 调度执行链路（人工触发 vs 定时触发）

```
① 人工触发（前端点按钮）
   前端 POST {account, region, mode}
     → API View 验证参数、创建 ExecutionRecord、生命周期埋点
     → orchestrator.delay(account, region, mode)
     → Redis 队列消息: {task, args:[account, region, mode]}
     → Worker 反序列化 → 任务函数直接用参数

② 定时触发（cron）
   PeriodicTask.args = '["account", "region", "full"]'
     → Celery Beat 到点 → 从 PeriodicTask 读出 args/kwargs
     → 组装消息投递（与①同格式）
     → Worker 收到 → 参数传入任务函数
```

**结论：账号/区域"创建时写入 args，执行时由调度器传递"**，任务函数是纯函数，参数进来直接用，不查"我属于哪个账号"。

## 五、任务管理模块编排（三源设计）

### 5.1 三层数据来源

```
┌─────────────────────────────────────────────────────────────────┐
│                    前端 (任务树渲染 + Cron 设置)                   │
│   渲染: 账号→区域→资源组→(资源+关联关系)    写入: cron 定时配置      │
└──────────────────────────┬──────────────────────────────────────┘
                           │  GET /tasks/tree   │  PUT cron
┌──────────────────────────▼──────────────────────────────────────┐
│                    服务层 (三源数据合并)                           │
├─────────────────────────────────────────────────────────────────┤
│  ① 配置层 (Apollo)       ② 能力层 (代码注册)     ③ 调度层 (DB)     │
│  账号 + 区域 + endpoint   资源组/资源/关联关系    PeriodicTask     │
│  {"prod": [{"apne1":     {"ec2-group": {         (django-beat)   │
│    "https://..."}]}       "resource": [...],     cron + args     │
│                           "asst": [...]}}                         │
│  ← 数据，可热更新         ← 代码，随发布          ← 运行时状态      │
│  不随代码发布              启动自动收集           前端可读写        │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 各层职责与变更方式

| 层 | 承载内容 | 为什么放这里 | 变更方式 |
|----|---------|-------------|---------|
| **配置层**（Apollo/DB） | 账号/区域/endpoint | 账号是数据，会增删、有环境差异，改配置不用发版 | 配置中心热更新 |
| **能力层**（代码 dict） | 资源组/资源/关联关系 | 资源类型是代码能力，新增要写 schema/transform/sync | 开发发版 |
| **调度层**（PeriodicTask） | cron + 任务参数 | 运行时状态，需要 CRUD、需要被前端改 | 前端/接口 |

**关键洞察：能力层（系统支持什么资源）本来就是代码定义的，不需要 DB 表承载**——`discover_modules()` 收集的 dict 即元数据。真正需要 DB 承载的只有调度配置（PeriodicTask 一张表）。

### 5.3 启动生命周期（幂等初始化）

```
项目启动
  ├─ migrate（建表）
  ├─ discover_modules()     ← 导入各 resource_modules
  │    自动收集 ResourceDef + Association → registry dict
  ├─ 幂等预建 PeriodicTask   ← 对每个 (账号,区域,资源组/资源/关系)
  │    get_or_create(name=...)
  │    enabled=False, crontab=None（占位，不参与调度）
  ├─ 合并 Apollo 账号/区域配置
  └─ 服务可用，前端可拉取任务树
```

### 5.4 树结构查询（三源合并）

```
GET /tasks/tree
  ① 账号/区域   ← 配置层（Apollo/DB）
  ② 资源组/资源/关系 ← 能力层（registry dict）
  ③ cron 状态   ← 调度层（PeriodicTask，按 args 匹配）
  合并成四级树返回
```

| 层级 | 来源 | 备注 |
|------|------|------|
| 账号 | 配置层 | Apollo/DB |
| 区域 | 配置层 | 含 endpoint |
| 资源组/资源/关系 | 能力层（代码 dict，不进 DB） | `ResourceDef`/`Association` 声明 |
| cron 状态 | 调度层（PeriodicTask） | 配了就有记录 |

## 六、PeriodicTask 预建占位方案（方案1，已确认）

### 6.1 方案选型

在"预建占位"与"按需创建"两种方案中，**确认采用预建占位（方案1）**：

- 数据量估算：20 账号 × 3 区域 × 50 资源 ≈ **3000 条**，对 Celery Beat 无压力（Beat 每 5 分钟增量同步一次，仅加载 `enabled=True` 的任务，3000 条查询+遍历几十毫秒级）
- 预建占位优势：任务树与 PeriodicTask 一一对应，前端一条查询即得"存在哪些任务 + 哪些配了 cron"；`get_or_create` 天然幂等

### 6.2 字段状态机

| 阶段 | enabled | crontab | Beat 行为 |
|------|---------|---------|----------|
| 初始化预建 | `False` | `None` | 完全不加载（安全） |
| 前端设置 cron | `True` | `0 2 * * *` | 正常调度 |
| 前端取消 cron | `False` | `None` | 不再调度 |

> 预建时 `enabled=False`，Beat 的 `filter(enabled=True)` 在用户配置之前一条都不加载，双保险。

### 6.3 幂等与命名

- `name` 唯一约束，命名规则：`{account}-{region}-{group}-{task_type}`
- 使用 `get_or_create(name=...)`，重复部署不产生脏数据
- `args='["account", "region", ...]'` 存放任务参数（JSON 字符串）

### 6.4 账号/区域下线清理（可选）

启动时对账：`disabled` 掉配置中不存在的账号/区域对应的任务（`filter` + `update(enabled=False)`）。demo 阶段可不做，面试时说明"账号增删走配置中心发布 + 启动对账清理"。

## 八、执行历史设计（最终确认）

### 8.1 统一记录模型（两级实体）

所有粒度的执行都写入同一张 `ExecutionRecord` 表：

| 字段 | 说明 |
|------|------|
| `scope` | 任务粒度标签：region / group / resource（展示逻辑不依赖） |
| `parent` | 自关联 FK：null=任务级，非空=进程级子记录 |

创建规则：

| 任务粒度 | 父记录 | 子记录 |
|---------|--------|--------|
| region / group | 1 条 | 各资源进程 N 条（同表） |
| resource | 1 条 | 无 |

### 8.2 详情页模式（取代展开面板）

- **列表页**：轻量摘要字段（id/任务名/模块/目标/触发/状态/耗时/时间），不返回 `result`/`lifecycle`/`logs`
- **列表新增「触发方式」列**：定时触发 / 人工触发
- **点击记录进入详情页**，从上到下多块展示：
  - ① 任务摘要（状态/耗时/目标/触发）
  - ② 📊 流程（生命周期时间线）
  - ③ 📋 日志
  - ④ 📦 结果
  - ⑤ 🧩 进程列表（子记录，按需显示）
- **统一逻辑**：前端只看"有没有子记录"决定是否显示进程块，**不判断 scope**，一套代码兼容所有粒度
  - region/group 级：有子记录 → 显示进程列表
  - resource 级：无子记录 → 隐藏进程块

### 8.3 保留策略（3 天）

- 执行明细保留 3 天，每日 Celery Beat 清理任务：
  `ExecutionRecord.objects.filter(started_at__lt=now-3天).delete()`（子记录级联删除）
- 3 天窗口足够溯源/排查，自动清理避免历史膨胀

### 8.4 聚合表（30 天，供大盘）

- `DailyTaskStat`：按天聚合（日期/模块/成功数/失败数/总耗时/同步资源量）
- 任务完成时增量更新，**保留 30 天**，可观察可靠性是否有提升（成功率周/月变化）
- 大盘趋势/可靠性观察从聚合表查询，与明细解耦

## 九、多级并发锁设计

### 9.1 为什么需要

多级下发（区域/资源组/资源）存在**层级覆盖关系**，同一资源同时只能有一个同步在执行（防止 cron 与人工叠加、区域级与组级重叠）。

### 9.2 方案：资源集合 + Redis 交集检测

- 每个任务"展开"为覆盖的资源集合：
  - 区域级 → 该区域下所有 group:resource
  - 资源组级 → 该组下所有 resource
  - 资源级 → 单个 resource
- 下发时遍历执行中集合，`SINTER` 检查交集：
  - 有交集 → 返回 409 拒绝
  - 无交集 → 加锁
- 任务完成/失败（Celery 信号或 Chord 回调）→ 释放锁
- Redis TTL 兜底（防异常死锁）

### 9.3 前端配合

- 任务树节点显示锁状态（🟡 执行中），下发按钮禁用
- 重复下发返回 409，toast 提示"该范围已有任务在执行中"

## 十、大盘统计设计

### 10.1 指标（对齐任务管理系统语义，弃用无意义的 24h 分钟趋势）

| 指标 | 说明 |
|------|------|
| 7 天执行趋势 | 按天任务数/成功/失败（聚合表，匹配日级任务节奏） |
| 任务健康度排行 | 失败 TOP / 耗时 TOP，主动发现问题 |
| 累计同步规模 | 累计同步资源量 / 累计 diff（数据价值量化） |
| 当前执行中 | 实时任务 + 锁状态（配合并发锁） |

### 10.2 数据源

- 聚合表 `DailyTaskStat` 保留 30 天，增量更新
- 趋势/可靠性观察（成功率的周/月变化）从聚合表查询

## 十三、待确认 / 待讨论点

**已确认：**

- [x] PeriodicTask 预建占位方案1（`enabled=False, crontab=None` 预建，前端配置时激活）
- [x] Celery 映射：prefork 一任务一进程 = 每资源一进程；Task 内 asyncio 协程 = 进程内协程
- [x] 任务粒度三级化（区域/资源组/资源），移除账号级全量同步
- [x] **两波次调度**：Wave1 全资源并行 → Wave2 全关系并行（`chain(group, group)`）
- [x] 关系任务解耦：基于全局库幂等绑定，单资源失败不阻塞，最终一致
- [x] 资源组选型：ec2 / rds / cache（新增 cache 模块）
- [x] 配置层：JSON 模拟 Apollo（`source` 字段 + `enabled` 下线字段）
- [x] 执行历史两级实体模型（父+子同表），详情页展示，保留 3 天
- [x] 列表新增「触发方式」列（定时/人工）
- [x] 聚合表 `DailyTaskStat` 保留 30 天，供大盘展示可靠性观察
- [x] 多级并发锁：资源集合 + Redis 交集检测，冲突返回 409
- [x] 大盘指标：7 天趋势 + 任务健康排行 + 累计规模 + 当前执行中；整体重构
- [x] 令牌桶限流：文档说明 + demo 加能力（不触发也无妨）

**待确认：**

1. 协程化改造落地：先文档化，后续 openlibrary 采集任务改为协程并发请求详情页（作为真实示例）—— 具体实现方案待细化
2. 关系数据模型：`ResourceRelation`（source_type/source_id/relation/target_type/target_id）的表结构待定
3. 关系任务在真实并发规模（50 类型 × 10 关系 = 500）下按源端资源聚合的扩展方案，文档说明即可
