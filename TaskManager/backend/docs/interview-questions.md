# 一、基础题

> 考察：语言/框架/组件/概念的基础掌握。这一部分不要求全部答出，但面试官会用它快速建立你的知识面画像。**Celery 是本系统重点，单独成节且覆盖面最广**。

## 1.1 Python / Django / DRF

### Q1. Python 的 GIL 是什么？对并发编程有什么影响？
- 🎯 考察点：是否理解 GIL 的本质与局限，能否说清"多线程 vs 多进程 vs 协程"的取舍
- 💡 参考要点：
  - GIL 是 CPython 解释器级别的互斥锁，同一时刻只有一个线程执行 Python 字节码
  - 影响：CPU 密集任务多线程无优势（要换多进程/语言），I/O 密集任务多线程可用（GIL 在 I/O 等待时释放）
  - 关联到本系统：任务并发用的是 **Celery prefork（多进程）+ 任务内 asyncio 协程**——进程间天然规避 GIL，协程适合 I/O 密集的采集/对比

### Q2. Django 的请求生命周期是怎样的？
- 🎯 考察点：WSGI → 中间件 → URL 路由 → View → ORM → 响应的完整链路
- 💡 参考要点：浏览器请求 → WSGI 服务器（gunicorn）→ 中间件（process_request）→ URL 解析 → View（DRF 里再走认证/权限/序列化）→ ORM 查库 → 序列化返回 → 中间件（process_response）

### Q3. Django ORM 的 `select_related` 和 `prefetch_related` 区别？
- 🎯 考察点：N+1 查询问题与查询优化意识
- 💡 参考要点：`select_related` 用 SQL JOIN 解决**单值外键**；`prefetch_related` 用**额外查询 + 内存关联**解决多值关系/反向外键。本系统历史详情页加载父记录 + 子记录列表时用 prefetch 避免 N+1

### Q4. DRF 的序列化器（Serializer）和 ModelSerializer 有什么区别？
- 🎯 考察点：序列化/反序列化、字段校验、嵌套序列化
- 💡 参考要点：ModelSerializer 自动从模型生成字段并带 ModelForm 式校验；Serializer 手动声明。本系统 `ExecutionRecord` 的列表/详情用不同 Serializer（列表轻量不返回 result/lifecycle，详情才全量）——这是接口性能优化的常见手法

### Q5. Django 中间件的作用？写一个中间件的步骤？
- 🎯 考察点：AOP 思想、请求横切关注点
- 💡 参考要点：请求/响应前后统一处理（认证、日志、限流、CORS）；实现 `__call__`/`process_request`/`process_response` 等方法并注册到 `MIDDLEWARE`

### Q6. Python 装饰器与 Django 的 `@shared_task` / `@api_view` 是什么关系？
- 🎯 考察点：装饰器本质（函数闭包）、框架如何用装饰器注入能力
- 💡 参考要点：装饰器是"包装函数"的语法糖；`@shared_task` 把普通函数注册成 Celery 任务并注入 `self.request`（bind=True）；`@api_view` 包装 DRF 视图函数

## 1.2 Celery（重点 · 覆盖面最广）

### Q7. Celery 是什么？核心组件有哪些？
- 🎯 考察点：任务队列的基础认知
- 💡 参考要点：分布式任务队列，四个核心组件——**Producer**（发任务）、**Broker**（消息中间件，本系统 Redis）、**Worker**（执行任务）、**Result Backend**（存结果）。外加 **Beat**（定时调度器）与 **Flower**（监控）

### Q8. Celery 的 Broker 有哪些选择？为什么本系统用 Redis？
- 🎯 考察点：中间件选型
- 💡 参考要点：RabbitMQ（功能强、更可靠，生产首选）、Redis（轻量、够用、多角色复用）。本系统 Redis 一专多能：Broker + Checkpoint + CMDB 虚拟存储 + 并发锁，demo 单机可跑通

### Q9. `task.delay()` 和 `task.apply_async()` 的区别？`task.apply()` 呢？
- 🎯 考察点：异步 vs 同步执行、参数传递
- 💡 参考要点：`delay` 是 `apply_async` 的简写（异步入队）；`apply_async` 可传 `queue/countdown/eta/expires` 等选项；`apply` 是**同步执行**（阻塞当前进程，常用于测试）

### Q10. Celery 任务签名（signature / .s）是什么？为什么有用？
- 🎯 考察点：编排原语的基础
- 💡 参考要点：`task.s(arg)` 生成"尚未执行的任务描述"，可像数据一样传给 `group`/`chain`/`chord` 组合，也支持 `delay`/`apply_async` 真正执行。本系统 `build_waves()` 用 `.s(...)` 构建 Wave1/Wave2 任务集

### Q11. `group`、`chain`、`chord` 三个原语分别是什么？
- 🎯 考察点：Celery 编排原语语义
- 💡 参考要点：
  - `group`：并行执行一组任务，返回结果列表
  - `chain`：串行执行，前一个结果传给后一个
  - `chord`：header 组全部完成后执行 body 回调（"等一组完成再启动下一组"）
  - 本系统：`chord(group(资源任务), wave1_done)` → Wave2 `chord(group(关系任务), finalize)`

### Q12. Celery Worker 的并发池有哪几种？prefork 和 gevent/eventlet 的区别？
- 🎯 考察点：并发模型
- 💡 参考要点：prefork（默认，多进程，CPU 密集合适，一个任务一个进程）、gevent/eventlet（协程池，I/O 密集高并发）、solo（单进程调试用）。本系统用 prefork，一个资源任务 = 一个进程，与"一个资源一个进程"的架构语义天然契合

### Q13. Celery 任务重试怎么做？`autoretry_for` 和 `bind=True + self.retry()` 区别？
- 🎯 考察点：可靠性基础
- 💡 参考要点：`self.retry(exc=exc, countdown=...)` 手动重试（`bind=True` 拿到 self）；`@task(autoretry_for=(Exception,), retry_backoff=True)` 声明式自动重试。本系统用 `max_retries + countdown` 指数退避，并配合生命周期 `retrying` 事件记录

### Q14. Celery 的 `task_prerun` / `task_postrun` / `task_failure` / `task_retry` 信号是干什么的？
- 🎯 考察点：信号机制（本系统生命周期的基础）
- 💡 参考要点：任务执行关键节点的钩子，注册回调即可**零侵入**埋点；本系统用它们自动写 `received/completed/failed/retrying` 生命周期事件，业务代码不用改一行

### Q15. Celery Beat 是什么？和 `crontab` 有什么区别？
- 🎯 考察点：定时调度
- 💡 参考要点：Beat 是 Celery 的定时调度器，到点把任务推入队列（与系统 crontab 不同，任务由 Worker 分布式执行）；配合 django-celery-beat 可把调度规则存数据库动态增删改

### Q16. Celery 的 ack 机制是什么？`task_acks_late` 有什么用？
- 🎯 考察点：消息可靠性（防丢失）
- 💡 参考要点：worker 处理完才回 ack，Broker 收到 ack 才删消息；`task_acks_late=True` 让 worker 执行**开始前不 ack**、完成后才 ack——崩溃时任务会被重新投递（at-least-once），代价是任务必须**幂等**

### Q17. Celery 结果存哪里？如果不设置 result_backend 会怎样？
- 🎯 考察点：结果后端
- 💡 参考要点：存 result_backend（本系统虽配 Redis 但结果**自己落 PostgreSQL**，result_backend 只是兜底）——任务结果进数据库 JSONField，页面看到的历史就是真实落库数据，可长期审计

### Q18. 多个 Celery 任务并行会重复执行吗？怎么避免？
- 🎯 考察点：幂等与并发控制
- 💡 参考要点：会（at-least-once + 并发）；用**幂等键**（本系统 celery_task_id get_or_create 子记录）+ **分布式锁**（本系统 Redis 集合交集锁，重复触发 409）

### Q19. Celery 任务超时怎么处理？`soft_time_limit` 和 `hard_time_limit`？
- 🎯 考察点：任务失控防护
- 💡 参考要点：`soft_time_limit` 到点抛 `SoftTimeLimitExceeded`（可捕获做清理）；`hard_time_limit` 到点直接杀进程。本系统巡检任务用超时保护 + 失败落库，避免任务永久挂起

### Q20. 消息积压（队列堆积）了怎么办？
- 🎯 考察点：生产故障处理思路
- 💡 参考要点：先定位是消费者能力不足还是生产者打爆；横向加 worker / 提高并发；区分优先级队列；临时放大 prefetch；排查是否有"毒丸消息"（一直失败重试）——用断路器+最大重试拦截

## 1.3 Redis / PostgreSQL

### Q21. Redis 的常用数据结构？本系统分别用在哪？
- 🎯 考察点：数据结构与场景映射
- 💡 参考要点：String（Broker 消息、Checkpoint、锁）、Hash（CMDB 虚拟存储对象）、Set/List（队列底层、资源集合）、ZSet（排行榜/趋势）。本系统资源集合交集锁用 Set 做交集检测

### Q22. Redis 怎么实现分布式锁？`SET NX EX` 是什么？
- 🎯 考察点：分布式锁原理
- 💡 参考要点：`SET key value NX EX ttl`——NX 保证只有不存在才写入（互斥），EX 设置过期（防死锁）；进阶：看门狗续期、Redlock 多节点、owner 标识防误删。本系统用集合交集锁实现"同一资源范围只允许一个任务"

### Q23. Redis 持久化 RDB 和 AOF 的区别？本系统 Redis 挂了会怎样？
- 🎯 考察点：可靠性认知
- 💡 参考要点：RDB 定时快照（快、可能丢最近数据）、AOF 追加日志（更可靠、恢复慢）。本系统 Redis 是 Broker，挂了任务不丢（未 ack 消息在 Worker/PostgreSQL 侧有记录可重发），执行记录本身在 PostgreSQL 不依赖 Redis

### Q24. PostgreSQL 的 JSONField 有什么好处？什么时候该用？
- 🎯 考察点：关系型 + 半结构化
- 💡 参考要点：灵活存结构多变数据、可查询（`->>` 运算符）、免建多表。本系统执行结果/生命周期/params 都是 JSONField——不同任务 details 结构不同，用 JSONField 免去大量建表；但统计类字段（status/duration）用普通列方便聚合

### Q25. 数据库事务的 ACID？批量写怎么保证原子性？
- 🎯 考察点：事务基础
- 💡 参考要点：原子性/一致性/隔离性/持久性；本系统 Diff 写入用 `bulk_create/bulk_update` 在事务内提交，一批失败整批回滚（天然成为 Checkpoint 断点）

### Q26. 数据量大时查询慢怎么优化？
- 🎯 考察点：索引/查询优化常识
- 💡 参考要点：加索引（本系统 celery_task_id/status 建索引）、避免 N+1、分页、聚合表（本系统 DailyTaskStat 30 天聚合，明细只留 3 天）

## 1.4 Vue 3 前端

### Q27. Vue 3 的 Composition API 和 Options API 区别？
- 🎯 考察点：Vue 3 基础
- 💡 参考要点：Options 用 data/methods/computed 组织（本系统采用，简单直观）；Composition 用 setup + 响应式 API 组合逻辑，复用性强

### Q28. Vue 的响应式原理？
- 🎯 考察点：Vue 核心
- 💡 参考要点：Vue3 用 Proxy 拦截对象读写，get 收集依赖、set 触发更新；依赖是组件渲染函数/计算属性

### Q29. computed 和 watch 的区别？
- 🎯 考察点：响应式数据派生
- 💡 参考要点：computed 是**派生状态**（有缓存，依赖变化才重算）；watch 是**副作用**（数据变化后执行逻辑）。本系统详情页 resultStats/artifacts/logs 都用 computed 从 result 派生，避免模板里写复杂表达式

### Q30. 前端怎么处理加载状态/错误状态？
- 🎯 考察点：UX 与状态管理
- 💡 参考要点：loading/error/data 三态分离；本系统历史列表/详情/文档都有"加载中 / 加载失败 / 空态"三态；文件预览弹窗也处理 loading/error

## 1.5 分布式与通用概念

### Q31. 什么是幂等？为什么分布式任务必须幂等？
- 🎯 考察点：分布式基础（进阶高频）
- 💡 参考要点：同一操作执行一次与多次结果一致；at-least-once 投递 + 重试 + 人工重发都可能导致重复执行，非幂等会脏数据。本系统：子记录 celery_task_id get_or_create、Diff 只写变化、关系绑定是"设置"非"追加"

### Q32. 什么是熔断（Circuit Breaker）？和重试什么关系？
- 🎯 考察点：可靠性设计
- 💡 参考要点：连续失败达到阈值打开熔断，快速失败保护下游；重试解决"偶发抖动"，熔断解决"持续故障"，两者配合避免重试风暴

### Q33. 什么是 Checkpoint / 断点续传？
- 🎯 考察点：长任务可靠性
- 💡 参考要点：长任务切成可独立提交的批次，每完成一批记录断点，恢复时从断点继续。本系统四阶段 Pipeline 每阶段存断点，目标恢复 < 30s

### Q34. 什么是 CAP 定理？对系统设计有什么指导？
- 🎯 考察点：分布式理论基础
- 💡 参考要点：一致性/可用性/分区容忍性三选二；本系统更看重**最终一致性**（周期修正）+ 可用性，牺牲强一致换取可扩展

### Q35. Docker 和 Docker Compose 的区别？
- 🎯 考察点：容器基础
- 💡 参考要点：Docker 是单容器；Compose 编排多容器（本系统 6 容器：backend/frontend/redis/db/celery_worker/celery_beat）

### Q36. 什么是消息队列？什么时候该用？
- 🎯 考察点：异步解耦认知
- 💡 参考要点：解耦（生产/消费分离）、削峰（积压缓冲）、异步（不阻塞请求）。本系统用 Celery+Redis 做任务调度，前端点按钮只负责"下发"，实际同步在 Worker 异步执行

# 二、进阶题

> 考察：某一技术点/架构设计的**深度**。面试官会顺着你的回答往下挖，答不出深度会明显减分。每题都指向本系统的关键实现。

### Q1. 深挖：为什么两波次编排用 `chord` 而不是 `chain(group, group)`？（Celery 编排深度）
- 🎯 考察点：对 Celery 原语隐式行为的真正理解（不是背概念）
- 💡 参考要点：
  - `chain` 会把前一组结果**作为位置参数注入后一组每个任务**：Wave1 有 N 个资源结果，Wave2 每个关系任务都会收到整个结果列表作多余参数 → 签名不兼容、任务无法执行
  - `chord(group, callback)`：header 组完成 → 结果只交给**一个**回调任务（body），由回调负责启动 Wave2，Wave2 任务参数保持干净
  - 本系统 `orchestrate` 构建 `chord(group(资源), wave1_done)`；`wave1_done` 再构建 `chord(group(关系), finalize)`
  - 加分：能说出 `wave1_done` 收到的是 header 聚合结果、此处不使用（`results` 参数），还能指出资源级任务没有关系波次时 `wave1_done` 直接 `finalize.delay()` 的边界处理

### Q2. 深挖：生命周期"零侵入"是怎么做到的？信号回调怎么定位到具体记录？
- 🎯 考察点：Celery 信号 + 关联设计
- 💡 参考要点：
  - 注册全局信号处理器（`@task_prerun.connect` 等），不修改任何业务任务代码
  - 定位：`@shared_task(bind=True)` 的 `self.request.id` 就是 Celery 任务 ID → 通过 `celery_task_id` 索引查 ExecutionRecord → 追加事件到 `lifecycle_events`
  - 事件带时间戳形成时间线；前端详情页还能算**相邻事件时差**（+X.Xs）定位"哪一步慢"
  - 加分：能说清 created/dispatched 由 API 层埋点、received/running/completed/failed/retrying 由 Worker 侧信号/任务体埋点，两类来源如何合并

### Q3. 深挖：统一结果结构（ResultBuilder）解决了什么？怎么设计才能让前端"一套代码渲染所有任务"？
- 🎯 考察点：schema 设计、前后端契约
- 💡 参考要点：
  - 问题：V1/V2 结果字段各写各的（count/file/report_file/data_file），前端每种任务一套解析，加任务就改前端
  - 设计：`{status, summary, duration, logs[], stats[{key,label,value,unit}], artifacts[{name,path,kind,size}], details{}}`
  - 收益：前端 `summaryOf/statsOf/artifactsOf` 一套 helper；测试任务/资源同步/关系任务/父记录汇总全部同构；`logs` 带时间戳落库（解决"控制台有页面没有"）；`artifacts` 自动取文件名+大小（支持预览）
  - 加分：能说出 `stats` 强制四元组（无 unit 也显式空串）、`details` 承载任务特有数据的边界划分、以及兼容旧结构（file/report_file/data_file）的兜底解析

### Q4. 深挖：多级并发锁（资源集合交集）是怎么设计的？和普通分布式锁有什么区别？
- 🎯 考察点：锁的建模、冲突检测
- 💡 参考要点：
  - 普通锁：锁单个 key（同一资源互斥）
  - 本系统：任务展开成**资源集合**（区域级 = {EC2,VPC,...}），新任务集合与已持有集合**有交集即 409**——区域级与资源级天然互斥，不同区域/账号可并行
  - 实现：Redis Set + `SET NX EX`，TTL 4h 防死锁；释放时校验 owner
  - 加分：能讨论"为什么是集合而非单 key"（粒度重叠检测）、看门狗续期、Redlock 在真实多节点下的必要性

### Q5. 深挖：指数退避重试 + 断路器 + Checkpoint 三者的分工与配合？
- 🎯 考察点：可靠性体系的层次设计
- 💡 参考要点：
  - **重试**：解决偶发抖动（源端 API 抖动），指数退避 + 抖动防重试风暴，`max_retries` 封顶
  - **断路器**：解决持续故障（源端挂了），OPEN 快速失败，HALF_OPEN 试探 3 次
  - **Checkpoint**：解决"重跑成本"（数据量大时中断恢复 < 30s），四阶段断点
  - 三者是"**是否重试 → 是否熔断 → 重跑成本**"三个层面的配合，且都依赖**幂等**（重试/重跑不会脏数据）
  - 加分：能指出"重试耗尽返回失败结果而非抛异常"的架构决策（保证 Wave1 组不整体失败、Wave2 照常执行）

### Q6. 深挖：父/子两级记录 + 同表自关联是怎么设计的？为什么用 celery_task_id 做幂等？
- 🎯 考察点：数据模型设计、幂等
- 💡 参考要点：
  - `ExecutionRecord` 自关联：`parent=None` 任务级 / `parent` 非空进程级；父记录存 params（派发参数）与生命周期，子记录存独立结果/错误
  - `get_or_create(celery_task_id)`：Celery 重试会重执行任务体，但幂等键保证不产生重复子记录；重试成功后 failed 记录更新为 success
  - 收益：钻取（父→子进程）、级联清理、保留策略统一
  - 加分：能说清 `params` 字段的作用（一键重试的"原参数重发"依据）以及为什么任务级/进程级重试逻辑不同

### Q7. 深挖：Diff 增量同步的原理？怎么避免"全量覆盖"的问题？
- 🎯 考察点：数据同步一致性
- 💡 参考要点：
  - 全量覆盖三宗罪：误删风险（源端临时故障清空存量）、写放大、不可审计
  - 增量 Diff：用唯一键（cloud_id）三方对比 → 只在源端=新增 / 两边变化=更新 / 只在存量=删除 / 一致=不变（不动）
  - 配套批量写（bulk_create/update）+ 事务；diff 四项落库可审计；幂等友好（重跑=全部 unchanged）
  - 加分：能讨论"删除"的坑（源端暂时查询不到不等于删除，需要二次确认/软删除）

### Q8. 深挖：Celery Beat + PeriodicTask 怎么实现"页面配置定时任务"？哨兵 cron 是什么？
- 🎯 考察点：调度设计与框架机制
- 💡 参考要点：
  - django-celery-beat 把调度规则存数据库（PeriodicTask），运行时动态增删改，不用改代码重启
  - 哨兵 cron：`0 0 31 2 *`（2月31日永不到期）占位满足 `validate_unique` + `enabled=False` 保证 Beat 不加载未配置任务
  - 定时与人工走同一 `dispatch_execution`（trigger 字段区分 cron/人工），行为一致、都可重试
  - 加分：能说清"预建占位 + 用户配置后启用"与"全部实建"两种方案的取舍

### Q9. 深挖：多队列（aws/connector/inspection/default）的设计目的是什么？和单一队列有什么区别？
- 🎯 考察点：故障隔离、资源分配
- 💡 参考要点：
  - 故障隔离：aws 源端故障只堵 aws 队列，钉钉/Jira、巡检不受影响
  - 资源分配：不同队列配不同 worker 数与并发，CPU 密集（巡检）与 I/O 密集（采集）分开
  - ack/prefetch 控制：每个 worker 预取数决定公平性与并发度
  - 加分：能讨论"队列打满怎么办"（HPA、优先级、限流）以及为什么 demo 单 worker 也能验证路由逻辑

### Q10. 深挖：任务失败时"返回失败结果而非抛异常"是为什么？对编排有什么影响？
- 🎯 考察点：编排容错的深层理解
- 💡 参考要点：
  - 抛异常 → Celery 标记任务失败 → chord/group 语义下可能影响整组（导致回调不触发或整体失败）
  - 返回失败结果 → 任务"正常完成但结果是 failed"，Wave1 组正常结束、Wave2 照常启动；父记录 finalize 汇总"子任务 17（✓16 ✗1）"呈现部分成功
  - 这是"**部分成功**"语义的基础，符合真实运维（一个资源失败不该拖垮整个区域）
  - 加分：能讨论这与"重试耗尽后仍失败"的关系，以及如何从页面看到具体是哪个进程失败并单独重试

### Q11. 深挖：为什么 Redis 同时做 Broker、Checkpoint、虚拟 CMDB、锁？有没有问题？
- 🎯 考察点：多角色复用 vs 单点风险
- 💡 参考要点：
  - 原因：prefork 进程间共享（Wave2 关系任务要读 Wave1 数据，内存不行必须共享存储）；无额外组件；demo 单机可跑通
  - 风险：Redis 是单点；解决方案是真实项目用 Sentinel/Cluster 高可用 + 持久化策略
  - 加分：能指出"CMDB 数据在 Redis 而非 PostgreSQL"是 demo 妥协（真实项目 CMDB 在蓝鲸/PostgreSQL），并说明任务记录/结果在 PostgreSQL 才是"真相源"

### Q12. 深挖：前端详情页"可钻取执行链"是怎么设计的？数据从哪来？
- 🎯 考察点：前端与数据契约
- 💡 参考要点：
  - 详情接口返回父记录（含 result + lifecycle_events + children 列表）
  - 前端按 result.details 分组：含 added/resource → Wave1 资源进程；含 bound/source+target → Wave2 关系进程
  - 进程行可展开显示 stats + logs + error（统一结构解析），失败进程红色高亮 + 重试按钮
  - 生命周期时间线 + 相邻事件时差（+X.Xs）一眼定位慢的环节
  - 加分：能说清"用结果结构推导进程类型"而非硬编码，是统一结构带来的扩展性

# 四、场景题

> 考察：**全局思维**。这类题一般放在最后，面试官给一个场景看你怎么拆解、设计、权衡。回答建议按"**设计 → 能力 → 规避 → 价值**"四步走。以下场景都贴合本系统，你可以用真实设计作答。

### 场景 1：某账号某个区域要全量同步 10 万条资源数据，你怎么设计？
- 🎯 考察点：编排、并发、性能、可靠性
- 💡 参考要点：
  - **设计**：区域级任务 → 按资源类型分组（Wave1 资源并行），每个资源进程内协程并发对比子任务 → Wave2 关系 → finalize 汇总；分页/分批拉取源端（避免一次性拉爆内存）
  - **能力**：两波内部并行（并行度 = 资源类型数 × 进程内协程数）；Diff 只写变化（10 万条可能只有几百条变化）
  - **规避**：并发锁防重复触发（409）；Checkpoint 断点（跑到 80% 断了从 80% 继续）；指数退避 + 熔断（源端限流不被打爆）；幂等（重跑安全）
  - **价值**：全量同步从"小时级串行"降到"分钟级并行"，数据准确率与时效性提升，且每次同步可审计（diff 四项落库）

### 场景 2：夜间定时全量同步，白天有人工修复单个资源，怎么避免冲突？
- 🎯 考察点：并发控制、任务隔离
- 💡 参考要点：
  - **设计**：多级并发锁（资源集合交集）——定时区域级任务持有 {EC2,VPC,...} 集合，人工资源级 {EC2} 有交集 → 409 拒绝，明确提示"该范围已有任务在执行中"
  - **能力**：粒度互斥 + 区域/账号并行；人工修复可等定时跑完再点（或页面看到锁状态）
  - **规避**：双跑导致数据互相覆盖；锁 TTL 防死锁；失败重试不重复执行
  - **价值**：定时与人工两条链路安全共存，运维可以放心"看到失败就点重试"

### 场景 3：凌晨源端 API 突然开始 50% 报错，你的系统会怎样？你怎么处理？
- 🎯 考察点：可靠性体系、故障应对
- 💡 参考要点：
  - **设计**：指数退避重试（偶发抖动自愈）→ 连续失败触发断路器 OPEN（快速失败，不再打源端）→ 任务失败落库 + 生命周期 failed → 页面红色高亮
  - **能力**：故障不扩散（多队列隔离，aws 队列堵了 connector/inspection 不受影响）；部分成功（一个资源失败不拖垮整组）
  - **规避**：重试风暴（退避 + 抖动）、队列打爆（熔断）、数据写坏（Diff 只写变化）
  - **价值**：源端恢复后定时兜底自动修正；运维从页面看到"哪个进程失败、失败几次、每次隔多久"（生命周期 retrying 事件），而不是翻日志

### 场景 4：某类资源的同步任务持续失败，你从哪几个方向排查？
- 🎯 考察点：故障排查思路
- 💡 参考要点：
  - 看执行链：该进程的 result.error + 生命周期时间线（哪一步失败：采集/对比/写入？相邻事件时差定位慢的环节）
  - 看日志：进程展开的带时间戳阶段日志（①读取存量 ②采集源端 ③对比 ④写入——失败在哪个阶段）
  - 分类：源端问题（网络/权限/限流 → 重试/熔断）、数据问题（格式/缺字段 → 看 transform）、写入问题（约束/事务 → 看批量写）
  - 处置：源端恢复后"一键重试"该进程（进程级重试，从 result.details 推断 scope/target）；长期失败 → 断路器拦截 + 告警
  - **价值**：全链路可观测让"定位"从小时级降到分钟级

### 场景 5：领导说"系统要支撑 10 倍数据量"，你从哪些方面考虑？
- 🎯 考察点：容量规划、架构演进
- 💡 参考要点：
  - **计算**：任务量 × 10 → worker 数、并发、队列吞吐；Redis Broker/锁压力；PostgreSQL 写入
  - **设计**：横向加 worker（Celery 天然支持）；多队列按类型扩容；聚合表避免明细查询；索引优化；Checkpoint 粒度调优（数据量大了断点更细）
  - **规避**：单点（Redis 上 Sentinel/Cluster、数据库主从）；重试风暴（参数按量调优）；监控大盘告警（失败率/积压量）
  - **价值**：把"扛不扛得住"变成可量化的容量模型 + 可横向扩展的架构
  - 加分：指出 demo 里哪些是"演示值"（重试次数/熔断阈值/并发数）真实环境要重调，体现你分得清 demo 与生产的边界

### 场景 6：如果从零设计一套 CMDB 任务调度系统，你的核心设计是什么？
- 🎯 考察点：全局架构能力（这是综合题）
- 💡 参考要点：
  - **分层**：API（校验/派发/埋点）→ 编排（粒度展开/两波次/队列路由）→ 执行（Pipeline/可靠性组件）→ 存储（执行记录 + 聚合）
  - **核心决策**：任务粒度四级（区域级为主）；统一结果结构（前端一套渲染 + 可钻取）；父/子两级记录（幂等 + params 可重试）；并发锁（防重复执行）；生命周期信号埋点（零侵入可观测）
  - **可靠性**：重试/熔断/Checkpoint/幂等四件套 + 保留策略（明细 3 天、聚合 30 天）
  - **规避**：编排语义坑（chord 而非 chain）、日志不落库、结果字段不统一、前端 id 带 # 前缀、组件类名冲突
  - **价值**：一套"可编排、可观测、可重试、可审计"的任务平台，支撑 CMDB 数据准确率 95% 的目标
  - 加分：主动说出"演进而非重写"（django-q → Celery）与"demo 与真实项目的边界"，体现工程判断而非堆概念

### 场景 7：业务方抱怨 CMDB 数据不准，你怎么证明/改进数据质量？
- 🎯 考察点：数据质量、可量化
- 💡 参考要点：
  - **证明**：用 diff 四项指标（每次同步 +新增/更新/删除/不变 落库）做数据准确率量化；聚合表看趋势
  - **设计**：质检任务（本系统 data_quality_check：完整性/字段/去重/异常统计）；产物报告（Markdown 质检报告可预览）
  - **规避**：误删（Diff 而非全量覆盖 + 删除二次确认）；过期数据（周期修正/定时全量兜底）
  - **价值**：把"数据准不准"从主观感受变成可量化的指标（准确率/新鲜度/健康度），并用大盘可视化呈现

## 附：讲解时的 3 个注意点（给自己）

1. **细节是防撒谎的通行证**：刁难题多说具体现象（报错、字段名、类名、数字），少说结论。"页面黑屏 → 根因是 `.hd` 类名冲突"比"我修过样式 bug"可信一百倍。
2. **主动分边界**：主动说出"demo 哪些是演示值、真实项目要重调"（重试次数、熔断阈值、并发数、Checkpoint 粒度），面试官会觉得你分得清 demo 与生产，这是加分项。
3. **场景题按"设计→能力→规避→价值"回答**：先给方案骨架，再讲能力，主动说"要规避什么"，最后落到业务价值（准确率、时效、可审计）——全局思维是这一维的考察核心。
