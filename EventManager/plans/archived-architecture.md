 # 已归档架构设计文档（Python + Django 实现）
 
 本文档整理自之前基于 Python + Django 实现的资源同步与事件管理系统设计。两份模块的设计均来源于同一套基础设施：自定义 CMDB ORM、任务链调度、协程并发处理。
 
 ---
 
 ## 一、定时任务模块系统设计
 
 ### 1.1 模块目录结构
 
 每个资源模块遵循相同的目录结构：
 
 ```
 <module_name>/
 ├── schema.py          # 预设定义，接受 AWS API 返回数据格式作为处理对象
 ├── transform.py       # 预定义转换器，将 AWS schema 对象转换为 CMDB 数据格式
 ├── model.py           # Django model，CMDB 字段，通过自定义 Manager 操作 CMDB
 ├── resource.py        # 定义模块的资源类型，如 EC2、Volume、Interface
 ├── association.py     # 模型间的关联关系定义
 └── tasks.py           # 预定义任务，编排一个或多个资源的同步集合
 ```
 
 ### 1.2 各层职责
 
 #### schema
 
 用于预设定义，接受 AWS 资源的 API 返回数据格式作为处理对象。核心目的是"明确 AWS 接口数据"，通过 dataclass 或其他 Python 模块实现。
 
 #### transform
 
 一个预定义的转换器，将 AWS 返回的 schema 对象转换为 CMDB 的数据格式。核心是类似 Django Serializer 的声明式编程风格，例如：
 
 ```python
 instance_id = toString(
     source_type='InstanceId',
     required=True,
     default='xxx',
     tf_func=xxx
 )
 ```
 
 最后通过一个方法输出转换后的数据格式。
 
 #### model
 
 Django model 模型，字段对应 CMDB 中的字段。其 ObjectManager 被替换为自定义的 `CmdbQuerySet`，代理 QuerySet 做 CRUD，内部实现了 Django 原生 QuerySet 的所有方法，因此可以像操作普通 Django model 一样操作 CMDB 的数据。
 
 #### resource
 
 定义当前模块的资源类型。例如 EC2 模块会同步 EC2、Volume、Interface 等相关子资源。每个资源是一个 class，设置的属性包括：
 
 - **aws_data_provider** — AWS 数据查询的接口类
 - **cmdb_model_id** — CMDB 模型的 ID
 - **aws_schema** — 定义的 AWS Schema
 - **cmdb_model** — 定义的 Model
 - **associations** — 引用的关联关系清单
 - **管理关系编排**
 
 示例：
 
 ```python
 class Ec2:
     associations = [Ec2IncludeVolume, Ec2IncludeInstances]
 ```
 
 #### association
 
 定义了模型之间的关联关系。每个关系是一个 class，例如 `Ec2IncludeVolume`，属性包括：
 
 - **上游模型**
 - **关联关系类型**
 - **下游模型**
 - **关系比例**（1:1、1:n 等）
 
 被 resource 引用，在对应资源类中编排管理关系。
 
 #### tasks
 
 预定义任务。一个任务编排一个或多个（也可全部）资源的集合，默认是当前模块的全部 resource。
 
 示例：
 
 ```python
 class Ec2All:
     resources = [Ec2, Volume, Instance]
 
 class Ec2Volume:
     resources = [Volume]
 ```
 
 ### 1.3 核心调度逻辑（基类实现）
 
 通过 **django-q** 下发任务后，指定资源类型、范围、账号、区域：
 
 1. **任务拆解** — 将整个任务拆分为多个子任务
 2. **任务链编排** — 通过 django-q 的任务链（Chain）实现前后顺序保障
 3. **执行顺序** — 先全部同步资源，再执行关联关系任务
 
 ### 1.4 单个资源的同步流程
 
 ```
 ┌──────────────────────────────────────────────────────────┐
 │  1. 从 CMDB 批量拉取数据                                │
 │     → 计算后存入缓存                                      │
 ├──────────────────────────────────────────────────────────┤
 │  2. 从 AWS 批量拉取数据                                  │
 │     → 逐条扔到协程队列中                                  │
 ├──────────────────────────────────────────────────────────┤
 │  3. 逐条比较（协程）                                     │
 │     → 判断：新增 / 更新 / 删除 / 无需处理                │
 │     → 追加到对应池子                                      │
 ├──────────────────────────────────────────────────────────┤
 │  4. 计算完成后                                            │
 │     → 批量创建、批量更新                                  │
 │     → 逐条删除                                            │
 ├──────────────────────────────────────────────────────────┤
 │  5. 结果记录 & 异常告警                                   │
 └──────────────────────────────────────────────────────────┘
 ```
 
 关键特点：
 - 先从 CMDB 拉取已有数据放到缓存
 - 从 AWS 批量拉取后通过协程逐条比较
 - 最终采用 **批量创建 / 批量更新 / 逐条删除** 的策略
 - 完成后记录结果，异常触发告警

 ## 二、事件管理模块设计
 
 ### 2.1 整体架构
 
 ```
 AWS Event (EventBridge)
     │
     ▼
 Lambda (事件触发器)
     │
     ├── 基本过滤：不在处理范围则跳过
     │
     └── 发送 API 请求 → 事件管理系统
                             │
                             ▼
                   总队列（快速返回，不阻塞）
                             │
                             ▼
                   找到对应处理 Class
                   判断：快速任务 / 慢速任务
                             │
                    ┌────────┴────────┐
                    ▼                  ▼
               快速任务队列          慢速任务队列
                    │                  │
                    ▼                  ▼
             进程 + 协程           线程池
             (快速分发处理)      (长时间运行)
                    │                  │
                    └────────┬────────┘
                             ▼
                   原始 event 数据记录
                   处理时间、结果记录
 ```
 
 ### 2.2 处理流程
 
 1. **事件触发** — AWS EventBridge 将事件触发器绑定到一个 Lambda
 2. **初步过滤** — Lambda 接收到事件后先做基本过滤，不在处理范围的直接跳过
 3. **API 请求** — 需要处理的事件发送到事件管理系统的 API
 4. **入队** — 确认是需要处理的事件后，先丢到总队列中，快速返回（不阻塞）
 5. **消费分发** — 总队列的消费者根据事件找到对应的处理 Class，其中登记了该事件属于快速/慢速任务，二次分发到对应的队列中
 
 ### 2.3 快速任务
 
 - 使用 **进程 + 协程** 模型
 - 快速分发处理
 - 记录原始 event 数据、处理时间、结果等
 
 ### 2.4 慢速任务
 
 - 使用 **线程池** 长时间运行
 - 主要用于资源创建、变更等场景，需要循环等待或其他长时间操作
 - 同样记录相关信息
 
 ### 2.5 配套模块
 
 - **队列监控模块** — 监控各队列状态
 - **异常告警模块** — 处理失败时告警
 - **历史任务记录模块** — 支持搜索、重试等操作

 ## 三、技术栈总结
 
 | 模块 | 技术 | 备注
 |------|------|------
 | 定时任务调度 | django-q | 任务链保证顺序
 | 数据定义 | dataclass / 声明式转换器 | schema / transform
 | CMDB ORM | 自定义 CmdbQuerySet | 替代 Django QuerySet
 | 并发处理 | asyncio 协程 | 比较/分发阶段
 | 数据同步策略 | 批量创建/更新 + 逐条删除 | 基于差异比较
 | 事件分发 | 双层队列（总队列 → 快速/慢速） | 快速返回 + 分类处理
 | 快速任务 | 进程 + 协程 | 低延迟
 | 慢速任务 | 线程池 | 长时间等待场景
 | 监控告警 | 自定义模块 | 队列监控 + 异常告警 + 重试
