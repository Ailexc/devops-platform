> 调研日期：2026-08-03
> 调研范围：BPMN 2.0 / 工作流引擎 / ITSM 工单系统 / 中国 OA 审批 / Python 生态方案

## 一、行业事实标准：BPMN 2.0

BPMN 2.0（OMG 制定，2010 年发布）是流程建模的行业事实标准，核心是"**一图两用**"——既面向业务人员（图形符号），又能被引擎直接执行（可执行 XML）。

### 核心元素体系

| 类别 | 子类 | 对应工单/审批场景 |
|---|---|---|
| **事件 Events** | 开始/中间/结束、捕获/抛出、边界事件、定时/消息/信号/错误/补偿 | 定时提醒、超时催办、外部系统消息触发 |
| **活动 Activities** | 任务（用户/服务/脚本/发送/接收）、子流程、**多实例活动** | 审批节点=用户任务；自动处理=服务任务 |
| **网关 Gateways** | 排他 XOR、并行 AND、包容 OR、事件网关 | 条件分支、并行分支、会签合并 |
| **泳道 Swimlanes** | 泳池、泳道 | 部门/组织边界 |
| **数据对象** | 数据对象、数据存储、消息 | 表单数据、附件 |

### 关键建模手法（重点）

| 场景 | BPMN 建模 | 执行语义 |
|---|---|---|
| 普通审批 | 用户任务 + 人工完成 | 任务待办、认领 |
| **会签**（全部通过） | **多实例用户任务（并行）** + 完成条件 `completed >= total` | 生成 N 个并行子任务，全部完成后汇合 |
| **或签**（任一通过） | 多实例 + 完成条件 `completed >= 1` | 任一完成即满足，其余取消 |
| 依次审批 | 多实例（顺序模式） | 一个完成才生成下一个 |
| 条件分支 | 排他网关 XOR + 每条出线带条件表达式 | 按顺序求值，命中第一条 |
| 并行分支 | 并行网关 AND | 生成多个 Token，同步合并 |
| 超时/催办 | 边界定时事件 | 定时器到期触发边界路径 |

> **要点**：BPMN 没有"审批"专用元素，审批 = 用户任务 + 多实例 + 网关的组合。**会签/或签在标准里就是 Multi-Instance Activity**，这是理解所有引擎实现的钥匙。

## 二、主流工作流引擎架构实践

### 引擎共同架构模式（五大骨架）

| 模式 | 说明 | 代表 |
|---|---|---|
| **定义/实例分离** | 流程定义（静态）与流程实例（运行时）分表存储，实例绑定启动时的定义版本 | 全部引擎 |
| **Token 执行模型** | 执行指针；并行分支=Token 分裂，合并=Token 汇合 | Camunda/Flowable |
| **事件驱动状态机** | 内部处理 = 状态机 + 命令 + 事件流，不是直接改状态字段 | Zeebe/Temporal |
| **命令模式 + 事务** | 每个写操作是一个命令、一个数据库事务，保证原子性 | Camunda 7/Flowable |
| **幂等** | 重复提交不重复执行（Job 重试、事件去重） | 全部引擎 |

### 代表性产品

- **Camunda 7**：Java 单体引擎，Execution 树（Token 物化），关系库 `ACT_*` 表族，命令上下文+事务。
- **Camunda 8 / Zeebe**：云原生，**事件溯源 + 分区日志**（分布式存储，无中心 DB），外部 **Job Worker** 模式（任务发布为 Job，worker 拉取执行，引擎不阻塞）。
- **Flowable / Activiti**：与 Camunda 同源，Service API（`RepositoryService`/`RuntimeService`/`TaskService`/`HistoryService`）是标准门面。
- **Temporal**：Durable Execution（代码即流程），事件溯源 History 重放恢复状态，Workflow 确定性要求，Signal/Query/Update 通信。适合长时运行编排，**不是** BPMN 引擎。

### 引擎标准 API 范式（对自研的启示）

对外暴露的就是这一组"动词"，内部实现再复杂不影响 API 稳定：

```
startProcessInstanceByKey/ById（+variables+businessKey）
complete(taskId, variables)        # 完成任务
claim(taskId, userId) / unclaim    # 认领
delegate(taskId, userId)           # 委派（原处理人保留）
resolve(taskId, variables)         # 委派后归还
suspend / resume / terminate       # 实例控制
rejectTo(nodeKey)                  # 驳回指定节点
signalEventReceived                # 外部事件触发
addComment / setPriority
```

## 三、Workflow Patterns（van der Aalst）

学术界的流程模式体系，是评估流程引擎表达力的"标尺"。

| 模式 | 语义 | 工单场景 |
|---|---|---|
| 顺序 Sequence | 任务依次执行 | 串行审批链 |
| 并行分支 AND-split | 同时激活多条分支 | 会签并行派发 |
| 同步合并 AND-join | 等所有分支到达才继续 | 会签"全部通过" |
| 排他选择 XOR-split | 从多条分支选一条 | 条件路由 |
| 简单合并 XOR-join | 任一前驱到达即继续 | 或签"任一通过" |
| 多选 OR-split | 可选 0..n 条分支 | 多选抄送 |
| 判别 Discriminator | N 条中 M 条到达即继续，其余忽略 | 或签（M=1）、半数通过 |
| 多实例 M of N | 生成若干实例，M 个完成即满足 | 会签（M=N）/或签（M=1） |

> **关键结论**：真正的难点不是"分叉"，而是**汇合（join）的语义**——AND-join 要计数等待、XOR-join 要即时通过。会签/或签的差异本质就是 join 语义的差异。

## 四、中国互联网公司审批引擎（钉钉/飞书/企业微信）

国内主流采用**"节点式"流程模型**，本质是 BPMN 的受约束子集 + **JSON 序列化**，刻意牺牲表达力换取简单性（覆盖 OA 审批 95% 场景）：

| 节点类型 | 说明 | 对应 BPMN |
|---|---|---|
| 审批节点 | 审批人：发起人自选/主管链/角色/指定人 | 用户任务 |
| 条件节点 | 按表单字段路由（金额 > X、部门 = Y） | 排他网关 |
| 抄送节点 | 知会，不阻塞 | 用户任务（非阻塞） |
| 办理节点 | 填表/处理业务 | 用户任务（办理类） |
| 会签/或签 | 节点级属性开关 | 多实例 + 完成条件 |
| 加签/转交/委派 | 运行时操作 | 引擎扩展 |

**动态审批人**是国内系统核心特色：主管链、发起人自选、表单字段指定、角色解析。

**JSON 化流程定义趋势**：流程定义 = JSON（节点列表 + 连线/条件表达式 + 节点属性），**版本化管理**（发布后生成新版本，实例绑定启动版本），表单与流程绑定（条件表达式基于表单字段值）。

## 五、流程引擎与业务系统解耦

**为什么分离存储/建模：**
1. 生命周期不同：业务数据有增删改，流程实例是"执行轨迹"只增不改
2. 写入模式不同：流程引擎高频小写且要事务性
3. **可替换性**：引擎是可替换组件，通过 `businessKey`/`processInstanceId` 弱关联业务
4. 可观测性：实例/任务/历史单独建模，天然支持流程追踪、待办中心、审批历史
5. 事务边界清晰：通过**发消息 + 幂等回调**衔接（Outbox 模式），避免跨库分布式事务

**Task 与 ProcessInstance 的关系：**
- ProcessInstance：一次流程运行的**整体状态**（定义版本、businessKey、Token 集合、全局变量）
- Task：一个实例在某节点上的**待办**（N:1 属于实例），一个实例可以有 0..N 个活动任务（并行）
- **任务表（给人看的待办）与 Token（引擎内部执行状态）是两套概念**，轻量实现可合并，但概念要分开

## 六、ITSM 工单系统实践

### 核心状态（行业共识）

```
新建 → 待分派 → 处理中 →（等待/挂起，暂停 SLA）→ 已解决 → 已关闭
                              ↘ 已取消（异常终态）
                       已解决 → 处理中（客户驳回/重开）
```

关键设计点：
- 状态分**活跃态**与**终态**；SLA/看板/报表以"是否终态"过滤
- **等待（Waiting）**建模为状态 + 暂停原因，暂停 SLA 计时
- **不要合并"解决"与"关闭"**：Resolved → Closed 之间是客户确认环节（防代理自关单）
- 保留 **已解决→重开** 回路（客户满意度闭环）

### ITIL 三类工单

| | Incident 故障 | Service Request 服务请求 | Change 变更 |
|---|---|---|---|
| 目的 | 恢复服务 | 交付标准化服务 | 受控变更 |
| 核心 | 影响度×紧急度→优先级 | 服务目录项+表单 | 风险等级+CAB 审批 |
| 审批 | 通常无 | 按目录项配置 | 强审批 |

> **设计结论**：三类工单**共用一张表 + type 字段**（ServiceNow `task` 表族超类+子类），差异体现在表单字段、状态机、审批流、SLA 规则——正好对应"一张表 + 按类型配置工作流"。

### Jira Workflow 设计思想（最值得参考）

Workflow = **状态 + 转换 + 条件（谁能执行）+ 校验器（字段校验）+ 后处理函数 Post Function（发通知/更新字段/触发自动化/Webhook）**

把"转换"建模成**数据结构**而非散落的 if/else：

```
Transition { from, to, required_fields, allowed_roles, on_enter: [动作列表] }
```

### 自动审批/自动办理的行业实现

统一范式是**事件驱动规则引擎**：`事件（Event）→ 规则匹配（Trigger+Condition）→ 动作（Action）`

"自动审批"不是魔法，本质是**在审批节点加一条策略规则：满足条件 → 由系统扮演审批人**，同时写入审计日志（"Auto-approved by policy #12"）。三种实现：
1. **Jira Automation 风格**：Trigger（状态变更/字段更新/定时）→ Action（自动执行转换）
2. **ServiceNow Flow 风格**：Flow 中挂审批任务，低风险配置跳过审批（Auto-approve）
3. **策略驱动（Policy/Rule 表）**：`{工单类型, 条件, 审批人 or AUTO}`——**最值得 demo 实现**

### 功能模块清单

| 模块 | 行业标准做法 |
|---|---|
| 工单模板/表单 | 按类型绑定动态表单，JSON Schema 描述，前后端共用一份 schema |
| SLA | 按优先级配置响应/解决时限，等待状态暂停时钟，到期升级 |
| 通知 | 事件→接收人 订阅规则，站内+邮件+Webhook |
| 队列 Queue | 工单进队列，队列绑组/团队，按队列分派 |
| 分派路由 | 轮询/最少负载/技能匹配/人工认领 |
| 评论协作 | 内部评论（客户不可见）与外部评论分离 |
| 审计日志 | 不可变追加：谁在何时对哪字段做了什么（old→new） |
| 自动化规则 | Trigger→Condition→Action |
| 权限 | 四层：角色 + 数据范围（队列/组/归属）+ 操作权限 + 字段级 |

### 国内外差异

| 维度 | 国内 OA（蓝凌/泛微） | 国外 ITSM（Jira/ServiceNow） |
|---|---|---|
| 核心抽象 | **审批流**：表单+审批节点 | **服务目录 + 状态机 + SLA** |
| 组织模型 | 强组织架构（部门/岗位/上级） | 队列/组 + 角色 |
| 驱动 | 表单流转 | 状态转换 + 自动化规则 |

> **统一结论**：国外思路是"事件→状态机→自动化"，国内思路是"表单→审批节点→归档"。**兼容两者的核心是：审批 = 状态机里的一个特殊等待态**。

## 七、Python 生态技术选型（调研结论）

### 工作流/状态机方案对比

| 方案 | 类型 | 活跃度 | 定位 |
|---|---|---|---|
| **django-fsm + django-fsm-log** | Django 状态机 | ★ 高（Django 6.0 支持） | 对象生命周期状态机 + 审计日志，业界认可度最高 |
| **Viewflow** | Django 工作流库（BPMN） | ★ 高（v2.4.0） | Django 内嵌可视化流程，AGPL 许可 |
| **SpiffWorkflow** | 纯 Python BPMN 引擎 | ★ 高 | 可视化低代码引擎（SpiffArena） |
| **transitions** | 通用状态机（HSM） | ★ 中 | 非 Django 专用 |
| Airflow/Prefect | 任务编排 | — | **不适合工单**（人工审批弱） |
| Temporal | Durable Execution | — | 需独立部署 Server，工单场景过重 |

### 动态表单方案（行业标准）

- **JSON Schema**（json-schema.org，2020-12 draft）是事实标准：前后端共用同一份 schema，前端 **Formily / form-render** 渲染，后端 **`jsonschema` 库**校验
- Python 端：`JSONField` 单列存表单数据 + `jsonschema` 校验（自定义 DRF `JSONSchemaField`）
- 表单 schema 入库**带版本**，数据与 schema 解耦

### 异步任务与事件

- **Celery + Redis**（含 Beat 定时）：工单场景最稳妥
- 异步状态回传模式：`TaskJob` 记录（job_id、状态、回调数据）→ Worker 完成回写 → 工单 FSM 用 `on_success` 钩子推进 → 前端轮询或 WebSocket/SSE
- **关键**：状态以 DB 为准，队列只负责投递，Worker 必须幂等
- Webhook：`WebhookSubscription` + `WebhookDelivery`（重试/指数退避）+ HMAC-SHA256 签名 + `X-Event-Id` 幂等键

### API 设计

- DRF + **drf-spectacular**（OpenAPI 3.1）
- URL 前缀版本化 `/api/v1/`
- **Idempotency-Key** 中间件防重复提交（Stripe 模式）
- 回调：`OpenApiCallback` 描述契约，签名+幂等+事件类型

### 权限

- RBAC 打底（Django `Group + Permission`）
- **django-guardian**（对象级权限）：每个工单单独授权（指派人/关注人可看）
- **django-rules**（规则推导，无表）：如"仅作者/编辑组成员"

## 八、推荐技术选型（结论）

| 模块 | 选型 | 理由 |
|---|---|---|
| Web 框架 | Django 5 + DRF | 用户熟悉，生态成熟 |
| 流程引擎 | **自研轻量引擎**（JSON 定义 + 状态机执行器） | 不移植 BPMN 引擎（Python 性价比低），对标钉钉/飞书模型 + 补充 BPMN 语义 |
| 生命周期状态 | **django-fsm + django-fsm-log** | 状态迁移规则显式声明，审计日志自动落库 |
| 动态表单 | JSON Schema + `jsonschema` 校验 | 前后端共用，行业事实标准 |
| 异步任务 | **Celery + Redis**（含 Beat） | 生态最成熟 |
| 事件/回传 | 自建 `TaskJob` 表 + Redis Streams | DB 为准、任务幂等 |
| API 文档 | drf-spectacular | OpenAPI 3.1 |
| 幂等 | Idempotency-Key 中间件 | 防重复提交 |
| 权限 | RBAC（Group+Permission）+ django-guardian | 全局+对象级双轨 |
| 数据库 | PostgreSQL（Docker/OrbStack） | 生产一致 |

### 核心设计原则（贯穿整个 demo）

1. **定义与实例分离**：ProcessDefinition（模版）↔ ProcessInstance（流动工单），实例绑定启动版本
2. **状态机驱动，而非散落的状态字段**：生命周期用 FSM 显式声明迁移规则；流程推进由引擎在**单个事务**内完成
3. **任务模型（Task）与实例模型（Instance）分离**：Task 表管待办/指派/认领
4. **事件驱动**：领域事件（创建/完成/拒绝/超时）串联通知、审计、Webhook、SLA
5. **幂等**：所有写操作幂等，Worker 幂等，状态以 DB 为准
6. **会签/或签 = 多实例 + 完成条件**：TaskInstance 子任务 + 计数
7. **条件分支 = 排他网关 + 条件求值**（基于表单字段值）
8. **自动办理 = 策略规则 + 审计留痕**，而非随机抽人
