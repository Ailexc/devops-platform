# 差距分析：旧版自研工单系统 vs 行业标准

> 目的：对照行业调研结论，逐项分析旧版系统的实现方式与行业标准/常规实现的差异，明确 demo 系统要改进的点。

---

## 一、旧版系统实现回顾（来自用户描述）

1. **前端**：开源项目，支持自定义表单、流程设置、条件分支、审批/办理/抄送节点
2. **表单**：静态数据/API 接口数据；多选项卡联动；前端只请求后端数据，**去掉了验证，失去开放性**
3. **流程**：条件分支常规；办理节点允许绑定 API + 表单字段作入参；可绑定任务由后端接口返回（后端真实原子能力）；**节点输出不能作为下一节点输入（阉割）**，字段均从表单获取或存中间公共区域
4. **工单配置（模版）**：配置保存为模版，每次发起加载模版 → 渲染表单 → 填表 → 计算流程 → 发起生成**流动工单**（记流动工单表）+ 按流程节点计算**任务**（记任务表）
5. **待办/已办**：数据来自任务表，基于**状态字段**实现不同板块查询
6. **办理能力**：后端实现 API，基于**数据库状态字段**做可行性判断并执行动作、更新数据表
7. **自动办理**：办理节点可开启自动办理按钮，后台检测到自动模块后**随机抽选一名办理人作代理**，更新数据库状态，执行办理
8. **自动任务**：任务板块与流程板块同库但分离，通过 API 调用和数据转发；办理节点绑定任务 = API + 参数
9. **任务状态流转**：分同步/异步任务，节点打标签；同步=请求等待按结果更新；异步=发出立即返回成功，节点转"办理中"，等后续状态更新
10. **作业平台**：公共平台，可注册任务（标准任务 ID、输入输出说明），承担外部审批等能力；任务状态实时更新到指定队列，通过**监听队列**更新节点日志与状态
11. **整体架构**：后台分两大块——前端交互/流程管理 + 原子任务开发/编排/下发/状态监听（同一代码库）
12. **发起途径**：前端提单 + 程序发起提单

## 二、逐项差距分析

### 差距 1：状态表示方式（最核心）

| 旧版 | 行业标准 | 差距本质 |
|---|---|---|
| 基于**数据库状态字段**判断流转可行性，分散在各处 if/else | **状态机**（显式迁移规则 + 条件 + 权限 + 副作用）；状态是引擎执行的**结果投影**而非驱动原因 | 旧版状态散落、规则隐式、易出非法流转；行业版状态迁移集中、显式、可审计 |

**改进方向**：用 `django-fsm` 把"生命周期状态机"显式声明；流程推进由引擎在单事务内完成（校验→记录→推演→生成新任务）。

### 差距 2：流程定义模型

| 旧版 | 行业标准 |
|---|---|
| 流程配置散落在前端开源项目，定义不独立、无版本概念 | **定义/实例分离** + 定义**版本化**（key+version，实例绑定启动版本） |

**改进方向**：JSON 化流程定义（对标钉钉/飞书），存库、版本化、发布后不可改（不可变快照）。

### 差距 3：会签/或签语义

| 旧版 | 行业标准 |
|---|---|
| "基本和市面上通用"，未明确多实例语义 | **多实例活动 + 完成条件**（会签=全通过 AND-join；或签=任一通过 Discriminator） |

**改进方向**：TaskInstance 子任务表 + 实例级计数 + 完成条件，明确 join 语义。

### 差距 4：节点间数据传递（旧版被阉割）

| 旧版 | 行业标准 |
|---|---|
| 节点输出不能作为下一节点输入；字段只能从表单获取或存"中间公共区域" | **流程变量（variables）**：全局变量 JSONField，节点可读可写，条件表达式/下游节点输入均可引用 |

**改进方向**：恢复变量传递能力——`variables` 贯穿实例生命周期，服务节点输出写入变量，条件分支与下游节点输入可引用 `{var}` 表达式。

### 差距 5：表单校验与开放性

| 旧版 | 行业标准 |
|---|---|
| 前端只请求后端数据，去掉验证，失去开放性 | **JSON Schema** 前后端共用：前端渲染、后端 `jsonschema` 校验，开放且可扩展 |

**改进方向**：表单定义为 JSON Schema，后端强制校验，前端按 schema 渲染，保留开放性。

### 差距 6：自动办理

| 旧版 | 行业标准 |
|---|---|
| **随机抽选**一名办理人作代理执行 | **策略驱动（Policy）**：规则表命中（如低风险/金额阈值）→ 系统扮演审批人，写审计"Auto-approved by policy #X" |

**改进方向**：自动办理 = 节点策略（auto 标记）+ 规则求值 + 系统代理执行 + 审计留痕；保留"随机代理"作为策略之一，但更强调可追溯。

### 差距 7：异步任务与作业平台（旧版做得好的部分）

| 旧版 | 行业标准 | 评价 |
|---|---|---|
| 同步/异步任务标签；作业平台注册任务；监听队列更新状态 | TaskJob 记录 + Worker 幂等 + 事件驱动回传 + DB 为准 | **思路与行业一致**，是旧版亮点 |

**改进方向**：把"作业平台"抽象成**能力注册中心（Capability Registry）**：原子能力以 API 注册（输入/输出 schema），同步/异步两种执行模式，异步通过**事件/队列监听**回传，状态以 DB 为准、Worker 幂等。demo 中内置 mock 作业平台 + 真实 HTTP 客户端两种实现。

### 差距 8：架构分层

| 旧版 | 行业标准 |
|---|---|
| "流程管理 + 原子任务"两大块在同一代码库，靠 API 互通 | 领域分层：流程引擎（引擎内部）↔ 工单业务（表单/业务数据，经 businessKey 弱关联）↔ 能力/任务（原子能力注册 + 执行）↔ 事件总线（解耦通知/SLA/Webhook/审计） |

**改进方向**：Django app 划分 + 领域事件解耦，让模块之间不硬编码调用。

### 差距 9：审计与可观测性

| 旧版 | 行业标准 |
|---|---|
| 节点日志、状态流转（有基础） | 不可变审计日志（谁在何时对哪个字段做了什么 old→new）+ 事件日志 + 流程追踪 |

**改进方向**：`django-fsm-log` 自动落状态审计 + `ApprovalRecord`（审批意见）+ `EventLog`（领域事件）。

### 差距 10：权限模型

| 旧版 | 行业标准 |
|---|---|
| 未提及，大概率简单 | RBAC 四层：角色 + 数据范围（队列/组/归属人）+ 操作权限 + 字段级 |

**改进方向**：RBAC（Group+Permission）打底 + django-guardian 对象级（谁能看这张单/谁能办这个任务）。

### 差距 11：工单业务能力（ITSM 特性，旧版基本没有）

| 行业标准 | demo 建议 |
|---|---|
| SLA（响应/解决时限 + 等待暂停 + 到期升级） | 可选，作为加分项 |
| 优先级矩阵（影响×紧急度） | 简单实现 |
| 队列/分派路由 | 简化（节点配置审批人 + 候选组） |
| 评论协作（内/外部分离） | 简单实现 |
| 通知（站内/Webhook） | 事件总线 + Webhook 订阅 |
| 报表统计 | 可选 |

---

## 三、核心结论：demo 系统要"改"什么

1. **状态机显式化**：生命周期用 FSM，流转规则集中、可审计，杜绝散落状态判断
2. **定义/实例分离 + 版本化**：模版与流动工单严格分离，模版发布后不可变
3. **流程变量传递**：恢复节点间数据传递能力（旧版阉割点）
4. **会签/或签标准语义**：多实例 + 完成条件
5. **表单 JSON Schema 化**：前后端共用 + 后端校验，保留开放性
6. **自动办理策略化**：策略驱动 + 审计留痕
7. **能力注册中心**：把"作业平台"抽象为注册制原子能力（同步/异步），异步事件回传
8. **事件驱动架构**：领域事件串联审计/通知/Webhook/SLA，模块解耦
9. **幂等设计**：写操作 + Worker 幂等
10. **权限双轨**：RBAC + 对象级

### 保留旧版的优秀设计（作为亮点继续讲）

- 模版派发模型（模版 → 流动工单 → 任务）与行业"定义 → 实例 → 任务"同构
- 作业平台/异步任务状态监听思想与行业事件驱动一致
- 同步/异步任务标签体系
- 程序发起提单（API 提单）
