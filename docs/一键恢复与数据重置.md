# 一键恢复与数据重置（make demo-reset）

> 无论业务数据被如何破坏（误删、篡改、清空、脏数据、异常停机），
> 一条命令即可把整个 DevOps 平台恢复到**干净出厂态**，保证随时可演示。
> 本能力基于「**从代码重建**」而非「从备份恢复」，因此不依赖备份是否完整、何时备份，
> 任何数据层损坏都在覆盖范围内。

---

## 1. 核心原理（为什么可靠）

统一平台（`infra/docker-compose.yml`）采用**一实例多库**的 PostgreSQL（`devops-postgres`）
与统一 Redis（`devops-redis`），每个系统对应独立业务库：

| 系统 | PostgreSQL 库 | Redis DB 索引 |
|------|--------------|--------------|
| 认证中心 Authentication | `devops_auth` | - |
| 多云管理 CloudManager | `devops_cloud` | 1 |
| 事件管理 EventManager(Python) | `devops_event` | 2 |
| 事件管理 EventManager(Go) | `devops_event_go` | 8 |
| 权限中心 PermissionCenter | `devops_iam` / `devops_openfga` | - |
| 发布管理 ReleaseManager | `devops_release` | - |
| 任务管理 TaskManager(Python) | `devops_cmdb` | 5 |
| 任务管理 TaskManager(Go) | `devops_cmdb_go` | 7 |
| 流程中心 WorkFlowCenter | `devops_workflow` | 6 |

一键恢复做的事情：

1. **硬重建数据库**：`DROP DATABASE ... WITH (FORCE)` 删除重建全部业务库（10 个），
   从代码重新 `migrate` 建表 + `seed` 灌入演示数据；
2. **清空 Redis 业务数据**：`FLUSHDB` 清掉各业务 DB 索引（asynq 队列、任务状态、缓存等），
   避免残留脏状态；
3. **逐项目回种**：收编各系统既有的 reset 脚本（`Authentication/reset.sh`、
   `CloudManager/reset_db.sh`、`EventManager/init-all.sh`、`PermissionCenter make seed-reset`、
   `ReleaseManager/reset-all.sh`、`TaskManager`、`WorkFlowCenter`），统一执行；
4. **重建并启动全部应用**：`up -d --build` 保证镜像/代码为最新；
5. **冒烟测试**：curl 校验门户 + 各系统 + 演示应用 + 认证 API 的 HTTP 可达性，
   任何一项失败都会**报错并返回非零退出码**（不再静默吞错）。

> **重要设计变更（Phase 4）**：EventManager 的 Go 栈原先有一个独立的 `go-seed` 容器
> （`cmdb-event-go-seed`），每次 `docker compose up -d` 都会自动跑一次并 **TRUNCATE 清库再灌**
> 1000 条假数据，导致正常启动也会清掉真实事件数据。现已将其**收敛为 go-api 启动时的幂等种子**
> （`backend-go/internal/seed`）：空库自动灌演示数据、非空跳过、`SEED_FORCE=true` 才强制重灌，
> 并已删除 `go-seed` 服务定义。

## 2. 使用方式

```bash
# 一键恢复到干净出厂态（推荐）
make demo-reset

# 只重置单个项目（内部仍保证容器就绪 + Redis 清理）
make reset P=event
make reset P=cmdb
make reset P=workflow
```

> 入口脚本：`scripts/demo-reset.sh`（根目录 Makefile 的 `demo-reset` 目标）。
> 重置/恢复基座：`scripts/reset-all.sh`。

---

## 3. 一键恢复流程（分阶段详解）

执行 `make demo-reset` 时按以下阶段推进，任一步失败即中止并报错：

```
阶段 0  校验 Docker 环境（docker info）
阶段 1  确保统一基础设施运行（bootstrap 幂等：PostgreSQL / Redis / RabbitMQ）
阶段 2  构建全部业务镜像 + 统一网关镜像
阶段 3  全量硬重置（reset-all.sh）
        ├─ 3.1  DROP DATABASE 重建 10 个业务库
        ├─ 3.2  OpenFGA migrate（权限模型，先于 iam 种子）
        ├─ 3.3  cmdb-go 按当前 compose 重建（--seed 自动迁移+播种）
        ├─ 3.4  逐项目重置回种（auth/cloud/event/iam/release/cmdb/workflow）
        │        └─ 每项目 exec 前先确保容器 up（不再依赖"容器恰好运行中"）
        └─ 3.5  清空 Redis 业务数据（db 1/2/5/6/7/8）
阶段 4  重建并启动其余业务应用（up -d --build）
阶段 5  启动统一网关（Traefik，8088-8099）
阶段 6  冒烟测试（见下节）
```

## 4. 冒烟测试内容

| 系统 | 端口 | 检查 |
|------|------|------|
| 统一门户 | 8088 | HTTP 200/3xx |
| 任务管理 cmdb | 8089 | HTTP 200/3xx |
| 多云管理 cloud | 8090 | HTTP 200/3xx |
| 流程中心 workflow | 8091 | HTTP 200/3xx |
| 事件管理 event | 8092 | HTTP 200/3xx |
| 发布管理 release | 8093 | HTTP 200/3xx |
| 权限中心 iam | 8094 | HTTP 200/3xx |
| 演示 mock-app | 8095 | HTTP 200/3xx/401 |
| 演示 direct-app | 8096 | HTTP 200/3xx/401 |
| 演示 pilot-app | 8097 | HTTP 200/3xx |
| 演示 oidc-demo | 8098 | HTTP 200/3xx |
| 认证 API | 8099/api/system/health | HTTP 200 |

冒烟通过 `curl -s -o /dev/null -w '%{http_code}'` 校验；判定规则：
`200/301/302/303/401/403` 视为服务可用（401 表示"受保护但网关在响应"，属正常），
其余（含连接失败 `000`）视为失败并中止。

## 5. 定时每日恢复（可选）

如需"每天早上自动恢复到干净状态"，在 ECS 上配置 cron 即可（服务器本地时区）：

```bash
# crontab -e
# 每天早上 04:30 一键恢复到干净出厂态，日志追加到 /var/log/demo-reset.log
30 4 * * * cd /opt/DevOpsPlatform && make demo-reset >> /var/log/demo-reset.log 2>&1
```

- 恢复本身幂等、可重复执行，不会因重复运行产生问题；
- 若某天某系统冒烟失败，脚本会以非零退出码结束（cron 默认邮件/日志可见），
  同时脚本末尾会打印 `❌` 失败项；
- 也可用 `make reset`（不带 P）做"仅数据重置、不重建镜像"的轻量定时任务：

```bash
# 每天晚上 02:00 仅重置数据（更快，保留已构建镜像）
0 2 * * * cd /opt/DevOpsPlatform && make reset >> /var/log/reset.log 2>&1
```

> 说明：`make demo-reset` 是「恢复 + 重建 + 冒烟」全流程，适合演示前或每日兜底；
> `make reset` 只做数据层重置回种，速度快，适合低峰期定时执行。

## 6. 常见问题与边界

### 6.1 恢复范围
- ✅ 覆盖：全部 PostgreSQL 业务库、Redis 业务数据、应用容器/镜像（重建）、演示 app、认证 API。
- ⚠️ 不覆盖：**账号口令/权限等凭据级**破坏（如改掉 admin 密码、回收安全组）。
  这类破坏不属于"数据恢复"范畴，需通过账号管理/安全组配置修复；
- ⚠️ 不删除：历史 `backups/` 备份目录（保守保留，如需清理请手动处理）。

### 6.2 演示应用与认证 API 归属
- 演示应用（mock/direct/pilot/oidc）与认证 API 属于 `Authentication` 项目 compose，
  由统一网关（Traefik）经 `devops-net` 网络路由到 8095-8099；
- `Authentication/reset.sh` 已统一处理其构建与启动，故 `demo-reset` 无需单独处理。

### 6.3 边界修复记录（Phase 4）
| 原问题 | 修复 |
|--------|------|
| `reset` 用 `docker compose exec` 依赖容器已在运行，容器停机时失败且被 `\|\| true` 吞掉 | 每项目 exec 前先 `ensure_up`（`up -d --build`）确保容器就绪；移除 `\|\| true` 吞错，失败即中止报错 |
| Redis 业务数据未清理（asynq 队列/任务状态/缓存残留） | `reset-all.sh` 新增 `flush_redis()`，统一清空 db 1/2/5/6/7/8 |
| EventManager Go 栈 `go-seed` 容器每次 `up` 自动清库 | 收敛为 go-api 启动幂等种子，删除 `go-seed` 服务（见第 1 节） |
| workflow 重置缺少 migrate（schema 重建后表结构需先建） | workflow 分支改为 `migrate --noinput` + `reset_demo` 两步 |

### 6.4 平台可移植性
- 冒烟测试默认 `DEMO_RESET_BASE=http://127.0.0.1`，本机/ECS 均可用（ECS 内部访问走 loopback，
  避免 NAT loopback 下访问公网 IP 返回 000 的问题）；
- 如需指定其他地址：`DEMO_RESET_BASE=http://<host> make demo-reset`。
