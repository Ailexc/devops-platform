# DevOps 平台合集 —— 公网部署验证与底层架构统一方案

> 调研日期：2026-08-16 · 依据：Render 官方文档（free / pricing / compute-plans / blueprint-spec / monorepo-support / deploys / disks / key-value / postgresql）
> 结论先行：**「全免费 + 每项目独立 SQLite + 8 服务常开」的旧方案在 Render 免费版跑不通**；但 **Blueprint 一键部署、免费 Postgres/Redis、公网访问** 均属实。下文给出核实事实 + 修正后的完整方案。

---

## 一、Render 免费额度核查（以官方文档为准）

### 1.1 免费能力清单（属实 ✅）

| 资源 | 免费规格 | 公网访问 | 备注 |
|------|----------|----------|------|
| Web Service | $0/月 · 512MB RAM / 0.1 CPU | ✅ `xxx.onrender.com` | 15 分钟无流量自动休眠，唤醒约 1 分钟 |
| Static Site | $0/月 · 全球 CDN | ✅ | 展示页 / 门户静态页用 |
| Render Postgres | $0/月 · 256MB / 1GB / 100 连接 | ✅ 外网 URL（需凭证） | **每工作区仅 1 个 · 30 天过期** |
| Key Value (Redis/Valkey 8) | $0/月 · 25MB / 50 连接 | 需配 IP 白名单 | **每工作区仅 1 个 · 仅内存无持久化** |

### 1.2 免费版关键限制（旧方案为何跑不通 ❌）

1. **750 实例小时 / 工作区 / 月（全免费 Web 共享）**
   8 个 Web 服务"常开"= 8 × 730 ≈ 5840 小时/月 ≫ 750 小时 → 当月中旬就被 `suspend` 到下月。
   省小时的唯一办法就是靠"15 分钟无流量休眠"——意味着**只能逐个唤醒演示，不能 8 个长期在线**。

2. **免费 Web 服务是 ephemeral 文件系统，且不能挂持久化磁盘**
   容器内文件（如 SQLite 数据库文件）在**重启、重部署、甚至休眠**后全部丢失。
   → 旧方案「每个项目独立 SQLite + 内存缓存」在 Render 免费版**不可行**（数据随时蒸发）。

3. **免费 Postgres 仅 1 个 / 工作区**
   1GB 存储、256MB 内存、无备份、无连接池、**创建 30 天后过期**（宽限 14 天，逾期删除）。
   同一实例内可 `CREATE DATABASE` 多库（"一个 PG 分 7 库"技术上可行），但 **1GB 分摊 7 个项目非常紧张**，且 30 天必须续期重建。

4. **免费 Key Value（Redis）仅 1 个 / 工作区，且仅内存**
   25MB、50 连接、**无持久化**（实例重启即清空）。
   适合做共享缓存；**不适合**做需要持久性的 Celery broker / 业务状态。

5. **免费实例不支持**：background worker、私有服务（pserv）、cron job、one-off job、`preDeployCommand`（迁移等部署前命令）、SSH。
   → Celery worker 无法免费独立部署；迁移/种子只能放 **startCommand**。

6. **Hobby 工作区额度**：出站带宽 **5GB/月**（超出 $0.15/GB 或直接 suspend）、构建管道 **500 分钟/月**、最多 **25 个服务**、2 个自定义域名。
   另外免费 Web **频繁主动出站**（如 CMDB 高频轮询外部 API）可能被平台临时 suspend。

### 1.3 结论：之前调研"部分正确"

| 之前的判断 | 核实结果 |
|-----------|---------|
| 免费部署 + 公网访问 | ✅ 属实（Web/静态站/PG/Redis 都有免费档） |
| 一键部署多个应用 | ✅ 属实（Blueprint / render.yaml IaC，见第二节） |
| 免费提供数据库 | ⚠️ 属实但极受限（1 个、1GB、30 天过期） |
| 每项目独立 SQLite + 8 服务常开 | ❌ 免费版跑不通（750 小时共享 + 无持久化磁盘） |

## 二、Render 一键部署多个应用：Blueprint（render.yaml）

Render 的 **Blueprint** 就是为"一个仓库多服务、一键全建"设计的（IaC）：

- 一个 `render.yaml` 可声明：`services`（web / static / keyvalue）+ `databases`（Postgres）+ `envVarGroups` + `projects/environments`
- 操作：GitHub 推到仓库 → Dashboard `New → Blueprint → Connect 仓库 → Deploy Blueprint` → **一次创建全部资源**
- Monorepo 支持完善：`rootDir` / `dockerfilePath` / `dockerContext` / `buildFilter`
- 变量自动接线：`fromDatabase` 自动注入 `DATABASE_URL`、`fromService(type: keyvalue)` 注入 `REDIS_URL`、`generateValue` 生成密钥
- **关键约束**：免费服务不能用 `preDeployCommand` → 所有迁移 + 幂等种子放 **startCommand**

### 2.1 render.yaml 草案（示意，需按各项目 Dockerfile 细化）

```yaml
services:
  # —— 展示页（静态） ——
  - type: web
    name: showcase
    runtime: static
    rootDir: showcase
    buildCommand: 'true'
    staticPublishPath: .

  # —— 统一门户（Authentication 前端，静态化或独立 Web） ——
  - type: web
    name: portal
    runtime: docker
    rootDir: Authentication
    dockerfilePath: frontend/Dockerfile
    plan: free

  # —— 认证中心 ——
  - type: web
    name: auth-api
    runtime: docker
    rootDir: Authentication/backend
    plan: free
    envVars:
      - key: DATABASE_URL
        fromDatabase:
          name: devops-pg
          property: connectionString
      - key: APP_SECRET
        generateValue: true

  # —— 其余系统（Event/Permission/Release/Task/Workflow/Cloud 同理） ——
  #   rootDir 各自指向 backend，runtime: docker，plan: free
  #   envVars 统一接 devops-pg 的 connectionString（各服务用各自 database 名）

  # —— 共享 Redis（免费，仅缓存；Celery 演示用 EAGER） ——
  - type: keyvalue
    name: devops-kv
    plan: free
    ipAllowList:
      - source: 0.0.0.0/0
        description: everywhere
    maxmemoryPolicy: allkeys-lru
    persistenceMode: off

databases:
  - name: devops-pg
    plan: free
```

> ⚠️ 免费 PG 每工作区仅 1 个 → 蓝图里只定义 1 个 `devops-pg`，各项目在**启动时** `CREATE DATABASE devops_<proj> IF NOT EXISTS`（或统一建库脚本）。
> ⚠️ 免费 KV 每工作区仅 1 个 → 只定义 1 个 `devops-kv` 共享。

## 三、底层架构统一（本地与 Render 一致）

### 3.1 数据库统一为 PostgreSQL（一实例多库）

| 项目 | 现状 | 目标 |
|------|------|------|
| Authentication | SQLite | → `devops_auth` |
| CloudManager | MySQL | → `devops_cloud`（驱动 + 方言 + JSON/bool 差异改造） |
| EventManager | PostgreSQL | → `devops_event`（改连接即可） |
| PermissionCenter | PostgreSQL | → `devops_iam`（改连接即可） |
| ReleaseManager | SQLite | → `devops_release` |
| TaskManager | PostgreSQL | → `devops_cmdb`（改连接即可） |
| WorkFlowCenter | PostgreSQL | → `devops_workflow`（改连接即可） |

统一连接约定：
```bash
DATABASE_URL=postgres://devops:devops@<pg-host>:5432/devops_<proj>
REDIS_URL=redis://<redis-host>:6379/<index>   # 本地按项目分 db index，Render 共用一个 KV
```
配套：本地一个 `postgres` 容器 + `db/init.sql`（一次性建 7 个库），一套 `pgdata` 卷。

### 3.2 缓存 / 队列统一为 Redis

- **本地**：一个 `redis` 容器，各项目用不同 db index（0–6）或 key 前缀隔离，一套 `redisdata`。
- **Render（免费）**：共享 1 个免费 Key Value，**只放缓存**（内存态、可丢失）。
- **Celery 在 Render 免费版的现实**：免费不支持独立 worker → 演示一律开 **EAGER 模式**（`CELERY_TASK_ALWAYS_EAGER=1`，同步执行、无需 broker/worker）；本地开发仍可跑真 worker。这是"零成本 + 演示完整"的折中。

### 3.3 网关 / SSO 在 Render 的现实

- Traefik `forwardAuth` 是本地/内网利器；但 Render 免费版没有可托管的 Traefik，且**免费 Web 不能收私网流量**（只能发）。
- 务实做法：每个系统独立 `*.onrender.com` 公网 URL + 独立登录；统一门户（Authentication Portal）作为入口卡片聚合；**SSO 只打通 2–3 个核心系统**（Auth 签发 RS256 JWT → 目标系统用 JWKS 公钥验签，走公网 URL 同样成立），其余"仅跳转展示"。这与《免费部署计划》既有策略一致。

### 3.4 统一构建 / 部署 / 数据重置（本方案的核心工程）

在仓库根目录新增统一入口（顶层 `Makefile` + `scripts/`）：

| 命令 | 作用 |
|------|------|
| `make bootstrap` | 本地起 `pg` + `redis` 容器 + `init.sql` 建 7 库 |
| `make build` | 逐项目构建镜像（前端 dist + 后端镜像） |
| `make up` / `make down` | 全量起停（或 `make up P=release` 只起单个） |
| `make seed` | 全量种子（幂等，重复执行不重复插入） |
| `make reset` | **全量数据重置**：drop schema → migrate → seed（可 `make reset P=release` 单项目） |
| `make status` | 各容器健康检查 |
| `make deploy` | 校验并同步 `render.yaml` 蓝图 / 推送触发 Render 部署 |

**每个项目统一 4 件事**（解决"各搞各的"）：
1. **统一环境变量**：`DATABASE_URL` / `REDIS_URL` / `APP_SECRET` / `RENDER` 标记
2. **统一启动入口** `start.sh`：`migrate → 幂等 seed（空表才种 / 版本标记）→ 启动` —— Render 与本地同一条命令
3. **统一重置入口** `make reset`：现有 reset 脚本（`reset.sh`/`reset_db.sh`/`reset_data`/`reset_demo`/`make seed-reset`）统一包一层标准命名与参数
4. **幂等种子**：以"版本标记 / 空表判断"种数据，重部署不重复插入

### 3.5 "每次重新部署恢复如初"（快照语义）能做到吗？

- **Render 的真相**：数据在托管 PG 里**跨重部署保留**，不会自动重置（代码每次全新构建，DB 不清空）。所以"部署即重置"默认不成立。
- **要实现"恢复如初"**（三种手段，按需选）：
  1. **RESET_ON_START 开关**（推荐）：`startCommand` 判断 `RESET_ON_START=1` 就先 `drop schema → migrate → seed` 再启动。需要还原时：Dashboard 里给该服务临时加这个 env → 手动部署 → 数据即回到初始；演示完去掉该 env 再部署即恢复正常态。
  2. **受保护 Reset 端点**：各系统暴露 `POST /api/_reset`（共享密钥鉴权），统一脚本或门户按钮一键还原全部系统——适合演示中途"被搞乱"后秒回。
  3. **Render 回滚**：免费 Web 支持回滚最近 2 次部署（只回滚代码，不回滚 DB）。
- **本地**：`make reset` 即"一键回到出厂态"，完全可控、无额外成本。

## 四、推荐落地路径（两档）

### 方案 A：全免费（$0/月，适合短周期面试冲刺）
- 1 个免费 PG（分 7 库，严格控制种子体积 < 1GB）+ 1 个免费 KV（缓存）+ 7 个免费 Web + 1 静态展示页/门户
- Celery 全 EAGER；SSO 只打通 2–3 个核心
- 缺点：PG **30 天过期需重建重种**；1GB 很紧；KV 25MB 无持久化；演示前需逐个预热
- 适合：一个月内集中面试

### 方案 B：数据库 / 缓存升一档（约 $16/月，长期稳定在网）
- Render Postgres `basic-256mb`（$6/月）+ Key Value `starter`（$10/月）→ 无限时长、可持久化、可多实例、可建多个库
- 7 个 Web 仍全免费（常态休眠、面试唤醒）
- 适合：作品集长期挂在简历/官网，随时可演示

### 本地统一（两档都做，成本为 0）
- 统一 PG + Redis 容器、统一 Makefile、统一 reset —— 这是根治"开发期各搞各的、太乱"的关键

## 五、下一步行动计划（建议顺序）

1. **顶层脚手架**（本次可开工）：根目录 `Makefile` + `scripts/` + 统一 `env` 模板 + 统一 `reset` 入口 + `db/init.sql`（建 7 库）
2. **数据库迁移**（分项目小步走）：Authentication、ReleaseManager SQLite→PG；CloudManager MySQL→PG
3. **统一启动/种子**：每项目补 `start.sh`（幂等）+ `RESET_ON_START` 支持
4. **Render 蓝图**：写 `render.yaml` + `make deploy` 校验；先在 1 个系统（如 WorkFlowCenter 或 TaskManager）跑通，再推广全家桶
5. **门户/展示页收尾**：展示页 `CONFIG.portalUrl` 换成 Render 公网门户；准备面试预热脚本（批量访问唤醒）

> 备注：Render 官方对"免费 PG/KV 是否占用 750 实例小时"未在文档明示，本方案按"会占用"保守规划，保持低常开时长即可完全在额度内。
