# 权限中心改造计划：去中心化 IAM（Refactor Plan）

> **定位**：本文档是 2026-08-03 设计讨论（组即角色 / 去中心化授权 / 授权全审批 / TTL 临时组 / 策略双向账本 / 上下文过滤视图）的**改造计划**。
> **与 `implementation-plan.md` 的关系**：前者是当前已实现的 P0–P6 计划；本文档是**下一阶段的演进蓝图**，二者独立，避免混淆。
> **状态**：设计已收敛，待评审后进入实施。

---

## 1. 设计目标与核心理念

把权限中心从"中心管理员控制台"演进为**基于所有权的去中心化授权管理（ownership-based decentralized IAM）**：

| 核心理念 | 说明 |
|---|---|
| **用户即主体，即授权者** | "我"登录后是主体，也是我拥有的资源（组织/组/应用/程序）的授权者；无"切换个人空间/配置空间"，靠**上下文过滤**浮现管理能力 |
| **去中心化授权** | 授权由资源相关方（应用 owner / 组织上级 / 对方应用 owner）自治，无单一中心管理员 |
| **授权状态变更全审批** | 创建授权组、加成员、挂权限、策略变更等一律有控制点；审批即策略（可自动路由） |
| **组即角色** | 删除独立 Role，自建组 = 人的集合 + 权限集合；临时授权 = TTL 组 |
| **信任边界外置** | LDAP / 组织树 / 工单系统为外部信任依赖，默认信任；程序只处理信任根之上的逻辑 |
| **程序化兜底（fail-closed）** | 多 owner + 失联提醒 + N 次无响应停用，替代传统管理员兜底 |

## 2. 目标概念模型（与现状的差异）

### 2.1 主体（统一）

```
主体 Subject（一切可被授权对象）
├── 人（Person）        ← 身份源（LDAP/SCIM）同步，权威在外部
├── 组（Group）          ← 组织(同步) / 自建组(用户创建)
│     └─ 自建组 = 人的集合 + 权限集合（组即角色）
│     └─ TTL：组级有效期 / 成员级有效期（临时授权）
└── 程序（Service）      ← 应用下的 client（M2M）
      └─ 应用双角色：资源方（被别人申请）+ 主体方（去申请别人）
```

**差异**：现状 `Role`/`RoleAction` 独立存在且只挂接口层权限点；目标**删除 Role**，组直接挂权限点。`Group` 增加有效期与失活状态。

### 2.2 授权（策略统一表，记录方向）

```
策略 Policy（统一：能力层 + 数据层 + 来源）
├── 能力层 action_ids       接口级（Casbin）：cmdb:host:create
├── 数据层 resource_scope   数据级（OpenFGA）：实例勾选 / 维度范围
└── 来源 source ★新增       双向账本：
     ├── owner_grant     应用 owner 主动发布（预授权）
     ├── via_request     用户/应用申请 → 相关方审批生成
     └── app_request     应用间申请（service-to-service）
```

**差异**：现状 `Policy` 只有 `created_by`，无法区分"我给的 / 申请批的 / 我申请的"。目标补 `source` + 关联申请单 ID，形成双向可见的授权账本。

### 2.3 数据范围表达式（新增维度级）

```
现状：resource_scope = { model, operation, instance_ids: [...] }（实例勾选）
目标：+ 维度/属性级范围（审计这类海量数据场景）
      resource_scope = { model: "audit_log", dimension: "org", values: ["payment"] }
执行：filter（OpenFGA ListObjects）演进出"范围过滤"，PDP 返回可见范围条件供下游拼接
```

### 2.4 接口授权 vs 数据授权（已明确）

**统一建模、分层管理、同一执行链**：请求 → Casbin 接口层（能否调 API）→ OpenFGA 数据层（能否操作该数据）→ AND 放行。
- cmdb 场景：一起管理，管理界面分"接口授权 / 数据授权"两个视图，底层同一张策略。
- 审计场景：查询接口权限 + 数据范围（维度级）叠加。

## 3. 治理模型

### 3.1 审批（授权状态变更全审批）

```
敏感操作（全审批）：
  创建/删除授权组、组加/移成员、组挂/卸权限点、策略增删改、程序身份授权、数据范围变更
非授权性配置（仅审计）：
  改组名/描述、应用同步 OpenAPI、元数据更新
```

- **审批即策略（approval-as-policy）**：审批规则声明式，人审 + 自动审批（工单系统联动、组织层级计算、特定人员规则）
- **审批权威分布式**：组织上级、对方应用 owner、工单流程，皆可为审批链一环；**无单一管理员能决定复杂业务权限**
- **审批定性**：审批是**治理规范（流程纪律）而非安全闸门**——价值在①流程统一（流程外禁止）②留痕 ③相互 check（防单点失误）④事后审计；安全闸门是"谁能拥有所有权"（注册校验、风险分级）

#### 3.1.1 SoD / 审批规则（2026-08-04 细化）

```
硬约束（系统强制，不可外包）：
  ① 申请人 ∉ 审批链（谁申请谁退出；"自己批自己"精确化为"申请人退出"）
  ② 应用负责人 ≥2，互为审批人（互批：A 批 B、B 批 A）
  ③ 审批凭证（工单号 + 审批链记录）回存策略 + 审计留痕，形成可追溯闭环
软规则（默认 + 可编排）：
  ④ 有业务线上级 → 上级加入审批链（业务线负责人 = 组织树节点治理，非新主体，
     通过 App.OwnerGroupID 归属；即授权域边界的具体规则）
  ⑤ 单负责人且无上级 → 自批兜底 + 全量留痕 + 高风险自动转安全复核
  ⑥ 高风险（敏感/生产写/大范围）→ 自动追加安全/合规节点
  ⑦ 审批编排可外置工单系统（发起/查询/回调 契约化），权限中心保留 SoD 骨架
边界声明：
  ⑧ SoD 防单人失误，不防双人合谋（collusion 靠审计/异常检测/抽查缓解）
  ⑨ 所有权优先于层级：领导申请下属应用的权限，仍需该应用负责人审批
     （应用负责人对应用授权的话语权 > 组织等级）
```

**编排外置的边界**（权限中心不可让渡）：
- 可外包：审批人编排、多级节点、加安全节点、层级计算 → 工单系统
- 不可外包：① SoD 硬约束校验（申请人 ∉ 审批链）② 审批结果凭证校验（仅接受自己发起的审批单结果）③ 结果回存留痕 ④ 工单不可达 → 授权变更 fail-closed（不生效，保持现状）

### 3.2 信任边界（外部依赖默认信任）

LDAP（身份源）/ 组织树 / 工单系统为**外部信任依赖（trust boundary）**，默认信任；人员信息正确性由运维 IT 负责，程序只处理信任根之上的逻辑。威胁模型以此为边界假设。

### 3.3 程序化兜底（fail-closed，替代传统管理员）

```
多 owner（≥2）+ 离职提醒 → 另一 owner 补位
全部失联 → 向上查找领导认领（组织树）
N 次提醒无响应 → 判定高风险 → 直接停用
停用后恢复通道：新的认领者走审批重新启用
停用范围分级：owner 的授权权限 / 应用的程序身份
```

## 4. 前端：去中心化视图（上下文过滤，无切换按钮）

```
登录 → 我的工作台（所有与我相关：我的权限 / 我的申请 / 我的应用 / 审批待办）
  ├─ 组织权限：组织树、我所在组织的权限、组织权限申请
  ├─ 个人权限：我的权限汇总（组织继承+组+个人申请+临时）、权限申请、临时权限（TTL 组）
  ├─ 应用权限：我的应用、应用管理（配置对外 API / 能力）、权限中心（浏览应用能力/数据目录）
  │     └─ 应用上下文：我是 owner → 显示"授权管理"；否则只显示"申请 / 浏览能力"
  └─ 全局入口（主体目录 / 全局审计）→ 权限到位才可见（合规隔离，只读）
```

**差异**：现状前端是纯管理员视角（用户/组织/应用/角色/策略/申请/审计）；目标重排为"我的工作台 + 上下文过滤"，删除独立"角色"页，新增"授权主体"统一页。

## 6. 分阶段改造计划

### 阶段 0：模型收敛（地基）
- 删除 `Role`/`RoleAction`，组挂权限点（`GroupPermission`），迁移现有 seed 数据
- `Group` 加 `expires_at` / `status=expired`；成员表加 `expires_at`（成员级 TTL）
- `Policy` 加 `source` 字段与申请单关联
- `resource_scope` 支持维度级表达式（JSON schema 扩展）
- **验收**：现有 e2e（demo.sh）在迁移后全绿；组即角色替代角色

### 阶段 1：管理面 PEP + 授权域边界（去中心化安全前提）
- 管理 API 全部接入管理面鉴权：我能管理"我的组织 / 我的组 / 我的应用 / 我的程序"
- 应用 owner 只能管理自己应用的授权；跨域操作需审批或平台兜底
- **验收**：A 应用 owner 无法直接给 B 应用授权（报越权或进审批）

### 阶段 2：审批链路（全审批 + 审批即策略 + SoD）
- 授权状态变更统一进入审批流（含 TTL 组创建）
- 审批规则可配置：人审（组织上级 / 对方 owner）/ 自动（工单联动 / 层级计算）
- SoD 校验：审批人 ≠ 被授权人利益相关
- **验收**：创建授权组 / 加成员 / 挂权限均产生审批任务；自动规则正确路由

### 阶段 3：我的工作台 + 上下文过滤（前端重构）
- 登录默认进入"我的工作台"（我的权限汇总 / 申请 / 应用 / 待办）
- 应用上下文 / 组上下文浮现管理能力（owner 显管理，否则显申请）
- 新增"授权主体"统一页；删除"角色"页
- **验收**：普通用户与应用 owner 登录看到不同能力；无切换按钮

### 阶段 4：应用双角色 + 权限中心（应用间申请）
- 应用作为主体可申请其他应用能力（service-to-service onboarding）
- 权限中心：浏览应用暴露的能力目录 + 数据目录 + 申请入口
- 双向账本视图："我的应用被谁访问" + "我的应用申请了谁"
- **验收**：工单系统（程序身份）申请云管"创建 KMS"能力，云管 owner 审批后生效

### 阶段 5：数据范围表达式 + filter 增强（审计场景）
- 维度/属性级 scope 落库 + 执行链（filter 返回可见范围条件）
- 示例：小王可查 `audit_log` 且 `org IN (payment)`
- **验收**：filter 按维度返回范围条件，下游拼接查询

### 阶段 6：程序化兜底（多 owner 巡检 / 失联停用 / 恢复通道）
- 多 owner 校验（注册应用强制 ≥2）
- 定期巡检：owner 失联提醒 → N 次无响应停用 → 恢复通道（认领者审批）
- **验收**：模拟 owner 失联，N 次后应用自动停用；认领后恢复

## 8. 风险与注意点

1. **管理面 PEP 是最大工程**：管理操作的鉴权本身要完整（对管理的管理），否则去中心化 = 放任；先行设计授权域边界规则
2. **数据迁移**：阶段 0 删除 Role 需迁移现有 seed/策略，保证 demo.sh 回归
3. **审批体验**：全审批需配套审批即策略（自动路由），否则低价值变更卡人工，体验崩坏
4. **TTL 组与审计**：组到期"失活"不删除，历史授权引用保留；续期走审批闭环
5. **SoD 环路**：审批链要防自己批自己/同级互批，规则先行
6. **合规**：全局只读审计管理员是合规义务（审计独立于被审计方），不是特权
