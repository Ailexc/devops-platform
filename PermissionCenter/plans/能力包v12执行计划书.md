## 1. 背景

### 1.1 项目背景

权限中心（IAM）demo：Go + Gin 后端，Casbin（动作级 RBAC/ABAC）+ OpenFGA（实例级 ReBAC）双引擎；Traefik 网关作 PEP（forwardAuth → `/v1/gateway/check`）；Vue3 + Element Plus 管理台。叙事主线是「重构后的现代化方案」，用于面试展示与知识点回顾。

**能力包（Capability）** 是应用对外暴露能力、供下游申请的统一载体。v12 demo 是该能力包全生命周期交互的**最终定稿**，覆盖：应用中心（详情页含接口树/数据模型/网络信息/鉴权方式/能力包）、能力编辑器（查看/编辑 + 预设配置 + 范围字段类型系统 + 声明文件）、授权管理（预设级上架/下架 + 授权钻取 + 概况）、权限市场（双主体申请向导 + 数据范围友好交互 + 预览审批）。

### 1.2 痛点回顾（为什么需要本次改造）

1. **数据范围门槛过高**：v10 的 `expression` 类型要求 owner 手写 CEL、applicant 也手写，普通用户无法接受；
2. **编辑器配置不完整**：v10 的 `scopeOptRowHTML` 只处理 `all / instance / expression`，新增类型没有对应配置 UI；
3. **申请人端没有交互组件**：v10 申请端范围步只渲染选项卡片，没有下拉/复选/输入等真实控件；
4. **应用信息不透明**：申请前看不到提供方网络与鉴权方式，导致「申请了却不通」的典型痛点（讨论 Q5）；
5. **生命周期不闭环**：预设级上架/下架、授权管理、审批→工单→激活授权仍停留在 demo 与部分后端实现。

### 2.4 范围字段类型系统（v12 核心，六种类型定稿）

| 类型 | 中文名 | owner 配置项 | applicant 交互 | 自动生成表达式示例 |
|------|--------|--------------|----------------|---------------------|
| `all` | 所有数据 | label / desc | 提示「无需填写」 | （全量，无表达式） |
| `instance` | 具体实例 | label / desc / api（实例列表接口） | 实例 checkbox 多选 | OpenFGA tuple：`(host:web-01, reader, client:xxx)` |
| `select` | 单选 | label / field / op（== != in !in）/ choices[] | 单选 chips | `env == "prod"` |
| `multi_select` | 多选 | label / field / op / choices[] | 多选 chips | `account_id in ["acc-ops-001","acc-rd-002"]` |
| `variable` | 自动匹配 | label / field / op（== !=）/ variable（@currentUser/@currentOrg/@currentGroup/@currentAccount）/ varLabel | 自动匹配展示（无需填写，运行时解析） | `owner_id == "@currentUser"`（解析为当前身份） |
| `input` | 自由输入 | label / field / op（== != contains startsWith in）/ placeholder | 文本输入框 | `tags contains "web"` |

**定稿原则**：
1. applicant **永远不需要手写表达式**——选择/输入后系统实时生成；
2. `variable` 类型的运行时值由 IAM 在**授权生效/请求校验时按 grantee（权限作用主体）解析**（用户/组织/组/账号），申请单只存变量名；
3. 表达式目标语法 = **OpenFGA condition（CEL）**，与后端 `buildScopeExpression` 对齐（§5.5）；
4. 每种类型的 op 集合由 owner 配置，但**后端校验最终表达式合法性**（对齐 OpenFGA CEL 能力，见决策 D2/D6）；
5. 产品内不提供表达式手册弹窗/手写入口，能力对照沉淀为知识文档（§4.7），仅作学习与面试讲解用。

### 4.5 表达式自动生成规则（applicant 端 → 落库）

| 类型 | 生成表达式（CEL） | 说明 |
|------|-------------------|------|
| all | （无） | 全量数据 |
| instance | OpenFGA tuple：`(model:instance, reader, grantee)` | 复用现有实例写入通道 |
| select | `field op "value"` | 例：`env == "prod"` |
| multi_select | `field op ["v1","v2"]` | 例：`account_id in ["acc-ops-001"]` |
| variable | `field op "@currentUser"` | 申请单存变量名，**授权/校验时解析为 grantee（权限作用主体）的运行时身份** |
| input | `field op "value"` | 例：`tags contains "web"` |

### 4.6 `AccessRequest` 双主体（🔧，沿用 v10）

```go
type AccessRequest struct {
    // ... 已有
    GranteeType   string `json:"grantee_type"`   // user | org | group | app
    GranteeName   string `json:"grantee_name"`   // 程序身份 client:xxx / 用户 / 组织路径
    ApplicantID   string `json:"applicant_id"`   // 人（代理申请）
    // 数据范围结构化选择（v12）：每模型 { type, selectedValue, selectedValues[], expr }
    ScopeSelections JSONAny `json:"scope_selections"`
}
```

> **双主体语义（用户已确认，核心）**：
> - `grantee`（**权限作用主体**）= 权限最终作用的对象：用户 / 组织 / 自建组 / 程序（client）；
> - `applicant`（**权限申请主体**）= 发起申请的人；**当 grantee 是程序时，程序无法自己申请，由其负责人（owner）代理申请**——这是双主体的核心场景；
> - `variable` 类型的运行时解析对象 = **grantee**：grantee 为程序 `client:xxx` 时 `@currentUser` 解析为该 client 身份；grantee 为用户时解析为该用户。申请端展示当前登录人（applicant）仅为示意，不代表解析对象。
> - 现有 `ApplicantSubjectType/ID` 字段并入 `grantee` 语义（旧「申请主体」概念废弃），避免同义双轨。

### 4.7 表达式能力对照（知识文档 · 学习/面试用）

> 产品内**不提供表达式手册弹窗**；以下能力对照沉淀为 `docs/openfga-expression-guide.md`（随 Phase 5 同步编写），供学习与面试讲解。

| OpenFGA/CEL 能力 | v12 系统暴露 | 转换规则 |
|------------------|--------------|----------|
| `==` / `!=` | ✅ select / variable / input | `field == "value"` / `field != "value"` |
| `in` / `!in` | ✅ multi_select（建议 `in`） | `field in ["v1","v2"]` |
| `startsWith` / `contains` | ✅ input | `tags contains "web"` |
| 数值比较 `>=` `<=` | ❌ 本期不暴露（v10 曾有，v12 移除） | 需要时 owner 用 input + `==`，或留待 P2 扩展 |
| 逻辑组合 `&&` `||` `!` | ❌ 本期 UI 不暴露（单选项组合） | 多模型/多条件写入时由后端自动组合 |
| 实例级（tuple 关系） | ✅ instance | `(model:inst, reader, grantee)` 走 OpenFGA 关系通道 |
| 运行时变量 | ✅ variable（4 种枚举） | 解析对象 = grantee，PDP 注入 |
| 手写表达式 | ❌ 已移除 | 表达式一律由系统生成 + 后端自动校验 |

> 面试要点：OpenFGA condition 是完整的 CEL 语言；v12 通过「范围字段类型系统」暴露其**安全子集**（6 种表单类型），把复杂度收敛到 owner 的可选配置与 applicant 的友好交互，剩余能力由系统在后端生成，避免用户学习成本与注入风险。

  type host

### 6.6 鉴权前置 · 接入申请（D4 已定案：方案 B）

**矛盾点（用户提出）**：能力包可能**申请多次**，鉴权（凭证）基本**申请一次**——两者生命周期不同，不能绑死在能力包申请里。

**业界模式（一致的做法）**：**凭证注册一次，授权追加多次，鉴权与授权分离**：

| 业界参照 | 一次（身份/凭证） | 多次（授权/订阅） |
|----------|-------------------|-------------------|
| OAuth 2.0 | client registration（client_id/secret） | 授权服务器批准追加 scope |
| Azure API Management | 创建订阅 → 发放 subscription key | 产品内增删 API（key 不变） |
| AWS IAM | 创建 principal + 凭证（access key / 角色） | 反复 attach/detach policy |
| 企业内部平台 | 服务 onboarding 注册一次 | catalog 权限/依赖持续演进 |

**三个候选方案**：

| 方案 | 说明 | 评价 |
|------|------|------|
| A. 基础能力包 | 把「连接鉴权」做成一个特殊能力包，申请一次获得凭证 | ❌ 不推荐：循环依赖（申请鉴权包本身需要鉴权）、语义混淆（鉴权是基础设施而非业务能力）、业界无此做法 |
| B. **独立前置「接入申请」流程** | 权限市场增加独立入口：选目标应用 → 选鉴权方式 → 审批 → 签发凭证；之后能力包申请自动复用凭证，仅追加 scope | ✅ **推荐**：一次注册多次授权，与业界一致；复用现有申请/审批/工单机制，增量最小 |
| C. 申请向导第 0 步内嵌 | 每次申请能力包时先走接入 | ❌ 不推荐：把一次性动作反复暴露，交互重复 |

**定案流程设计（用户已确认）**：
1. 权限市场 / 应用详情页新增「🔑 接入申请」**独立入口**（与能力申请并列，同为一次性动作）；
2. 步骤：选择目标应用（提供方）→ 选择鉴权方式（**来自提供方 `app.auth` 支持列表**）→ 申请方信息自动带出（网络信息快照，衔接 Q5）→ 审批链（提供方 owner 确认 → 平台复核 → 工单）→ 签发凭证（client_id/secret 或 API key，模拟）；
3. **网络打通并入接入申请**（用户已确认）：在接入申请中直接帮助提交网络打通工单（模拟），与鉴权一次落地，不再单独出现在能力包申请里；
4. 之后申请能力包：已接入 → 自动复用凭证，仅追加 scope（凭证不变）；未接入 → 提示「尚未接入该应用，请先完成接入申请」，一键跳转；
5. 与 Q3 令牌模型闭环：凭证 = client 身份；每次能力包申请通过 = 向该 client 追加能力 scope；调用时换取的 JWT 只含已授权 scopes。

**落点**：`AccessRequest` 新增 `RequestType=接入申请`（复用审批/工单机制）；产出物 = 凭证记录（复用现有 `Client` 表，扩展绑定 auth_method）；前端独立入口 + 向导；实施见 **Phase 6.5**。
> **demo 层说明（用户已确认）**：v12 demo 不新增接入申请入口，仅真实系统实现。

## 10. 风险与注意事项

1. **范围选项已独立表化（D1），但 presets 其余字段仍为 JSONB**：`status/grantee_types/apply_scope/data_models` 写入前必须经结构校验（枚举/引用/非空），防止脏数据（沿用 v10 风险 1）；
2. **OpenFGA condition 能力版本依赖**：Phase 5 先做能力探测，确认支持 `with condition`（沿用 v10 风险 2）；
3. **variable 注入**：变量名只允许枚举值（@currentUser 等），禁止任意字符串拼入表达式（防注入）；解析对象固定为 **grantee**，避免与 applicant 混淆；
4. **市场过滤破坏现有申请**：草稿预设历史授权仍生效，查询授权不受 status 过滤（沿用 v10 风险 4）；
5. **YAML 双向漂移**：以「规范字段集」为准，未知字段保留（forward compat）（沿用 v10 风险 5）；
6. **旧数据兼容**：已有 `expression` 类型 scope_definitions、能力级 `data_control`、`allowed_scopes` 需在 Phase 1 直接废弃清理（开发阶段不保留兼容层），避免旧数据渲染崩溃与双轨并存；
7. **mgScope 门禁**：新增接口全部补白名单 + owner 校验，防止越权（沿用 v10 风险 7）。
