⚡ 鉴权链路与双引擎

核心技术复盘总结

本文复盘系统的鉴权链路设计：动作级与数据级如何分层、决策缓存如何工作、策略如何被物化与失效。

1. 动作级 vs 数据级

一次「能不能做」的判断拆成两个层次：

层次问题引擎粒度
动作级用户能否执行该动作？Casbin（RBAC + ABAC 条件）策略级（subject → action）
数据级用户能访问哪些数据实例？OpenFGA（关系元组）实例级（subject → object）

设计动机：动作权限数量少、规则化强，适合 Casbin；实例级授权数量大、关系化强，适合 Zanzibar 模型。

2. PDP 决策流程（CheckWithPids）

1解析主体：resolveSubject 把用户/程序身份解析为内部 subject key（u:2 / s:cloud-mgmt）
2决策缓存：查 authz:dec:{sub}:{app}:{action}，命中直接放行（值 1|pid1,pid2 或 0|）
3加载策略快照：LoadOrBuild 从 Redis 版本化快照 authz:pset:* 重建策略集
4Casbin 求值：EnforceEx(sub, app, action, "*") 动作级 RBAC 判断
5ABAC 条件：收集命中策略，逐条求值条件（环境/地域/实例等）
6写缓存 + 记日志：allow 写 1|pids，deny 写 0|；异步写决策日志（含 PEP 来源）

3. 决策缓存：性能与一致性

命中路径：缓存 TTL 内命中 → 直接返回决策，亚毫秒级，不触碰策略计算与 DB。
失效路径：策略发布 / 授权变更 → 按 app 调用 DelPattern("authz:dec:*:app:*") 全量失效，保证策略变更即时生效。
观测：决策日志记录来源（cache / remote），指标面板据此统计缓存命中率。
// 决策缓存键格式
authz:dec:u:2:cmdb:cmdb:host:read = 1|1,33,24,85,gp:53   // allow + 命中策略 ID
authz:dec:u:3:cmdb:cmdb:host:create = 0|                 // deny

4. 策略快照与版本化

策略集（Policies + Groupings + Conditions）构建后缓存到 Redis（authz:pset:{app}），以版本号 authz:ver:{app} 标记。Agent 与网关共享同一套快照，保证「中心与本地」判定一致。

LoadOrBuild(appID)
   │  authz:ver:{app} 版本比对
   ├─ 命中 → 直接用 Redis 快照重建
   └─ 未命中 → 从 DB 构建 → 写快照 + 更新版本

5. 数据级授权（OpenFGA）

动作级通过后，数据级用 OpenFGA 检查实例关系：

// 授权模型（type 定义）
type user      {}
type service   {}
type group     { relation member: [user, service] }
type host      { relation owner: [user, service, group#member]
                 relation reader: [user, service, group#member]
                 relation writer: [user, service, group#member] }

// 授权通过后写入关系元组
WriteTuple(user:u:2, reader, host:host-01)

数据面 `CheckInstance`：动作短路通过 → OpenFGA Check → 返回该用户可访问的实例集合 → 网关据此过滤数据。

6. 踩坑复盘

  • 主体类型映射：程序申请（ReqSubjectApp）在落库策略时需映射为服务主体（SubjectService），否则策略主体类型错乱。
  • 决策缓存误判：调试时误以为缓存未写入——实际是 curl 路径错误（`/v1/authz/check` 非 `/api/v1/authz/check`）被 `> /dev/null` 吞掉 404。PEP 接口需 `X-PEP-Token` 共享密钥。
  • 策略快照一致性：策略变更必须同时使决策缓存失效，否则出现「改了不生效」的假象。

7. 小结

双引擎 + 决策缓存 + 策略快照 + Agent 分发，构成了从「判断」到「执行」的完整链路；动作级短路保证性能，数据级兜底保证精确，缓存失效保证一致。
